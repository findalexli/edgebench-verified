EdgeBench Verified

Which problems in the hidden checkers behind the 51 public EdgeBench tasks hold up

Version 1.12 November 2026 Code, data and fixes on GitHub How to cite

In short

EdgeBench ranks AI agents on 51 public engineering and science tasks. In each task an agent works for hours, and a hidden checker program scores what it submits, from 0 to 100. Our first audit reported problems in 32 of those tasks. We then tried to break our own findings: an independent AI reviewer attacked each one, and we measured what survived on the current community judge, using real agent submissions where they exist. 12 tasks hold up as problems that matter: a good-faith solver is scored wrongly or non-repeatably, and we measured how much. The rest are small, already changed upstream, or not confirmed, and we say which.

12tasks confirmed: a measured score change on the current judge, large enough to matter.

The other tasks: 15 real but small or unseen, 1 changed upstream, 8 not confirmed, 15 with no problem found. Why each is there.

See the confirmed tasks →

Each task has its own page with the instructions the agent receives, how EdgeBench scores the work, the second review's status and the first audit's full record.

1What EdgeBench is and how it scores an agent

An EdgeBench task gives the agent written instructions and starter files: make a trading engine faster, write a bot for a strategy game, finish the proofs in a mathematics library, infer the source of groundwater pollution from sensor readings. The agent can submit as often as it likes during its twelve hours, and it sees each score. A hidden checker program (EdgeBench calls it the grader), written by the task's authors, runs every submission on hidden test cases and produces a raw result, such as a cost, a speed or a count of passed tests. EdgeBench converts the raw result to a score from 0 to 100 using reference points the authors chose for that task. Each run keeps its best score. Each model has three runs per task; EdgeBench averages the valid runs and drops a run that failed as a whole, for example by crashing. A model's headline number is its average over tasks.

A score can therefore go wrong at four points (Figure 1): the checker can accept wrong work; it can reject correct work or apply a rule the agent was not told; the conversion to 0–100 can be unreachable or mismeasured; and the run can keep the wrong submission. We found all four, and a fifth source of error outside the checker's code, the machine it runs on. EdgeBench's official settings give a checker 4 CPUs unless the task overrides it, and six checkers run more work at once than that (Vibrating Path).

Each task page gives these details for its task: the checker command, the time limit, what is submitted, how the raw result becomes 0–100 and which submission a run keeps. Open the task list.

2How we reviewed

The first audit asked of each task whether an agent that solves it correctly and by the rules gets the score the task promises. It tested the original release and published fixes for 31 tasks. The second review, in November 2026, asked which of those findings hold up against the current judge, using EdgeBench's own contribution rule: a good-faith solver is scored wrongly or non-repeatably, and the final score moves.

  1. Attack. An independent model (GPT-6 Astra) reviewed 146 claims in the current code, rechecked 48 from scratch and attacked 46, trying to refute them. It ran pure functions but no containers.
  2. Measure. Where we could, we built the judge from community at 1187e2c and graded a control and a trigger differing only at the defect, repeated at least twice; repeatability claims used at least three gradings of one file. Other evidence includes single agent runs, direct evaluator runs, local scoring tests and calculations, and each result says which.
  3. Check against real runs. A claim counts for less if real solvers score well despite it. One reviewer-approved claim fell this way: on Borden Inversion, a real run reached raw 108.97 of 109.

Limits: most tasks have one model's real runs, or none. The SMT results ran below official resources, because of our cloud account's cap. "Not confirmed" means we could not show harm on the current judge, not that the first audit's measurements on the original release were wrong; those are kept on each task page.

3What holds up

A task is confirmed when the measured change reaches real work: regrading a real submission shows it, or a repeatability failure affects any submission. A defect that is large only on a trigger no real submission we hold uses stays with the others. Graph Node, for example, drops from 90.52-90.57 to 1.95-2.01 if predictions use integer keys, which the task permits.

Each entry gives the defect, the measured effect on a score out of 100 unless stated otherwise, and whether upstream knows.

Apple Incremental Game. The same eight-at-once pool costs real files points at 4 CPUs and many cases under load. At true 4 CPUs a real file scores 68.10-70.60, against 73.25-73.92 with a smaller pool, with no timeouts (n=5). In an overload test, five judges sharing 8 CPUs, it scored 3.09-19.78 with the original pool and 17.81-68.87 with the smaller one across three workers (n=20 each). The smaller pool also lost cases on the noisiest worker. Same mechanism as PR #36; not reported separately.

Arc Compiler Runtime. Hidden tests expect an analyze() return shape that nothing the agent sees describes. A real Opus submission scores 61.31 as submitted and 94.81 with only the return shape changed (n=2 each). One real run each: best 61.31 on the original task, 96.06 with the shape documented. Not yet reported.

Integer Compression Codec. A stored baseline figure is impossible for the documented starter, which distorts how the datasets are weighted. The starter gets 0.25 raw against the documented 1.0, and 0.855 with the exact figures. A real submission scores 73.60 today; with the figures corrected its raw score is 164.4, which clips to 100 on the existing scale, or gives 51.22 on a new 1..320 scale. So the size of the fix depends on the scale. No ranking change was shown, and real runs reach 73.78 today. Not yet reported. Choosing a fix means choosing a new scale, which is the maintainers' call.

Juliet Vulnerability Analyzer. Any .py or .sh file containing the word infer, even in a comment, loses 100 points. Separately, CWE-416 findings that start at the release are rejected. A real analyzer scores 0 and would score 79.59 with the fix; another goes from 90.70 to 0 with one added comment (n=6). CWE-416: a real analyzer loses 3.34, from 89.00 to 85.66 (n=3), though that solver turned the option off and its best score lost nothing. Reported: issue #39 and PR #35 (the infer part).

NetHack Dungeon Agent. Seeding silently fails, so the 20 graded games differ every time. Our bot scores 6.8-15.5 over 12 gradings, and 14.5 on all 12 once seeding works, all on one day; NetHack also reads the clock, so repeatability across dates is untested. The bot is ours; there is no real submission to test. Listed in upstream's known issues.

OpenRCT2 Theme Park AI. The instruction promises about four game years, but the 120 seconds per scenario fit 68 to 69 of 992 game days. A real plugin scores 27.50 under the official budget (n=3). Direct evaluator runs continued to 992 days score 16.44 (n=2), so for this plugin the short run inflates the score. No judge fix was tested. Real files also vary between gradings, up to 11.40-44.73, but randomness in the plugins may cause that, so we don't count it against the judge. The short run is listed in upstream's known issues; issue #12 raises a separate question about this task's scale.

Rust Multicrate Reconstruction. Four source files are missing, which blocks nine scored crates. At 8 vCPUs, restoring the files raises a real submission from 17.20 to 27.17 and a reference we rebuilt from upstream code from 27.61 to 73.99 (n=2). Original-judge scores matched 4-CPU results, but the restored arm wasn't run at 4 CPUs. Two crates still fail because of separate hidden-test defects. The starter also rises, from 1.47 to 3.82, so old scores don't carry over. Listed in upstream's known issues.

Schemathesis Datagen Pipeline. The hidden header test imports names and expects format keys that TODO.md never gives, so every real headers module scores 0 of 15 on it. Once those are supplied, a real submission goes from 72.31 to 85.64 or 86.67; the two values come from a flaky test. The 8 real modules are 2 distinct versions. Not yet reported.

SMT Solver. The validator's recursion crashes on 5 hard files when a solver answers sat; no score file gets written, and the judge still reports a valid 0. A real solver scores 0.00 on the shipped judge and 47.04 and 46.17 with a larger validator stack. The 5 crashing answers still fail validation; preventing the crash restores credit earned on other cases. Measured at 8 CPUs and 7 GB, not the official 16 and 16 GB, with 6 to 7 solver OOM kills per run. No real run shows it. Not yet reported.

Treant Forest. The tester stops each game at an undocumented turn cap, so no submission can pass 21.02, while the 0-100 scale assumes totals the cap rules out. All 87 archived real reports sit at 20.46-21.02, so the cap hides real differences between them. Removing the cap with the scale unchanged raises one real submission by 15.83 and reorders the ones we tested, though some long replays hit the tester's time limit. The four real submissions we measured read a destination list the README says solutions don't use; a grid-only control scores 3.04 with or without the cap. Listed in upstream's known issues. Whether to change the cap, the scale or both is the maintainers' call.

Vibrating Path Graph Coloring. Eight cases run at once on the official 4 CPUs, and one timeout makes the whole total inf. A real Opus solver gets inf on all 15 gradings and 19.77-19.98 with 4 cases at once. The same file passed all 7 grades during its own run on the published judge image, so the grading is non-repeatable. Reported: issue #40 and PR #36.

Wesnoth Tactical AI. The same file gets different scores despite fixed seeds. Wesnoth's stock AI scores 36 to 43 over 8 gradings with no timeouts. We haven't found the cause, and there is no real submission to test. Listed in upstream's known issues.

The other tasks, including first-audit claims we withdrew

3.1Real, but small or unseen in real work

  • D-ABIC Gravity Inversion. An undisclosed gate costs a model-space solver 1.08 points, but 0 of 75 real reports use that form. The self-reported points are a separate design question.
  • DCSS Dungeon AI. Upstream's notes record one bot at raw 1556.0-5211.2 on the current judge, which computes to 32.82-54.61. Our own weaker bots spread by under 1 point, so we did not reproduce the large swing or isolate its cause.
  • Exchange Core Throughput. Broken engines do earn credit, but at the official 4 CPUs correct work mostly scores 0 too, and no real run was affected.
  • FFmpeg swscale Reimplementation. Making a conversion fail raises a score by 12.82, but no real run gained from it.
  • Git Rewrite in Zig. An ordinary object file or an unimported test calling system git takes a real implementation from 36.86 to 0, but none of the 46 distinct real archives has either.
  • Graph Node Classification. Changing a real solver's predictions to integer keys, which the task permits, takes it from 90.52-90.57 to 1.95-2.01. No real submission we hold uses them.
  • Grid Turing Robot. A smaller pool is worth +0.67 to +0.71 on valid real files. No real file goes from invalid to valid.
  • Lean Analysis Proofs. Two required statements are false, which is proved in Lean. The computed score effect is tiny, and the grader image is too large for us to rerun.
  • Molecular Self Assembly. A smaller pool gives deadline search more CPU, worth +1.13 to +1.46. The timeouts we first blamed on the pool occur on both pools.
  • Ordinal Notation Well-Foundedness. A file-name filter can drop a needed proof helper (1.18 to 0). Only our own proof triggers it. We hold no real submission for this task, though upstream records historical runs.
  • PFR Formalization. Five scored statements carry a hidden sorry in their type, so no submission can earn them: 5 of 423 targets, or 1.18 points. A volunteer Lean user checked this by hand and passed it: with the workaround, all five completed proofs receive credit (398/423 to 403/423). We did not rerun it on the current judge.
  • Schemathesis Config Modernization. A forwarding decorator gets 0.67 points too many. No real submission writes one.
  • Schemathesis Reporting Observability. Two checks give 1.00 to 1.43 points too many, and a third takes 1.43 from a valid report without the word schemathesis. One unchanged real file is affected (2.0 instead of 1.0).
  • Triangulation Coloring Optimization. A smaller pool is worth +0.32 to +0.59, with no timeouts in any condition.
  • Warehouse Forklift Routing. The judge allows 60 s per input. Five cases at 30 s each suggest 150 s, though another README passage calls whole inputs test cases. Edited solvers with long deadlines recover under a longer limit; real submissions we hold are unaffected, and the pool makes about no difference.

3.2Changed upstream

  • Order Addition Permutation Optimization. Real on the original release: a real run kept 3.79 instead of the 41.24 a later submission earned. community changed how a run picks its best, so this no longer applies there.

3.3Not confirmed

A first-audit claim listed here may still be a true statement about the code. It is here because we could not show that it moves a good-faith solver's score on the current judge.

  • Borden Source Inversion. The unstated model didn't stop one real run from reaching raw 108.97 of 109 through score feedback, while a run with the model documented reached 52.86. Single runs like these don't show what documenting it would change.
  • College English Exam Bank. The code gives full marks for omitted rules, but every example is a constructed grader reply, and no real submission hit it.
  • CTA Risk Budget Optimization. The limit formula differs from the policy, but a real submission we checked scores 50.0 both ways.
  • Equivalence Class Divide and Conquer. The cost accounting is off, but reference and naive submissions score the same either way, and the swing needs an input we added.
  • Jagua Nesting Optimization. The overlap bug exists, but we have no good-faith submission that gains or loses from it.
  • OpenTTD Transport AI. The named API doesn't exist, but we measured no loss for a productive AI. The archived idle script scored 0, and a corrected one was not game-tested.
  • Portfolio Risk Calibration. The excess-return formula differs from the stated one, but a modified file on a local scoring path moved only from 15.35 to 15.34 (or 15.27 with aligned annualization). Harm on the current judge remains unverified.
  • Tree Block Partitioning. The supplied multiply is wrong when operands alias, but none of the 61 real archives hits it.

4The first audit

This review corrects our first audit, which tested the original release, reported problems in 32 of the 51 tasks and estimated ranges for the published leaderboard. Of those 32, 10 are confirmed, 13 are real but small or unseen, 1 has changed upstream and 8 are not confirmed. Those ranges count every first-audit fix, including fixes for claims this review did not confirm, and we have not recomputed them. Each task page keeps the first audit's record.
