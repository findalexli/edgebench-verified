EdgeBench Verified

An audit of the graders behind the 51 public EdgeBench tasks

Version 1.012 October 2026 Code, data and fixes on GitHub How to cite
Browse all 51 tasks →

Every task has its own page: the instructions the agent receives, how EdgeBench grades the work, and what we found.

Abstract

EdgeBench scores agents on engineering and science tasks. This audit examines all 51 public tasks. The historical dispositions are 31 repair packages, 19 tasks kept with notes and 1 removed task. A repair package is not a certification of the whole task. Evidence includes original-helper controls, native grader runs and formal models, each with its own limits. Datagen's year-domain correction passes native evaluator controls. FFmpeg's output checks and exact-zero failure rule pass native scorer controls. CTA's NAV-denominator correction passes paired native runs through the original scoring command. Warehouse needs a separate host-side drain repair. 31 of 32 packages were rebuilt from scratch on a clean machine; Lean Analysis's grader image needs about 45 GB of disk and was not rebuilt. Remaining gates: FFmpeg's submission-build path; Warehouse's backend integration of the drain repair; Lean Analysis's image builds and actual grading path; PFR's credit on the five actual targets, which needs real proofs; Equivalence's per-problem checks on all six problems; and Vibrating Path's zero-hit formatting effect, unresolved on 13 of 50 cases. Triangulation's regenerated inputs now cover their convex hull exactly (v2.2). Published model averages cannot identify the corrected leaderboard: Treant needs intervals, Portfolio's sweep is only a sensitivity scenario, and interval overlap does not prove a ranking reversal. See the current package status and impact analysis.

1What EdgeBench is and how it scores an agent

An EdgeBench task gives the agent written instructions and starter files: make a trading engine faster, write a bot for a strategy game, finish the proofs in a mathematics library, infer the source of groundwater pollution from sensor readings. The agent can submit as often as it likes during its twelve hours, and it sees each score. A hidden grader program, written by the task's authors, runs every submission on hidden test cases and produces a raw result, such as a cost, a speed or a count of passed tests. The raw result is converted to a score from 0 to 100 using reference points the authors chose for that task. Each run keeps its best score; each model has three runs per task, and the valid ones are averaged (a run that failed as a whole, for example by crashing, is dropped); and a model's headline number is the average over tasks.

A score can therefore go wrong at four points (Figure 1): the grader can accept wrong work; it can reject correct work or apply a rule the agent was not told; the conversion to 0–100 can be unreachable or mismeasured; and the run can keep the wrong submission. We found each of the four, and a fifth that lies outside the grader's code: the machine it runs on. EdgeBench's official settings give a grader 4 CPUs unless the task overrides it, and six graders run more work at once than that (Section 3.1).

Each task page spells this out for one task: its grader command, time limit, what is submitted, how its raw result becomes 0–100 and which submission a run keeps. Open the task list.

2What we did

For each of the 51 public tasks we asked one question: if an agent does honest, correct work, does it get the score the task promises? Evidence is traced to original grader code and final scores. Native runs, component controls and formal models answer different questions; none alone certifies every current repair package (Figure 2). Each task then received one of three outcomes:

  • Repair packages (31 tasks). The grader's logic, data or setup can be corrected. We publish versioned repair packages. Case pages state the scope of paired checks and remaining integration requirements.
  • Kept, with a note (19 tasks). No correctable problem found. The note records caveats that no change to the grader removes, such as variation between runs or machines.
  • Removed (1 task). No sound fix was possible.

3What goes wrong

The examples below are representative, grouped by kind of problem. Every task is listed on the Tasks page, and each has a full case with the test submissions, the independent checks and the fix. Every task name below links to its page.

3.1The grader is given fewer CPUs than it runs work on

EdgeBench's official leaderboard settings give each grader 4 CPUs unless the task overrides it; seven Lean tasks get 8 and SMT Solver 16 (the settings, quoted). Six graders with no override run 8 test cases at once under the promised time limit per case (Treant Forest also runs 8 at once, but allows twice the promised time). On 4 CPUs each case therefore gets about half a CPU, and the instructions never state the grader's CPU count; inside the grader, the system reports the host's CPU count (8 on our test machines), not the limit. Grid Robot promises 30 seconds per test case. A solution that computes for 16 seconds per case times out on 48 of its 50 cases at 4 CPUs, and a single timeout voids the whole submission; with 8 CPUs the same solution passes every case. Vibrating Path, Molecular Assembly, Apple Game, Triangulation and Warehouse Routing behave the same way: CPU-budgeted solutions lose most cases or the whole score. A wall-clock limit does not promise dedicated CPU seconds; the repair chooses a more consistent resource policy. Solutions that stop at a fixed clock time usually are not voided, but get half the computing time; in one of nine original-grader gradings on Vibrating Path such a solution was voided, probably because the task's own checker, sharing the CPUs, timed out. The fixes run no more cases at once than the grader has CPUs, which we measured at 4 and at 8 CPUs side by side. In Exchange Core, whose score is a speed, the unmodified engine scores 0 at 4 CPUs and about 47–76 at 8, so its note records that scores there depend on the grader's CPU count.

Evidence: reproduced on the original grader · Lean 4: note proved · fix tested side by side, three runs

3.2Correct work is scored too low

Rust Multicrate. The agent rebuilds a large Rust project. The grader inserts its hidden tests into two parts of the project in a way that does not compile, so those parts, worth 22 of the 100 points, score 0 for every agent that follows the rule not to edit tests. A complete solution scores 73.99 instead of 94.70. (The public archive also lacks four library files; with them restored, the starter reproduces the publisher's recorded score exactly, so the publisher's own grading most likely had these files and this second problem affects only people who grade with the public images.)

Evidence: reproduced on the original grader · TLA+: fix partly model-checked correct · fix tested side by side, three runs (1 of 4 comparisons once)

Git in Zig. The agent rewrites git in the Zig language. Checks the instructions never mention set the whole score to 0 if the project contains an ordinary build file, such as the one a common Zig build command leaves behind, or a test that compares the agent's output with the real git, which the instructions invite. The fix deletes leftover build files and drops the check on test code, instead of zeroing the score.

Evidence: reproduced on the original grader · fix tested side by side, three runs

PFR Formalization. The agent completes proofs in a mathematics library. Five of the 423 statements contain a gap marker (Lean's sorry) hidden inside the statement itself, introduced by how the file declares a default argument, so no proof can earn them; any later proof that uses them is rejected too. The five are worth 1.18 of the 100 points, and up to 2.13 with the later proofs that use them (inferred). Only an agent that would have proved them loses points, so the defect can also hide differences between agents.

Evidence: reproduced on the original grader · fix tested side by side, three runs

SMT Solver. The agent builds a solver for logic formulas. When a formula can be satisfied, the solver must give an example assignment, which the grader checks. The checker looks up a function's value by how the call is written, not by what its arguments evaluate to, so the same written call can stand for two different values. Correct answers are therefore rejected on 27 hidden problems, and a perfect solver's score falls from 78.61 to 72.40.

Evidence: reproduced on the original grader · Lean 4: fix proved correct · fix tested side by side, three runs

Borden Inversion. The agent infers the location, size and timing of an underground pollution source from monitoring wells. The grader predicts the hidden readings with a physics model whose conventions the instructions never state: among other things, it ignores soil porosity, treats a rate as a total amount and places the source at the bottom of its region. An honest fit built from textbook physics scores 7.0; the same fitting method using the grader's conventions scores 31.2. The fixed version gives agents the grader's model. An agent that iterates against the grader's scores can partly learn the convention instead (see the check against real agent runs).

Evidence: reproduced on the original grader · Lean 4: published numbers proved · fix tested side by side, three runs

3.3Wrong work is accepted

Exchange Core. The agent speeds up a stock-exchange matching engine without changing its behaviour. The grader's correctness check confirms only that money balances overall and that the order books match. Two realistic one-edit bugs, charging selling takers the maker fee instead of the taker fee and not delivering trade messages, pass the check and receive full credit, although the project's own test suite catches both. The fixed version requires those tests to pass before speed is measured.

Evidence: reproduced on the original grader · Lean 4: finding partly proved · fix tested side by side, three runs (6 of 13 comparisons once)

Jagua Nesting. The agent packs flat shapes into a strip as tightly as possible. The grader misses many overlaps, such as one shape slid halfway over another, so an infeasible layout can beat every feasible one.

Evidence: reproduced on the original grader · Lean 4: fix partly proved correct · fix tested side by side, three runs

3.4The grader applies a rule the instructions do not state

Triangulation Coloring. The instructions allow an edge flip only when the two triangles form a convex shape. The grader omits that condition, and the same faulty rule generated the hidden test cases: all ten contain overlapping triangles, and a forbidden flip improved the score on one of them.

Evidence: reproduced on the original grader · Lean 4: fix proved correct · fix tested side by side, three runs

Warehouse Routing. The instructions promise 30 seconds per test case, or 150 seconds for each input of five cases. The grader stops each input after 60 seconds, and one time-out voids the whole submission, so a solution that uses the time it was promised scores zero.

Evidence: reproduced on the original grader · Lean 4: finding proved · fix tested side by side, three runs

3.5The 0–100 scale cannot be reached

Treant Forest. Each test case is scored by the number of turns survived, and the grader caps turns, so no total can exceed 92,304. The reference points of the 0–100 scale were set far above that cap. No submission can score above 21.02 out of 100. The fixed scale runs from the starter program's total to the proved upper bound (attainability unproved). Warehouse Routing has the same problem, established by proof rather than measurement: a lower bound proved in Lean shows that no valid answer can score above about 30.6 (30.3 at the exact bound).

Evidence: reproduced on the original grader · Lean 4: published numbers partly proved · fix tested side by side, three runs

3.6The wrong submission is kept

Order Addition. One of the five grader tests compares a helper file against an out-of-date checksum, so every submission fails it. Under the task's rule for picking a run's best (most tests passed, earliest among ties), every run's reported best is frozen at its first valid submission, and later improvements never count. Anyone who instead keeps the highest score is not affected. The check against real agent runs shows this happening in a real agent run.

Evidence: reproduced on the original grader · TLA+: fix model-checked correct · fix tested side by side, three runs

3.7A task without a sound fix

D-ABIC Gravity Inversion. Forty-two of the task's points come from numbers the submission reports about its own work, which the grader cannot check. The grader also quietly penalises one of two mathematically equivalent forms that the instructions explicitly allow. We fixed the second problem, but the first has no fix that preserves the task, so the task is removed.

Evidence: reproduced on the original grader · partial fix tested side by side, three runs; task removed

4Effect on the published leaderboard

EdgeBench publishes each model's score on every task: the mean, over three twelve-hour runs, of each run's best score. We asked how each model's average over the 51 public tasks changes once the problems are corrected. The honest answer is that it cannot be determined from public data. Measuring it requires either regrading the agents' original submissions, which EdgeBench has not released, or rerunning the models on the fixed tasks, which this audit did not do. What can be stated precisely:

  • Conditional intervals. The calculation includes rounding and Treant's clipped, piecewise scale. Midpoints describe intervals; they are not known corrected model means.
  • Scope matters. Bounds cover named defect components. Portfolio's restricted sweep is a separate sensitivity scenario, not a global bound.
  • Ranking. Overlapping intervals do not certify an ordering and do not prove an attainable reversal.

The conditional bounds cannot certify the order of Opus 4.8 and GPT-5.5; overlap does not prove an attainable reversal.

5How we verified

  1. Use the original grader, EdgeBench's published grading software, pulled from its public images and identified by a cryptographic fingerprint.
  2. Quote the promise verbatim from the instructions and documents the agent receives.
  3. Show the problem with test submissions: a correct one, which must score as promised; one that triggers the problem; and a wrong one, which must be rejected.
  4. Confirm it independently, with exact arithmetic, a separate implementation, exhaustive search, or a formal proof in Lean 4 or TLA+.
  5. Follow it to the final score. A problem counts only if it changes the 0–100 score of honest work.
  6. Compare original and repaired versions on the same test submissions: 254 graded comparisons, 240 of them run three times.

26 of the 51 tasks have formal results, with 286 Lean theorems and 20 TLA+ model-checking runs. The saved formal results cover 10 repair mechanisms within explicit models, and 4 more partly. They do not certify changed candidates, full evaluator behavior or image integration. The formal checks also corrected us: one shipped fix was narrower than published, and has been revised.

6Lessons

  • Run the original grader before reasoning about it. Most problems were found by reading code but settled only by a submission that triggers them. Several plausible findings did not survive that step.
  • Formal tools pay off on small, crisp questions. A false theorem, an arithmetic gap, a lower bound and an aliasing bug were each settled conclusively. Most grader problems concern conventions, file formats or timing, which no proof addresses as cheaply as a side-by-side run.
  • A proof is only as good as its link to the code. We stated the Lean Analysis refutations against the task's own definitions inside its own image. We matched the Warehouse model to the real tester on 294 strings, and mapped each TLA+ step to a line of source. Without those links, a proof would be about something else.
  • Every check needs a counter-check. Each TLA+ model has a configuration that must fail, each Lean proof prints its axioms, and each fix is tested on wrong work as well as right work. A check that cannot fail shows nothing.
  • Formal proofs check our own work, not only the benchmark's. Writing each fix down precisely enough for Lean or TLA+ exposed one fix that was narrower than published and eight imprecise statements. Each was found because a proof attempt failed on a case we had not thought to test.
  • Test on the publisher's machine settings, not only on a convenient machine. Our first round of side-by-side tests ran graders on 8 CPUs. The leaderboard's settings give most of them 4, and at 4 six graders time out honest work that passes at 8. We also first assumed SMT Solver got 4; its settings give it 16. The code was correct in both settings; only the combination of the machine and the code was wrong.
  • Fresh reviewers find what the authors cannot. A second round of reviewers who did not share our context found the CPU problem, two hidden-test problems in Rust Multicrate, undisclosed checks in Git in Zig and a hidden placeholder in PFR, mostly in tasks we had kept, and several of our own fixes that needed extending or revising. Each was then settled by a run, not by argument.
  • Test what a fix is for, not only what it changes. The first Integer Codec fix corrected the baseline exactly as documented and passed every test, yet real submissions showed it saturated the score scale. Checking fixes against real agent work found what neither proofs nor authored tests did.
