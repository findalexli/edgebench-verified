EdgeBench Verified

An audit of the graders behind the 51 public EdgeBench tasks

Version 1.012 October 2026 Code, data and fixes on GitHub How to cite

Abstract

EdgeBench ranks AI agents on long, open-ended engineering and science tasks. Each agent works on a task for up to twelve hours, and a hidden grader program scores its work from 0 to 100. We examined the grader of each of the 51 publicly released tasks and asked whether an agent doing honest, correct work receives the score the task promises. For 23 of the 51 tasks it does not: correct work is scored too low, wrong work is accepted, the grader applies a rule the agent was never told, the score scale cannot be reached, or the wrong submission is kept. Every finding was reproduced on EdgeBench's own grading software, and for 26 tasks the claims were also checked formally with the proof assistant Lean 4 or the model checker TLA+, which prove 12 of our fixes correct within their models. We publish fixed versions of 22 tasks in EdgeBench's own format and remove 1; each fix was tested side by side against the original grader on the same submissions, three times over. Applied to EdgeBench's published scores, the corrections that can be computed exactly raise every model's average by 1.2–1.9 points, and the public tasks alone do not establish whether Opus 4.8 or GPT-5.5 ranks first.

1How EdgeBench scores an agent

An EdgeBench task gives the agent written instructions and starter files: make a trading engine faster, write a bot for a strategy game, finish the proofs in a mathematics library, infer the source of groundwater pollution from sensor readings. The agent can submit as often as it likes during its twelve hours, and it sees each score. A hidden grader program, written by the task's authors, runs every submission on hidden test cases and produces a raw result, such as a cost, a speed or a count of passed tests. The raw result is converted to a score from 0 to 100 using reference points the authors chose for that task. Each run keeps its best score; each model has three runs per task, which are averaged; and a model's headline number is the average over tasks.

A score can therefore go wrong at four points (Figure 1): the grader can accept wrong work; it can reject correct work or apply a rule the agent was not told; the conversion to 0–100 can be unreachable or mismeasured; and the run can keep the wrong submission. We found each of the four.

2What goes wrong

The examples below are representative. Every task is listed in Section 4, and each has a full case with the test submissions, the independent checks and the fix.

2.1Correct work is scored too low

SMT Solver. The agent builds a solver for logic formulas. When a formula can be satisfied, the solver must give an example assignment, which the grader checks. The checker looks up a function's value by how the call is written, not by what its arguments evaluate to, so the same written call can stand for two different values. Correct answers are therefore rejected on 27 hidden problems, and a perfect solver's score falls from 78.61 to 72.40.

Borden Inversion. The agent infers the location, size and timing of an underground pollution source from monitoring wells. The grader predicts the hidden readings with a physics model whose conventions the instructions never state: among other things, it ignores soil porosity, treats a rate as a total amount and places the source at the bottom of its region. An honest fit built from textbook physics scores 7.0; the same fitting method using the grader's conventions scores 31.2. The fixed version gives agents the grader's model. An agent that iterates against the grader's scores can partly learn the convention instead (Section 3.3).

2.2Wrong work is accepted

Exchange Core. The agent speeds up a stock-exchange matching engine without changing its behaviour. The grader's correctness check confirms only that money balances overall and that the order books match. Two realistic one-edit bugs, charging sellers the wrong fee and not delivering trade messages, pass the check and receive full credit, although the project's own test suite catches both. The fixed version requires those tests to pass before speed is measured.

Jagua Nesting. The agent packs flat shapes into a strip as tightly as possible. The grader misses many overlaps, such as one shape slid halfway over another, so an infeasible layout can beat every feasible one.

2.3The grader applies a rule the agent was not told

Triangulation Coloring. The instructions allow an edge flip only when the two triangles form a convex shape. The grader omits that condition, and the same faulty rule generated the hidden test cases: all ten contain overlapping triangles, and a forbidden flip improved the score on one of them.

Warehouse Routing. The instructions promise 30 seconds per test case, or 150 seconds for each input of five cases. The grader stops each input after 60 seconds, and one time-out voids the whole submission, so a solution that uses the time it was promised scores zero.

2.4The 0–100 scale cannot be reached

Treant Forest. Each test case is scored by the number of turns survived, and the grader caps turns, so the largest possible total is 92,304. The reference points of the 0–100 scale were set far above that cap. Even a perfect submission scores 21.02 out of 100. The fixed scale runs from the starter program's total to the true maximum. Warehouse Routing has the same problem, established by proof rather than measurement: a lower bound checked in Lean shows that no valid answer can score above about 30.3.

2.5The wrong submission is kept

Order Addition. One of the five grader tests compares a helper file against an out-of-date checksum, so every submission fails it. The run keeps the submission that passes the most tests and, among ties, the earliest. Every run's reported best is therefore frozen at its first valid submission, and later improvements never count. Section 3.3 shows this happening in a real agent run.

2.6A task without a sound fix

D-ABIC Gravity Inversion. Forty-two of the task's points come from numbers the submission reports about its own work, which the grader cannot check. The grader also quietly penalises one of two mathematically equivalent forms that the instructions explicitly allow. We fixed the second problem, but the first has no fix that preserves the task, so the task is removed.

3Effect on the published leaderboard

EdgeBench publishes each model's score on every task: the mean, over three twelve-hour runs, of each run's best score. Starting from those numbers, we asked how each model's average over the 51 public tasks changes once the problems are corrected. No model was rerun, and EdgeBench has not released the agents' submissions, so the effect can be computed only in part.

3.1What can and cannot be computed

  • Exact. Three corrections only change how a raw result maps to 0–100, so each published score converts directly: the Treant Forest scale, the scale Borden Inversion lacked, and the removal of D-ABIC Gravity Inversion. Together they raise every model by 1.2–1.9 points and leave the order unchanged.
  • Known maximum. For eight fixed tasks we proved or demonstrated the largest possible effect. Together they move an average by at most 0.3 points down or 1.4 up. That is enough to reverse Opus 4.8 and GPT-5.5: their gap is 1.2 points, and these fixes alone could move it by up to 1.3. The 51 public tasks therefore do not establish which of the two is ahead.
  • Direction only. For twelve fixed tasks we know whether scores rise or fall, but not by how much. The widest range in Table 2 lets each take its largest possible effect. It is an outer limit, not a prediction.

3.2Why the exact column is a floor

Several of the largest effects fall in the direction-only group. Integer Compression Codec measures every submission against stored reference numbers that the documented starter cannot reach, which understates raw results roughly four- to eightfold. In OpenTTD, a program that follows the instructions calls a function that does not exist and stops. Two features of EdgeBench's scoring make such effects larger rather than smaller. Because each run keeps its best score, a check that only sometimes over-credits still raises the run's result, and an agent that sees its scores for twelve hours is well placed to find a lenient check and keep using it. And because only valid runs are averaged, a run that a defect kills may be dropped rather than counted as zero.

3.3A check against real agent runs

EdgeBench has not released its runs. A third party has, however, published one run of Claude Opus 5.5 on 16 of the public tasks, four hours each, with every submission and its original score. Seven of those tasks are ones we fixed, so we read every submission history and regraded the decisive submissions with both graders.

  • Order Addition. Every submission failed one of the five tests, so the run kept its first agent submission, scoring 3.79, and ignored a later one scoring 41.24. Under the fixed grader every submission passes, and the run keeps 41.24.
  • Integer Compression Codec. The run's best submission scores 66.31 (raw) on the original grader and 160.76 on the fixed one. The original 0–100 scale would clip that to 100, so this check exposed a flaw in our first fix: the fixed task now uses a scale running from the starter's documented score (1.0) to the formula's maximum (320), on which the submission scores 50.08.
  • Borden Inversion. The agent reached 60.10 on the original grader by iterating against its scores, far above the 7.0 of a one-shot textbook fit. For agents that iterate, the effect is smaller than our one-shot comparison suggests.
  • Tree Block Partitioning scored 100 and Graph Node Classification showed no malformed predictions, so neither defect affected this run. Schemathesis Config and Lean Analysis were not regraded.

One model, one run per task and four hours rather than twelve cannot measure the leaderboard effect, but it shows that the problems occur in practice.

5Method

  1. Use the original grader. Every check ran on EdgeBench's published grading software, pulled from its public images and identified by a cryptographic fingerprint, with network access switched off.
  2. Quote the promise. What a task promises is taken verbatim from the instructions and documents the agent receives, and read next to the grader's code.
  3. Show the problem with test submissions. For each suspected problem we wrote three submissions and ran them through the original grader: a correct one, which must score as promised; one that triggers the problem; and a wrong one, which must be rejected.
  4. Confirm it independently. Claims were checked a second way, with exact arithmetic, a separate implementation, exhaustive search, or a formal proof in Lean 4 or TLA+ (Section 5.1).
  5. Follow it to the final score. A problem counts only if it changes the 0–100 score of honest work; problems that do not are recorded as notes.
  6. Test every fix side by side. The same test submissions were graded by the original and the fixed grader. A fix is accepted only if the problem disappears, correct work keeps its score and wrong work is still rejected. Each comparison was repeated three times on fresh machines; across 132 comparisons, no outcome changed.

5.1Formal verification

Testing shows that a problem occurs; it cannot show that something holds for every input. Wherever a claim could be stated precisely, we also checked it with a formal tool. Lean 4 is a proof assistant: a claim counts only once its kernel accepts a complete proof, and every proof lists the basic axioms it relies on, so a hidden gap would show. TLA+ describes a system as a state machine, and its model checker explores every reachable state of a bounded version.

Three rules applied to every formal result. The model is tied to the real grader code: each step maps to a source line, the file's fingerprint is recorded, and wherever possible the model is run against the real code's saved outputs. Each result has a counter-check that must fail, such as the original rule violating the property or a deliberately too-strong claim being false. And each states its limits.

In total, 26 of the 51 tasks have formal results: 25 Lean files with 288 reported theorems, and 20 model-checking runs over 3 TLA+ models (Table 4). For 12 of the 22 fixes, Lean or TLA+ proves the fix itself correct within its model, and one more is partly proved. The rest cannot be usefully formalized. ARC and OpenTTD are documentation fixes, Borden's physics convention is a modelling choice, and Exchange Core's fix relies on the project's own test suite. Those fixes rest on the side-by-side runs and the real-run check in Section 3.3. Every formal result reruns with one command, and the TLA+ checks rerun automatically on every change.

The formal checks also corrected us. One shipped fix was narrower than published: the College English grader still gave full marks in four rare kinds of contradictory assessment. It has been revised, re-proved and re-tested three times. Eight other statements were imprecise and have been corrected, for example the SMT comparability claim, the exact PSNR thresholds of the FFmpeg fix, and an undocumented side effect of the Order Addition fix. None changed a score we report.

Limitations

  • Only the 51 public tasks are covered; EdgeBench's other 83 tasks are unreleased.
  • No model was rerun. Effects on the leaderboard are computed where possible and bounded otherwise.
  • Deliberate attacks on the grader by a malicious submission concern how the benchmark isolates its grader, and are out of scope.
  • Side-by-side tests ran on one machine type (8 virtual CPUs, 8 GiB of memory); speed-based scores may differ elsewhere.
  • The reviews were carried out by AI agents. Every claim is tied to a saved evidence file and a rerunnable check, which is not the same as independent human reproduction.

6Lessons

  • Run the original grader before reasoning about it. Most problems were found by reading code but settled only by a submission that triggers them. Several plausible findings did not survive that step.
  • Formal tools pay off on small, crisp questions. A false theorem, an arithmetic gap, a lower bound and an aliasing bug were each settled conclusively. Most grader problems concern conventions, file formats or timing, which no proof addresses as cheaply as a side-by-side run.
  • A proof is only as good as its link to the code. We stated the Lean Analysis refutations against the task's own definitions inside its own image. We matched the Warehouse model to the real tester on 294 strings, and mapped each TLA+ step to a line of source. Without those links, a proof would be about something else.
  • Every check needs a counter-check. Each TLA+ model has a configuration that must fail, each Lean proof prints its axioms, and each fix is tested on wrong work as well as right work. A check that cannot fail shows nothing.
  • Formal proofs check our own work, not only the benchmark's. Writing each fix down precisely enough for Lean or TLA+ exposed one fix that was narrower than published and eight imprecise statements. Each was found because a proof attempt failed on a case we had not thought to test.
  • Test what a fix is for, not only what it changes. The first Integer Codec fix corrected the baseline exactly as documented and passed every test, yet real submissions showed it saturated the score scale. Checking fixes against real agent work found what neither proofs nor authored tests did.
