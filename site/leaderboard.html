Leaderboard

Effect on the published leaderboard

What the corrected graders could change, and what cannot be determined from public data

On the published leaderboard, Opus 4.8 leads GPT-5.5 by 1.1 points (44.2 against 43.1). With the per-task limits we documented, their ranges are 45.49–47.30 and 44.30–46.35. These overlap, so the public data can no longer confirm which of the two is ahead. This does not show that they change places. The ranges count the 19 fixes whose size on the leaderboard is unknown as zero.

Each range in Table 3 is the lowest and highest average the fixes could give, using only what we could measure or prove. EdgeBench publishes each model's average over its valid runs; its runs and submissions are not public, so the corrected leaderboard itself cannot be computed. The ranges are not estimates of the corrected scores, and their ends are not results anyone is known to reach. They keep the same runs valid, treat the tasks we kept as unchanged, and assume the direction and limit stated for each effect. If a fix changed which runs fail, or how agents work, new evidence would be needed.

1What can and cannot be said

  • Scale only. Remove D-ABIC, convert Borden to its new 0–100 scale, and allow for Treant's new scale run by run. Treant's scale has two parts and cuts scores at zero, so a published Treant average does not tell us each run's score; the range allows for every possibility. Every kept task's published score is rounded, so it may be off by up to 0.05. The middle of a range is not an estimate of the corrected score.
  • Documented limits. The next range adds 10 per-task limits, each the most that task's fix can change its score. They include PFR credit that we inferred from the rules, not credit shown on the actual proof targets. Each limit is taken on its own; the ranges do not claim that all of them can be reached together. The 19 fixes whose size is unknown count as zero here, so any order these ranges confirm holds only if those fixes change nothing. The ranges for Opus 4.8 and GPT-5.5 overlap. The public data therefore cannot confirm which of the two is ahead; this does not show that they change places.
  • Plus Portfolio. A separate column adds +0.3921/−0.10 points for Portfolio Risk. The estimate comes from a limited numerical search (242 or 243 shared dates, strategy returns from −30% to +100%): the largest rise it found was 0.3913, and 0.3921 adds a margin. Neither the search nor Lean proves that no larger rise is possible.
  • Widest possible. The widest range lets every fix whose size is unknown move its task's score as far as it can go in its stated direction, and lets Portfolio take any value from 0 to 100. With these ranges every pair of neighbouring models overlaps, so no place on the leaderboard can be confirmed. These are outer limits, not confidence intervals or predictions.

2Why the true effect may be large

Several of the largest effects fall in the group whose size is unknown. Integer Compression Codec measures every submission against stored reference numbers that the documented starter cannot reach; on all 37 submissions of a real agent run the original raw result was 1.7 to 4 times lower than the documented definition gives. In OpenTTD, a program that follows the instructions calls a function that does not exist and stops. Two features of EdgeBench's scoring make such effects larger. Because each run keeps its best score, a check that only sometimes over-credits still raises the run's result, and an agent that sees its scores for twelve hours is well placed to find a lenient check and keep using it. And because only valid runs are averaged, a run that a defect kills may be dropped rather than counted as zero.

3A check against real agent runs

EdgeBench has not released its runs, but a third party has published one run of Claude Opus 5.5 on 16 of the public tasks: four hours per task, with every submission the agent made and the score the original grader gave it. Nine of those 16 tasks are ones we fixed. The other seven we kept unchanged, so there is nothing to regrade.

Which fixes old submissions can test. A saved submission is the agent's answer to the task as it was. If a fix changes only the grader, the same answer can be given to the original grader and to the fixed one, and the comparison is fair, because the agent saw exactly the same task either way. If a fix changes only what the agent sees (the instructions or a starter file), the grader is the same, so old answers score the same under both versions; the agent would have worked differently with the new instructions, so only a new run can show the fix's effect.

  • Regraded: 7 tasks. Their fixes change the grader alone. We graded 314 submissions with both graders (349 paired gradings, counting repeats), using the run's own grading script and the official 4 CPUs, and recomputed each task's score with EdgeBench's rule of keeping the best submission so far. Both columns of Table 4 are these regrades on our machines; where the run's own recorded score differs, the note gives it. Graders that depend on timing were run three times for the submissions that decide the score. As a check on the replay, the original grader reproduced the run's recorded result exactly for all 144 submissions of the three tasks whose graders do not depend on timing.
  • Not regraded: 2 tasks. The Borden Inversion fix changes only the instructions and a starter file; its grader is unchanged, so the run's answers score the same under both versions. The Lean Analysis grader needs an image that unpacks to about 33 GB and 16 GB of memory, more than our machines have, so its effect was computed from the original grader's verdict on each proof target instead. Its fix also corrects two statements to prove; they were false, so no answer could earn them before, and the run's verdicts on every other target do not depend on them.

In Juliet, 14 of 105 submissions, all early ones, rose under the fix, and the kept score of 99.66 did not change. In Borden Inversion, whose grader is unchanged, the run's best score climbed from 7.01 to 60.10 over 36 submissions while the checker reported its error on the hidden wells after each one; 7.01 is about what a one-shot fit that follows the documentation scores.

This is one model and one four-hour run per task, rather than three twelve-hour runs. It shows that the problems occur in practice, but it cannot measure the effect on the leaderboard.
