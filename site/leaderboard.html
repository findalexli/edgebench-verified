Leaderboard

Effect on the published leaderboard

What the corrected graders could change, and what cannot be determined from public data

EdgeBench publishes each model's score on every task: the mean, over three twelve-hour runs, of each run's best score. We asked how each model's average over the 51 public tasks changes once the problems are corrected. The honest answer is that it cannot be determined from public data. Measuring it requires either regrading the agents' original submissions, which EdgeBench has not released, or rerunning the models on the fixed tasks, which this audit did not do. What can be stated precisely is the largest possible change, a narrower range from the fixes whose effect has a proven limit, and the part that can be computed exactly (Table 3). All three assume that no fix turns a failed run into a scored one or the reverse.

1What can and cannot be said

  • Largest possible change. Letting every fix take its largest possible effect moves a model's average by as much as 9.4 points down or 23.1 up. For 18 fixed tasks we know only whether scores rise or fall; with the open part of Borden Inversion, they account for up to 9.0 down or 21.1 up. This is a limit, not a prediction; the true change lies inside it if no fix changes which runs count as valid.
  • Proven limit. For 11 fixed tasks the task's own scoring bounds the largest possible effect (computed from the grader; for PFR inferred from its rule; for Portfolio Risk from a decimal sweep, not a proof). Together they move an average by at most 0.4 points down or 2.0 up. That is enough to reverse Opus 4.8 and GPT-5.5: their gap is 1.2 points, and these fixes alone could move it by up to 1.8. The 51 public tasks therefore do not establish which of the two is ahead.
  • Exactly computable part. Two fixes only change how a raw result becomes 0–100, and one task is removed, so each published score can be recomputed directly. Together they raise every average by 1.2–1.9 points: the Treant Forest scale adds 1.0 to 1.4, the removal of D-ABIC Gravity Inversion adds 0.2 to 0.5, and the scale Borden Inversion lacked subtracts 0.01 to 0.08. This is only the part we can calculate; the other fixes can still push an average up or down. The conversions inherit the one-decimal rounding of EdgeBench's table.

2Why the true effect may be large

Several of the largest effects fall in the group whose size is unknown. Integer Compression Codec measures every submission against stored reference numbers that the documented starter cannot reach; on two real submissions the original raw result was 2.4 and 3.7 times lower than the documented definition gives. In OpenTTD, a program that follows the instructions calls a function that does not exist and stops. Two features of EdgeBench's scoring make such effects larger rather than smaller. Because each run keeps its best score, a check that only sometimes over-credits still raises the run's result, and an agent that sees its scores for twelve hours is well placed to find a lenient check and keep using it. And because only valid runs are averaged, a run that a defect kills may be dropped rather than counted as zero.

3A check against real agent runs

EdgeBench has not released its runs. A third party has, however, published one run of Claude Opus 5.5 on 16 of the public tasks: four hours per task, with every submission the agent made and the score the original grader gave it. Nine of those 16 tasks are ones we fixed. The other seven we kept unchanged, so there is nothing to regrade.

Which fixes old submissions can test. A saved submission is the agent's answer to the task as it was. If a fix changes only the grader, the same answer can be given to the original grader and to the fixed one, and the comparison is fair, because the agent saw exactly the same task either way. If a fix changes what the agent sees (the instructions, a starter file, a statement to prove), the agent would have worked differently, so grading its old answers with the fixed version measures nothing.

  • Regraded: 7 tasks. Their fixes change the grader alone. We graded 314 submissions with both graders (349 paired gradings, counting repeats), using the run's own grading script and the official 4 CPUs, and recomputed each task's score with EdgeBench's rule of keeping the best submission so far. Graders that depend on timing were run three times for the submissions that decide the score. As a check on the replay, the original grader reproduced the run's recorded result exactly for all 144 submissions of the three tasks whose graders do not depend on timing.
  • Not regraded: 2 tasks. The Borden Inversion fix changes only the instructions and a starter file. The Lean Analysis grader needs a 33 GB image and 16 GiB of memory, more than our machines have, so its effect was computed from the original grader's verdict on each proof target instead.

In Juliet and Borden Inversion the agent learned the hidden convention from the grader's feedback. Early submissions lost points; later ones did not. In Juliet the run's final score is therefore unchanged by the fix. This is one model and one four-hour run per task, rather than three twelve-hour runs. It shows that the problems occur in practice, but it cannot measure the effect on the leaderboard.
