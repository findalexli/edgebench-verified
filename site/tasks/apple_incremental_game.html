Apple Incremental Game

Fixed Engineering and runtime environment apple_incremental_game

On the publisher's 4-CPU grader, cases within the 30-second limit time out and score 0.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Write a program that plays a machine-production incremental game adapted from an AtCoder programming contest (AHC058) on 50 fixed test cases; the score is the sum of per-case scores.
What goes wrong
The grader runs 8 cases at once under a 30-second wall-clock limit. On the publisher's 4-CPU setting each case gets half a CPU, so a valid solution using 20 seconds of CPU per case timed out on 48 of 50 cases and its score fell to 0. The lower end of the score scale is consistent; the upper reference points were not checked. The stated 1 GB memory limit is not enforced for each solution.
How much it matters
Up to nearly the full score for solutions using about 15 to 30 seconds of CPU per case on a 4-CPU grader; solutions that stop at a deadline got half the computing time. The memory note matters only to users relying on the stated limit.
What we did
Fixed in a new version: the grader runs at most as many cases at once as it has CPUs, so each case keeps its 30 seconds. The memory limit and the unchecked upper reference points remain notes.
Problem category
Engineering and runtime environment
Validation status
CPU-share controls validated: three identical paired native runs at 4 CPUs plus a pair at 8 CPUs (each ledger exit=0); package rebuilt from scratch on a clean machine (materialize-check-g1). Not tested in a Kubernetes pod or at 3 or 5-7 CPUs; below 3 CPUs a submission that reaches eval_timeout loses its whole output.

Apple Incremental Game - Machine Production (AHC058)

Write solution.py in the project root that reads from stdin and writes to stdout.

Problem Overview

Read README.md and tools/README.md for full problem details. A baseline solution.py already exists (it produces syntactically valid but low-quality output). Your job is to improve it.

Evaluation

Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Higher is better.

Local Testing

Generate local random tests with ./tools/bin/gen <seed>, using seeds in the range 0..10000 only.

# Generate a random test case (seed-based, deterministic)
./tools/bin/gen 0 > input.txt

# Run your solution
python3 solution.py < input.txt > output.txt

# Score output (Higher is better)
./tools/bin/tester input.txt output.txt
# Outputs to stderr: Score = <N>

Rules

  • Write your solution as solution.py in the project root directory
  • Do NOT modify files in tools/
  • Use tools/bin/gen and tools/bin/tester for local testing
  • For local scoring, use only ./tools/bin/tester; do not use tools/src/verifier.py for scores
  • Your program should read from stdin and write to stdout
  • Run your solution to completion and verify with the tester before finishing

What we found

The full case: the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. On the publisher's 4-CPU grader, a valid solution using more than about 15 s of CPU per case times out, although the README promises 30 s per case, and each timed-out case scores 0. The fixed version runs at most as many cases at once as the grader has CPUs. The lower end of the score scale agrees with an independent simulation; the upper reference points were not checked; the 1 GB memory limit is not enforced for each solution.

What the task asks

The task is adapted from an AtCoder Heuristic Contest problem (AHC058), a machine-production incremental game. The task text says: "Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Higher is better." The score for one case is round(1e5·log2 S) (README:34-36). Category: Combinatorial Optimization.

What we checked

One scoring defect was found, the CPU dependence of the time limit (fixed). These parts were checked:

  • Score scale. The raw result (before conversion to 0–100) is converted with the piecewise_max method. Its reference point for 0 is 45,000,000 (900,000 per case, that is S = 2⁹). The rank-1 point, 282,791,094, maps to 80, and 100 corresponds to 289,952,856.4 (tasks/apple_incremental_game.json, judge.rescale; sforge/harness/score_rescale.py, piecewise_max). The shipped do-nothing starting solution has S = K = 1. It therefore scores a raw result of 0, which maps to 0. A simple greedy simulator, written independently, reaches a raw result of 237,518,875 (4.75M per case). That maps to 17.7 out of 100. This is below the reference point for the 30th-ranked level (5.25M per case), which is the expected order. This checks only the lower end of the scale.
  • Upper reference points not checked. The rank30, rank1 and 100 points (262,328,915.67, 282,791,094 and 289,952,856.42) are not whole numbers; ×3 and ×12 give whole numbers (786,986,747 and 3,479,434,277), which suggests they were rescaled from another case count. Where they come from, and whether 100 can be reached on these 50 cases, was not checked. The sister task Treant, which uses the same evaluator code, has a rank-1 point 3.58 times its attainable maximum (evidence/reviews/_game-tasks-correctness.md, section 8).
  • The 30 s per case shrinks to about 15 s of CPU on a 4-CPU grader (fixed). The README promises "Time limit | 30 seconds / test case" (line 71). The limit is wall-clock time (TIME_LIMIT = 30, /tmp/eval_apple_incremental_game.py line 9), 8 cases run at once (max_workers=min(8, len(case_files)), line 45), and a timed-out case scores 0 (line 37). The task sets no CPU count. In EdgeBench's leaderboard configuration examples/all-tasks-k8s/experiment.yaml (quoted in evidence/impact/edgebench-leaderboard-config.md) (sha256 d9d299794ba946cae8d2b7f68a7879a35bb8565d95e78107edf79802993643be), the grader inherits judge_cpu_limit: 4, so each of the 8 cases gets about half a CPU. Measured on the original grader at --cpus 4 (evidence/runs/apple_incremental_game-cpu4v8-a/result/out/summary.txt, -b; repeated in apple_incremental_game-v2-paired) with an honest greedy control we wrote (TOTAL 99,714,418, 5.04 out of 100; the shipped baseline scores 0 on every case and would hide the difference between OK and TLE): with 12 or 14 s of extra CPU work per case it passes 50/50; with 20 s, 48 of 50 cases time out on both workers and the total falls to 3,955,266, which is 0 out of 100. At --cpus 8 all pass with 99,714,418. A solution that stops at a 25 s wall-clock deadline gets a mean of 13.00 s of CPU per case at 4 CPUs and 24.94 s at 8 CPUs.
  • Repeatability. The evaluator code adds no randomness. The per-case score comes from the tester program tools/bin/tester; it scored our greedy control's outputs in the CPU runs (99,714,418 in every run), but its code was not examined.

The task text (README) states a 1 GB memory limit, but the grader does not enforce it for each solution.

The note says: the advertised 1 GB memory policy is not enforced per solution.

Not in the shipped note: the source of the upper reference points (rank30, rank1 and 100) is not stated and was not checked.

How much it matters

CPU count. Under the original grader at the publisher's 4 CPUs, a solution using more than about 15 s of CPU per case loses those cases (0 each); losing 48 of 50 cases takes nearly the whole score (measured: 5.04 → 0 for our control; for stronger solvers this follows from the case count and was not measured). Under the fixed version these cases are scored. A solution that stops at a wall-clock deadline gets about twice the CPU per case under the fixed version (mean 13.00 s → 24.99 s for the 25 s deadline solution); how much that changes its score is not measured.

Notes. No score effect was found from the lower end of the scale. The upper reference points were not checked, so an effect from them is not ruled out. The memory note had no score effect on an honest solution. It matters only to users who rely on the stated limit.

The fix

The fixed version (repairs/apple_incremental_game-v2/) changes how many cases /tmp/eval_apple_incremental_game.py runs at once. A new function cpu_quota_workers(), the same as in repairs/grid_turing_robot-v2/, reads the grader's CPU quota from the cgroup (cpu.max, or the cgroup v1 quota and period), rounds it down to whole CPUs, falls back to os.cpu_count() when there is no quota, and keeps the result between 1 and 8. The pool becomes ProcessPoolExecutor(max_workers=min(cpu_quota_workers(), len(case_files))). docker run --cpus N and the publisher's k8s backend both set this quota; at --cpus 1/2/3/4/8 the fixed grader runs 1/2/3/4/8 cases at once (apple_incremental_game-v2-paired/result/out/v2_workers.txt). The task JSON changes only judge.image_tag. The 30 s limit, the 600 s eval_timeout, the README, the tester, the cases and the score scale are unchanged. With 8 or more CPUs the fixed grader runs 8 cases at once, exactly as the original.

Paired run at --cpus 4 (one pair at --cpus 8), same solutions on both graders (evidence/runs/apple_incremental_game-v2-paired/result/out/summary.txt; repairs/apple_incremental_game-v2/paired/results.md):

Under the fixed version the slowest 28 s case took 28.02 s from start to end (result/out/timing_summary.txt). Grading at 4 CPUs takes at most ⌈50/4⌉ = 13 rounds of 30 s; the bad control, which times out on every case, took 390.8 s (original: 210.7 s), inside the task's 600 s eval_timeout. The 390.8 s is that measured run, not a computed bound.

Are scores comparable? At 8 or more grader CPUs the two versions grade the same way. At 4 CPUs a deterministic solution that finished every case in time under the original gets the same output and score under the fixed version, and a solution needing about 15 to 30 s of CPU per case is scored on those cases instead of getting 0. A solution that searches until a wall-clock deadline gets about twice the CPU per case, so its scores under the two graders at 4 CPUs are not comparable. Per-case CPU never decreases under the fixed version.

These notes still ship with the fixed version: the 1 GB memory limit is not enforced for each solution, and the source and reachability of the upper reference points were not checked.

How we checked it

  • Original grader source. We read the grader file eval_apple_incremental_game.py from the original public image. It uses the same code as the Treant task, with TIME_LIMIT=30, and the piecewise_max score scale.
  • CPU runs and paired run on E2B. Valid solutions doing 12 to 28 s of CPU work per case, a 25 s wall-clock-deadline solution and a 40 s bad control ran on the original grader at --cpus 4 and --cpus 8 (evidence/runs/apple_incremental_game-cpu4v8-a, -b; ledger jobs cpu4v8-games-a, -b) and side by side on the original and fixed graders (evidence/runs/apple_incremental_game-v2-paired), each job status: exit=0, in the digest-pinned grader image with --network none --memory 4g. Each solution runs our honest control (a level-0 return-on-investment greedy), then does its extra work, then prints the control's answer, and logs its own start, end and CPU time per case (result/out/timing/).
  • Independent simulator. A greedy simulator that looks one step ahead and follows the rules in the task text ran on all 50 shipped cases. It is not the original tester program.
  • Arithmetic on the time budget and the score scale (evidence/scripts/_game-tasks-correctness/check_arith.py). The greedy total of 237,518,875 is entered there as an observed value; the simulator's own output is not saved in this repository.

Limits

  • The fixed grader reads its CPU quota from the cgroup (cpu.max). This was tested with docker run --cpus only, not inside a Kubernetes pod, which is the backend EdgeBench's leaderboard settings use.
  • No AI model or solver runs were made. Effects are shown only on test submissions and counterexamples that we wrote.
  • The greedy check uses an independent simulator, not the original tools/bin/tester. Scoring one greedy output with the original tester would close this gap.
  • The original and fixed graders were run inside the digest-pinned grader image only for the CPU measurements and the paired run, at 4 and 8 CPUs, on E2B workers with 8 vCPUs. 3, 5, 6 and 7 CPUs were not tested.
  • The CPU test solutions are single-threaded: fixed CPU work, or work until a 25 s wall-clock deadline. Multi-threaded solvers were not tested.
  • Deadline-based solvers get about twice the CPU per case under the fixed version at 4 CPUs, so their scores under the two graders are not comparable. How much their scores change is not measured.
  • With fewer than 3 grader CPUs the 600 s eval_timeout, not the 30 s per case, becomes the binding limit (25 rounds × 30 s = 750 s at 2 CPUs). The grader prints its results only after every case has finished, so a submission that reaches the eval_timeout loses its whole output and scores 0. Below 3 CPUs the fixed version can therefore score lower than the original for a solution that times out on most cases (derived from the code, not run). The quota is rounded down: 2.5 CPUs run 2 cases at once.
  • Without a cgroup quota the fixed grader falls back to os.cpu_count(), which counts all host CPUs rather than the ones the grader may use (os.sched_getaffinity); under a CPU-set limit with no quota it can still run more cases at once than it has CPUs.
  • The package was rebuilt from scratch on a clean machine (evidence/runs/materialize-check-g1, status: exit=0): materialize.sh ran unchanged, the output matched the lock and the built image holds the locked file.
  • The origin and reachability of the upper reference points were not checked.
