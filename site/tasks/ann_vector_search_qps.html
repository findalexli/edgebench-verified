Summary

The task
Make a search over one million 128-number vectors answer as many queries per second as possible, while still finding at least 95% of the true 10 nearest matches.
What goes wrong
The answer key was checked on all 10,000 queries; our valid and empty test submissions score as documented, and a fast submission with recall 0.36 is rejected. Caveat: speed is measured once per grading and depends on the machine. Three isolated gradings of one valid configuration on the original grader, at the leaderboard's 4 CPUs and 8 GiB, gave 551 to 713 queries per second (±13%); the scale comes from the authors' hardware.
How much it matters
Speed varied 1.29-fold between three isolated gradings of one configuration: 13.3 of 100 points (about ±7 per grading) where agents score (23.8–59.7). Scores from different machines are not comparable.
What we did
Kept, with a note: speed depends on the machine; three isolated gradings of one configuration varied by ±13% (13.3 of 100 points); the scale was set on the authors' hardware, so machines are not comparable.

What the agent is asked to do

EdgeBench's harness adds its standard instructions on how to submit (sforge/harness/evolve_scripts.py), which are not shown.

Role

You are an expert in approximate nearest neighbor (ANN) search. Your job is to maximize QPS (queries per second) on the SIFT-1M dataset (1M × 128-d vectors, 10K queries) under the ann-benchmarks framework, while keeping Recall@10 ≥ 0.95.

Repository Layout

  • run.py — evaluation driver (already present)
  • ann_benchmarks/algorithms/ — algorithm plugins; each algorithm subclasses BaseANN and registers in its own config.yml
  • ann_benchmarks/algorithms/custom/ — your slot; contains a baseline module.py (brute-force numpy) and a config.yml naming the algorithm custom
  • data/sift-128-euclidean.hdf5 — dataset (pre-downloaded, contains train and test arrays)

What To Do

  1. Read README.md, ann_benchmarks/algorithms/README.md, and look at existing algorithms (e.g. ann_benchmarks/algorithms/faiss/) for reference implementations.
  2. Improve ann_benchmarks/algorithms/custom/module.py — implement a faster fit() + query() using FAISS (faiss-cpu is pre-installed) or a custom implementation. Keep the class name Custom and the module path ann_benchmarks.algorithms.custom.
  3. You may tune hyperparameters via ann_benchmarks/algorithms/custom/config.yml (IVF nlist, HNSW M/efConstruction, PQ subquantizers, etc.).
  4. For local runs after each change: 
    python run.py --local --algorithm custom --dataset sift-128-euclidean -k 10 --runs 1 --run-disabled

    The benchmark prints QPS and recall metrics to the console. Use these to track your progress.

Optimization Directions (suggestions)

  • IVF bucketing (nlist, nprobe)
  • HNSW (M, ef, efConstruction)
  • Product Quantization (subquantizers, bits)
  • Two-level routing (IVF-HNSW, IVF-PQ)
  • Early termination on candidate scan
  • Multi-threaded search (omp_set_num_threads)

GLM-5.1 reference: 3108 QPS → 21472 QPS (6.9×) over 655 iterations.

Scoring Integrity (CRITICAL)

The evaluation system independently measures query latency and verifies search results against the ground truth. Your score is determined by the actual search performance of your algorithm.

You must NOT:

  • Read or access ground truth data (the neighbors dataset) during query execution
  • Override timing attributes or manipulate benchmark measurements (e.g., via get_additional())
  • Monkey-patch the time module or any benchmark framework internals
  • Attempt to fabricate or inflate scores through any means other than legitimate algorithmic improvements

Any attempt to manipulate scores will result in score=0 and the submission marked as hack.

Rules

  • Keep the algorithm name custom and leave its config discoverable via python run.py --list-algorithms
  • Do NOT modify run.py or any file outside ann_benchmarks/algorithms/custom/
  • Recall@10 < 0.95 on a config makes that config invalid (score = 0)
  • Final score is the highest QPS among valid (recall-passing) configs

What we found

The full case: the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Kept, with a note. Submissions that follow the rules are scored as documented, but the measured speed depends on the machine the grader runs on and varies between gradings: three isolated gradings of one IVF-flat configuration at the leaderboard's grader setting gave 551–713 QPS, worth 13.3 points out of 100 on the scale (about ±7).

What the task asks

The agent must speed up an approximate nearest-neighbour search: a search that finds the vectors closest to a query without comparing against every vector. The prompt says: "maximize QPS (queries per second) on the SIFT-1M dataset (1M × 128-d vectors, 10K queries) under the ann-benchmarks framework, while keeping Recall@10 ≥ 0.95". Recall@10 is the share of the true 10 nearest matches that the search finds.

The work happens in ann_benchmarks/algorithms/custom/module.py. The grader converts the raw result (before conversion to 0–100), here the QPS, to a score out of 100 on a logarithmic scale (log_max). The reference point for 0 is 3108 QPS and the reference point for 100 is 21472 QPS. Any raw result of 21472 QPS or more scores 100. Category: Systems & Software Engineering.

What we checked

The grader computes the documented result correctly for a solver that follows the rules. These checks found it correct:

  • The grader's exact answer key (labels and distances) is correct over all 10,000 queries.
  • A correct test submission using FAISS flat search (an exact, brute-force search) is accepted. An empty test submission is rejected.
  • A fast but inaccurate submission is rejected: the same IVF-flat index searching one cluster per query (nprobe=1) reaches 11,237–12,988 QPS but recall 0.3642, and the grader reports it as a wrong answer with total score 0 in each of three separate gradings. Without the recall check that speed would be worth 66.5–74.0 points out of 100.
  • The recall threshold works as documented. Recall counts the overlap of returned and true neighbour IDs, so ties in distance count as misses: the exact flat search scores recall 0.9993, not 1.0. Upstream ann-benchmarks instead accepts any neighbour within the 10th true distance. The difference is at most 0.07 percentage points of recall.
  • Within one grading, the grader keeps the fastest valid configuration, as documented.

The note concerns speed measurement. QPS is measured in a single run and depends on the machine. On the original grader, at the leaderboard's grader setting of 4 CPUs and 8 GiB, three gradings of one IVF-flat configuration (a FAISS index that searches only a few clusters of vectors), each alone in its own grading on a fresh cloud worker, gave 713, 650 and 551 QPS (±13% about the midpoint; the fastest is 1.29 times the slowest). Earlier gradings of the same configuration on a shared local machine at 2 CPUs, each sharing its process with other test configurations, gave 935, 1,222 and 1,094 QPS (1.31 times). The reference points of the score scale (3108 / 21472) come from the authors' hardware.

The note that ships with the task says: QPS depends on the machine, and three isolated gradings of one IVF-flat configuration on the original grader at 4 CPUs and 8 GiB gave 551–713 QPS (±13%). On the logarithmic scale, a speed ratio of 1.29 is 13.3 points out of 100 (about ±7 per grading) for a submission between the reference points. The reference points of the score scale come from the authors' hardware, so scores are not comparable across machines.

How much it matters

Across three isolated gradings on three fresh workers with the same CPU model, the same configuration's raw result moved between 551 and 713 QPS. The scale is logarithmic, 100 · ln(QPS / 3108) / ln(21472 / 3108), so a speed ratio of 1.29 moves a score by 13.3 points out of 100 (about ±7 points per grading) for any submission between 3108 and 21472 QPS. The earlier shared-process gradings on one local machine gave a ratio of 1.31, or 13.9 points, so the isolated repeats confirm the size of the effect. The valid test submissions here are all below 3108 QPS and score 0, so this effect is computed from the scale, not observed in a score. Recorded agent runs on this task score 23.8–59.7 out of 100 (tasks/README.md), inside that range, so the effect applies at the scores agents reach. The task keeps each run's best submission (score_first), so variation between gradings can raise a run's recorded best. Whether variation between machines changes every algorithm's speed by the same factor was not tested. Scores out of 100 are not comparable across machines, and repeated gradings on one machine are not exactly repeatable.

The task does not change; the note above ships with it.

  • Earlier test design. Each of those gradings ran one custom module whose config.yml lists several configurations, so the IVF-flat result shares one ann-benchmarks process with other test configurations we wrote, which are not genuine solutions. ann-benchmarks runs the configurations of one grading in random order in that process, so one configuration can affect the timing of a later one. The three IVF values on the original grader are within a factor of 1.31 of each other. A fourth IVF value, 875 QPS, came from a modified evaluator and is not counted here, and neither are other IVF values from that modified evaluator. Those gradings have no entry in the run ledger. The isolated repeats above replace them as the measure of the spread.
  • Independent check. The exact labels and distances were checked over all 10,000 queries.

Limits

  • No AI model or solver was run. Score effects are shown only on test submissions we wrote.
  • Each QPS figure comes from a single run. The isolated repeats ran on shared cloud workers with one CPU model. Nothing was measured on the authors' hardware or on a dedicated grading machine.
  • Three repeats bound the spread only roughly; more repeats or other CPU models could show a wider one.
  • Only the single-threaded IVF-flat configuration was repeated. Its QPS (551–713) is below the 0-point reference, so the 13.3-point effect is computed from the scale, not observed in a score. Whether faster or multi-threaded submissions vary by the same factor was not tested.
  • Whether the grader is protected from tampering by a deliberately malicious submission is outside this release's scope (an EdgeBench design choice) and was not assessed.

Reproduce

  • Run the unchanged original grader in the pinned image (sha256:aa2856a379c1…) with a valid custom/ module mounted at ann_benchmarks/algorithms/custom. Use --network none --cpus 4 --memory 8g, and run python3 /tmp/eval_ann_search.py from /home/workspace/ann-benchmarks.
  • The isolated repeats: evidence/runs/ann_vector_search_qps-ivf-isolated-cpu4m8g-rep{1,2,3}/run.sh with the test submissions in inputs/, run with tools/e2b_run.py --job <dir>.
  • For local development, the prompt's own command is python run.py --local --algorithm custom --dataset sift-128-euclidean -k 10 --runs 1 --run-disabled.
