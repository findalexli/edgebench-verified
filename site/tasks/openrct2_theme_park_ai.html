OpenRCT2 Theme Park AI

Fixed Instruction–grader mismatch openrct2_theme_park_ai

Instructions promise about 4 game years; the grader runs about 68 game days.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Write a plugin for OpenRCT2, a theme-park simulation game, that raises each park's company value across three scenarios.
What goes wrong
The instructions say each scenario runs about 4 game years. The grader stops each scenario after 120 real seconds, which covers 68 to 69 game days at the top speed, about 7% of that target. The score is the company value at this early point. A plugin can also slow the game down, so fewer days pass.
How much it matters
Not measured as a score change. It changes what is measured: company value after about 2 months, not 4 years, for solvers who planned for the stated length.
What we did
Fixed in a new version: the instructions now state the real 120-second limit, about 70 game days at speed 4, and that the plugin may set speed 1 to 4. Grading is unchanged.
Problem category
Instruction–grader mismatch
Validation status
Prompt-only correction: the measured horizon (about 70 game days in 120 s at speed 4) is reproduced from saved logs and the arithmetic is in Lean; package rebuilt from scratch on a clean machine (materialize-check-g3). The full wrapper, the Kubernetes grader and a competitive plugin were not run; lowering the game speed can still freeze value.
Formal check
Proved in Lean 4. 992 game days need about 1,658 seconds at the model rate and 1,661 to 1,705 seconds at the measured rates, against a 120-second budget per scenario. Limit: Arithmetic only.

What the agent is asked to do

Role

You are an expert OpenRCT2 plugin developer. Write a single JavaScript (ES5) plugin file my_plugin.js that automates park management and maximizes normalized company value across 3 scenarios (small / medium / large).

Files

  • my_plugin.js — your plugin (a baseline no-op is pre-placed)
  • openrct2.d.ts — OpenRCT2 v0.5.0 plugin API types (5782 lines)
  • samples/ — 4 reference plugins: park_info, staff_manager, ride_builder, finance_manager

Key APIs

  • park.cash, park.companyValue, park.rating, park.guests, park.bankLoan
  • park.entranceFee (read-only for strategy; set it with context.executeAction('parksetentrancefee', {value: ...}))
  • park.getMonthlyExpenditure(type) — monthly financials history
  • context.executeAction('ridecreate', {...}) — build a ride
  • context.executeAction('staffhire', {staffType: N, ...}) — hire staff (staffType is numeric 0-3)
  • context.executeAction('ridesetprice', {...}), parksetentrancefee, parksetloan, parkmarketing, parksetresearchfunding — normal management actions
  • context.executeAction('gamesetspeed', {speed: 4}) — max speed (host mode cap is 4)
  • context.subscribe('interval.tick', fn), context.subscribe('interval.day', fn)

Plugin Skeleton

var main = function() {
    if (context.mode !== 'normal') return;
    context.executeAction('gamesetspeed', {speed: 4});
    context.subscribe('interval.tick', function() { /* strategy */ });
};
registerPlugin({
    name: 'MyParkAI', version: '1.0', authors: ['agent'],
    type: 'remote', licence: 'MIT', targetApiVersion: 34, main: main
});

Allowed Strategy Surface

Build a fair management bot. Prefer these normal gameplay actions:

  • Build rides, paths, shops, scenery, and entrances with context.executeAction(...)
  • Open/close rides, set ride prices, set the park entrance fee, manage loans, run marketing, and set research funding through normal actions
  • Hire staff and adjust staffing through normal actions
  • context.executeAction(...) and context.queryAction(...) may only use plain string-literal action names from this allowlist: gamesetspeed, ridesetprice, ridesetstatus, ridesetsetting, ridesetname, ridesetappearance, ridesetcolourscheme, ridecreate, ridedemolish, rideentranceexitplace, rideentranceexitremove, trackplace, trackremove, mazeplacetrack, mazesettrack, footpathplace, footpathlayoutplace, footpathremove, footpathadditionplace, footpathadditionremove, parksetentrancefee, parksetloan, parkmarketing, parksetresearchfunding, parksetname, staffhire, stafffire, staffsetname, staffsetorders, staffsetpatrolarea, staffsetcostume, landraise, landlower, landsetheight, landsmooth, landbuyrights, landsetrights, waterraise, waterlower, watersetheight, clearscenery, smallsceneryplace, smallsceneryremove, smallscenerysetcolour, largesceneryplace, largesceneryremove, largescenerysetcolour, wallplace, wallremove, wallsetcolour, bannerplace, bannerremove, bannersetcolour, bannersetname, bannersetstyle, parkentranceplace, parkentranceremove
  • Read park, date, map, rides, and entities to make decisions; keep your own bookkeeping in ordinary local variables or plain objects
  • Optimize cash flow, ride mix, pricing, guest satisfaction, loan repayment, marketing timing, and staff coverage

Explicitly Prohibited Behavior

The following behavior is forbidden even if the OpenRCT2 JavaScript API exposes it:

  • Do not directly assign or mutate protected game state such as park, ride, guest, peep, staff, entity, date, scenario, climate, or context.research fields. Use normal gameplay actions instead.
  • Do not change guest generation, guest soft caps, suggested guest counts, spawn probability, guest initial stats, or guest generation hooks. Do not call direct guest-spawn or peep-spawn APIs.
  • Do not use high-risk runtime or bypass APIs, including parksetparameter, scenariosetsetting, parksetdate, guestsetflags, peepspawnplace, ridefreezerating, context.registerAction, console.executeLegacy, eval, Function, Proxy, Reflect.set, Object.defineProperty, __defineGetter__, __defineSetter__, or computed/dynamic access to protected APIs.
  • Do not monkey-patch globals, built-ins, console, context, map, park, or judge/runtime APIs.
  • Do not construct action names dynamically. Action names passed to context.executeAction(...) or context.queryAction(...) must be plain string literals from the allowlist above.

Scoring Expectations

The hidden judge rewards real park operation, not just preserving starting value. At startup, inspect the current park state. Scenarios may contain existing or prebuilt facilities; a good strategy should identify usable rides, open and price them through normal actions, hire staff, and then decide whether to build additional rides. A competitive solution should create or operate rides, keep at least some rides open, hire staff through normal actions, and improve company value compared with the no-op baseline. Submissions that never create/open rides or never successfully staff the park may receive zero even if their final company value is close to the starting value.

Rules

  • Only edit my_plugin.js in the project root
  • ES5 only — no arrow fns, no let/const, no template strings
  • Do NOT modify openrct2.d.ts or samples/
  • The engine runs each scenario for ~4 game years at speed 4 (host --headless)
  • Scoring is performed by a hidden judge monitor that reads the real in-game park.companyValue; your stdout is ignored for scoring
  • You may print ordinary debugging messages for action result codes and strategy state (for example action ridecreate err 4); these logs are feedback only and do not affect score
  • Do not cheat, exploit, bypass, or tamper with the game, runtime, scoring, tests, judge, or evaluation environment.
  • The judge applies hidden anti-cheat checks. The details of those checks are intentionally not disclosed.
  • Any cheating or attempted cheating receives a zero score for the submission.
  • If an approach might be considered cheating, do not use it; implement only fair park-management behavior through normal gameplay mechanisms.

What we found

The full case: the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. The prompt promises about 4 game years per scenario, but the 120 s time budget covers about 68 game days, so the score is a snapshot taken early in the game; the fix corrects the prompt.

What the task asks

The solver writes a plugin for OpenRCT2, a theme-park simulation game, that "maximizes normalized company value across 3 scenarios". The Rules section of the original prompt says: "The engine runs each scenario for ~4 game years at speed 4 (host --headless)", and that scoring "reads the real in-game park.companyValue". The Key APIs section describes gamesetspeed {speed: 4} as "max speed (host mode cap is 4)", but the prompt does not require the solver to use speed 4. Category: Interactive Games & Simulators.

What goes wrong

The promised length of play cannot be reached. The wrapper script sets OPENRCT2_TIMEOUT=120 per scenario and caps the whole run at 1,800 s. The task manifest's eval_timeout is 2,400 s. The grader's monitor has targetDays = 992 and emits DONE only at that date. The scoring code uses the last monitor sample and never checks whether DONE was reached.

  • With 2 CPUs and speed 4 the engine advances 0.593 to 0.597 game days per wall-clock second (0.602 when speed 8 was requested, which runs as speed 4). The rate is limited by real time, not by the host's CPU: at 0.25 CPU it was 0.582, about 2% lower. Start-up is CPU-bound, though: at 0.25 CPU the first sample arrived at 11.5 s instead of 4.6 s, so a 60 s run reached 27 game days instead of 33 (paired/check_horizon.out).
  • Each 120 s scenario covered 68 to 69 game days, about 7% of the 992-day target, and DONE was never seen.
  • Reaching 992 days would take about 1,667 s per scenario, far beyond the 120 s scenario budget. For all three scenarios together (about 83 minutes) it would also exceed the 1,800 s wrapper cap and the 2,400 s manifest timeout.

Example on the original grader (120 s, speed 4, medium scenario):

  • Expected from the prompt: about 4 game years.
  • Observed: the game ran from date 8,4,25 to 8,7,2, which is 69 game days. Company value went from 198,010 to 133,260, and the normalized company value (the task's per-scenario result) was 0.915.
  • The average over the three scenarios was 1.038, which the wrapper would print as TOTAL_SCORE 10384 (computed; the wrapper itself was not run).

The solver controls the game speed. gamesetspeed is on the list of allowed calls, and the submission's later call overrides the monitor's speed 4. Speed 1 ran at 0.077 days/s (2 game days from 2 samples over 25.8 s; it agrees with the model's 0.075) and speed 3 at 0.291 days/s. Speed 8 is rejected. A slower game can hold company value near its starting value. In these runs the cap of 1.10 hid this.

This matters because the task measures company value after about 2 months, not about 4 years. A solver that plans for the stated length of play is optimizing the wrong thing.

How much it matters

This was not measured as a score change. The problem changes what is measured: value after about 2 months instead of about 4 years. It was not shown to raise or lower any particular solver's score. All solvers that planned for the stated length of play are affected.

Scoring only runs that reach DONE is not a fix: under the shipped 120 s budget it would score every submission 0.

The fix

The fixed version replaces one Rules bullet in work.agent_query (the task prompt) with two. The new text says:

  • Each scenario runs for "120 wall-clock seconds, not to a fixed game date". At speed 4 that covers "only about 70 game days".
  • The score uses the monitor's last sample before the cutoff.
  • The plugin may call gamesetspeed with speed 1-4, the most recent call takes effect, and a lower speed simulates proportionally fewer days.

The images, eval_cmd, timeouts, parser and the reference points of the score scale (linear, 0 to 40000) are unchanged. No other file the solver sees states a length of play.

Are scores comparable?

  • Same grader, same scores. A given my_plugin.js gets the same score under the original and fixed versions, up to the usual run-to-run variation of a real-time game. Runs of the original version already had the same real 120 s length.
  • Not comparable as measures of solver ability where a solver's strategy depended on the prompt. A solver of the original version may have planned for 4 years. A solver of the fixed version can front-load its strategy or deliberately lower the speed.

How we checked it

  • Original grader, from the public image pinned by digest. The original helper's own validate_plugin, run_scenario and score_scenario functions ran in the grader image. The only addition was a tee on the engine's stdout. Runs used --network none --memory 2g --cpus 2, and one run used --cpus 0.25. Runs covered 120 s on all three scenarios and 60 s at speeds 1, 3, 4 and 8, with a simple test plugin.
  • Independent rate model. A model built from first principles, using the tick and month constants documented in openrct2.d.ts, predicts the measured rates (the "model" column above).
  • Nothing executable changed in the fixed version, so there is no side-by-side scoring run to repeat.

Limits

  • No AI model or solver was run. The effects shown are on the test plugins we wrote only, and no effect on the leaderboard is estimated.
  • The incentive to lower the speed remains. The fixed version states the speed rule accurately but does not stop a plugin from lowering the speed. Removing the incentive needs a change to the grader: re-assert speed 4 every tick, or score at a fixed game date with a long enough budget.
  • About 70 days assumes the engine keeps real time. Hosts are not pinned. A slower host, an overloaded host or a heavy plugin could fall further behind.
  • Small set of runs. Each configuration ran once, with one simple test plugin whose staff hiring failed. No competitive plugin was run.
  • Not run through the wrapper. The full three-scenario sequence ran through the helper's functions, not through eval_openrct2.py. The reference point of 40000 on the score scale was not examined.
