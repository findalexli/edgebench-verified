Order Addition Permutation Optimization

Fixed order_addition_permutation_optimization

An outdated file check fails every submission, so later improvements are ignored.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Find an ordering of the numbers 1 to 1000 that makes the output of a hidden cost function as small as possible.
What goes wrong
One grader test compares a helper file against an outdated fingerprint; only the file's comments changed, but the test fails for every submission. Each submission's own score is still correct, yet no submission can pass all tests. Under this task's rule for choosing a run's best result, the run then keeps its first valid submission and ignores better later ones.
How much it matters
Each submission's own score is unaffected. A run's reported best score is wrong whenever a later valid submission scores higher; how often this happened was not measured.
What we did
Fixed in a new version: the check uses the current file's fingerprint, so correct submissions pass all five tests and the best submission, not the first, is chosen.
Validation status
Paired runs (3, each exit=0): valid submissions pass 5/5 and the better later submission is selected, invalid controls rejected; a real archived run regraded through materialize.sh; package rebuilt from scratch on a clean machine (materialize-check-g2). Selection computed offline with select_best, not through a live judge_server.
Formal check
Model-checked in TLA+. With the original checksum a run always keeps its first valid submission (under the task's highest-pass-rate-first rule); with the fixed one it keeps the highest-scoring valid submission. Checked over 5.4 million states, and against the real selection code on 112,944 runs. Limit: Runs of up to four submissions and three score values.

What the agent is asked to do

Role Setting

You are an expert in black-box combinatorial optimization algorithms. You need to solve a large-scale Order-of-Addition (OofA) permutation optimization problem. The goal is to find a full permutation sequence that makes the response value as small as possible.

This is a scientific problem in the field of statistical experimental design. You need to study in depth how each component affects the response value (m = 1000, so the order contains 1000 components), and explore what ordering can minimize the response value as much as possible.

Black-Box Evaluation Interface

You do not need to know the specific business scenario or cost calculation formula. The only available response-value calculation interface is the Cython extension in the current directory:

from cost_complex_cy import cost_complex_with_builtin_data

m = 1000
pai = list(range(1, m + 1))
cost = cost_complex_with_builtin_data(pai, m=m, seed=1)
  • Input: an integer array of length m = 1000, which must be a permutation of 1..1000.
  • Output: a floating-point number representing the total cost/response value of that permutation; lower is better.
  • Example calling file: test_cost_complex_cython.py.

Mandatory Black-Box Constraints

You may only pass candidate permutations to the public function cost_complex_with_builtin_data(pai, m=1000, seed=1) and read the response value it returns.

It is forbidden to use, call, probe, or reflectively access any internal attributes, private functions, or private data structures of the cost_complex_cy module, including but not limited to:

cost_complex_cy._build_ctx(...)
cost_complex_cy._build*
cost_complex_cy._ctx*
cost_complex_cy._data*
cost_complex_cy._cache*
getattr(cost_complex_cy, ...)
dir(cost_complex_cy)
cost_complex_cy.__dict__

It is also forbidden to reproduce the cost function using the internal data above, bypass the black-box interaction, or export the internal data and then search with it. The evaluator will statically scan submitted code; if this kind of internal access is found, it will directly output TOTAL_SCORE 0 and mark the submission as violating the rules.

Evaluation Isolation Notice

The files cost_complex_cy.cpython-311-x86_64-linux-gnu.so and score_vcpom_result.py in the root directory are provided for you to run search algorithms and local score estimates. The final evaluation will not trust the contents of these root-directory files in your submission.

The evaluator will use private copies from a hidden test directory:

tests/cost_complex_cy.cpython-311-x86_64-linux-gnu.so
tests/score_vcpom_result.py

The work environment deletes the tests/ directory, so the agent cannot see these tests or private copies; tests/ will also not be archived when submitting. Therefore, modifying the root-directory .so file or scoring function will not improve the score. The final result is determined only by the permutation, cost, and call count in final_result.txt.

Reference Result

A reference result file is provided in the directory:

vcpom_m1000_final_result.txt

This file may only be read; it must not be modified, deleted, or overwritten. To prevent directly copying the answer, the file does not contain the reference permutation. It contains only the reference cost and reference search count:

my_cost=200690260.6677975
my_num=200000

It may only be used as a comparison for result quality and call count, and must not be used as a permutation starting point.

Final Submission Requirements

You must generate a new result file:

final_result.txt

Do not write the result back to vcpom_m1000_final_result.txt.

final_result.txt must use the following key-value format:

final_pai=3,1,4,2,...
final_cost=123456789.0
final_num=1000

Field requirements:

  1. final_pai: a permutation of length 1000. It must contain exactly 1..1000, separated by English commas, without square brackets.
  2. final_cost: the response value you report for final_pai. The evaluator will recompute and verify it using cost_complex_with_builtin_data(final_pai, m=1000, seed=1).
  3. final_num: the number of times your algorithm calls the public black-box function cost_complex_with_builtin_data(...). You may also use the field name num or my_num, but final_num is recommended. Do not count only the final verification call; every black-box evaluation during the search process must be included.

Task Goals

  1. Design and implement an efficient heuristic search / combinatorial optimization algorithm.
  2. Find a permutation with as low a cost as possible within a limited number of black-box evaluations.
  3. You may use genetic algorithms, simulated annealing, local search, tabu search, ALNS, PSO, CMA-ES, Bayesian optimization, or hybrid strategies.
  4. The final result is determined by the contents of final_result.txt.

Scoring Method

The evaluator will check that:

  1. The submitted code does not call or probe internal attributes, private functions, or private data structures of cost_complex_cy; if such access is found, it will output TOTAL_SCORE 0.
  2. vcpom_m1000_final_result.txt has not been modified and does not contain final_pai.
  3. final_result.txt exists and contains the required fields.
  4. final_pai is a valid permutation of 1..1000.
  5. final_cost matches the cost recomputed by the black-box function.
  6. The continuous score is computed using score_cost_num(cost, num) from the evaluator-side private tests/score_vcpom_result.py.

Lower cost and fewer calls give a higher score.

The scoring function uses the reference cost and reference call count from vcpom_m1000_final_result.txt:

score_cost_num(
    cost,
    num,
    cost_ref=200690260.6677975,
    num_ref=200000,
    cost_weight=3.0,
    num_weight=0.5,
)

The scoring first caps both subscores:

cost_sub = min(1.0, cost_ref / cost)
num_sub = min(1.0, num_ref / num)
score = 100 * (cost_sub ** 3.0) * (num_sub ** 0.5)

If final_cost <= cost_ref and final_num <= num_ref, the score is the full 100. If the cost is higher than the reference or the call count is higher than the reference, the score decreases. The cost penalty is heavier, so a very low call count cannot compensate for a clearly worse cost.

What we found

The full case: the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. A file-integrity test expects an outdated fingerprint of a helper file, so every submission fails one of five tests; under this task's rule for picking a run's best submission, the run then stays on its first valid submission and ignores better later ones.

What the task asks

The prompt asks for a permutation (an ordering) of 1..1000 that minimises a black-box response. It lists what "the evaluator will check": no private access; the baseline file is unmodified; final_result.txt exists; final_pai is a valid permutation; final_cost matches the recomputed cost.

A continuous score is then "calculated using score_cost_num(cost, num) from the evaluator-side private tests/score_vcpom_result.py". Nothing in the contract mentions a helper fingerprint. The solver cannot affect one, because tests/ is excluded from submissions. Category: Combinatorial Optimization.

What goes wrong

One test always fails. test_private_judge_files_are_available asserts that the installed helper's sha256 fingerprint equals 3023b9a4…. That is the fingerprint of an earlier helper with Chinese comments. A later image layer replaced the helper with an English-comment translation, 337837af…, and the expected value was not updated. The two helper versions differ only in comments, a docstring and example labels. parse_result_file and score_cost_num work identically. The check is unconditional and fails for every submission.

  • Each submission's score is correct. Only this one test fails. The other four still run, and TOTAL_SCORE is computed with the installed helper.
  • Pass rate is capped. A fully correct submission gets pass rate 0.8 instead of 1.0.
  • The run's choice of best submission freezes. This task's rule (pass_rate_first) keeps the submission that passes the most tests. It compares scores only when both pass rates are 1.0. Otherwise a later submission wins only with a strictly higher pass rate. Every valid submission is capped at 0.8, so the run's best_score / best_round stay on the first valid submission.

Example under the original grader: two valid submissions in the order identity, then search. The identity permutation scores 3.3e-09, and the search result scores higher. Expected: search is chosen. Observed: identity is chosen, and the better later submission is ignored.

How much it matters

This changes the recorded score of any run with more than one valid submission where a later one scores higher. The later improvement is ignored in the run's best score. Some consumers instead take the maximum over all submissions, which does not depend on order. So whether a published number is wrong depends on which consumer produced it. Each submission's own score is unaffected.

The fix

The fixed version changes one value in tests/test_final_result.py: EXPECTED_SCORE_HELPER_SHA256 becomes the installed helper's fingerprint, 337837af…. These are unchanged: the helper, .so, baseline file, prompt, agent's working image, parser, the rule for picking the best submission and the score scale. The task JSON changes only judge.image_tag.

How we checked it

  • Original grader. The installed helper was hashed inside the original public image, pinned by digest, and compared with the value the test expects. The original eval_cmd (python -m pytest tests/test_final_result.py -s -v) ran under --network none --memory 2g --cpus 2 on valid and invalid test submissions.
  • Choice of best submission. The saved logs were fed through the harness's own grade_output, rescale_score and select_best, from EdgeBench's harness (sforge at 6e4e5f4).
  • Formal check (TLA+). A bounded model of the selection rule, tied to selection.py and grading.py line by line, was model-checked: 5,421,361 states with no violation; three further configurations (k1–k3) are violated as the note states (evidence/formal/tla/order_addition_permutation_optimization/, evidence/formal/notes/order_addition_permutation_optimization.md).
  • Side-by-side run of the original and fixed graders. Each submission ran in a fresh --network none container through the TaskSpec eval.sh. A check beforehand confirmed that each image collects 5 tests. It was repeated three times with no verdict change (data/paired-repeatability.md).

Limits

  • No AI model or solver was run. Effects are shown only on test submissions and counterexamples we wrote.
  • The submissions are simple: the identity permutation, and short random-swap search runs (30 s and 60 s). They are far from the reference cost. The effect on the choice of best submission does not depend on score size.
  • The choice of best submission was computed with EdgeBench's select_best on saved reports, not through a live judge_server run. The agent's working image was not run.
  • How often past leaderboard runs had a better later submission was not measured.
  • The earlier helper (3023b9a4…) is not kept in this repository, so the statement that the two helpers differ only in comments rests on the earlier extraction. Scores do not depend on it, because both versions grade with the installed helper.
  • The fixed image is not published to a registry; users build it with the package's materialize.sh and Dockerfile (rebuilt from scratch on a clean machine in evidence/runs/materialize-check-g2, status: exit=0).
  • The fix also changes one harness fallback. pass_rate_first reports best_score = pass_rate when the chosen submission has no score (sforge/harness/selection.py, _pass_rate_first). A run with only invalid submissions (for example badcost) therefore reports 0.6 under the original version and 0.8 under the fixed version. In both versions that value is above every valid submission's score measured here (3.3e-09 to 0.0094 out of 100, table above), so an all-invalid run reports a higher best_score than these valid runs.
