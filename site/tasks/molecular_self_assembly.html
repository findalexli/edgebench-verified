Molecular Self Assembly

Fixed molecular_self_assembly

On the publisher's 4-CPU grader, cases within the 30-second limit time out and score 0.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Write a Python program for an atom-bonding optimization puzzle adapted from an AtCoder programming contest (AHC057), scored on 50 fixed test cases with 30 seconds each.
What goes wrong
The grader runs 8 cases at once under a 30-second wall-clock limit. On the publisher's 4-CPU setting each case gets half a CPU, so a valid solution using 16 seconds of CPU per case timed out on 48 of 50 cases and scored 0 on them. Separately, the stated 1 GB memory limit per solution is not enforced; only a shared overall limit applies.
How much it matters
Up to nearly the full score for solutions using about 15 to 30 seconds of CPU per case on a 4-CPU grader; solutions that stop at a deadline got half the computing time. No way found for extra memory to raise a score.
What we did
Fixed in a new version: the grader runs at most as many cases at once as it has CPUs, so each case keeps its 30 seconds. The 1 GB memory limit is still advice only, as noted.
Validation status
CPU-share controls validated: three identical paired native runs at 4 CPUs plus 8-CPU controls (each ledger exit=0); package rebuilt from scratch on a clean machine (materialize-check-g2). The effect on strong solutions is derived, not measured; not tested in a Kubernetes pod or with multi-threaded solvers.

Molecules - Atom Bonding Optimization (AHC057)

Write solution.py in the project root that reads from stdin and writes to stdout.

Problem Overview

Read README.md and tools/README.md for full problem details. A baseline solution.py already exists (it produces syntactically valid but low-quality output). Your job is to improve it.

Evaluation

Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Higher is better.

Local Testing

Generate local random tests with ./tools/bin/gen <seed>, using seeds in the range 0..10000 only.

# Generate a random test case (seed-based, deterministic)
./tools/bin/gen 0 > input.txt

# Run your solution
python3 solution.py < input.txt > output.txt

# Score output (Higher is better)
./tools/bin/tester input.txt output.txt
# Outputs to stderr: Score = <N>

Rules

  • Write your solution as solution.py in the project root directory
  • Do NOT modify files in tools/
  • Use tools/bin/gen and tools/bin/tester for local testing
  • For local scoring, use only ./tools/bin/tester; do not use tools/src/verifier.py for scores
  • Your program should read from stdin and write to stdout
  • Run your solution to completion and verify with the tester before finishing

What we found

The full case: the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. On the publisher's 4-CPU grader, a valid solution using more than about 15 s of CPU per case times out, although the README promises 30 s per case, and each timed-out case scores 0. The fixed version runs at most as many cases at once as the grader has CPUs. The 1 GB memory limit stated in the README is still not enforced; no way was found for extra memory to raise scores.

What the task asks

The solver writes a solution.py that reads standard input, writes standard output, and is "scored on 50 fixed test cases". The README's "Runtime Limits" table states | Time limit | 30 seconds / test case | and | Memory limit | 1 GB |. It does not say which memory measure is meant (resident memory, RSS, or address space), which unit (10^9 bytes or GiB), or what happens when the limit is exceeded. Category: Combinatorial Optimization.

What goes wrong

The 1 GB per-solution limit is not enforced (note). The helper run_case starts python3 solution.py with a 30 s timeout and sets no memory limit. By default, up to 8 cases run at the same time. The task JSON sets no memory limit. The published leaderboard configuration sets judge_mem_limit: "8g" and judge_cpu_limit: 4 for the whole grader container. That limit is shared by up to 8 solution processes running at once and their testers.

  • What the container cap does (R3). It partly penalizes a solution that is over the limit on every case: 4 of 50 cases lost in this single run. Which cases are lost is expected to depend on timing. This is not a per-solution limit.

The 30 s per case shrinks to about 15 s of CPU on a 4-CPU grader (fixed). The 30 s limit is wall-clock time, and up to 8 cases run at once (eval_molecules.py: TIME_LIMIT = 30, SEBENCH_MOLECULES_WORKERS default 8). The task sets no cpu_limit. In EdgeBench's leaderboard configuration examples/all-tasks-k8s/experiment.yaml (quoted in evidence/impact/edgebench-leaderboard-config.md) (sha256 d9d299794ba946cae8d2b7f68a7879a35bb8565d95e78107edf79802993643be, headed "OFFICIAL EDGEBENCH LEADERBOARD SETTING") the grader gets judge_cpu_limit: 4, so each of 8 running cases gets about half a CPU. A single-threaded solution that needs more than about 15 s of CPU per case then times out, and a timed-out case scores 0 while the submission stays valid (the same path as R3's RE cases).

Measured on the original grader on all 50 official cases (evidence/runs/molecular_self_assembly-cpu4v8/result/out/summary.txt, repeated in molecular_self_assembly-v2-paired). Each test solution is the shipped baseline preceded by fixed work:

A solution that searches until a wall-clock deadline gets about half the computation it would get with a whole CPU per case (CPU per case: molecular_self_assembly-v2-paired/result/out/timing/c4-wall25-v1/).

The note that ships with the fixed version: treat the README's 1 GB memory figure as advice only. Memory is limited only by the grader container: in the published setting, 8 GiB shared by 8 cases running at once. That cap penalizes solutions that are heavy on every case, in a way that cannot be predicted. No evidence was found that extra memory improves scores.

How much it matters

Memory: no way to gain score was found. The task is pure Python (the grader image has no numpy) with a 30 s limit per case. A full table of pairwise distances over time fits in about 180 MB, and the time limit is reached long before memory runs out. The hidden cases are not visible to the solution. This conclusion is reasoning; it was not measured. The problem is a missing rejection, so it never rejects valid submissions. Only solutions that use more than the stated limit are affected, and the container cap may penalize them unpredictably.

CPU count: under the original grader at 4 CPUs, a solution using more than about 15 s of CPU per case loses every such case (score 0 each, about 6.5 million of a 326 million total per case in the real run below); losing 48 of 50 cases costs nearly the whole score. Under the fixed version these cases are scored. For solutions that stop at a wall-clock deadline, the score depends on the search quality reached with half a CPU; under the fixed version such a solver gets about twice the CPU per case (mean 13.01 s → 24.91 s for the 25 s control); the effect on its score is not measured. A third-party Claude Opus 5.5 run (4 hours, published on Hugging Face as adafadaq/edgebench-opus-5-5-xhigh-rollouts) on this grader with 4 grader CPUs (run_config.json: "judge_cpu_limit": 4) had all 13 submissions valid with 50/50 cases OK. Its best submission (agent-6) totals 326,392,210, above the reference point for 100 (322,991,707.7), so it scores 100. Its grading took 178.7 s (report.json runtime_seconds), about 7 rounds of 8 cases at 25.5 s each, which is what a solution that stops at a deadline of about 25 s per case would give; its source was not inspected. Its best submission already scores 100, so for this run the fixed version would change only the CPU per case available to a deadline-based solver.

The fix

The fixed version (repairs/molecular_self_assembly-v2/) changes how many cases the grader /tmp/eval_molecules.py runs at once. A new function cpu_quota_workers() reads the grader's CPU quota from the cgroup (cpu.max, or the cgroup v1 quota and period), rounds it down to whole CPUs, falls back to os.cpu_count() when there is no quota, and keeps the result between 1 and 8. The pool size becomes min(SEBENCH_MOLECULES_WORKERS or 8, cpu_quota_workers(), len(case_files)). At --cpus 1/2/4/8 the fixed grader runs 1/2/4/8 cases at once (molecular_self_assembly-v2-paired/result/out/v2_workers.txt). The task JSON changes only judge.image_tag. The 30 s limit, the README, the tester, the cases and the score scale are unchanged. With 8 or more CPUs the fixed grader runs 8 cases at once, exactly as the original. The memory note above still ships with the fixed version.

Paired run at --cpus 4 (one pair at --cpus 8), same solutions on both graders (evidence/runs/molecular_self_assembly-v2-paired/result/out/summary.txt; repairs/molecular_self_assembly-v2/paired/results.md):

These controls build on the shipped baseline, so their own scores out of 100 are near 0 (69,280,072 → 0.0133; 2,849,909 → 0; sforge/harness/score_rescale.py). For a strong solution, losing 48 of 50 cases costs nearly its whole score. Under the fixed version the slowest 28 s case took 29.08 s from start to end (result/out/timing/c4-cpu28-v2/), less than 1 s inside the limit. Grading at 4 CPUs takes at most ⌈50/4⌉ = 13 rounds of 30 s; the bad control took 390.9 s (original: 210.8 s), inside the task's 600 s eval_timeout.

Are scores comparable? At 8 or more grader CPUs the two versions are the same grader. At 4 CPUs a deterministic solution that finished every case in time under the original gets the same output and score under the fixed version, and cases needing about 15 to 30 s of CPU are scored instead of 0. A solution that searches until a wall-clock deadline gets about twice the CPU per case, so its score under the two graders is not comparable. Per-case CPU never decreases under the fixed version.

A per-solution memory limit could be added in a separate, newly versioned variant, using either RLIMIT_AS (an address-space limit) or a check of peak RSS after the run. Its scores must not be merged with scores from the original version. A threaded pure-Python program (1 to 64 threads) ran successfully under RLIMIT_AS=1e9 with about 11 MB RSS, so an address-space limit would not wrongly reject such programs.

How we checked it

  • Original grader in the original image, pinned by digest. The original helper ran on all 50 official cases in the grader image with --network none --memory 2g --memory-swap 2g --cpus 2, giving the table above.
  • Source and configuration. The helper, task JSON and published leaderboard configuration were read to establish where memory is and is not limited.
  • CPU runs and paired run on E2B. The shipped baseline preceded by 12 to 28 s of CPU work per case, by work until a 25 s wall-clock deadline, or by 40 s of work (bad control) ran on the original grader at --cpus 4 and --cpus 8 (evidence/runs/molecular_self_assembly-cpu4v8) and side by side on the original and fixed graders (evidence/runs/molecular_self_assembly-v2-paired), each job status: exit=0. Each solution logs its own start, end and CPU time per case (result/out/timing/), which does not affect grading. The solution files contain the shipped baseline and are not stored in the repository; how they were made is in each job's sol/README.md.

Limits

  • The fixed grader reads its CPU quota from the cgroup (cpu.max). This was tested with docker run --cpus only, not inside a Kubernetes pod, which is the backend EdgeBench's leaderboard settings use.
  • Without a cgroup quota the fixed grader falls back to os.cpu_count(), which counts all of the host's CPUs, not the ones the grader may use (os.sched_getaffinity). Under a CPU-set limit with no quota (for example docker run --cpuset-cpus), or where the pod cannot see its own cpu.max, it can still run more cases at once than it has CPUs, as the original does. Using the affinity count would need a new paired run, so it is not changed here.
  • No AI model or solver was run by us. Effects are shown on test submissions and counterexamples we wrote, and the third-party run above was also regraded at 4 CPUs: 8 of its 13 submissions each score 3–4% higher in raw terms under the fixed version, and the run's score stays 100 because it was already above the top of the scale (evidence/runs/opus55-regrade2-summary/summary.json). No effect on the leaderboard is estimated.
  • The CPU dependence was measured at 4 and 8 CPUs with single-threaded test solutions; multi-threaded solvers were not tested, and 3, 5, 6 and 7 CPUs were not tested.
  • At 4 CPUs the fixed version leaves less than 1 s of margin for a solution that uses 28 s of CPU per case (slowest case 29.08 s), so the usable budget is a little under 30 s of CPU once interpreter start-up is counted.
  • Deadline-based solvers get about twice the CPU per case under the fixed version at 4 CPUs, so their scores under the two graders are not comparable. How much their scores change is not measured.
  • With fewer than 3 grader CPUs the 600 s eval_timeout binds before the 30 s per case: at 2 CPUs, 25 rounds × 30 s = 750 s, so only about 24 s per case is usable (the original gives about 7.5 s of CPU per case there). The quota is rounded down: 2.5 CPUs run 2 cases at once.
  • The memory runs used a 2 GiB container with 1 to 2 cases at once, not the official setup of 8 GiB, 8 cases at once and 4 CPUs. R3 imitates the official setup by scaling the ratio, and how many cases it loses to memory depends on timing.
  • Each memory configuration ran once. There are no repeatability statistics for R3. The CPU rows of the original grader were run four times (molecular_self_assembly-cpu4v8 once, -v2-paired with -rep2 and -rep3) with the same counts and totals.
  • Past deployment overrides are unknown, so a different memory policy in the past cannot be excluded.
  • The conclusion that extra memory gives no advantage is reasoning, not a measured experiment. No strong solver was built.
