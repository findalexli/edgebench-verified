D-ABIC Gravity Inversion

Removed Grader correctness and factual errors dabic_gravity_inversion

42 points come from the submission's own unchecked self-reported results.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Implement a method that infers underground density from gravity measurements (a D-ABIC gravity inversion), choosing between two equivalent mathematical forms as the task allows.
What goes wrong
Two parts worth 42 points are taken from results the submission reports about itself; the grader does not recompute them. Also, the grader quietly penalises the 'model-space' form, though the task text allows either form and both give the same result. For the same work at a strong level, this is calculated to give about 89 points in one form and about 43 in the other.
How much it matters
42 points cannot be verified, for any submission. Choosing the allowed but penalised model-space formula can cost a strong solution 46.06 points at C = 26 and 48.06 at C = 30, computed from the grader's own rule (the gap grows with C) (3.2 points of the total before the grader's penalty factor, at every level).
What we did
Removed: 42 points still come from unverified self-reported results. A partial fix removes the hidden form penalty, but that alone does not make the task usable.
Problem category
Grader correctness and factual errors; also Instruction–grader mismatch

What the agent is asked to do

This is EdgeBench's original task text, the work.agent_query field of tasks/dabic_gravity_inversion.json, from the EdgeBench dataset on Hugging Face by ByteDance Seed, licensed under CC BY 4.0. It is shown unchanged, rendered from Markdown to HTML; links to files inside the task's workspace are shown as plain text. EdgeBench's harness adds its standard instructions on how to submit (sforge/harness/evolve_scripts.py), which are not shown.

Task objective: Port the D-ABIC method proposed by Song Han et al. in the 2025 Geophysics paper doi 10.1190/geo-2025-0233 to 3D gravity inversion, and validate it on the measured Vinton salt dome dataset. Read starter/README.md for detailed instructions.

The inversion must be completed separately under both L0 and L1 sparse regularization norms. For each norm, run a three-way comparison among D-ABIC, Cooling, and L-curve. Xu et al.'s 2025 Geophysical Prospecting paper doi 10.1111/1365-2478.70016 performed gravity inversion on the same Vinton dataset using an HMC method; use it as the comparison benchmark.

Four stages:

  1. Algorithm implementation: read docs/geo20250233.pdf and implement a D-ABIC beta-adaptive directive. The suggested name is class DABIC_Beta_Estimator(directives.InversionDirective), placed in a separate module outputs/dabic_directive.py. Decide for yourself whether to use the model-space or data-space form, how to compute determinants, and in which space to optimize beta. The directive must work under both the L0 and L1 norms.
  2. Synthetic validation: starter/starter.py provides the synthetic density model Model 3, survey points, noisy observed data, and forward simulation object, but does not include an inversion framework. Build the SimPEG inversion workflow yourself, and implement both Cooling and L-curve scan baselines. Run the three-way comparison for both L0 and L1.
  3. Field-data application: data/saltdome_s7_100.grd is the measured Vinton salt dome gravity-anomaly data, in Surfer 7 binary format. It can be parsed by starter/explore_xu_data.py. Refer to docs/Xu2025_HMC.pdf for the inversion mesh, depth range, density bounds, and related settings.
  4. Result comparison: compare quantitatively and qualitatively with the Xu 2025 HMC results, and write outputs/report.md, 800 to 1500 words/characters in length.

Deliver to outputs/: dabic_directive.py, run_synthetic.py, run_vinton.py, results.json, report.md.

All dependencies are preinstalled; you do not need to and cannot install additional packages. The container has no network access and cannot access external resources.

Constraints: beta must not be hard-coded as a constant; do not import any third-party ABIC package; do not use SimPEG's built-in high-level automatic beta directives; BetaEstimate_ByEig may only be used to set the initial beta_0 value; both L0 and L1 inversions must be fully completed; do not expand the work to other regularization strategies such as GCV or HMC; do not modify starter/explore_xu_data.py or starter/starter.py.

What we found

The full case: the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Removed. 42 points come from results the submission reports about itself, which the grader cannot verify; a partial fix removes a second, undisclosed penalty on one of two allowed forms, but does not make the task usable.

What the task asks

The solver implements a D-ABIC gravity inversion: a method that infers underground density from gravity measurements and picks its regularization strength (beta) with Akaike's Bayesian Information Criterion (ABIC). The method can be written in two equivalent forms. The model-space form works with matrices sized by the number of hidden model cells. The data-space form works with matrices sized by the number of data points.

The task text says: "Decide for yourself whether to use the model-space or data-space form, how to compute determinants, and in which space to optimize beta." The starting README (line 48) repeats that the choice is "to be determined by the implementer." README line 5 expands D-ABIC as "Data-space variant of Akaike's Bayesian Information Criterion". Even so, the task text leaves the choice open twice, and no text the solver can see says that the model-space form loses score. Category: Scientific Problems & ML.

What goes wrong

42 points are self-reported. This is the reason for removal. Components B and D (42 points together) are taken from results the submission reports about itself. The grader does not recompute them from hidden data. For a solver that reports truthfully, these components therefore reflect what the submission reports, not what the grader verifies. Component F, the written report, is scored by keywords.

An undisclosed requirement to use the data-space form. The grader decides which form a submission uses from the shape of the square matrices passed to the log-determinant routines it monitors. A model-space submission is marked is_data_space=false and structural_failure=true. That costs it 3.2 points of the total before the penalty factor is applied, at every level of quality: these are the E1 behaviour points. It also blocks the uncapped penalty factor of 1.0, so a model-space submission is capped at a factor of 0.5×. By Sylvester's determinant identity, both forms compute the same ABIC curve.

  • Example on the original grader: the data and model forms give the same results on the hidden cases up to run noise (C 17.39 against 17.44), but score 26.82 and 25.77 (repairs/dabic_gravity_inversion-v2/paired/evidence/logs/{data,model}-v1.structured.json). At this moderate level both received the penalty factor 0.334, so the observed gap is small.
  • At a strong level (C ≥ 26, D ≥ 20, F ≥ 10), applying the grader's own penalty function gives about 89 in the data form against about 43 in the model form for the same work (88.92 against 42.86 at C = 26).

How much it matters

  • Self-reported components: 42 points cannot be verified, for every solver.
  • Form penalty: computed from the grader's own rule, 46.06 points at C = 26 and 48.06 at C = 30 at the strong level (the gap grows with C), and 3.2 points of the pre-penalty total at every level, for solvers who choose the model-space form.

The fix

The fixed version is partial. It removes the form penalty only. It does not address the reason for removal; what a full fix would need is stated at the end of this section.

The fix changes one file, the grader eval_dabic_v2.py, in both places where it sits in the grader image. It adds is_model_space, which mirrors the existing data-space check: most captured square matrices have the hidden cell count as their dimension. It then uses uses_abic_form = is_data_space or is_model_space for the E1 points and for the structural_failure term. Every threshold, the 0.334/0.5/1.0 penalty levels, the other behaviour rules, valid_for_selection and all other components are unchanged. The task JSON changes only judge.image_tag. The work image and the files the solver sees are unchanged. Mirroring the check, rather than removing it, keeps the requirement that the log-determinant is taken on an ABIC matrix.

What a full fix would need. The grader would have to recompute the B and D components (42 points) from hidden data, instead of reading them from the results the submission reports. Until then the task is removed.

Score compatibility. By reading the code, scores from the fixed grader equal scores from the original grader, up to run noise, for every submission classified as data-space. This was measured once: the correct data-space submission went from 26.82 to 26.84. The same holds for submissions whose matrices match neither the hidden data count nor the hidden cell count. Scores are not comparable for model-space submissions, which gain the 3.2 E1 points and, at the strong level, the uncapped penalty factor 1.0. The score scale is unchanged.

How we checked it

  • Original grader in the original public image, pinned by digest, using the exact evaluation command with --network none --cpus 8 --memory 6g. One D-ABIC submission was scored in two forms that differ only in the line FORM = "data" / FORM = "model". Fixed input files held the self-reported components (B, D) and the keyword-scored report (F) constant in every test submission, so only the form varied. Their values are not task performance.
  • Source reading of the behaviour monitor (BehaviorMonitor.report) and the penalty function (structural_penalty_v34).
  • Effect at the strong level. The grader's own penalty function was applied to each test submission's real breakdown, with only the hidden-case score C substituted.
  • Side-by-side run of the original and fixed graders on the same inputs, plus an invalid submission (log-determinant via np.linalg.det) and the empty shipped workspace. It was repeated three times, and no test submission changed outcome (see data/paired-repeatability.md).
  • Units check. An independent prism gravity code (Nagy's formula) passed a check against an infinite flat slab (the Bouguer slab). Its output was not saved.

Limits

  • No AI model or solver runs were made. Effects are shown only on test submissions and counterexamples that we wrote.
  • One moderate good-faith implementation was used (C ≈ 17.4/35), with fixed input files for B, D and F. The effect at the strong level is computed with the grader's own penalty function, not observed with a strong submission.
  • The form classification still depends on matrix shapes. A correct implementation that computes the log-determinant without passing an N×N or M×M square matrix to a monitored routine (for example a low-rank or iterative estimator) is still marked structural_failure in both versions.
  • The partial fix does not address the reason for removal: B and D (42 points) still come from results the submission reports about itself, and F is scored by keywords. The fix's README says it "does not make the task retainable on its own".
  • The invalid submission is rejected only through the valid flag. Its numeric score is not low.
  • The hidden cases use the same simulator to generate and to invert the data, which is acceptable for synthetic tests. SimPEG was not compared, and the Xu benchmark constants were not verified.
