Vibrating Path Graph Coloring

Fixed Engineering and runtime environment vibrating_path_graph_coloring

On the publisher's 4-CPU grader, a solution within the 30-second limit can leave the whole submission without a score.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Solve 50 graph-colouring puzzles (colouring points of a network so linked points differ), outputting a sequence of point "hits" and a colour per point, for the lowest total score.
What goes wrong
The grader runs 8 cases at once under a 30-second wall-clock limit. On the publisher's 4-CPU setting each case gets half a CPU, so a valid solution using 20 seconds of CPU per case timed out on 48 of 50 cases, and one timeout leaves the whole submission without a score. Separately, the tester accepts a no-hit answer only in two lines, not the documented three; zero-hit answers are proved invalid on 37 cases, but the format effect remains unresolved on the other 13.
How much it matters
Up to the full score for solutions using about 14 to 30 seconds of CPU per case on a 4-CPU grader; solutions that stop at a deadline got half the computing time. The format mismatch has zero effect on 37 certified cases; its effect on the other 13 is unresolved.
What we did
CPU parallelism is limited to available CPUs and grading gets 900 seconds. The zero-hit format mismatch remains: its effect is ruled out on 37 certified cases but unresolved on 13. One failed case still voids the submission.
Problem category
Engineering and runtime environment; also Instruction–grader mismatch
Validation status
CPU controls validated; zero-hit formatting effect ruled out on 37 of 50 cases only, unresolved on the other 13.
Formal check
Partly proved in Lean 4. A zero-hit answer is wrong on 37 of the 50 official puzzles, each by a certificate the tester cannot satisfy. Limit: The other 13 large puzzles would need a SAT-scale refutation; the CPU-count fix is not formalized (checked by runs).

Vibrating Path - Graph K-Coloring (CodeChef VBR)

Write solution.py in the project root that reads from stdin and writes to stdout.

Problem Overview

Read README.md and tools/README.md for full problem details. A baseline solution.py already exists (it produces syntactically valid but low-quality output). Your job is to improve it.

Evaluation

Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Lower is better.

Local Testing

Generate local random tests with ./tools/bin/gen <seed>, using seeds in the range 0..10000 only.

# Run your solution
python3 solution.py < input.txt > output.txt

# Score output (Lower is better)
./tools/bin/tester input.txt output.txt
# Outputs to stderr: Score = <N>

What we found

The full case: the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. On the publisher's 4-CPU grader, a valid solution using more than about 14 s of CPU per case times out, although the README promises 30 s per case, and one timeout leaves the whole submission without a score. The fixed version runs at most as many cases at once as the grader has CPUs and allows 900 s instead of 600 s for the whole run. The tester's rejection of the README's three-line zero-hit form remains as a note; its score effect is ruled out on 37 certified cases and remains unresolved on 13 cases.

What the task asks

The agent solves graph-colouring puzzles: it colours the points (vertices) of a network so that linked points differ, and may "hit" vertices along the way. The prompt says: "Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Lower is better." It defers to "README.md and tools/README.md for full problem details". The README's output format has three lines:

  • "Line 1: number of hits $Q$"
  • "Line 2: the vertices hit in order (1-indexed)"
  • "Line 3: coloring of each vertex ($1 \leq x_i \leq K$)"

The README gives no exception for the case with no hits. tools/README.md contains no output-format text and no exception. Category: Combinatorial Optimization.

What we checked

Rule. For zero hits, the README form is three lines with an empty hit line. The tester accepts zero hits only in a two-line form. The shipped baseline solution.py prints the two-line form, and tools/src/verifier.py reads it the same way.

What the evidence establishes. On 37 of the 50 official cases, the input graph provably cannot be coloured with K colours without hits. A zero-hit answer on those cases is wrong in either format. The remaining 13 fixed graphs have no certificate here; a probability bound under an assumed generator does not establish their actual colourability. A solver can use hits on the certified cases and zero hits elsewhere, so the 37 certificates do not establish zero effect on a complete submission.

  • 37/50 cases have exact certificates (short proofs that the graph cannot be coloured with K colours):
    • 13 cases with K=1: any edge;
    • 12 cases with K=2: an odd cycle;
    • 6 cases with N=1000, K=3: an explicit K4 clique (four mutually linked vertices; the K4 in case 0043 was also checked separately);
    • 6 cases with N=1000, K=4: an explicit K5 clique.
  • The other 13 cases have N=10000, K∈{3,4} and average degree 20, and admit no small certificate. A union bound (adding up the probabilities of every possible valid colouring) gives ln P ≤ −14895 for K=4 and ≤ −29550 for K=3. This assumes the cases came from the published uniform generator.

A single failed case voids the whole submission. The evaluator gives every wrong answer, timeout or runtime error a case score of float('inf') and adds it to the total (/tmp/eval_vibrating_path.py, lines 20, 35, 37, 39 and 54). One failed case therefore makes TOTAL_SCORE inf. EdgeBench's harness accepts it as raw infinity, for which rescale_score gives no score out of 100 (sforge/harness/score_rescale.py:75-76). So that submission gets no score; under score_first, an earlier submission with no failed case is still kept. The prompt says only "Final score = sum of individual case scores" and does not say what a failed case scores.

The 30 s per case shrinks to about 14 s of CPU on a 4-CPU grader (fixed). The README promises "Time limit | 30 seconds / test case" (line 54). The limit is wall-clock time (TIME_LIMIT = 30, line 9), and 8 cases run at once (ProcessPoolExecutor(max_workers=min(8, len(case_files))), line 45). The task sets no CPU count. In EdgeBench's leaderboard configuration examples/all-tasks-k8s/experiment.yaml (quoted in evidence/impact/edgebench-leaderboard-config.md) (sha256 d9d299794ba946cae8d2b7f68a7879a35bb8565d95e78107edf79802993643be), the grader inherits judge_cpu_limit: 4. Eight cases on 4 CPUs get about half a CPU each, and they share it with the task's Python tester, which takes 5.6–19.0 s of CPU per case (579.6 s for all 50 cases, measured one case at a time at 1 CPU on the honest control's outputs: repairs/vibrating_path_graph_coloring-v2/paired/tester_time.out).

Measured on the original grader at --cpus 4 (evidence/runs/vibrating_path_graph_coloring-cpu4v8-a/result/out/summary.txt, -b; repeated in vibrating_path_graph_coloring-v2-paired-a):

In one more original-grader run at 4 CPUs (evidence/runs/vibrating_path_graph_coloring-v2-paired-b), the 25 s deadline solution lost 14 cases (36 OK, 14 TLE, TOTAL inf). Every solution process in that run ended at most 27.14 s after its start, and all 14 timed-out cases are among the 25 cases with the slowest tester. The evaluator reports a timeout of the tester (its own timeout=60) with the same TLE label as a timeout of the solution. The likely cause is therefore the tester reaching its 60 s timeout with about half a CPU. This cause is inferred, not observed: that run did not log tester starts, and a repeat on another worker that did (vibrating_path_graph_coloring-v2-paired-c) passed 50/50 twice. Across all nine original-grader gradings of this solution (three runs each of -b and -c, the latter grading it twice per run), it failed only this once; under the fixed version it passed all six of its gradings (repeatability).

Note shipped with the task. For zero hits, the tester accepts a two-line output and rejects the README's three-line form with an empty hit line. Zero-hit answers are proved invalid for 37 official cases; the other 13 remain unresolved. Accepting both forms would remove the format mismatch, but such a parser repair is not part of this package and identical official scores have not been demonstrated.

How much it matters

  • CPU count. On the original grader at the publisher's 4 CPUs, any valid solution using about 14–30 s of CPU per case loses its whole score (measured with 20 and 28 s per case); under the fixed version these solutions are scored. A solution that stops at a wall-clock deadline gets about twice the CPU per case under the fixed version (mean 12.84 s → 24.98 s for the 25 s deadline solution, vibrating_path_graph_coloring-v2-paired-b); how much that changes its score is not measured. A solver sees the per-case TLE results after each submission, and the run keeps its best valid submission, so a run loses its score only if it never submits a faster valid solution.
  • One failed case. The all-or-nothing rule is unchanged and still undisclosed.
  • Zero-hit format. Score effect is zero on the 37 certified cases. On the other 13 it is unresolved: a valid zero-hit answer rejected for formatting would make the whole submission nonfinite. No such official-case witness or universal zero-effect proof is available.

The fix

The fixed version (repairs/vibrating_path_graph_coloring-v2/) changes how many cases /tmp/eval_vibrating_path.py runs at once. A new function cpu_quota_workers(), the same as in repairs/grid_turing_robot-v2/, reads the grader's CPU quota from the cgroup (cpu.max, or the cgroup v1 quota and period), rounds it down to whole CPUs, falls back to os.cpu_count() when there is no quota, and keeps the result between 1 and 8. The pool becomes ProcessPoolExecutor(max_workers=min(cpu_quota_workers(), len(case_files))). docker run --cpus N and the publisher's k8s backend both set this quota. With 8 or more CPUs the fixed grader runs 8 cases at once, exactly as the original.

The task JSON changes judge.image_tag and raises judge.eval_timeout from 600 to 900 s. With whole CPUs per case the grading takes longer, and this task's tester is slow: for valid solutions near the 30 s limit the worst case at 4 CPUs is (50 × 30 s + 579.6 s) / 4 + 3/4 × 49 s ≈ 557 s, only 7% under 600 s. The longest grading measured under the fixed version was 558.0 s (the 25 s deadline solution, vibrating_path_graph_coloring-v2-paired-b), so 600 s is too close. The 30 s limit, the README, the tester, the cases, the parser and the score scale are unchanged, and so is the rule that one failed case voids the submission.

Are scores comparable? At 8 or more grader CPUs the two versions grade the same way. At 4 CPUs a deterministic solution that finished every case in time under the original gets the same output and score under the fixed version, and a solution needing about 14 to 30 s of CPU per case is scored instead of getting no score. A solution that searches until a wall-clock deadline gets about twice the CPU per case, so its scores under the two graders at 4 CPUs are not comparable. Per-case CPU never decreases under the fixed version.

These notes still ship with the fixed version:

  1. For zero hits, the tester accepts only the two-line form, not the README's three-line form. A zero-hit answer is proved wrong on 37 official cases; score effects on the other 13 are unresolved.
  2. One crashed, timed-out or malformed case makes the total inf, so the whole submission gets no score.

How we checked it

  • CPU runs and paired runs on E2B. Valid solutions doing 12 to 28 s of CPU work per case, a 25 s wall-clock-deadline solution and a 40 s bad control ran on the original grader at --cpus 4 and --cpus 8 (evidence/runs/vibrating_path_graph_coloring-cpu4v8-a, -b) and side by side on the original and fixed graders (vibrating_path_graph_coloring-v2-paired-a, -b, -c), each job status: exit=0, in the digest-pinned grader image with --network none --memory 4g. Each solution runs our honest control (greedy K-colouring, hits simulated by the shipped tester's rule), then does its extra work, then prints the control's answer, and logs its own start, end and CPU time per case (result/out/timing/). The tester time per case was measured separately at --cpus 1 (paired/tester_time.out).
  • Original grader. The original tester and helper ran in the original public image, pinned by digest, with --network none. The inputs were graphs we wrote with two-line and three-line zero-hit outputs, a known-bad colouring, a known-good output with hits, and six official cases. tools/bin/tester is identical in the grader image and the agent's working image. tools/README.md was read from the working image.
  • Exact certificates. For each official case, a proof that the graph cannot be coloured with K colours: an edge for K=1, an odd cycle for K=2, and explicit K4 or K5 cliques checked pair by pair.
  • Probabilistic bound. For the remaining large, sparse cases, a closed-form union bound under the published generator's model.

Limits

  • The fixed grader reads its CPU quota from the cgroup (cpu.max). This was tested with docker run --cpus only, not inside a Kubernetes pod, which is the backend EdgeBench's leaderboard settings use.
  • Without a cgroup quota the fixed grader falls back to os.cpu_count(), which counts all of the host's CPUs, not the ones the grader may use (os.sched_getaffinity). Under a CPU-set limit with no quota (for example docker run --cpuset-cpus), or where the pod cannot see its own cpu.max, it can still run more cases at once than it has CPUs, as the original does. Using the affinity count would need a new paired run, so it is not changed here.
  • No AI model or solver was run. Effects are shown only on test submissions and counterexamples we wrote.
  • 13/50 cases rely on a probabilistic bound and assume the cases came from the published uniform generator. The exact seeds were not found, and no SAT refutation (a machine proof by a satisfiability solver) was run.
  • The vibrating-path graph rules themselves were not reviewed.
  • Past submissions were not examined.
  • The CPU dependence was measured at 4 and 8 CPUs, on E2B workers with 8 vCPUs, with single-threaded fixed-work and deadline test solutions. Multi-threaded solvers were not tested. 3, 5, 6 and 7 CPUs were not tested.
  • Deadline-based solvers get about twice the CPU per case under the fixed version at 4 CPUs, so their scores under the two graders are not comparable. How much their scores change is not measured.
  • The cause of the 14 timeouts of the 25 s deadline solution in one original-grader run is inferred (the tester's own 60 s timeout at half a CPU), not observed.
  • The tester times, and so the 557 s bound behind the 900 s eval_timeout, are for the honest control's outputs; other outputs may take longer to check. Below 3 grader CPUs the 900 s eval_timeout can bind before the 30 s per case (about 1,065 s of work at 2 CPUs). The quota is rounded down: 2.5 CPUs run 2 cases at once.
