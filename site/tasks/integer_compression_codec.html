Integer Compression Codec

Fixed Scoring scale and selection integer_compression_codec

Scores compare against stored numbers the documented starter cannot produce.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Write a library that compresses lists of integers more tightly and decodes them faster than a supplied simple starter (Varint, which stores each number in whole bytes), on eight datasets.
What goes wrong
The documentation says the starter scores 1.0, but the grader compares against stored numbers the starter cannot produce: five are below 8 bits per integer, impossible for this byte-based format, and speeds were timed elsewhere. On raw results the starter scores about 0.24, and a simple correct codec about 0.8 instead of 6 to 8. Dataset weights differ from the documentation.
How much it matters
All submissions. Raw: starter about 0.23, not 1.0; a simple correct codec about 0.8, not 6 to 8; dataset weights off 7 to 9 times. Fixed scale: starter 0, codec about 1.8.
What we did
Fixed in a new version: the grader measures the starter in the same run, as documented, and the 0–100 scale runs from the starter (0) to the formula's maximum (100). Scores are not comparable with the original version.
Problem category
Scoring scale and selection
Validation status
Three side-by-side native runs (all finished): starter 0.23 -> about 1.0 raw as documented, correct codec 0.83-0.97 -> 6.70-8.27, corrupting codec 0 in both; the scale's end points are exact; package rebuilt from scratch on a clean machine (materialize-check-g3). Timing noise about ±15% per dataset; other machine types and the Kubernetes grader not tested.
Formal check
Partly proved in Lean 4. No submission can score above 320 raw; the fixed scale maps the starter's documented score to 0 and that maximum to 100. The regraded real submission's 160.76 and 50.08 are exact. The fix's main change, measuring the starter in the same run, is not modelled. Limit: Scale arithmetic only; timing noise is outside the model.

What we found

The full case, with the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. The grader compares submissions against stored baseline numbers that the documented Varint starter cannot produce, so the starter scores about 0.23 instead of the documented 1.0 and the datasets are in effect weighted differently from what is published.

What the task asks

The solver must "Implement a stronger libintcompress.so … to improve both compression ratio and decode throughput on the provided datasets". There are eight datasets. The score on each dataset is defined relative to "the baseline (official Varint) compressed bits-per-integer and decoding throughput": S_i = min(B_i^0 / B_i, 8.0) × min(T_i / T_i^0, 40.0). Varint is a simple format that stores each integer in whole bytes. scoring_scheme.md states, "The baseline implementation is the publicly provided Varint starter. Its composite score is defined as 1.0." The task is in the Systems & Software Engineering category.

What goes wrong

The grader never measures the baseline. runner_judge.py reads B_i^0 and T_i^0 from a stored file, baseline_results.json, labelled "varint-v1 (reference)". Those values cannot come from the starter that ships with the task. In the table, bpi means bits per integer.

A byte-oriented varint needs at least one byte per value, so it always uses at least 8 bits per integer. Five of the stored "Varint" values are below 8, which no byte varint can reach. The stored run log also contradicts itself, since for docids the decode time and the throughput disagree by about 1000×. The stored throughputs come from another machine.

The original grader gave these results:

Every score is off the documented scale. The distortion differs by dataset, so the grader in effect weights the datasets differently from the documentation.

Other parts work correctly. The data regenerate exactly, and the roundtrip check (decoding must return the original integers) rejects a codec that corrupts data. Two small deviations do not matter for solvers that follow the rules: the image ships g++ 11.4 instead of the documented 12.2, and the grader enforces "encode + decode ≤ 300 s" as two separate 300 s limits.

How much it matters

  • The problem affects all solvers. On raw results, the starter gets about 0.24 instead of 1.0, and the correct codec about 0.8 instead of about 6–8 (timing-dependent; see the table below).
  • The compression term alone is distorted by a factor of 0.12 to 0.81 per dataset, up to 6.7× relative to one another. The speed term adds its own per-dataset distortion. Together, the unchanged starter's per-dataset scores on the original grader, which should all be 1.0, range from 0.078 (ts_sec) to 0.647 (rand) in the published paired run, 8.3× apart; the two repeats give 8.9× and 7.5× (paired/evidence/summary.txt and the -rep2, -rep3 runs). On the machine we measured, the effective weights of the datasets therefore differ from the documented weights by about 7–9× relative to one another, and solutions that trade compression between datasets can rank differently than the documentation implies.
  • Within a single dataset, the score still rises with better compression and speed.
  • The speed term divides a local measurement by a constant from another machine, so scores also depend on the machine that grades them.

The fix

The fixed version implements the documented definition, in which the grader measures the starter in the same run and uses it as the baseline. After the submission builds and passes the symbol check, runner_judge.py builds the starter from pristine copies with the shipped Makefile, so the compiler and flags are the same. On each dataset, the starter and the submission run back to back through the same runner_encode and runner_decode. The starter's measured bpi and decode throughput become B_i^0 and T_i^0.

  • It adds three pristine starter files under internal/baseline/starter/, byte-identical to the starter the solver sees.
  • It no longer reads the stored baseline_results.json.
  • If the starter itself fails to build or to pass the roundtrip check, the run reports an error instead of a score.
  • The score scale changes from linear 0..100 to linear 1.0..320, so the starter (documented score 1.0) maps to 0 and the largest result the formula allows (8 × 40 = 320) maps to 100. Without this change, real submissions saturate the scale (see the real agent submissions below). A correct codec that is worse than the starter (raw below 1.0) scores 0 on the fixed scale, the same as a failing submission. The unchanged starter itself scores 0.00 to 0.02 (raw 0.97 to 1.06 over six runs).
  • The formula, the caps (8×, 40×), the weights, the datasets, the roundtrip check, the work image and all text the solver sees stay as they were. In the task JSON, judge.image_tag and the score scale change.

Under the fixed version the starter's compression ratio is exactly 1.0 on every dataset, and its speed ratios per dataset range from 0.93 to 1.07 in this run and from 0.84 to 1.14 over all six fixed-version starter runs. The remaining distance from 1.0 is timing noise. The correct codec's compression terms are exact; ts_sec, for example, is 40.00 / 8.00 bpi = 5.0×. The original-grader values in this table differ slightly from those in "What goes wrong" because the speed term varies between runs. The fixed version adds about 20 s per grading (44 s instead of 24 s of wall time).

Scores from the fixed version are not comparable with scores from the original for any submission. Each per-dataset score changes by the ratio of the measured starter to the stored constants. In the published paired run that ratio ranged from about 1.5× (rand, 1/0.647) to about 13× (ts_sec, 1/0.078), so rankings between solutions that trade off across datasets can change. Failing submissions still score 0. The fixed grader's scores out of 100 in the table use the fixed score scale (1.0..320), computed from the recorded raw results.

We also regraded real agent submissions. A public Claude Opus 5.5 run (16 tasks, 4 hours each, published on Hugging Face as adafadaq/edgebench-opus-5-5-xhigh-rollouts) recorded 75.72 for this task. That is the original grader's raw result for its best submission (agent-20), and on the original linear 0..100 scale it is also the score out of 100. We regraded the run twice, each time with both graders on the same machine, so there are two sets of numbers:

  • The first regrade covered two submissions, graded once (evidence/runs/opus55-regrade/). agent-20 scores raw 66.31 on the original grader and 160.76 on the fixed one, and an earlier submission (agent-3) scores 31.11 and 114.19. On the original 0..100 scale both fixed results would clip to 100, which is why the scale changes; on the fixed scale they score 50.08 and 35.48.
  • The second regrade covered all 37 submissions, the top 6 three times on separate machines (evidence/runs/opus55-regrade2-summary/summary.json). Picking the run's best submission by the run's own rule (highest score) under each grader, the original grader's best is raw 71.93 (auto-3) and the fixed grader's best is raw 173.10 (agent-26), which is 53.95 on the fixed scale. agent-20 itself scores 59.21 to 72.17 raw on the original grader and 124.27 to 171.26 raw (38.64 to 53.37) on the fixed one over its three repeats.

Comparing like with like on our machines (second regrade), the run's kept score moves from 71.93 on the original grader to 53.95 on the fixed one. The run itself recorded 75.72 on its own machine. The first regrade's 66.31 → 50.08 is one submission (agent-20) graded once on one machine. The two regrades differ because of timing noise between machines (see Limits; the first regrade's 160.76 for agent-20 lies inside its second-regrade range) and because the second regrade grades every submission, so its best can be a different one.

How we checked it

  • We ran the original grader's eval_cmd (python3 runner_judge.py) in the public grader image, pinned by digest, on an 8 vCPU Xeon @ 2.6 GHz, 7 GB host, with --network none --cpus 4 --memory 6g, on the three submissions above.
  • We rescored the run logs offline under the documented definition, with the starter measured on the same machine (rescore_documented.py).
  • gen_data.py --full inside the image regenerated all 8 shipped data files byte for byte.
  • The floor of 8 bits per integer for any byte varint follows from one byte per value, so we needed no formal tool for it.
  • We alternated the original and fixed graders on the same submission, one container at a time, which gave the table above, and repeated the comparison three times. The verdict never changed (starter about 1.0 and the corrupting codec 0 under the fixed version, 8/8 and 0/8 datasets passed), but timing-based scores moved by up to 25% between runs (data/paired-repeatability.md). The paired runs used the original 0..100 scale; we computed the fixed-scale values in the table from the recorded raw results.

Limits

  • We ran no AI model. The effects shown come from three test submissions we wrote (the starter, a simple correct codec and a corrupting codec) and from a third-party Claude Opus 5.5 run, with all 37 submissions regraded with both graders, the top 6 three times on separate machines (the first regrade covered two submissions, once each).
  • The dependence on the machine and the timing noise remain. The speed term is now a ratio of wall-clock times on the same machine. Over six runs of the fixed version in three separate jobs (two per job), the starter scored 0.97 to 1.06 and the correct codec 6.70 to 8.27 (about ±10% around 7.42); the original grader gave the starter 0.23 to 0.30. The starter's own throughput moved by up to about 18% between runs (grid 0.789 vs 0.646 GB/s), although running the two back to back cancels most of that.
  • Real submissions show timing noise too. In the second regrade of the third-party run (37 submissions with both graders; the top 6 three times on separate E2B workers), the same submission's raw score varied by up to ±20% between machines (for example 55.4 to 73.0 under the original grader), because decoding is timed over only a few milliseconds per dataset (about 3 to 35 ms for these submissions). This holds for both graders and comes from the grader's timing method, which the fix does not change. The fix's direction is stable, and every submission scores 1.7 to 4 times higher under the fixed grader (evidence/runs/opus55-regrade2-codec-a/, -codec-b/, -reps2/, -reps3/; combined in evidence/runs/opus55-regrade2-summary/summary.json).
  • The fixed grader measures the baseline once per dataset (best of 5 decodes). We did not use medians over several baseline runs.
  • We used only one machine type. The correct test submission is a simple codec, not a strong solution. No expert reference solution ships with the task.
  • The image still has g++ 11.4, not the documented 12.2. This affects both versions equally.
