Borden Source Inversion

Fixed Instruction–grader mismatch borden_source_inversion

Hidden grading model uses unstated, non-physical conventions, so one-shot textbook solutions score near baseline.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
From readings at groundwater monitoring wells, work out the location, size, timing and strength of a hidden underground pollution source.
What goes wrong
The grader predicts well readings with a hidden model; the documentation gives its ingredients but not how they combine. The model treats a rate as a total amount, ignores porosity and source duration, mislabels units, and puts the source on one face of its region, not at the centre. A textbook model fits the public data equally well yet scores lower.
How much it matters
For a one-shot fit that follows the documentation, about 24 of the original 109 points (22 of 100): 7.0 with a textbook model, 31.2 with the hidden conventions. Agents that submit repeatedly lose less, by an unmeasured amount. One real run climbed from 7.01 to 60.10 while the grader reported its error on the hidden wells.
What we did
Fixed in a new version: solvers receive the grader's own prediction code and an exact description of its conventions, and the score scale runs from 0 up to the true source's score of 109.
Problem category
Instruction–grader mismatch; also Scoring scale and selection
Validation status
Two side-by-side native runs and their repeats (all finished) give identical raw results under the original and fixed versions; the shipped forward model equals the grader's; 109 is the exact computable maximum; package rebuilt from scratch on a clean machine (materialize-check-g3). No agent run on v2; the effect rests on one textbook variant.
Formal check
Proved in Lean 4. The fixed scale and every converted leaderboard value follow exactly from the published (one-decimal) scores. Limit: Only the change of scale; the physics convention is not formalizable.

Borden 3D Groundwater Contaminant Source Inversion

Task

You are given a Borden-style 3D groundwater contaminant migration scene derived from a Borden-AdePy reproduction workflow. Your task is to infer a finite-duration rectangular-region contaminant source from public monitoring-well readings.

This is not a point-source task. A point-source answer or the old x0,y0,z0,C0 schema is accepted only as a degenerate fallback and cannot receive full credit.

Required source parameterization

Create answer.json in the task root using this schema:

{
  "source_type": "rectangular_region",
  "dimension": 3,
  "x_center": 0.0,
  "y_center": 0.0,
  "z_center": 0.0,
  "half_length_x": 0.0,
  "half_length_y": 0.0,
  "half_length_z": 0.0,
  "C0": 0.0,
  "t_start": 0.0,
  "duration": 0.0,
  "transport_model": {
    "equation_type": "advection_dispersion_reaction",
    "governing_equation": "R*dC/dt = div(D grad C) - v dot grad C - lambda*C + source",
    "velocity_m_per_day": 0.0,
    "alpha_L_m": 0.0,
    "alpha_TH_m": 0.0,
    "alpha_TV_m": 0.0,
    "porosity": 0.0,
    "retardation_factor": 1.0,
    "lambda_per_day": 0.0,
    "numerical_approach": "brief description of forward model and optimization"
  },
  "method": "brief description of your inversion method"
}
  • x_center,y_center,z_center: center of the rectangular source region, in meters.
  • half_length_x,half_length_y,half_length_z: half sizes of the rectangular source region, in meters.
  • C0: effective source concentration/intensity, in mg/L.
  • t_start: release start time in days.
  • duration: release duration in days.
  • transport_model: your groundwater solute transport construction. Include the ADE/reaction governing equation, public hydrogeologic parameters used, and the numerical or analytical approximation used to predict concentrations.

All parameters must stay within public_problem_config.json → source_search_bounds_for_agent.

Provided files

  • public_problem_config.json: Borden grid, hydrogeological parameters, source prior bounds, and column definitions.
  • public_source_prior.json: explicit range summary for the finite-duration rectangular-region source parameters.
  • borden_grid.npz: grid arrays exported from the Borden-AdePy scene, including x/y grid and bottom profile.
  • public_wells.csv: public monitoring-well coordinates.
  • public_monitoring_data.csv: noisy, censored public monitoring observations. Clean generated concentrations are not provided to the agent.
  • baseline_solver.py: writes a legal low-quality baseline answer.json from the center of the parameter bounds.
  • answer_template.json: required output schema.

No runnable scientific starter solver is provided. You should write your own Python code to read files, construct the groundwater solute transport equation, build an ADE/AdePy or equivalent forward approximation, optimize the source parameters, and update answer.json.

Mandatory baseline workflow

Before implementing a complex inversion algorithm, first ensure that a valid answer.json exists:

python baseline_solver.py

Then iteratively improve answer.json using public monitoring data. Missing answer.json gives zero.

Scoring policy

The judge does not grade old point-source location error directly. It evaluates whether your finite-duration rectangular-region source predicts withheld monitoring readings:

  1. Read answer.json.
  2. Check required finite-region fields and parameter bounds.
  3. Use a hidden Borden-ADE region-source forward model to predict concentrations at hidden monitoring wells and hidden future times.
  4. Compare predictions with hidden readings using relative RMSE and log-scale metrics.
  5. Hidden prediction dominates the score. Easy format/prior/method/transport-equation points are capped and cannot exceed the hidden-quality caps.
  6. Region-shape and physical-consistency points are gated by hidden prediction quality.
  7. Very poor hidden/future prediction is capped at 15 points; poor-but-improving prediction is capped at 30 points; moderate prediction is capped at 45 points.

If hidden monitoring prediction is poor, the final score is capped. This makes early baseline or shallow point-source fits low-scoring, while still allowing genuine improvement through better region-source inversion.

Rules

  • Do not read or reference hidden scoring files.
  • Do not hard-code hidden monitoring readings.
  • Do not modify judge files.
  • Do not call FloPy, MODFLOW, MT3DMS, or external groundwater executables.
  • You may use Python libraries such as NumPy, SciPy, pandas, matplotlib, pymoo, and AdePy if available.
  • Submit all scripts/results needed to reproduce your answer.json.

Critical submission rule

The judge only reads answer.json in the task root.

It does not automatically run inverse_solver.py, run_checks.py, write_fit_report.py, write_public_predictions.py, or any other script during scoring.

Therefore, after every meaningful inversion or optimization step, you must immediately overwrite the task-root answer.json with the best current source parameters.

If answer.json is unchanged, the score and all METRICS will remain unchanged, even if you create new Python scripts, reports, or prediction files.

Recommended workflow:

  1. Run python baseline_solver.py only as an initial fallback.
  2. Implement and run your inversion script.
  3. After each improved parameter set is found, write it to answer.json.
  4. Run python validate_answer.py if available.
  5. Submit only after confirming that answer.json has changed.

What we found

The full case, with the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. The grader predicts well readings with a hidden model whose conventions are unstated and not physical, so a one-shot fit with a textbook model scores at the baseline level.

What the task asks

The agent receives readings from groundwater monitoring wells and must work out a hidden pollution source. The prompt says the solver must "infer a finite-duration rectangular-region contaminant source from public monitoring-well readings". It defines C0 as "effective source concentration/intensity, in mg/L". It gives the governing equation R*dC/dt = div(D grad C) - v dot grad C - lambda*C + source, the advection–dispersion equation (ADE), the textbook model of a dissolved substance that flows and spreads in groundwater.

The README says to "construct the groundwater solute transport equation, build an ADE/AdePy or equivalent forward approximation". It also says the grader will "Use a hidden Borden-ADE region-source forward model". A forward model predicts well readings from a proposed source. The task is in the Scientific Problems & ML category.

What goes wrong

The grader's forward model uses conventions that are unstated and not physical. The hidden model:

  • gives each of 225 pulses an amplitude C0·q·1000/225, which uses a mass rate (mg/d) as if it were a mass;
  • does not use porosity (the share of soil volume that holds water);
  • gives the same total mass whatever duration is;
  • reports mg/m³ as mg/L;
  • with nz=1, places the source plane at z_center − half_length_z, not at the box centre (this looks like an unintended linspace(num=1) artifact).

The documentation gives the ingredients but not how the model combines them. public_problem_config.json lists q (q_source_m3_per_day), a factor of 1000 (fallback_source_scale_factor), a 5×5×1 grid of sub-points with 9 release steps, and a note that the grader superposes point-source responses. It does not give the per-pulse normalisation, the missing porosity, the duration-independent mass, the unit reading or the resulting plane position. At the true source, on the 24 public readings above 0.01 mg/L, a textbook ADE model differs from the grader's model by 10.9× to 323× (median 33×). The difference comes from an amplitude factor of duration/(1000·n) ≈ 8.5 at the true source, plus the plane offset. Yet the public data cannot tell the conventions apart, because the textbook model and the grader's convention fit them equally well (RMS log residual 0.0079 for both).

  • On the original grader, the textbook ADE fit scores 7.03. The baseline, which answers with the midpoint of every parameter's bounds, scores 7.01. The same least-squares fit with the grader's exact convention scores 31.2. A fit that uses the grader's convention except for the source plane (placed at z_center, the natural reading) scores 12.9, so the plane placement alone costs about 18 points.

A smaller reporting inconsistency is that the raw result has no defined score out of 100. The true source scores 109 on the raw result (before conversion to 0–100). The task had no score scale, so score_0_100 was undefined and raw results were reported on 0–109. No recorded submission reaches 100 raw. Our best public-data fit reaches 31.2, and the best submission in a third-party Claude Opus 5.5 run reached 60.10 (below). The missing ceiling therefore clips no recorded score, but it leaves results on a 0–109 scale.

We also confirmed that the agent's working files hold no scoring/ directory and no hidden file.

How much it matters

A one-shot least-squares fit to the public data with one textbook model variant loses about 24 points on the 0–109 raw scale (7.0 against 31.2). We did not test other textbook variants.

For an agent that submits repeatedly the effect is smaller, and we did not measure its size. The grader's per-test output includes the hidden-well and future rRMSE as CASE feedback_… lines, so an agent can tune towards the hidden convention. In a third-party Claude Opus 5.5 run on the original grader (36 submissions over 4 hours), the best submission, agent-23, describes its model as a textbook point-source ADE solution and scores 60.10 raw, with hidden-well rRMSE 0.223 and future rRMSE 0.101 (evidence/runs/opus55-rollouts-meta/result/meta/opus-16x4h-1009-0036-w1/borden_source_inversion/final_result.json and submissions/agent-23/test_output.txt). Our grader-convention fit has 0.552 and 0.200. The published 12-hour results for this task are 48.4, 38.5 and 38.2 for three models and 8.0 and 15.1 for two others (evidence/impact/leaderboard_12h.json).

The fix

The fixed version changes only the agent's working image and the task JSON. The answer key, the grader and the grader image stay as they were.

  • The working image adds forward_model.py, the grader's forward model with byte-identical function bodies and only the 2-line header comment replaced.
  • A README section states the convention exactly, covering the sub-points and the z_center − half_length_z plane, release offsets, pulse amplitude, the absence of porosity and of any dependence on duration, and units as reported. The fixed version inserts the same section into work.agent_query. A revision (2026-10-12) also says, in the file list, scoring steps and rules, that forward_model.py is an exact copy of the grader's model and may be used freely; the first published fixed prompt still called the model "hidden" and forbade reading hidden scoring files without that statement. Grading the same seven test submissions in the first and revised fixed working directories gave byte-identical results (evidence/runs/borden_source_inversion-v2-paired-r3).
  • task.json.in adds judge.rescale = {"kind": "linear", "lower": 0, "upper": 109}, which sets the score scale so that 0 maps to 0 and 109 maps to 100. It keeps results above 100 in order instead of tying them at a cap.

The shipped forward_model.py matches the grader's model with max |diff| = 0.0 over all 656 answer-key rows. The fixed-version solver ran in the fixed working image with no network, using only files the agent can see, and converged to the same point as the grader-convention fit.

Original raw results are on 0–109. Agent runs on the fixed version are not comparable with agent runs on the original version, because the fixed version tells solvers the convention (the same least-squares fit: 7.0 → about 31 raw).

How we checked it

  • We ran all test submissions on the original public image, pinned by digest and unchanged in the fixed version. Each ran the original grading command with --network none, against the original and fixed working directories.
  • A separate implementation of the forward model (5×5×1 sub-points, 9 pulses, Gaussian kernel) reproduces all 656 clean answer-key readings from the hidden true source (rerun with evidence/scripts/borden_source_inversion/forward_check.py). The grader's own model, run in the grader image, matches the stored readings to 8.9e-13 relative.
  • Our good-faith solver experiments used multi-start bounded least squares (60–80 starts) on the public noisy, censored data only. One run used a textbook ADE model built from the documentation, and the other used the grader's exact convention. The original evaluate.py scored each fitted answer.json with the original arguments (local Python; numpy 1.24.4, scipy 1.10.1, pandas 2.0.3).
  • We repeated the side-by-side run of the original and fixed graders three times, and no test submission changed verdict (see data/paired-repeatability.md).

Limits

  • We ran no AI model. The paired results use test submissions and fits we wrote. We read one third-party Claude Opus 5.5 run on the original grader but did not regrade it (raw results are identical under both graders for the same answer); its best raw score climbed from 7.01 to 60.10 over 36 submissions while the grader reported its error on the hidden wells after each one. We did not verify how the agent used that feedback, and the run does not test the fix.
  • The data still determine the inverse problem only weakly. The best public-data fit with the exact model reaches 31.2 raw (28.6 out of 100). The fix removes the penalty for the hidden convention, not the difficulty.
  • C0 remains an "effective intensity" in a non-physical convention. The fixed version documents it instead of fixing it, because fixing the physics would require regenerating the answer key.
  • We used one fitting method (multi-start least squares, log/hinge loss, one seeded run of 60 or 80 starts) and one textbook model variant. The 24-point gap is for that variant.
  • The prompt says parameters "must stay within" the bounds, but the original grader does not reject the out-of-bounds test submission outright (4 raw, capped at 15). The fixed version keeps this.
  • For the hidden-file check we listed only the /home/workspace working files.
  • The grader imports its own copy of the model from the scoring directory (hidden_forward_model.py), not the forward_model.py in the work directory, so a submission that edits the shipped forward_model.py cannot change its own score. This follows from the grader code; we graded no such submission.
  • We rebuilt the package from scratch on a clean machine (evidence/runs/materialize-check-g3, status: exit=0). materialize.sh ran unchanged, all 5 outputs matched the lock, and the built image holds the locked files. The fixed work image tag f389fcf94240-ebv-v2.1 is a local build tag; no image is published to a registry.
