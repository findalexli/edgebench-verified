Wesnoth Tactical AI

Kept, with a note wesnoth_tactical_ai

The supplied starter program is broken, and repeat games give different results.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Write a computer player in Lua, a scripting language, for the strategy game Battle for Wesnoth that wins matches against the game's built-in opponent.
What goes wrong
No scoring problem. The supplied starter uses a setting this game version does not recognize, so it never recruits and scores 0; the game's own player scored 41. Games do not repeat even with a fixed seed. All 60 games must finish within 900 seconds (about 15 each), a limit the task does not state. A forbidden name in any file, even in a comment, scores 0.
How much it matters
The broken starter scores 0 for anyone submitting or building on it unchanged. Non-repeatable games move a score by about ±4–5 of 100 points per grading (binomial estimate, not measured).
What we did
Kept, with a note: the starter's recruiting setting is broken on this game version, games are not repeatable, and 60 games must fit in 900 seconds.

Wesnoth Tactical AI

Write a Lua AI for The Battle for Wesnoth 1.18 that wins turn-based multiplayer matches against the default AI.

Goal

Maximize total_score = 80 x win_rate + 20 x avg_efficiency, evaluated over 3 maps x N seeds (default 10) x N repeats (default 2) as side 1 (your AI) vs side 2 (default Wesnoth AI).

  • win_rate = wins / total_games
  • avg_efficiency = mean(min(1, baseline_turns / actual_turns)) over wins only

Baseline turn counts (default vs default): Weldyn_Channel=16, The_Freelands=15, Fallenstar_Lake=20.

Note: The baseline AI (default C++ CAs) typically scores 0-20. Focus on incremental improvements.

API Restrictions (CRITICAL — violation = score=0 and hack flag)

Forbidden APIs (not for AI decisions):

  • wesnoth.wml_actions.* — scene design API (WML actions like kill, message, etc.), NOT for AI decisions
  • wesnoth.game_events.* — can fire arbitrary WML events, NOT for AI decisions
  • os.execute — system command execution
  • io.open — file system access
  • debug.* — can bypass sandbox restrictions

Allowed APIs (AI decision APIs):

  • wesnoth.units.* — unit queries (find_on_map, etc.)
  • wesnoth.current.* — current game state
  • wesnoth.sides.* — side information (gold, recruit list, villages, etc.)
  • wesnoth.map.* — map queries
  • wesnoth.interface.* — chat messages, UI
  • wesnoth.ai.* — AI aspects and actions

Using forbidden APIs or attempting to bypass restrictions (e.g., string concatenation, metatable manipulation, variable indirection) will result in score=0 and the submission marked as hack.

Files you must write in /home/wesnoth_agent/

  1. my_custom_ai.cfg — AI definition (WML). Must include id=my_custom_ai, a [stage], and [candidate_action] blocks.
  2. Any number of *.lua files referenced by location=... in the cfg.

A baseline my_custom_ai.cfg already exists (uses default C++ CAs). Improve it.

Wesnoth CA configuration (key rules from docs)

  • Config file must have id= field, else wesnoth skips it with "skipped AI config due to missing id".
  • CAs must be inside [stage] with name=ai_default_rca::candidate_action_evaluation_loop.
  • For a Lua CA, use engine=lua + location="~add-ons/my_ai/my_recruit.lua". The Lua file must return a table whose :evaluation() and :execution() methods drive the CA.
  • Do NOT mix location with inline evaluation=/execution=.
  • --ai-config does not accept absolute paths; only wesnoth-relative or ~add-ons/....
  • Do NOT use [kill], [event], or [command] WML tags in your .cfg file — these are scene design tools, not AI decision mechanisms.
Example Lua CA (place in my_recruit.lua)
local my_recruit = {}
function my_recruit:evaluation()
  local side = wesnoth.current.side
  local leader = wesnoth.units.find_on_map({ side = side, canrecruit = true })[1]
  if not leader or wesnoth.sides[side].gold < 14 then return 0 end
  return 300000
end
function my_recruit:execution()
  local side = wesnoth.current.side
  local recruit_types = wesnoth.sides[side].recruit
  if recruit_types and #recruit_types > 0 then
    wesnoth.interface.add_chat_message('my_ai', 'Recruiting ' .. recruit_types[1])
  end
end
return my_recruit

Local Testing

Run a quick game locally to verify your AI loads:

wesnoth --nogui --multiplayer --nosound \
  --controller 1:ai --controller 2:ai \
  --ai-config 1:~add-ons/my_ai/my_custom_ai.cfg \
  --scenario multiplayer_Weldyn_Channel \
  --log-debug=ai/testing

Rules

  • Write your AI as my_custom_ai.cfg and optional *.lua files in /home/wesnoth_agent/
  • Do NOT modify files outside /home/wesnoth_agent/
  • Do NOT delete .config/ or .cache/ directories — the evaluation system handles add-ons installation automatically
  • Your AI plays as side 1
  • Run your AI locally to verify it loads before finishing
  • Submit for evaluation

Strategy Hints

  • The default AI is decent at combat but poor at strategic recruit selection and village capture timing.
  • Lua CAs give you full control over move ordering, targeting, and recruitment.
  • Focus on: (1) efficient recruitment, (2) village capture, (3) focus-fire kills, (4) leader safety.
  • Read my_custom_ai.cfg for the baseline structure.

What we found

The full case, with the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Kept, with a note. The full grading run fits its time budget on one 8-vCPU host (80 to 172 s against 900 s), but the supplied starter's recruiting setting is broken on the pinned game version, so it scores 0, and games are not repeatable.

What the task asks

The Battle for Wesnoth is a turn-based strategy game. The solver writes "a Lua AI for The Battle for Wesnoth 1.18 that wins turn-based multiplayer matches against the default AI". Lua is the scripting language the game uses for computer players. The score is "total_score = 80 x win_rate + 20 x avg_efficiency, evaluated over 3 maps x N seeds (default 10) x N repeats (default 2)". The prompt also says "The baseline AI (default C++ CAs) typically scores 0-20." The default grading run is 60 games under an eval_timeout of 900 s. Category: Interactive Games & Simulators.

What we checked

We found no problem in how games are scored. We note four points: the time limit, the broken starter, games that do not repeat, and a text scan that can reject a harmless file.

1. The time budget fits, but there is a limit the task does not state. A full-length game with the default AI takes about 3 s.

  • With the supplied starter, the full default grading run finished in 80 s, exit 0, TOTAL_SCORE 0, CASES_OK 0/60, TIMEOUT_COUNT 0.
  • A correct test submission using the game's stock AI finished in 172 s, exit 0, 60/60 games, TIMEOUT_COUNT 0, TOTAL_SCORE 41 (18/60 wins). Wall time per game had a mean of 2.86 s, a median of 2.79 s and a maximum of 5.65 s.
  • A submitted AI could spend about 5x the stock AI's time per game, or about 15 s per game on average, before reaching 900 s. The per-game limit is 180 s, but 60 x 15 s = 900 s, so a heavy Lua AI could exceed the total budget. The task does not state this limit.
  • Past 900 s, the submission loses everything, including the games already played. The grader prints its CASE lines and TOTAL_SCORE only after all 60 games finish, and when the harness timeout kills the grader it prints no TOTAL_SCORE, so the submission has no score (EdgeBench's grading does not use the timeout flag itself, sforge/harness/grading.py:224-241).

2. The supplied starter is broken on Wesnoth 1.18.5. All three captured game logs of the starter (one per map) contain:

error ai/engine/cpp: side 1 : UNKNOWN candidate_action[ai_default_rca::aspect_recruitment_phase]

The game's stock 1.18 macro uses name=default_recruitment::recruitment instead. The starter's side 1 therefore never recruits units, and its leader is overrun. We ran one original run_game per map.

MapWall timerun_game return valueMarkers in game output
Weldyn_Channel2.08 s(False, 8, False)WINNER: 2, GAME_END_TURN: 8
The_Freelands1.40 s(False, 6, False)WINNER: 2, GAME_END_TURN: 6

The prompt's "typically scores 0-20" is technically met, since the score is 0. The fault is in the starter, not the scoring, because the grader scores a working AI correctly (41).

3. Repeat games are not repeatable. A fixed --rng-seed does not fix the outcome of games between two AIs. Repeat pairs (same map and seed, repeat 0 vs 1) were identical in only 1 of 30 pairs for the stock-AI test submission and 6 of 30 for the supplied starter. The second repeat therefore adds new samples instead of duplicating them.

We also saw two stock-AI games on The_Freelands reach the 50-turn cap and print no WINNER, and the grader scored them as losses.

We can estimate, but did not measure, how large this variation is per grading. If the 60 games are independent with win probability p, the standard deviation of the win component (80 x win rate) is 80 x √(p(1 − p)/60). That is about 4.7 points out of 100 at p = 0.3 (the stock-AI control won 18/60) and about 3.7 points at p = 0.85, before any variation in efficiency.

4. The grader's text scan can reject a harmless file. Before any game, scan_for_hacks() searches the raw text of every submitted .lua file for wml_actions, game_events, os\.execute, io\.open and debug\., and every .cfg file for [kill], [event], [command] and wml_actions. Comments and parts of longer names also match. Any match scores the whole submission 0. The prompt lists these APIs as forbidden ("violation = score=0 and hack flag") but does not say that comments and substrings count.

  • A comment -- never use wesnoth.wml_actions here, a table named mydebug used as mydebug.log, or a variable n_game_events_seen each matches a pattern (checked by applying the grader's patterns with Python's re.search). Such a submission scores 0. We graded no such submission.

The task ships with this note.

  • The supplied starter's recruiting candidate action is invalid on Wesnoth 1.18.5, so the starter scores 0. The suggested starter fix, name=default_recruitment::recruitment as in the stock macro, is not tested.
  • Games are not reproducible despite --rng-seed.
  • The 60-game total must fit in 900 s, about 15 s per game on average, even though the per-game limit is 180 s.

How much it matters

  • The broken recruiting setting affects only solvers who submit the starter unchanged or build on it; it scores 0.
  • The total time limit affects only AIs that average more than about 15 s per game.
  • Games that do not repeat add variance to every solver's score, about ±4 to ±5 points out of 100 per grading by the binomial estimate above (not measured). Recorded agent runs on this task score 36.3 to 88.0 out of 100 (tasks/README.md), so this variation is at a scoring level. The task's selection rule (score_first) keeps the best submission, so variation between gradings can raise a run's recorded best.
  • The text scan affects only solvers whose files mention a forbidden name, in code or in a comment; it scores them 0.

There is no code change; the note above ships with the task.

How we checked it

  • We ran the original grader image (Wesnoth 1.18.5), pinned by digest, with --network none on one 8-vCPU host with no CPU limit. For the supplied starter, the unmodified grader's scan_for_hacks(), install_agent_ai() and original run_game(map, 0, 0) ran once per map. We wrapped only subprocess.run, to record the game output and elapsed time. Then the exact eval_cmd (python3 /tmp/eval_wesnoth.py) ran with defaults under timeout 900.
  • In the correct test submission, side 1 was Wesnoth's own stock data/ai/ais/ai_default_rca.cfg, with only id= renamed to my_custom_ai. It passes the grader's hack scan. The full default grading run ran under timeout 900, through the unmodified grader with a timing wrapper on subprocess.run.
  • No formal model applies.

Limits

  • We ran no AI model or solver. The effects shown come only from the supplied starter and the stock-AI test submission.
  • We used one 8-vCPU host with no CPU limit. A grading host several times slower could still fit in 900 s.
  • The stock-AI test submission is Wesnoth's own AI, not a solver's submission. Each configuration ran one full grading run, so the variance of TOTAL_SCORE is a binomial estimate, not a measurement.
  • The text-scan false positives come from reading the grader source and applying its patterns to sample strings; we graded no such submission.
  • We did not exercise a possible problem installing Lua files in a subdirectory.
