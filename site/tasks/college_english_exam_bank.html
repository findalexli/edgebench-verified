College English Exam Bank

Fixed Grader correctness and factual errors college_english_exam_bank

Rubric rules the AI grader leaves out are counted as full marks.

SummaryThe instructionsHow it is gradedWhat we foundFiles

Summary

The task
Produce 22 files for a college English exam bank: five exam papers, answer keys, scoring guides and two spreadsheets. An AI model grades them against 12 rubric rules.
What goes wrong
If the AI model's answer leaves a rule out, the grader's code keeps that rule at full marks and still reports a valid result; an empty assessment scores 100. Each rule starts at full marks and loses points for faults found, and a rule marked 0 with no faults listed also gets full marks. We do not know how often models omit rules.
How much it matters
Raises a score by up to the value of the left-out rules; an empty assessment scores 100. Any submission can be affected when the AI model's assessment is incomplete.
What we did
Fixed in a new version: the grader requests an incomplete or self-contradicting assessment again, and otherwise reports a grading failure instead of full marks. It scores only the last complete assessment block. If it fails the checks, the grader asks again rather than scoring an earlier draft. It uses an earlier block only when every later one is truncated or unreadable. Complete assessments score exactly as before.
Problem category
Grader correctness and factual errors
Validation status
v2.2 validated by three identical paired runs of the original, v2.1 and v2.2 graders on 29 responses (college_english_exam_bank-v2-paired-fix3, -fix3-rep2, -fix3-rep3; each ledger exit=0; package materialized with its own materialize.sh in each). The model's answers were fixed stubs; no AI model was called. The Lean model covers v2.1, not v2.2's block selection or decimal-string reading.
Formal check
Proved in Lean 4. The fixed grader never scores an assessment that leaves out a rule, gives exactly the original total for every assessment it accepts, and never gives full marks to a rule whose row records a deduction. The proof found three gaps in the first version of this fix and a probe of the real code found a fourth; the fix was then revised. The model is of v2.1 (`87f0e340…`), not the current v2.2 (`a0af4360…`). Limit: Models v2.1 only; v2.2's JSON block selection and reading of decimal-string rule scores are not modelled. Text fields reduced to yes/no; deductive rules only (all 12 here); the proof starts from an already-parsed assessment.

What we found

The full case, with the test submissions, the independent checks and the fix. File paths refer to the repository; links open on GitHub.

Outcome: Fixed. The original grader gave full marks for any rubric rule that the AI grading model did not assess, and still reported the result as valid.

What the task asks

The solver is told to "Read the complete task instructions in /home/workspace/task_instruction.md". Those instructions ask for 22 deliverables: five exam papers (A to E) as Word and PDF files, answer keys and scoring guides, a blueprint workbook and a workbook of repetition rates across papers. An AI grading agent (a large language model) scores the work against rubrics.json. That file has 12 rules (R001 to R012) worth 100 points in total. Every rule is deductive, meaning it starts at full marks and loses points for each fault the grading model finds. The grader's prompt tells the grading model to use the rules array strictly as the scoring list and not to add, delete or merge rules. The docstring of the grader's reconciliation step says "Force result coverage/order/max_score to match rubrics.json". The task is in the Professional Knowledge Work category.

What goes wrong

Rules left out get full marks. When a rule's row is missing from the grading model's JSON answer, the reconciliation step finds no recorded deductions, and because every rule is deductive, the rule keeps its full maximum. The grader writes the reason "Missing deductive detail scores; unreported deduction triggers treated as not triggered." and reports grader_status: ok, valid: true.

A row that contradicts itself also gets full marks. Case I is a row whose own score is 0 but whose checkpoints all report no deduction. The original reconciliation step trusts the checkpoints and awards the rule full marks (15.0 instead of 0).

The problem appears when the grading model returns JSON that parses but lacks some rule rows, for example a truncated or abandoned assessment of a heavy 22-file submission. The grader's prompt itself anticipates the model running short of time or context. It is plausible that a solver could cause an omission, but we have not demonstrated it. The fault is in fixed post-processing code that the task owns, which fails open when the model's output is incomplete.

How much it matters

A score can rise by up to the value of the rules left out, and an empty assessment scores 100. For this task the error only pushes scores up, because its rubric has no additive rules (rules that start at zero, which would push scores down instead). Any submission can be affected whenever the grading model returns an incomplete assessment.

The fix

The fixed version changes only /home/workspace/scoring/grade_with_codex.py:

  • It rejects score lists that are incomplete, duplicated, unknown or non-numeric. A row may leave out the rule-level score when it has a complete numeric list of checkpoints, which the original version scored correctly. On such a row it reads a rule score written as a plain decimal string, such as "11", as that number, and it still rejects booleans and other strings.
  • It rejects an assessment in which a deductive row reports a deduction (its own score is below the maximum, or a checkpoint is positive) but would still be scored at full marks, as in case I. To decide this it runs the original reconciliation step on the normalised rows, so it looks at exactly the data that produces the score.
  • An incomplete assessment becomes a grading failure (valid: false, score 0), the channel the original grader already uses for grading-side failures. EdgeBench's harness ranks it as a 0 for that submission (score_first does not read valid), and the run keeps its best other submission. We did not choose to score only the missing rule at zero, because that would silently understate an otherwise complete answer.
  • The last JSON block with scores in the model's output decides, as in the original. If it parses but fails these checks, the fixed version treats the output as incomplete. It does not score an earlier block, which may be a draft from before the model's own check. It falls back to an earlier block only when the last one is truncated or does not parse.
  • Because the harness does not retry, the fixed version asks the grading model again before giving up. It makes at most 1 + SEBENCH_CODEX_ASSESSMENT_RETRIES calls (the variable defaults to 1, so 2 calls), all within the original time budget.

The rubric, reference attachments and work image stay as they were. In task.json.in only judge.image_tag changes.

"–" marks a grading failure, for which the grader reports valid: false with score 0. The harness uses score_first selection, which keeps the submission with the highest score. score_first does not read valid and ranks a grading failure as 0, which can never beat a graded submission. Under this selection the original version picks the inflated round (C at 100, D at 81, I at 15) over the accurate one, and the fixed version picks the accurate one (77, 77, 0).

The original and fixed versions give the same score for complete, internally consistent assessments (rows A, B, F, L), from byte-identical structured results and one model call. Scores differ in four situations. The first is when the grading model leaves out, duplicates or invents a rule. The second is when it returns a row with neither a score nor a complete list of checkpoints, or a deductive row that reports a deduction but would be scored at full marks. The third is when the output ends with a scores block that fails these checks after an earlier block (N, NZ). The fourth is when a rule score is a boolean, a string that is not a plain decimal number, or a decimal string on a row without a complete checkpoint list. In the first three situations the original version filled in full marks or scored the failing last block. It scored rows of the fourth kind correctly from their checkpoints or rule score (QC: 77), so there the fixed version can turn a correct score into a grading failure when asking again does not help. In all four the fixed version asks again and otherwise reports a grading failure.

We revised the fix on 2026-10-12. The first published fixed version decided the deduction check on the raw row, before normalisation, and four rows still got full marks. The Lean model found the first three of them and a probe of the real code found the fourth. They are a veto stated only in veto_reason while rule_veto_triggered is false, a deduction in an extra checkpoint beyond the rubric's details, a veto flag on a rule without veto conditions, and floor wording after character 200 of reason. The fixed version now reads the normalised rows. A side-by-side run of the original grader, the first fixed version and the revised one gave the same results as the table above for every earlier response. The four rows score 3 or 15 points for the changed rule under the original grader and the first fixed version, and are grading failures under the revised one. The first fixed version rejected one row that the original scores consistently (a veto, score 0); the revised version scores it 0, as the original does.

We revised the fix a second time on 2026-10-13 (v2.2), after an independent review found two behaviours of the revised version that did not follow the contract. When the last JSON block of an output failed the checks, the revised version scored an earlier block that passed, without asking again. That block can be a draft from before the model's own check, and a full-marks draft followed by an incomplete final block scored 100. The revised version also treated a rule score written as a numeric string as a grading failure even when the row's checkpoints were complete and consistent, although the original scored that row correctly. Version v2.2 lets the last block decide and reads a plain decimal-string rule score on a row with complete checkpoints as that number. A side-by-side run of the original grader, the revised version (v2.1) and v2.2 on 29 fixed responses gave the same result under v2.1 and v2.2 for every earlier response except N. These rows changed:

How we checked it

  • We ran the original grader from the public image pinned by digest. The original main() ran end to end with --network none --memory 2g --cpus 1. We replaced only the codex executable, with a stub that prints a fixed model response, and used no model API or credential. We generated the fixed responses from the original rubrics.json. They include correct responses, responses for known-bad work and the responses that show the problem (rules left out, an empty score list, malformed rows). The fixed-version runs used the same eval_cmd in the fixed image.
  • We read EdgeBench's handling of valid: false (sforge/harness/grading.py, selection.py, at 6e4e5f4) and used it offline to grade and select on the saved results.
  • We repeated the side-by-side run of the original and fixed graders three times, and no response changed its result (see data/paired-repeatability.md). These repeats used the first fixed version. We also ran the side-by-side run with the revised fixed version three times (evidence/runs/college_english_exam_bank-v2-paired-fix2, -fix2-rep2, -fix2-rep3); its graded results (graded.json) are identical in all three apart from timing fields. We ran the side-by-side run with the second revision (v2.2) three times as well (evidence/runs/college_english_exam_bank-v2-paired-fix3, -fix3-rep2, -fix3-rep3); in each, the package's own materialize.sh regenerated the v2.2 grader from the pinned image before it was built, and graded.json and graded.md are byte-identical across the three runs.
  • A Lean 4 model of the normalisation, the reconciliation step and both fixed versions (evidence/formal/notes/college_english_exam_bank.md) proves three properties of the revised fixed version for every parsed assessment. An accepted assessment gets exactly the original score, an assessment that leaves out a rule is a grading failure, and a deductive rule whose row reports a deduction never gets full marks. The same model shows that the first fixed version awarded full marks in the four rows above. The model reduces text fields to yes/no facts, but the last result does not rely on that reduction, because the check uses the same functions as the score. The model starts from the parsed rows, so it does not cover which JSON block is parsed or the reading of decimal-string rule scores (both tested on the real code; see the second revision above).

Limits

  • We ran no AI solver. The effects shown come only from the fixed responses and counterexamples we wrote.
  • We used no live grading model. We did not measure how often real models leave out rows, or whether any past EdgeBench score was inflated. The problem is not evidence that past scores were inflated.
  • We graded no real 22-file submission. The fixed responses do not read the submission.
  • We did not run the harness judge_server live.
  • When a model output holds several JSON blocks, the original grader and the fixed version both let the last scores block decide. If that block fails the fixed version's checks, the fixed version asks again even when an earlier block would pass (N, NZ). If the earlier block was accurate and the second answer is again incomplete, that submission loses its score. The grader cannot tell a draft from a final answer, so it does not score the earlier block. We did not measure whether codex exec output in this image ever holds more than one block. As in the original, a fenced block takes priority over unfenced JSON.
  • A rule score that is a boolean or a non-numeric string, or a decimal string on a row without checkpoints, is a grading failure in the fixed version, although the original scores such rows correctly (QC, QD, QF). We did not measure how often a real model writes them.
  • In production, asking again may cost extra paid grading calls. We do not know whether a second attempt is usually complete. A model that keeps returning incomplete output still yields no measurement for that submission.
  • Other risks of AI graders (prompt injection, grading variance) are out of scope.
