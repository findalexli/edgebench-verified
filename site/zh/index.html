EdgeBench Verified

51 个公开 EdgeBench 任务的隐藏评分器中，哪些问题经得起检验

版本 1.12026 年 11 月 2 日 GitHub 上的代码、数据和修复 引用方式

概要

EdgeBench 用 51 个公开的工程和科学任务给 AI 智能体排名。每个任务里，智能体工作数小时，由一个隐藏的评分程序给提交打 0 到 100 分。我们的第一轮审计报告了其中 32 个任务的问题。随后我们反过来检验自己的发现：由一个独立的 AI 审查者逐条反驳，再把经受住反驳的说法放到当前的 community 评分器上实测，能用真实提交的地方就用真实提交。有 12 个任务的问题站得住，而且确实重要：善意的求解者得分错误或不可重复，影响大小都实测过。其余的问题要么很小，要么上游已经改变，要么未能确认，我们都逐一说明。

12个任务已确认：在当前评分器上测到足够大的分数变化。

其余任务：15 个确实存在但影响小或未见，1 个上游已改变，8 个未确认，15 个未发现问题。各自的原因。

查看已确认的任务 →

每个任务都有单独的页面，列出智能体收到的任务说明、EdgeBench 的评分方式、第二轮复核的状态和第一轮审计的完整记录。

1EdgeBench 是什么，怎样给智能体打分

每个 EdgeBench 任务都给智能体一份书面任务说明和一组初始文件，例如：让一个交易引擎跑得更快，为一款策略游戏写机器人，补全一个数学库里的证明，根据传感器读数推断地下水污染源。智能体有十二小时，可以提交任意多次，每次都能看到分数。评分器（EdgeBench 称之为 grader）由任务作者编写，对智能体隐藏。它在隐藏的测试用例上运行每份提交，得出一个原始结果，例如成本、速度或通过的测试数。原始结果再按作者为该任务选定的参考点换算成 0 到 100 分。每次运行保留它的最佳分数。每个模型在每个任务上运行三次，取有效运行的平均分，崩溃等整体失败的运行不计入。一个模型的总成绩是它在各任务上的平均分。

所以分数可能在四个环节出错（图 1）：评分器可能接受错误的工作；可能拒绝正确的工作，或执行智能体不知道的规则；0–100 分的刻度可能达不到，或参考点测得不对；一次运行可能保留了错误的提交。这四种情况我们都遇到了。还有第五种出在评分器代码之外，即运行评分器的机器。EdgeBench 的官方设置给评分器 4 个 CPU（任务另有设定的除外），而有六个评分器同时运行的工作量超过了这个数（Vibrating Path）。

每个任务页都针对该任务说明这些细节：评分器命令、时限、提交哪些内容、原始结果怎样换算成 0–100 分，以及一次运行保留哪份提交。打开任务列表。

2我们如何复核

第一轮审计对每个任务都问：智能体按规则把任务做对了，能不能拿到任务承诺的分数？它测试的是原始版本，并为 31 个任务发布了修复。2026 年 11 月的第二轮复核问的是：这些发现中哪些在当前评分器上站得住，标准是 EdgeBench 自己的贡献规则：善意的求解者得分错误或不可重复，而且最终分数确实改变。

  1. 反驳。一个独立的模型（GPT-6 Astra）审查了当前代码中的 146 条说法，从头复查了 48 条，又尝试反驳其中 46 条。它运行了纯函数，但没有运行容器。
  2. 实测。在能做到的地方，我们从 community 的 1187e2c 构建评分器，对只在缺陷处不同的对照和触发提交评分，至少重复两次；可重复性问题至少对同一文件评分三次。其他证据包括单次智能体运行、直接调用评估程序、本地评分测试和计算，每项结果都会说明属于哪一种。
  3. 对照真实运行。如果真实求解者不受影响也能得高分，这条说法的分量就要打折。有一条审查者认可的说法就是这样被推翻的：在 Borden Inversion 上，一次真实运行达到了原始分 108.97（满分 109）。

局限：大多数任务只有一个模型的真实运行，或者没有。SMT 的结果受云账号上限影响，运行资源低于官方配置。“未确认”的意思是我们无法在当前评分器上证明损害，并不是说第一轮审计在原始版本上的测量有误；这些记录都保留在各任务页上。

3哪些问题站得住

一个任务要算“已确认”，测到的变化必须落在真实工作上：重新评分真实提交时能看到，或者是任何提交都会受影响的不可重复问题。如果缺陷只在被触发时影响才大，而我们手上的真实提交都没有触发，就归入其余任务。例如 Graph Node：如果预测使用任务允许的整数键，分数从 90.52-90.57 掉到 1.95-2.01。

每一条都列出缺陷、实测影响（除非另有说明，都是 100 分制）以及上游是否知情。

Apple Incremental Game. 同样的 8 用例并行方式，在 4 个 CPU 上会让真实提交丢分，负载高时还会丢掉大量用例。 在真正的 4 个 CPU 上，一份真实提交得 68.10-70.60，缩小并行数后得 73.25-73.92，没有超时（n=5）。在过载测试中（五个评分器共用 8 个 CPU，三台机器），原并行数得 3.09-19.78，缩小后得 17.81-68.87（各 n=20）。在最嘈杂的机器上，缩小后的并行数同样丢了用例。 与 PR #36 机制相同，未单独报告。

Arc Compiler Runtime. 隐藏测试要求 analyze() 返回一种智能体看到的任何材料都没有说明的形式。 一份真实的 Opus 提交原样得 61.31，只改返回形式后得 94.81（各 n=2）。真实运行各一次：原任务最好成绩 61.31，写明返回形式后 96.06。 尚未向上游报告。

Integer Compression Codec. 存储的基准数字对文档所述的初始代码来说不可能达到，这扭曲了各数据集的权重。 初始代码的原始分是 0.25，文档写的是 1.0，用准确数字后为 0.855。一份真实提交现在得 73.60；修正数字后原始分是 164.4，在现有刻度上封顶为 100，换成新的 1..320 刻度则是 51.22。所以修复的影响大小取决于刻度。没有发现排名变化，真实运行现在能达到 73.78。 尚未向上游报告。选择修复方案就是选择新的刻度，这要由维护者决定。

Juliet Vulnerability Analyzer. 只要 .py 或 .sh 文件里出现 infer 这个词，哪怕在注释里，也要扣 100 分。另外，从释放点开始的 CWE-416 结果会被拒绝。 一个真实分析器得 0 分，修复后可得 79.59；另一个只加一行注释就从 90.70 变成 0（n=6）。CWE-416：一个真实分析器损失 3.34，从 89.00 降到 85.66（n=3），但该求解器后来关掉了这个选项，最好成绩没有损失。 已报告：issue #39 和 PR #35（infer 部分）。

NetHack Dungeon Agent. 设置随机种子会悄悄失败，所以每次评分的 20 局游戏都不一样。 我们写的机器人 12 次评分得 6.8-15.5，种子生效后 12 次都是 14.5，都在同一天运行；NetHack 还会读取时钟，所以跨日期的可重复性没有测试。机器人是我们自己写的，没有真实提交可供测试。 已列入上游的已知问题。

OpenRCT2 Theme Park AI. 任务说明承诺大约四个游戏年，但每个场景 120 秒的预算只够跑完 992 个游戏日中的 68 到 69 个。 一个真实插件在官方预算内得 27.50（n=3）。直接调用评估程序跑满 992 天则得 16.44（n=2），所以对这个插件来说，运行时间短反而抬高了分数。我们没有测试评分器修复。真实文件在多次评分之间也有波动，最大为 11.40-44.73，但这可能来自插件自身的随机性，所以我们不把它算作评分器的问题。 运行时间过短已列入上游的已知问题；issue #12 就这个任务的刻度提出了另一个问题。

Rust Multicrate Reconstruction. 缺少四个源文件，导致九个计分的 crate 无法通过。 在 8 个 vCPU 上，补回这些文件后，一份真实提交从 17.20 升到 27.17，我们根据上游代码重建的参考解从 27.61 升到 73.99（n=2）。原评分器的分数与 4 个 CPU 的结果一致，但补回文件的情况没有在 4 个 CPU 上运行。另外两个 crate 仍因隐藏测试的其他缺陷无法通过。初始代码也从 1.47 升到 3.82，所以旧分数不能直接沿用。 已列入上游的已知问题。

Schemathesis Datagen Pipeline. 隐藏的 header 测试要导入的名称和要求的格式键，TODO.md 都没有给出，所以每个真实的 headers 模块在这项测试上都是 0/15。 补上这些内容后，一份真实提交从 72.31 升到 85.64 或 86.67，两个值的差别来自一项不稳定的测试。8 个真实模块实际只有 2 个不同版本。 尚未向上游报告。

SMT Solver. 求解器对 5 个难题回答 sat 时，验证程序的递归会崩溃；分数文件没有写出，评分器却仍报告一个有效的 0 分。 一个真实求解器在原评分器上得 0.00，加大验证程序的栈后得 47.04 和 46.17。引发崩溃的 5 个答案仍然验证不通过；避免崩溃只是恢复了其他用例上已得的分数。测量条件是 8 个 CPU 和 7 GB，不是官方的 16 个 CPU 和 16 GB，每次运行有 6 到 7 次求解器被内存杀死。真实运行中尚未观察到这一现象。 尚未向上游报告。

Treant Forest. 测试程序在一个没有写明的回合上限处结束每局，所以任何提交都超不过 21.02，而 0-100 分的刻度却假定了这个上限不可能达到的总分。 全部 87 份真实报告都集中在 20.46-21.02，上限掩盖了它们之间的真实差别。保持刻度不变、去掉上限，会让一份真实提交提高 15.83 分，并改变测试过的提交的排序，不过一些较长的回放会触及测试程序的时限。我们测量的四份真实提交都读取了 README 称解法不使用的目的地列表；只读地图的对照提交无论有没有上限都得 3.04。 已列入上游的已知问题。是改上限、改刻度还是两者都改，要由维护者决定。

Vibrating Path Graph Coloring. 官方配置的 4 个 CPU 上同时运行 8 个用例，只要一个超时，总分就变成 inf。 一个真实的 Opus 求解器 15 次评分全部是 inf，同时运行 4 个用例时得 19.77-19.98。同一文件在自己那次运行中，在公开的评分器镜像上 7 次评分全部通过，所以评分结果不可重复。 已报告：issue #40 和 PR #36。

Wesnoth Tactical AI. 即使种子固定，同一文件也会得到不同分数。 Wesnoth 自带的 AI 8 次评分得 36 到 43，没有超时。我们还没有找到原因，也没有真实提交可供测试。 已列入上游的已知问题。

其余任务，包括我们撤回的第一轮说法

3.1确实存在，但影响小或未在真实工作中出现

  • D-ABIC Gravity Inversion. 一项未说明的门槛让模型空间解法损失 1.08 分，但 75 份真实报告没有一份采用这种形式。自报分数是另一个设计问题。
  • DCSS Dungeon AI. 上游说明记录一个机器人在当前评分器上的原始分为 1556.0-5211.2，折算为 32.82-54.61。我们自己写的较弱的机器人波动不到 1 分，所以没有复现这么大的波动，也没有查明原因。
  • Exchange Core Throughput. 有错误的引擎确实能得分，但在官方的 4 个 CPU 上，正确的工作大多也是 0 分，没有真实运行受影响。
  • FFmpeg swscale Reimplementation. 让一个转换失败反而能加 12.82 分，但没有真实运行因此得利。
  • Git Rewrite in Zig. 普通的目标文件，或一个未被引用、调用系统 git 的测试，会把一份真实实现从 36.86 变成 0，但 46 个不同的真实提交都没有这两种情况。
  • Graph Node Classification. 把真实求解器的预测改成整数键（任务允许这样做），分数就从 90.52-90.57 降到 1.95-2.01。我们手上的真实提交都没有这样做。
  • Grid Turing Robot. 缩小并行数让有效的真实提交提高 0.67 到 0.71 分。没有真实提交因此从无效变为有效。
  • Lean Analysis Proofs. 两条必须证明的命题是假的，这一点已在 Lean 中证明。计算出的分数影响极小，评分器镜像也太大，我们无法重跑。
  • Molecular Self Assembly. 缩小并行数让限时搜索得到更多 CPU，提高 1.13 到 1.46 分。我们最初归咎于并行的超时，在两种并行数下都会出现。
  • Ordinal Notation Well-Foundedness. 文件名过滤可能丢掉需要的证明辅助文件（1.18 变 0）。只有我们自己的证明触发过。我们手上没有这个任务的真实提交，不过上游记录了历史运行。
  • PFR Formalization. 五条计分陈述的类型里藏着 sorry，任何提交都拿不到这部分分数：423 个目标中的 5 个，即 1.18 分。一位志愿的 Lean 用户人工核查后判定通过：使用变通方案后，五个完成的证明全部得分（398/423 变为 403/423）。我们没有在当前评分器上重跑。
  • Schemathesis Config Modernization. 转发式装饰器多得 0.67 分。没有真实提交这样写。
  • Schemathesis Reporting Observability. 两项检查多给 1.00 到 1.43 分，第三项会让不含 schemathesis 一词的有效报告少得 1.43 分。只有一个未修改的真实文件受影响（得 2.0，应为 1.0）。
  • Triangulation Coloring Optimization. 缩小并行数提高 0.32 到 0.59 分，所有条件下都没有超时。
  • Warehouse Forklift Routing. 评分器每个输入只给 60 秒。五个用例各 30 秒意味着 150 秒，但 README 的另一处把整个输入称为测试用例。改成长时限的解法在放宽后能恢复得分；我们手上的真实提交不受影响，并行数也几乎没有影响。

3.2上游已改变

  • Order Addition Permutation Optimization. 在原始版本上确实存在：一次真实运行保留了 3.79，而不是后来一份提交得到的 41.24。community 改变了选取最好成绩的方式，所以这个问题在那里已不存在。

3.3未确认

这里列出的第一轮说法，就代码而言可能仍然是对的。之所以列在这里，是因为我们无法证明它会改变善意求解者在当前评分器上的分数。

  • Borden Source Inversion. 未说明的模型并没有阻止一次真实运行借助分数反馈达到原始分 108.97（满分 109），而写明模型后的一次运行只有 52.86。这样的单次运行不能说明写明模型会带来什么变化。
  • College English Exam Bank. 代码确实给遗漏的规则打满分，但所有例子都是构造的评分回复，没有真实提交触发。
  • CTA Risk Budget Optimization. 限额公式与政策不一致，但我们检查的一份真实提交两种算法都是 50.0 分。
  • Equivalence Class Divide and Conquer. 成本计算确实有误，但参考解和简单解在两种情况下得分相同，分数变化需要我们额外添加的输入才会出现。
  • Jagua Nesting Optimization. 重叠判断的缺陷确实存在，但我们没有发现哪份善意提交因此得利或受损。
  • OpenTTD Transport AI. 文中提到的 API 确实不存在，但我们没有测到它让正常工作的 AI 损失分数。存档的空闲脚本得 0 分，修正后的脚本没有实际运行游戏测试。
  • Portfolio Risk Calibration. 超额收益公式与文档不同，但一个修改过的文件在本地评分路径上只从 15.35 变成 15.34（年化方式对齐后为 15.27）。在当前评分器上的损害尚未验证。
  • Tree Block Partitioning. 提供的乘法在操作数别名时确实出错，但 61 个真实提交没有一个触发。

4第一轮审计

这次复核修正了我们的第一轮审计。第一轮测试的是原始版本，报告了 51 个任务中 32 个有问题，并估计了公开排行榜的分数范围。这 32 个任务中，10 个已确认，13 个确实存在但影响小或未见，1 个上游已改变，8 个未确认。这些范围计入了第一轮的所有修复，包括本次复核未确认的说法所对应的修复，我们也没有重新计算。每个任务页面都保留了第一轮的记录。
