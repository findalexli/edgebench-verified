摘要

EdgeBench 对工程与科学任务中的智能体进行评分。本审计检查了全部 51 个公开任务。历史处置为 31 个修复包、19 个附说明保留的任务和 1 个移除的任务。修复包不等于整个任务已经获得验证。证据包括原始辅助函数测试、原生评分器运行和形式化模型，各有其适用范围。Datagen 的年份范围修正通过了原生评分器对照，FFmpeg 的输出检查和失败归零规则通过了原生计分程序对照。CTA 以基金净资产为分母的修正，在原始评分命令下通过了原生并排对照运行。Warehouse 需要独立的主机端等待修复。32 个修复包中有 31 个在一台干净的机器上从零重建成功；Lean Analysis 的评分器镜像约需 45 GB 磁盘空间，未能重建。尚待完成的检验：FFmpeg 的提交构建路径；Warehouse 的等待修复在真实后端上的集成；Lean Analysis 的镜像构建和实际评分路径；PFR 在五个实际目标上的得分恢复，这需要真实的证明；Equivalence 在全部六道题上的逐题检查；以及 Vibrating Path 零命中格式问题的影响，在 50 个用例中有 13 个仍未解决。Triangulation 重新生成的输入现在恰好覆盖其凸包（v2.2）。公开平均分不能确定修正后的排行榜：Treant 需要区间，Portfolio 的扫描只是敏感性情景，区间重叠也不能证明排名能够反转。参见当前修复包状态及影响分析。

1EdgeBench 是什么，如何为智能体打分

一个 EdgeBench 任务给智能体书面的任务说明和初始文件：让一个交易引擎更快，为一款策略游戏编写机器人，补完一个数学库中的证明，根据传感器读数推断地下水污染的来源。智能体在十二小时内可以随意多次提交，并能看到每次的分数。一个由任务作者编写的隐藏评分器程序，在隐藏的测试用例上运行每份提交，并产生一个原始结果，例如成本、速度或通过的测试数。原始结果再按作者为该任务选定的参考点换算为 0 到 100 分。每次运行保留其最佳分数；每个模型在每个任务上有三次运行，对其中有效的运行取平均（整体失败的运行，例如崩溃的运行，被舍弃）；一个模型的总成绩是它在各任务上的平均分。

因此，分数可能在四个环节出错（图 1）：评分器可能接受错误的工作；可能拒绝正确的工作，或执行智能体未被告知的规则；换算到 0–100 分的刻度可能无法达到，或测定有误；一次运行可能保留了错误的提交。这四种情况我们都发现了，此外还有第五种，它位于评分器代码之外：评分器所运行的机器。EdgeBench 的官方设置给评分器 4 个 CPU（除非任务另有设定），而有六个评分器同时运行的工作量超过了这个数（第 3.1 节）。

每个任务页都针对单个任务详细说明这些内容：其评分器命令、时限、提交的内容、原始结果如何换算为 0–100 分，以及一次运行保留哪份提交。打开任务列表。

2我们做了什么

对 51 个公开任务中的每一个，我们只问一个问题：如果一个智能体做出诚实、正确的工作，它能否得到任务所承诺的分数？证据追踪至原始评分器代码和最终分数。原生运行、辅助函数对照和形式化模型分别回答不同问题，单独任何一种都不能验证整个当前修复包（图 2）。随后，每个任务得到以下三种结果之一：

  • 修复包（31 个任务）。评分器的逻辑、数据或配置可以纠正。我们发布带版本号的修复包，各案例说明对照测试的覆盖范围和待完成的集成验证。
  • 保留（附说明）（19 个任务）。未发现可纠正的问题。说明中记录了修改评分器也无法消除的附带情况，例如运行之间或机器之间的波动。
  • 已移除（1 个任务）。不存在可靠的修复。

3问题出在哪里

每个存在问题的任务（共 32 个：31 个已修复，1 个已移除）都有一个主要类别，按其主要缺陷的机制确定，还可能有次要类别。共有四个类别：

  • 工程与运行环境（5 个任务）：评分器在实际环境中不能正确运行。
  • 评分逻辑错误，事实性错误（15 个任务）：评分器把错误的工作判为正确，或把正确的工作判为错误。
  • 任务说明与评分不一致（9 个任务）：评分器要求了任务说明没有写明的东西，或与任务说明相矛盾。
  • 分数换算与选取（3 个任务）：0–100 分的刻度无法达到、参考点有误，或保留了错误的提交。

下面每个类别先给出通俗的解释和所属任务，再给出有代表性的例子。全部任务列在任务页，可按类别筛选；每个任务都有完整的案例，包括测试提交、独立检验和修复。下文中的每个任务名称都链接到其页面。

3.1工程与运行环境5 个任务

评分器的评分规则本身也许没有错，但它在实际使用的环境中不能正确运行。常见原因包括：同时运行的测试用例需要的 CPU 多于评分器分到的 CPU，诚实的解法因此超时；隐藏测试被插入到无法编译的位置；评分器需要的文件在公开镜像中缺失；测试在第一次失败时就停止，并把其余测试记为失败；或者结果取决于运行时机。这时，诚实的工作会因为与其质量无关的原因而失分。

以此为主要类别的任务共 5 个：Apple Incremental Game、Grid Turing Robot、Molecular Self Assembly、Rust Multicrate Reconstruction、Vibrating Path Graph Coloring。在任务列表中查看。以此为次要类别的任务：Exchange Core Throughput、Git Rewrite in Zig、Order Addition Permutation Optimization、Treant Forest、Triangulation Coloring Optimization、Warehouse Forklift Routing。

评分器分到的 CPU 少于它同时运行的工作数。EdgeBench 的官方排行榜设置给每个评分器 4 个 CPU，除非任务另有设定；七个 Lean 任务为 8 个，SMT Solver 为 16 个（设置原文引录）。有六个没有单独设定的评分器，在每个用例的承诺时限下同时运行 8 个测试用例（Treant Forest 也同时运行 8 个，但允许的时间是承诺时间的两倍）。因此在 4 个 CPU 上，每个用例只分到约半个 CPU，而任务说明从未写明评分器的 CPU 数；在评分器内部，系统报告的是宿主机的 CPU 数（在我们的测试机上为 8），而不是限制值。Grid Robot 承诺每个测试用例 30 秒。一个每个用例计算 16 秒的解法，在 4 个 CPU 上 50 个用例中有 48 个超时，而一次超时就会使整份提交作废；在 8 个 CPU 上，同一解法通过全部用例。Vibrating Path、Molecular Assembly、Apple Game、Triangulation 和 Warehouse Routing 的情况相同：按 CPU 时间预算设计的解法会失去大多数用例或全部分数。墙钟时限并不承诺独占 CPU 时间；该修复采用更一致的资源策略。按截止时间停止的解法通常不会被作废，但只得到一半的计算时间；在 Vibrating Path 的九次原始评分器评分中，有一次这样的解法被作废，原因可能是共享 CPU 的任务自带检查器超时了。修复后，同时运行的用例数不超过评分器的 CPU 数；我们在 4 个和 8 个 CPU 下分别进行了并排对照测量。在 Exchange Core 中，分数是速度，未修改的引擎在 4 个 CPU 上得 0 分，在 8 个 CPU 上约得 47–76 分，因此该任务的说明记录了：其分数取决于评分器的 CPU 数。

证据：已在原始评分器上复现 · Lean 4：说明：已证明 · 修复经并排对照测试，三次运行

Rust Multicrate。智能体要重建一个大型 Rust 项目。评分器以无法编译的方式把隐藏测试插入项目的两个部分，因此对每个遵守“不得修改测试”这一规则的智能体，这两个部分（共 100 分中的 22 分）都得 0 分。一个完整的解法得 73.99 分，而不是 94.70 分。（公开的归档还缺少四个库文件；恢复这些文件后，初始文件能够精确复现发布方记录的分数，因此发布方自己的评分很可能具备这些文件，这第二个问题只影响使用公开镜像评分的人。）

证据：已在原始评分器上复现 · TLA+：修复正确性：部分模型检验 · 修复经并排对照测试，三次运行（4 项对照中有 1 项只运行一次）

3.2评分逻辑错误，事实性错误15 个任务

任务要求的内容是对的，但评分器的检查有误：把错误的工作判为正确，或把正确的工作判为错误。例如：正确性检查漏掉真实的缺陷，校验器漏掉重叠的形状，成本检查少算一项，随任务提供的库计算出错，答案检查器误读有效答案，要证明的命题按原文是假的，或者分数取自提交对自身结果的报告。在错误的提交被接受时，它的得分可以与正确的提交一样高，甚至更高。

以此为主要类别的任务共 15 个：College English Exam Bank、CTA Risk Budget Optimization、D-ABIC Gravity Inversion（已移除）、Equivalence Class Divide and Conquer、Exchange Core Throughput、FFmpeg swscale Reimplementation、Graph Node Classification、Jagua Nesting Optimization、Lean Analysis Proofs、PFR Formalization、Schemathesis Config Modernization、Schemathesis Datagen Pipeline、Schemathesis Reporting Observability、SMT Solver、Tree Block Partitioning。在任务列表中查看。以此为次要类别的任务：Rust Multicrate Reconstruction。

SMT Solver。智能体要构建一个逻辑公式求解器。当公式可满足时，求解器必须给出一个示例赋值，由评分器检查。检查器按调用的书写方式而不是按参数求值的结果来查找函数的值，因此同一个书写形式的调用可能代表两个不同的值。因此，正确的答案在 27 道隐藏题目上被拒绝，一个完美求解器的分数从 78.61 降到 72.40。

证据：已在原始评分器上复现 · Lean 4：修复正确性：已证明 · 修复经并排对照测试，三次运行

Exchange Core。智能体要在不改变行为的前提下加速一个证券交易所撮合引擎。评分器的正确性检查只确认资金总体平衡、订单簿一致。两个现实中可能出现、只需改动一处的缺陷——向卖方吃单者收取挂单手续费而非吃单手续费，以及不发送成交消息——都能通过检查并获得满分，而项目自带的测试套件能发现这两个缺陷。修复版要求先通过这些测试，再测量速度。

证据：已在原始评分器上复现 · Lean 4：发现：部分证明 · 修复经并排对照测试，三次运行（13 项对照中有 6 项只运行一次）

Jagua Nesting。智能体要把平面形状尽可能紧密地排入一条带状区域。评分器漏掉了许多重叠，例如一个形状滑过另一个形状的一半，因此一个不可行的布局可以胜过所有可行的布局。

证据：已在原始评分器上复现 · Lean 4：修复正确性：部分证明 · 修复经并排对照测试，三次运行

PFR Formalization。智能体要在一个数学库中补全证明。在 423 条命题中，有五条在命题本身内部藏有一个缺口标记（Lean 的 sorry），这是由文件声明默认参数的方式引入的，因此任何证明都无法获得这些分数；任何使用了它们的后续证明也会被拒绝。这五条共占 100 分中的 1.18 分，连同使用它们的后续证明最多为 2.13 分（推断所得）。只有本来能证明它们的智能体才会失分，因此这一缺陷也可能掩盖智能体之间的差异。

证据：已在原始评分器上复现 · 修复经并排对照测试，三次运行

D-ABIC Gravity Inversion。该任务有四十二分来自提交对其自身工作所报告的数字，评分器无法核查这些数字。评分器还暗中惩罚任务说明明确允许的两种数学上等价的形式之一。我们修复了第二个问题，但第一个问题没有能保留该任务的修复办法，因此该任务被移除。

证据：已在原始评分器上复现 · 部分修复经并排对照测试，三次运行；任务已移除

3.3任务说明与评分不一致9 个任务

评分器执行的每条规则单独看也许都合理，但它不是智能体被告知的规则。评分器要求了任务说明没有写明的东西，或与任务说明相矛盾：时限比承诺的短，漏掉了一个几何条件，输出格式或约定没有文档说明，有任务说明从未提及的检查，有一个并不存在的函数，或用了不同的公式。于是，忠实遵循任务说明的智能体被按另一条规则评分。

以此为主要类别的任务共 9 个：Arc Compiler Runtime、Borden Source Inversion、Git Rewrite in Zig、Juliet Vulnerability Analyzer、OpenRCT2 Theme Park AI、OpenTTD Transport AI、Portfolio Risk Calibration、Triangulation Coloring Optimization、Warehouse Forklift Routing。在任务列表中查看。以此为次要类别的任务：CTA Risk Budget Optimization、D-ABIC Gravity Inversion（已移除）、Grid Turing Robot、Schemathesis Reporting Observability、SMT Solver、Vibrating Path Graph Coloring。

Triangulation Coloring。任务说明只允许在两个三角形构成凸形时翻转其公共边。评分器遗漏了这一条件，而隐藏测试用例也是由同一条错误规则生成的：全部十个用例都含有相互重叠的三角形，而且在其中一个用例上，一次被禁止的翻转改善了分数。

证据：已在原始评分器上复现 · Lean 4：修复正确性：已证明 · 修复经并排对照测试，三次运行

Warehouse Routing。任务说明承诺每个测试用例 30 秒，即每个由五个用例组成的输入 150 秒。评分器在 60 秒后就停止每个输入，而一次超时就会使整份提交作废，因此一个用足了所承诺时间的解法得零分。

证据：已在原始评分器上复现 · Lean 4：发现：已证明 · 修复经并排对照测试，三次运行

Git in Zig。智能体要用 Zig 语言重写 git。有几项任务说明从未提到的检查：只要项目中含有一个普通的构建文件（例如一条常用的 Zig 构建命令留下的文件），或含有一个把智能体的输出与真实 git 相比较的测试（而任务说明恰恰鼓励写这种测试），整个分数就会被设为 0。修复会删除遗留的构建文件，并取消对测试代码的检查，而不是把分数清零。

证据：已在原始评分器上复现 · 修复经并排对照测试，三次运行

Borden Inversion。智能体要根据监测井推断一个地下污染源的位置、规模和时间。评分器用一个物理模型预测隐藏的读数，而模型的约定在任务说明中从未写明：除其他问题外，它忽略土壤孔隙度，把速率当作总量，并把污染源放在其区域的底部。一个基于教科书物理的诚实拟合得 7.0 分；使用评分器约定的同一拟合方法得 31.2 分。修复版把评分器的模型提供给智能体。一个根据评分器的分数反复迭代的智能体，也可以部分地学到这一约定（见与真实智能体运行的对照）。

证据：已在原始评分器上复现 · Lean 4：已发布数字：已证明 · 修复经并排对照测试，三次运行

3.4分数换算与选取3 个任务

原始结果计算正确，但把它变成最终分数的环节出了错：把原始结果换算到 0–100 分的参考点无法达到，或是在别的对象上测得的，因此分数被压缩或偏移；或者，挑选每次运行最佳提交的选取规则保留了错误的提交。

以此为主要类别的任务共 3 个：Integer Compression Codec、Order Addition Permutation Optimization、Treant Forest。在任务列表中查看。以此为次要类别的任务：Borden Source Inversion、Grid Turing Robot、Warehouse Forklift Routing。

Treant Forest。每个测试用例按存活的回合数计分，而评分器限制了回合数，因此总数不可能超过 92,304。0–100 分数刻度的参考点却设得远高于这个上限。任何提交的得分都不可能超过 100 分中的 21.02 分。修复后的刻度从初始程序的总数延伸到已证明的上界（尚未证明可达）。Warehouse Routing 也有同样的问题，而且是通过证明而非测量确立的：一个在 Lean 中证明的下界表明，任何有效答案的得分都不可能超过约 30.6（在精确下界处为 30.3）。

证据：已在原始评分器上复现 · Lean 4：已发布数字：部分证明 · 修复经并排对照测试，三次运行

Order Addition。评分器的五项测试之一把一个辅助文件与一个过时的校验和作比较，因此每份提交都无法通过它。在该任务选取一次运行最佳结果的规则下（通过测试最多者优先，相同时取最早的），每次运行所报告的最佳结果都被冻结在其第一份有效提交上，后来的改进永远不被计入。如果改为保留最高分，则不受影响。与真实智能体运行的对照表明，这种情况确实在一次真实的智能体运行中发生了。

证据：已在原始评分器上复现 · TLA+：修复正确性：已模型检验 · 修复经并排对照测试，三次运行

4对已发布排行榜的影响

EdgeBench 公布每个模型在每个任务上的分数：三次十二小时运行中各次运行最佳分数的平均值。我们问的是，一旦问题得到纠正，每个模型在 51 个公开任务上的平均分会如何变化。如实的回答是：这无法从公开数据中确定。要测量它，要么需要对智能体的原始提交重新评分，而 EdgeBench 没有公开这些提交；要么需要在修复后的任务上重新运行这些模型，而本次审计没有这样做。可以精确陈述的是：

  • 条件区间。计算考虑了舍入及 Treant 带截断的分段刻度。中点只用于描述区间，并非已知的修正后模型平均分。
  • 适用范围。界限针对指定缺陷。Portfolio 的有限扫描单独作为敏感性情景，不作为全局界限。
  • 排名。区间重叠既不能确定先后，也不能证明实际可实现的排名反转。

这些条件界限无法确认 Opus 4.8 与 GPT-5.5 的先后顺序；区间重叠不证明排名颠倒可以实现。其余相邻模型的先后顺序，只在只知道方向的修复没有影响时才能确认；在完整分数域包络中，每一对相邻模型的区间都相互重叠。

5我们如何验证

  1. 使用原始评分器，即 EdgeBench 发布的评分软件，从其公开镜像中拉取，并以加密指纹标识。
  2. 引用承诺原文，逐字取自智能体收到的任务说明和文档。
  3. 用测试提交展示问题：一份正确的提交，必须得到所承诺的分数；一份触发问题的提交；以及一份错误的提交，必须被拒绝。
  4. 独立确认，通过精确算术、另一个独立实现、穷尽搜索，或在 Lean 4 或 TLA+ 中的形式化证明。
  5. 追踪到最终分数。只有改变了诚实工作的 0–100 分的问题才被计入。
  6. 对原版和修复版本进行对照，使用相同的测试提交：共 254 项评分对照，其中 240 项运行三次。

51 个任务中有 26 个有形式化结果，包括 286 个 Lean 定理和 20 次 TLA+ 模型检验运行。历史形式化结果在明确模型内覆盖 10 项修复机制，另有 4 项部分证明。它们不验证改动后的候选版本、完整评分器行为或镜像集成。形式化检验也纠正了我们：有一项已发布的修复覆盖范围比所说的窄，现已修订。

6经验

  • 先运行原始评分器，再对它进行推理。大多数问题是通过阅读代码发现的，但只有靠一份能触发问题的提交才得以确证。若干看似合理的发现没能通过这一步。
  • 形式化工具在小而明确的问题上很有成效。一个错误的定理、一个算术缺口、一个下界和一个别名缺陷，都得到了确定的结论。大多数评分器问题涉及约定、文件格式或时间，对这些问题，任何证明都不如一次并排对照运行来得省力。
  • 证明的价值取决于它与代码的联系。我们在 Lean Analysis 任务自己的镜像中、基于其自己的定义陈述了反驳。我们在 294 个字符串上把 Warehouse 的模型与真实的测试程序进行了对照，并把每个 TLA+ 步骤对应到一行源代码。没有这些联系，证明论证的就是另一回事了。
  • 每项检查都需要反向检验。每个 TLA+ 模型都有一个必须失败的配置，每个 Lean 证明都打印出它所依赖的公理，修复应同时接受正确及错误输入的测试；实际覆盖范围见案例页。一个不可能失败的检查什么也说明不了。
  • 形式化证明不仅检查基准，也检查我们自己的工作。把部分修复机制写成 Lean 或 TLA+ 模型，暴露出一项覆盖范围比发布时所说的窄的修复，以及八处不够精确的表述。每一处都是因为某次证明尝试在一个我们没想到要测试的情形上失败而发现的。
  • 要在发布方的机器设置下测试，而不只是在方便的机器上。我们第一轮并排对照测试是在 8 个 CPU 上运行评分器的。排行榜的设置给大多数评分器 4 个 CPU，而在 4 个 CPU 下，有六个评分器会让在 8 个 CPU 下能通过的诚实工作超时。我们起初还以为 SMT Solver 分到 4 个，而它的设置给了 16 个。代码在两种设置下都是正确的；出错的只是机器与代码的组合。
  • 新的审查者能发现作者自己看不到的问题。第二轮审查者不了解我们的背景，他们发现了 CPU 问题、Rust Multicrate 中两个隐藏测试问题、Git in Zig 中未公开的检查，以及 PFR 中一个隐藏的占位符，这些大多出现在我们原本保留的任务中；他们还发现我们自己的几项修复需要扩展或修订。每一项随后都由一次运行而不是由论证来确定。
  • 要测试修复的目的，而不只是它改变了什么。Integer Codec 的第一版修复完全按文档纠正了基线，并通过了每一项测试，然而真实提交表明它使分数刻度饱和了。用真实的智能体工作来检查修复，发现了证明和我们编写的测试都没有发现的问题。
