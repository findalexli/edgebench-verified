Optimize solution.py for the custom VLIW/SIMD kernel generator. Implement KernelBuilder.build_kernel so the generated instruction program is correct and faster on the simulator. Modify only solution.py. Do not change problem.py, runner.py, verifier.py, test cases, or hard-code public or hidden seeds.

任务要求

解题者要为一个模拟的 VLIW 处理器（一种同时发射多条指令的处理器）写程序生成器。任务文本写道 "Implement KernelBuilder.build_kernel so the generated instruction program is correct and faster on the simulator."（实现该方法，使生成的指令程序正确，并在模拟器上运行得更快。）它还写道 "Modify only solution.py. Do not change problem.py, runner.py, verifier.py, test cases, or hard-code public or hidden seeds."（只修改 solution.py；不要改动其他给定文件或测试用例，也不要硬编码公开或隐藏的种子。）

生成的程序必须通过每个正确性用例才计分，这时它的原始结果（换算为 0–100 分之前）就是性能用例上的周期数。分数刻度是 log_min，一种对数刻度，周期越少分越高。0 分参考点（基线）是 4475.53 个周期，100 分参考点（专家水平）是 1000 个周期。类别：系统与软件工程。

我们没有发现会改变分数的缺陷，检查过的部分如下。

  • 隐藏用例文件里有 8 个正确性用例和 1 个性能用例，高度都是 10，轮数 16，批大小 256。
  • 我们在原始评分器上运行了遵守规则的测试提交，结果见下表。

影响有多大

在遵守规则的提交上，我们没有测到任何影响。

低于 1000 个周期时，刻度就饱和了。 log_min 截断在 100，也就是到 1000 个周期的专家参考点就封顶。第三方有一次 Claude Opus 5.5 运行（4 小时，以 adafadaq/edgebench-opus-5-5-xhigh-rollouts 发布在 Hugging Face 上），它在这个评分器上的 18 份提交全部有效，都是 9/9 通过。各内核的周期数依次为 1122、1027、979、970、966、965、962、957、956、951 和 950（agent-1 到 agent-11，report.json 中的 score）。如果不截断，对应 92.3、98.2、101.4、102.0、…、103.4，所以从 979 个周期起，每个内核都是 100 分，刻度区分不出它们。已发布的最好成绩是 85.6（GPT-5.5，12 小时，tasks/README.md），约合 1240 个周期，所以已发布的分数不受影响。950 个周期的内核在 8 个正确性用例和 1 个性能用例之外是否正确，我们没有检查，也没有看它的源码。
