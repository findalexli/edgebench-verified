摘要

任务
根据地下水监测井的读数，推断一个隐藏的地下污染源的位置、规模、时间和强度。
问题所在
评分器用一个隐藏模型预测监测井读数；文档给出了模型的组成部分，却没有说明它们如何组合。该模型把速率当作总量，忽略孔隙度和污染源持续时间，标错单位，并把污染源放在其区域的一个面上，而不是中心。教科书模型对公开数据的拟合同样好，得分却更低。
影响有多大
对一次性的诚实拟合，约为原始 109 分中的 24 分（100 分中的 22 分）：教科书模型得 7.0 分，使用隐藏约定得 31.2 分。对反复提交的智能体，影响更小，幅度未测量：一次真实运行从 7.01 分升到 60.10 分，期间评分器每次都报告其在隐藏监测井上的误差。
我们的处理
已修复，发布新版本：解题者会拿到评分器自己的预测代码及其约定的准确描述，分数刻度从 0 到真实污染源的得分 109。
问题类别
任务说明与评分不一致；另涉及：分数换算与选取
验证状态
两次并排原生运行及其重复（全部顺利完成）在原始版和修复版下的原始结果完全相同；随附的正演模型与评分器的模型一致；109 是可精确计算的最大值；修复包在一台干净的机器上从零重建（materialize-check-g3）。没有在 v2 上运行智能体；影响依赖于一种教科书模型变体。
形式化检验
在 Lean 4 中已证明。修复后的刻度和每一个换算后的排行榜数值都由已发布的（一位小数的）分数精确推出。 局限：只涵盖刻度的改变；物理约定无法形式化。

要求智能体做什么

以下是 EdgeBench 的原始任务文本，即 tasks/borden_source_inversion.json 中的 work.agent_query 字段，来自字节跳动 Seed 团队在 Hugging Face 上发布的 EdgeBench 数据集，采用 CC BY 4.0 许可。文本未作改动，仅从 Markdown 渲染为 HTML；指向任务工作区内文件的链接以纯文本显示。EdgeBench 的评测框架还会附加关于如何提交的标准说明（sforge/harness/evolve_scripts.py），此处未显示。任务说明是 EdgeBench 的原文，在所有语言版本中均以英文显示，未作翻译。

Borden 3D Groundwater Contaminant Source Inversion

Task

You are given a Borden-style 3D groundwater contaminant migration scene derived from a Borden-AdePy reproduction workflow. Your task is to infer a finite-duration rectangular-region contaminant source from public monitoring-well readings.

This is not a point-source task. A point-source answer or the old x0,y0,z0,C0 schema is accepted only as a degenerate fallback and cannot receive full credit.

Required source parameterization

Create answer.json in the task root using this schema:

{
  "source_type": "rectangular_region",
  "dimension": 3,
  "x_center": 0.0,
  "y_center": 0.0,
  "z_center": 0.0,
  "half_length_x": 0.0,
  "half_length_y": 0.0,
  "half_length_z": 0.0,
  "C0": 0.0,
  "t_start": 0.0,
  "duration": 0.0,
  "transport_model": {
    "equation_type": "advection_dispersion_reaction",
    "governing_equation": "R*dC/dt = div(D grad C) - v dot grad C - lambda*C + source",
    "velocity_m_per_day": 0.0,
    "alpha_L_m": 0.0,
    "alpha_TH_m": 0.0,
    "alpha_TV_m": 0.0,
    "porosity": 0.0,
    "retardation_factor": 1.0,
    "lambda_per_day": 0.0,
    "numerical_approach": "brief description of forward model and optimization"
  },
  "method": "brief description of your inversion method"
}
  • x_center,y_center,z_center: center of the rectangular source region, in meters.
  • half_length_x,half_length_y,half_length_z: half sizes of the rectangular source region, in meters.
  • C0: effective source concentration/intensity, in mg/L.
  • t_start: release start time in days.
  • duration: release duration in days.
  • transport_model: your groundwater solute transport construction. Include the ADE/reaction governing equation, public hydrogeologic parameters used, and the numerical or analytical approximation used to predict concentrations.

All parameters must stay within public_problem_config.json → source_search_bounds_for_agent.

Provided files

  • public_problem_config.json: Borden grid, hydrogeological parameters, source prior bounds, and column definitions.
  • public_source_prior.json: explicit range summary for the finite-duration rectangular-region source parameters.
  • borden_grid.npz: grid arrays exported from the Borden-AdePy scene, including x/y grid and bottom profile.
  • public_wells.csv: public monitoring-well coordinates.
  • public_monitoring_data.csv: noisy, censored public monitoring observations. Clean generated concentrations are not provided to the agent.
  • baseline_solver.py: writes a legal low-quality baseline answer.json from the center of the parameter bounds.
  • answer_template.json: required output schema.

No runnable scientific starter solver is provided. You should write your own Python code to read files, construct the groundwater solute transport equation, build an ADE/AdePy or equivalent forward approximation, optimize the source parameters, and update answer.json.

Mandatory baseline workflow

Before implementing a complex inversion algorithm, first ensure that a valid answer.json exists:

python baseline_solver.py

Then iteratively improve answer.json using public monitoring data. Missing answer.json gives zero.

Scoring policy

The judge does not grade old point-source location error directly. It evaluates whether your finite-duration rectangular-region source predicts withheld monitoring readings:

  1. Read answer.json.
  2. Check required finite-region fields and parameter bounds.
  3. Use a hidden Borden-ADE region-source forward model to predict concentrations at hidden monitoring wells and hidden future times.
  4. Compare predictions with hidden readings using relative RMSE and log-scale metrics.
  5. Hidden prediction dominates the score. Easy format/prior/method/transport-equation points are capped and cannot exceed the hidden-quality caps.
  6. Region-shape and physical-consistency points are gated by hidden prediction quality.
  7. Very poor hidden/future prediction is capped at 15 points; poor-but-improving prediction is capped at 30 points; moderate prediction is capped at 45 points.

If hidden monitoring prediction is poor, the final score is capped. This makes early baseline or shallow point-source fits low-scoring, while still allowing genuine improvement through better region-source inversion.

Rules

  • Do not read or reference hidden scoring files.
  • Do not hard-code hidden monitoring readings.
  • Do not modify judge files.
  • Do not call FloPy, MODFLOW, MT3DMS, or external groundwater executables.
  • You may use Python libraries such as NumPy, SciPy, pandas, matplotlib, pymoo, and AdePy if available.
  • Submit all scripts/results needed to reproduce your answer.json.

Critical submission rule

The judge only reads answer.json in the task root.

It does not automatically run inverse_solver.py, run_checks.py, write_fit_report.py, write_public_predictions.py, or any other script during scoring.

Therefore, after every meaningful inversion or optimization step, you must immediately overwrite the task-root answer.json with the best current source parameters.

If answer.json is unchanged, the score and all METRICS will remain unchanged, even if you create new Python scripts, reports, or prediction files.

Recommended workflow:

  1. Run python baseline_solver.py only as an initial fallback.
  2. Implement and run your inversion script.
  3. After each improved parameter set is found, write it to answer.json.
  4. Run python validate_answer.py if available.
  5. Submit only after confirming that answer.json has changed.

任务要求

智能体拿到地下水监测井的读数，必须推断出一个隐藏的污染源。任务说明要求解题者 "infer a finite-duration rectangular-region contaminant source from public monitoring-well readings"（根据公开的监测井读数，推断一个持续时间有限的矩形区域污染源）。它把 C0 定义为 "effective source concentration/intensity, in mg/L"（有效源浓度/强度，单位 mg/L）。它给出了控制方程 R*dC/dt = div(D grad C) - v dot grad C - lambda*C + source。这就是对流–弥散方程（ADE），即描述溶解物质在地下水中流动和扩散的教科书模型。

README 要求 "construct the groundwater solute transport equation, build an ADE/AdePy or equivalent forward approximation"（建立地下水溶质运移方程，构建 ADE/AdePy 或等价的正演近似）。它还说评分器将 "Use a hidden Borden-ADE region-source forward model"（使用一个隐藏的 Borden-ADE 区域源正演模型）。正演模型根据给定的污染源预测井的读数。类别：科学问题与机器学习。

问题出在哪里

评分器的正演模型使用了没有写明、不符合物理的约定。 这个隐藏模型：

  • 给 225 个脉冲中的每一个赋予幅值 C0·q·1000/225，把质量速率（mg/d）当作质量来用；
  • 不使用孔隙度（土壤体积中容纳水的比例）；
  • 无论 duration 是多少，都给出相同的总质量；
  • 把 mg/m³ 当作 mg/L 报告；
  • 在 nz=1 时，把源平面放在 z_center − half_length_z，而不是盒子中心（这看起来是 linspace(num=1) 造成的无意结果）。

文档给出了各个组成部分，但没有说明它们如何组合。public_problem_config.json 列出了 q（q_source_m3_per_day）、一个 1000 的系数（fallback_source_scale_factor）、一个由子点组成的 5×5×1 网格及 9 个释放步，并注明评分器会叠加点源响应。它没有给出每个脉冲的归一化方式、孔隙度的缺失、与持续时间无关的质量、单位的解读方式，以及由此得到的平面位置。在真实污染源处，在 24 个高于 0.01 mg/L 的公开读数上，教科书 ADE 模型与评分器模型相差 10.9× 到 323×（中位数 33×）。差别来自真实污染源处约为 duration/(1000·n) ≈ 8.5 的幅值系数，加上平面偏移。然而公开数据无法区分这些约定。教科书模型和评分器的约定对公开数据拟合得一样好（两者的对数残差 RMS 都是 0.0079）。

  • 原始评分器上的例子：诚实的教科书 ADE 拟合得 7.03 分。基线以每个参数取值范围的中点作答，得 7.01 分。使用评分器精确约定的同一个最小二乘拟合得 31.2 分。除源平面外都采用评分器约定（源平面放在 z_center，即自然的理解）得 12.9 分。所以仅平面位置一项就损失约 18 分。

原始结果没有定义满分 100 的分数（报告上的不一致）。 真实污染源的原始结果（换算到 0–100 之前）是 109。任务没有分数刻度，因此 score_0_100 没有定义，原始结果按 0–109 报告。没有任何已记录的提交达到 100 的原始结果：我们基于公开数据的最佳拟合达到 31.2，一次第三方 Claude Opus 5.5 运行中的最佳提交达到 60.10（见下文）。所以缺少上限并没有截断任何已记录的分数；它只是让结果停留在 0–109 的刻度上。

经检查是正确的：智能体的工作文件中没有 scoring/ 目录，也没有隐藏文件。

影响有多大

对于用一种教科书模型变体对公开数据做一次性最小二乘拟合的情形，在 0–109 的原始刻度上约差 24 分（7.0 对 31.2）。其他教科书变体没有测试。

对于反复提交的智能体，影响更小，其大小没有测量。评分器的逐测试输出以 CASE feedback_… 行的形式包含隐藏井和未来读数的 rRMSE，因此智能体可以朝隐藏约定调整。在原始评分器上的一次第三方 Claude Opus 5.5 运行中（4 小时内 36 次提交），最佳提交 agent-23 把自己的模型描述为教科书点源 ADE 解，原始结果为 60.10，隐藏井 rRMSE 为 0.223，未来读数 rRMSE 为 0.101（evidence/runs/opus55-rollouts-meta/result/meta/opus-16x4h-1009-0036-w1/borden_source_inversion/final_result.json 和 submissions/agent-23/test_output.txt）。我们采用评分器约定的拟合分别为 0.552 和 0.200。本任务已发布的 12 小时结果中，三个模型分别为 48.4、38.5 和 38.2，另外两个为 8.0 和 15.1（evidence/impact/leaderboard_12h.json）。

修复

修复版只改动智能体的工作镜像和任务 JSON。答案、评分器和评分器镜像都没有改变。

  • 工作镜像新增 forward_model.py。这就是评分器的正演模型，函数体逐字节相同，只替换了 2 行的头部注释。
  • README 新增一节，精确说明约定：子点和 z_center − half_length_z 平面、释放时间偏移、脉冲幅值、不使用孔隙度、与持续时间无关、单位按报告值解读。同一节也插入到 work.agent_query 中。一次修订（2026-10-12）还在文件列表、评分步骤和规则中说明 forward_model.py 是评分器模型的精确副本，可以自由使用；最初发布的修复版任务说明仍把该模型称为"隐藏"的，并在没有这一说明的情况下禁止阅读隐藏的评分文件。在最初和修订后的修复版工作目录中为同样七个测试提交评分，结果逐字节相同（evidence/runs/borden_source_inversion-v2-paired-r3）。
  • task.json.in 新增 judge.rescale = {"kind": "linear", "lower": 0, "upper": 109}。这设定了分数刻度：0 对应 0，109 对应 100。高于 100 的结果仍保持其先后顺序，而不是在上限处并列。

我们如何检查

  • 原始评分器。 所有测试提交都在原始公开镜像上运行，该镜像按摘要固定，修复版中未改动。每个提交都以 --network none 运行原始评分命令，分别针对原版和修复版的工作目录。
  • 独立的正演模型。 一个独立实现（5×5×1 子点、9 个脉冲、高斯核）从隐藏的真实污染源重现了全部 656 个无噪声答案读数（用 evidence/scripts/borden_source_inversion/forward_check.py 重新运行）。评分器自己的模型在评分器镜像中运行，与存储的读数相对误差在 8.9e-13 以内。
  • 诚实解法实验。 这些实验只在公开的含噪声、截尾数据上使用多起点有界最小二乘（60–80 个起点）。一次使用根据文档构建的教科书 ADE 模型，另一次使用评分器的精确约定。原始 evaluate.py 以原始参数为每个拟合得到的 answer.json 评分（本地 Python；numpy 1.24.4、scipy 1.10.1、pandas 2.0.3）。
  • 可重复性。 原始评分器与修复版评分器的并排对照测试重复了三次。没有任何测试提交的判定发生变化（见 data/paired-repeatability.md）。

局限

  • 我们没有运行任何 AI 模型。并排对照测试使用的是我们编写的测试提交和拟合。原始评分器上的一次第三方 Claude Opus 5.5 运行经过阅读，但没有重新评分（对同一答案，原始结果在两个评分器下完全相同）；在 36 个提交中，其最佳原始分从 7.01 升到 60.10，而评分器在每次提交后都会报告其在隐藏监测井上的误差。智能体如何利用这些反馈没有核实，这次运行也没有检验修复。
  • 数据对这个反问题的约束仍然很弱。使用精确模型的最佳公开数据拟合达到原始结果 31.2（28.6 分，满分 100）。修复去掉的是隐藏约定带来的扣分，而不是问题本身的难度。
  • C0 仍是一种不符合物理的约定下的 "effective intensity"（有效强度）。修复版把它写进文档而不是修正它，因为修正物理需要重新生成答案。
  • 只使用了一种拟合方法（多起点最小二乘、log/hinge 损失、一次带种子的 60 或 80 个起点的运行）和一种教科书模型变体。24 分的差距针对的是该变体。
  • 任务说明说参数 "must stay within"（必须保持在）取值范围内，但原始评分器并没有直接拒绝越界的测试提交（原始结果 4，封顶 15）。这一点没有改变。
  • 隐藏文件检查只列出了 /home/workspace 中的工作文件。
  • 评分器从计分目录导入自己的模型副本（hidden_forward_model.py），而不是工作目录中的 forward_model.py，因此修改随附 forward_model.py 的提交无法改变自己的分数。这一点由评分器代码推出；没有对这样的提交评分。
