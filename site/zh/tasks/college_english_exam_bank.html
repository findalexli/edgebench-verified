摘要任务说明如何评分我们的发现文件

摘要

任务
为一个大学英语题库生成 22 个文件：五套试卷、答案、评分指南和两张电子表格。由一个 AI 模型按 12 条评分规则对它们评分。
问题所在
如果 AI 模型的回答遗漏了某条规则，评分器代码会让这条规则保持满分，并仍报告结果有效；一份空的评估得 100 分。每条规则从满分开始，按发现的错误扣分；一条被打 0 分但没有列出任何错误的规则，也会得到满分。模型遗漏规则的频率未知。
影响有多大
使分数最多提高被遗漏规则的分值；一份空的评估得 100 分。只要 AI 模型的评估不完整，任何提交都可能受影响。
我们的处理
已修复，发布新版本：不完整或自相矛盾的评估会被重新请求，否则报告为评分失败，而不是按满分计算。只为最后一个完整的评估块评分。如果它未通过检查，评分器会重新请求，而不是为更早的草稿评分。只有当之后的每个块都被截断或无法读取时，才使用更早的块。完整的评估得分与之前完全相同。
问题类别
评分逻辑错误，事实性错误
验证状态
v2.2 经三次结果相同的并排对照运行验证，在 29 份回答上比较原始、v2.1 和 v2.2 评分器（college_english_exam_bank-v2-paired-fix3、-fix3-rep2、-fix3-rep3；台账均为 exit=0；每次运行都用修复包自带的 materialize.sh 生成修复包）。模型回答是固定的替身输出，没有调用任何 AI 模型。Lean 模型针对 v2.1，不涵盖 v2.2 的块选取和十进制字符串读取。
形式化检验
在 Lean 4 中已证明。修复版评分器从不对遗漏了某条规则的评估计分，对它接受的每份评估给出与原版完全相同的总分，且从不给记录了扣分的规则满分。证明在这一修复的第一个版本中发现了三处漏洞，对真实代码的探查又发现了第四处；修复随后进行了修订。模型针对的是 v2.1（`87f0e340…`），而不是当前的 v2.2（`a0af4360…`）。 局限：只对 v2.1 建模；不涵盖 v2.2 的 JSON 块选取和对十进制字符串规则得分的读取。文本字段被简化为是/否；只涵盖扣分式规则（这里全部 12 条都是）；证明从已解析的评估开始。

任务要求

任务告诉解题者 "Read the complete task instructions in /home/workspace/task_instruction.md"（阅读完整的任务说明）。这些说明要求提交 22 项交付物：五套试卷（A 到 E）的 Word 和 PDF 文件、答案和评分指南、一份命题蓝图工作簿，以及一份各套试卷间重复率的工作簿。一个 AI 评分智能体（大语言模型）按照 rubrics.json 为作品打分。该文件有 12 条规则（R001 到 R012），总计 100 分。每条规则都是 deductive（扣分制）：从满分开始，发现问题就扣分。评分器的提示词要求评分模型严格以 rules 数组作为评分清单，不得增加、删除或合并规则。评分器对账步骤的文档字符串写着 "Force result coverage/order/max_score to match rubrics.json"（强制结果的覆盖范围、顺序和最高分与 rubrics.json 一致）。类别：专业知识工作。

问题出在哪里

被漏掉的规则得满分。 当评分模型的 JSON 回答中缺少某条规则的行时，对账步骤找不到任何已记录的扣分。由于每条规则都是扣分制，该规则保留其全部最高分。评分器写下理由 "Missing deductive detail scores; unreported deduction triggers treated as not triggered."（缺少扣分明细；未报告的扣分触发项视为未触发。）并报告 grader_status: ok、valid: true。

自相矛盾的行得满分。 情形 I 是这样一行：它自身的 score 为 0，但它的各检查点都报告没有扣分。原始对账步骤相信检查点，给该规则满分（15.0 而不是 0）。

何时发生。 这个问题需要评分模型返回能够解析、但缺少部分规则行的 JSON。一个例子是对一份 22 个文件的大型提交所做的评估被截断或中途放弃。评分器的提示词本身就预料到模型可能用尽时间或上下文。解题者有可能导致这种遗漏，但这一点没有得到证实。错误出在任务自带的固定后处理代码中，当模型输出不完整时，它会放行而不是报错。

影响有多大

分数最多可以抬高被漏掉规则的分值；一份空的评估得 100 分。对本任务而言，这一错误只会抬高分数，因为其评分细则中没有加分制规则（从零开始的规则，那种规则会反过来压低分数）。只要评分模型返回不完整的评估，任何提交都可能受到影响。

修复

修复版只改动 /home/workspace/scoring/grade_with_codex.py：

  • 它拒绝不完整、重复、未知或非数值的分数列表。如果一行有完整的数值检查点列表，它可以不给规则级分数，原版对这种情况的评分是正确的。在这样的行上，写成普通十进制字符串的规则分数（例如 "11"）按其数值读取；布尔值和其他字符串仍被拒绝。
  • 它拒绝这样的评估：某个扣分制行报告了扣分（其自身分数低于最高分，或某个检查点为正），却仍会按满分计分，如情形 I。为作出判断，它在归一化后的行上运行原始对账步骤，因此它检查的正是产生分数的那些数据。
  • 不完整的评估变为评分失败（valid: false，0 分），这是原始评分器本来就用于评分端故障的通道。EdgeBench 的评测框架把它当作该提交的 0 分来排序（score_first 不读取 valid）；该次运行保留其另一份最佳提交。我们没有选择只把缺失的规则记为零分，因为那样会悄悄低估一份其余部分完整的回答。
  • 与原版一样，由模型输出中最后一个带 scores 的 JSON 块决定结果。如果这个块能够解析却未通过上述检查，修复版不会改为给更早的块评分（那可能是模型自查之前的草稿），而是把这次输出视为不完整。只有当最后一个块被截断或无法解析时，它才退回到更早的块。
  • 由于评测框架不会重试，修复版在放弃之前会再次请求评分模型。它最多调用 1 + SEBENCH_CODEX_ASSESSMENT_RETRIES 次（该变量默认为 1，即 2 次调用），全部在原有的时间预算之内。

评分细则、参考附件和工作镜像都没有改变。task.json.in 中只改动 judge.image_tag。

"–" 表示评分失败：评分器报告 valid: false，分数为 0。EdgeBench 的 score_first 选取规则不读取 valid，把它按 0 分排序，因而它永远不可能胜过一份已评分的提交。评测框架使用 score_first 选取规则：该次运行保留得分最高的提交。在这一规则下，原版会选中被抬高的那一轮（C 为 100，D 为 81，I 为 15），而不是诚实的那一轮。修复版选中诚实的那一轮（77、77、0）。

分数是否可比？ 对于完整且内部一致的评估（A、B、F、L 行），原版和修复版给出相同的分数。这些分数来自逐字节相同的结构化结果和一次模型调用。当评分模型漏掉、重复或捏造一条规则时，分数不可比。当它返回的某一行既无分数也无完整的检查点列表，或者某个扣分制行报告了扣分却会按满分计分时，分数也不可比。当输出以一个未通过这些检查、且前面还有更早块的 scores 块结尾时（N、NZ），以及当规则分数是布尔值、不是普通十进制数的字符串，或出现在没有完整检查点列表的行上的十进制字符串时，分数也不同。原版在前面几种情况下填入满分，并为未通过检查的最后一个块评分。对最后一类行，原版根据其检查点或规则分数给出了正确的分数（QC：77），因此在这类情况下，如果再次请求无济于事，修复版可能把一个正确的分数变成评分失败。修复版会再次请求，仍不完整则报告评分失败。

我们如何检查

  • 原始评分器，来自按摘要固定的公开镜像。 原始的 main() 以 --network none --memory 2g --cpus 1 端到端运行。只有 codex 可执行文件被替换为一个输出固定模型回答的桩程序。没有使用任何模型 API 或凭据。固定回答根据原始的 rubrics.json 生成，包括正确的回答、针对已知差作品的回答，以及展示问题的回答（漏掉规则、空的分数列表、格式错误的行）。修复版的运行在修复版镜像中使用相同的 eval_cmd。
  • 评测框架检查。 阅读了 EdgeBench 对 valid: false 的处理（sforge/harness/grading.py、selection.py，版本 6e4e5f4），并离线用它对保存的结果进行评分和选取。
  • 可重复性。 原始评分器与修复版评分器的并排对照运行重复了三次。没有任何回答的结果发生变化（见 data/paired-repeatability.md）。这些重复使用的是最初修复版。与修订后修复版的并排对照运行也做了三次（evidence/runs/college_english_exam_bank-v2-paired-fix2、-fix2-rep2、-fix2-rep3）；除计时字段外，三次的评分结果（graded.json）完全相同。与第二次修订（v2.2）的并排对照运行同样做了三次（evidence/runs/college_english_exam_bank-v2-paired-fix3、-fix3-rep2、-fix3-rep3）；每次都先由修复包自带的 materialize.sh 从固定镜像重新生成 v2.2 评分器，再构建镜像，三次的 graded.json 和 graded.md 逐字节相同。
  • 形式化检查。 一个关于归一化、对账步骤和两个修复版的 Lean 4 模型（evidence/formal/notes/college_english_exam_bank.md）证明，对修订后的修复版和每一份已解析的评估：被接受的评估恰好得到原始分数；漏掉一条规则的评估是评分失败；而一个其行报告了扣分的扣分制规则永远不会得满分。同一模型还表明，最初修复版在上述四种行中给了满分。在模型中，文本字段被简化为是/否的事实；最后一项结果不依赖于这种简化，因为检查使用与计分相同的函数。该模型从已解析的行开始，因此不涵盖解析的是哪个 JSON 块，也不涵盖十进制字符串规则分数的读取（两者都在真实代码上测试过；见上文第二次修订）。

局限

  • 没有运行任何 AI 解题者。影响只在我们编写的固定回答和反例上展示。
  • 没有使用在线的评分模型。真实模型多久会漏掉行，以及过去是否有 EdgeBench 分数被抬高，都没有测量。这个问题本身并不是过去分数被抬高的证据。
  • 没有为任何真实的 22 个文件的提交评分。固定回答不读取提交内容。
  • 评测框架的 judge_server 没有在线运行。
  • 当一次模型输出包含多个 JSON 块时，原始评分器和修复版都由最后一个 scores 块决定结果。如果这个块未通过修复版的检查，即使更早的块能够通过，修复版也会再次请求（N、NZ）。如果更早的块是诚实的、而第二次回答仍不完整，这会让该提交失去分数；草稿无法与最终回答区分，因此不为它评分。该镜像中的 codex exec 输出是否会包含多个块，没有测量。与原版一样，围栏代码块优先于无围栏的 JSON。
  • 布尔值或非数字字符串形式的规则分数，以及没有检查点的行上的十进制字符串，在修复版中是评分失败，而原版对这些行的评分是正确的（QC、QD、QF）。真实模型多久写出这样的行，没有测量。
  • 在生产环境中，再次请求可能产生额外的付费评分调用。第二次尝试通常是否完整，尚不清楚。一个持续返回不完整输出的模型，仍然无法为该提交给出测量结果。
  • AI 评分器的其他风险（提示词注入、评分波动）不在范围内。
