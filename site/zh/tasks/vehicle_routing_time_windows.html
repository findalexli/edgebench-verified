摘要任务说明如何评分我们的发现文件

摘要

任务
加速并改进一个 C++ 程序，它为载重有限的车辆规划配送路线，且每个客户都必须在一个时间窗口内被访问。
问题所在
在文档所述的限制之内没有计分问题；使用原始的头文件和编译选项时，舍入从不改变判定结果。附带说明：检查器是用提交的头文件和 Makefile 构建的，因此修改它们也会改变检查器；每个实例有 60 秒，但全部 56 个实例必须在 20 分钟内完成；56 个公开用例权重相同；成本恰好相差 0.05 时可能判为失败。
影响有多大
对一个自行报告成本、并为每个实例预留约 20 秒的程序，没有影响。用满 60 秒会使分数上限接近 37（计算所得）。修改头文件或编译选项的情况未经测试。
我们的处理
保留（附说明）：修改距离头文件或编译器选项也会改变检查器；56 个公开用例权重相同；应精确报告计算出的成本；每个实例预留约 20 秒。

Read README.md, then optimize the C++17 CVRPTW solver. Modify only src/, include/, and Makefile. Preserve the cvrptw_solver binary name and CLI: ./cvrptw_solver <input.txt> <output.txt> <time_budget_sec>. Do not read hidden instances, internal judge files, BKS tables, reference solutions, or evaluator internals. Hidden judge submissions have a 20-minute total wall-clock budget; keep the solver efficient.

import csv, json, os, re, subprocess, time, traceback
from pathlib import Path

ROOT = Path('/home/workspace/task_cvrptw_905da6dd')
TOTAL_JUDGE_TIMEOUT_SEC = 20 * 60
COMPILE_TIMEOUT_SEC = 300
PER_INSTANCE_BUDGET_SEC = 60
VERIFIER_TIMEOUT_SEC = 30
DEADLINE_GRACE_SEC = 5

started = time.monotonic()
deadline = started + TOTAL_JUDGE_TIMEOUT_SEC
compile_output = ''
details = []
metrics = {
    'judge_time_limit_sec': TOTAL_JUDGE_TIMEOUT_SEC,
    'per_instance_budget_sec': PER_INSTANCE_BUDGET_SEC,
    'compile_timeout_sec': COMPILE_TIMEOUT_SEC,
    'score': 0.0,
    'compile_returncode': None,
    'cases': 0,
    'timeout_count': 0,
    'no_pass_count': 0,
    'judge_time_exceeded': False,
    'compile_timed_out': False,
}


def remaining() -> float:
    return deadline - time.monotonic()


def safe_text(x) -> str:
    if x is None:
        return ''
    if isinstance(x, bytes):
        return x.decode(errors='replace')
    return str(x)


def add_detail(name: str, status: str, score: float = 0.0, message: str = '', **extra) -> None:
    item = {'name': name, 'status': status, 'score': float(score), 'message': (message or '')[-1000:]}
    item.update(extra)
    details.append(item)


def compute(nv, td, bnv, btd):
    gap_nv = max(0, nv - bnv)
    gap_td = max(0.0, (td - btd) / btd * 100.0) if btd > 0 else 0.0
    s = max(0.0, 100.0 - 30.0 * gap_nv - 0.5 * gap_td)
    if nv < bnv:
        s += 30.0 * (bnv - nv)
    if nv <= bnv and td < btd:
        s += min(30.0, (btd - td) / btd * 100.0)
    return min(s, 160.0)


def load_bks():
    bks = {}
    for bp in [ROOT / 'internal/cases/bks_snapshot.csv']:
        if bp.exists():
            with open(bp, newline='') as f:
                for row in csv.DictReader(f):
                    bks[row['name']] = (int(row['nv']), float(row['td']))
    return bks


def case_files():
    case_dir = ROOT / 'internal/cases/raw'
    return sorted(case_dir.glob('*.txt'))[:56] if case_dir.exists() else []


def emit(valid: bool, score: float, summary: str):
    passed = sum(1 for d in details if d.get('status') == 'PASSED')
    failed = sum(1 for d in details if d.get('status') == 'FAILED')
    errors = sum(1 for d in details if d.get('status') == 'ERROR')
    total = len(details) or 1
    metrics['score'] = float(score)
    metrics['cases'] = metrics.get('cases') or len([d for d in details if d.get('name') != 'compile'])
    metrics['timeout_count'] = sum(1 for d in details if d.get('reason') in ('solver_timeout', 'judge_time_limit', 'verifier_timeout'))
    metrics['no_pass_count'] = failed
    metrics['runtime_seconds'] = time.monotonic() - started
    if metrics['timeout_count']:
        metrics['judge_time_exceeded'] = any(d.get('reason') == 'judge_time_limit' for d in details)
    report = {
        'valid': valid,
        'score': float(score),
        'pass_rate': passed / total if total else 0.0,
        'total_tests': total,
        'passed': passed,
        'failed': failed,
        'errors': errors,
        'summary': summary,
        'details': details[:100],
        'metrics': metrics,
    }
    print('>>>>> Start Structured Result')
    print(json.dumps(report, ensure_ascii=False))
    print('>>>>> End Structured Result')


try:
    bks = load_bks()
    cases = case_files()
    metrics['cases'] = len(cases)

    compile_timeout = max(1, min(COMPILE_TIMEOUT_SEC, int(remaining() - DEADLINE_GRACE_SEC)))
    if compile_timeout <= 0:
        for inp in cases or [Path('compile')]:
            add_detail(inp.stem, 'ERROR', 0.0, 'judge global time limit reached before compilation', reason='judge_time_limit')
        emit(False, 0.0, f'Judge timed out before compilation: 0 passed, {len(details)} timed out/no result')
    else:
        try:
            proc = subprocess.run(
                ['bash', '-lc', 'rm -f cvrptw_solver tools/verify && make -j4'],
                text=True,
                capture_output=True,
                timeout=compile_timeout,
            )
            compile_output = (proc.stdout or '') + (proc.stderr or '')
            metrics['compile_returncode'] = proc.returncode
            compiled = proc.returncode == 0 and Path('cvrptw_solver').exists()
        except subprocess.TimeoutExpired as ex:
            compile_output = safe_text(ex.stdout) + safe_text(ex.stderr) + '\nCOMPILE_TIMEOUT'
            metrics['compile_returncode'] = -9
            metrics['compile_timed_out'] = True
            compiled = False

        print(compile_output, end='')

        if not compiled:
            status = 'ERROR' if metrics['compile_timed_out'] else 'FAILED'
            reason = 'compile_timeout' if metrics['compile_timed_out'] else 'compile_failed'
            msg = compile_output[-1000:] or reason
            if cases:
                for inp in cases:
                    add_detail(inp.stem, status, 0.0, msg, reason=reason)
            else:
                add_detail('compile', status, 0.0, msg, reason=reason)
            emit(False, 0.0, f'Compilation did not pass ({reason}); score=0. Timeouts: {metrics["compile_timed_out"]}')
        else:
            bks = bks or {}
            score_sum = 0.0
            for idx, inp in enumerate(cases):
                name = inp.stem
                rem = remaining()
                if rem <= DEADLINE_GRACE_SEC + 1:
                    add_detail(name, 'ERROR', 0.0, 'judge global time limit reached before this instance could finish', reason='judge_time_limit')
                    continue

                budget = min(PER_INSTANCE_BUDGET_SEC, max(1, int(rem - DEADLINE_GRACE_SEC - 1)))
                out = Path(f'out_{name}.sol')
                try:
                    out.unlink(missing_ok=True)
                except OSError:
                    pass

                try:
                    run = subprocess.run(
                        ['./cvrptw_solver', str(inp), str(out), str(budget)],
                        text=True,
                        capture_output=True,
                        timeout=budget + DEADLINE_GRACE_SEC,
                    )
                    run_txt = (run.stdout or '') + (run.stderr or '')
                    solver_timed_out = False
                except subprocess.TimeoutExpired as ex:
                    run = None
                    run_txt = safe_text(ex.stdout) + safe_text(ex.stderr) + '\nSOLVER_TIMEOUT'
                    solver_timed_out = True

                if solver_timed_out:
                    add_detail(name, 'ERROR', 0.0, run_txt, reason='solver_timeout', budget_sec=budget)
                    continue
                if run is None or run.returncode != 0:
                    rc = getattr(run, 'returncode', 'unknown')
                    add_detail(name, 'FAILED', 0.0, f'solver exited without a passing solution: exit_code={rc}\n{run_txt}', reason='no_pass', budget_sec=budget)
                    continue
                if not out.exists():
                    add_detail(name, 'FAILED', 0.0, 'solver produced no output file', reason='no_pass', budget_sec=budget)
                    continue

                v_rem = remaining()
                if v_rem <= 2:
                    add_detail(name, 'ERROR', 0.0, 'judge global time limit reached before verification', reason='judge_time_limit', budget_sec=budget)
                    continue
                v_timeout = max(1, min(VERIFIER_TIMEOUT_SEC, int(v_rem - 1)))
                try:
                    ver = subprocess.run(
                        ['./tools/verify', str(inp), str(out)],
                        text=True,
                        capture_output=True,
                        timeout=v_timeout,
                    )
                    ver_txt = (ver.stdout or '') + (ver.stderr or '')
                    verifier_timed_out = False
                except subprocess.TimeoutExpired as ex:
                    ver = None
                    ver_txt = safe_text(ex.stdout) + safe_text(ex.stderr) + '\nVERIFIER_TIMEOUT'
                    verifier_timed_out = True

                if verifier_timed_out:
                    add_detail(name, 'ERROR', 0.0, ver_txt, reason='verifier_timeout', budget_sec=budget)
                    continue

                feasible = ver is not None and ver.returncode == 0 and 'feasible: true' in (ver.stdout or '')
                nv_m = re.search(r'NV:\s*(\d+)', ver.stdout if ver else '')
                td_m = re.search(r'TD:\s*([0-9.]+)', ver.stdout if ver else '')
                nv = int(nv_m.group(1)) if nv_m else 10**9
                td = float(td_m.group(1)) if td_m else 1e18
                bnv, btd = bks.get(name, (nv, td))
                si = compute(nv, td, bnv, btd) if feasible else 0.0
                score_sum += si
                if feasible:
                    msg = f'feasible; NV={nv}; TD={td}; BKS_NV={bnv}; BKS_TD={btd}; budget_sec={budget}'
                    add_detail(name, 'PASSED', si, msg, reason='passed', budget_sec=budget, NV=nv, TD=td, BKS_NV=bnv, BKS_TD=btd)
                else:
                    msg = (run_txt + '\n' + ver_txt)[-1000:] or 'solution did not pass feasibility/cost verification'
                    add_detail(name, 'FAILED', 0.0, msg, reason='no_pass', budget_sec=budget, NV=nv, TD=td, BKS_NV=bnv, BKS_TD=btd)

            total_cases = len(cases) or 1
            final_score = score_sum / total_cases * 100.0
            pass_cnt = sum(1 for d in details if d.get('status') == 'PASSED')
            fail_cnt = sum(1 for d in details if d.get('status') == 'FAILED')
            timeout_cnt = sum(1 for d in details if d.get('reason') in ('solver_timeout', 'judge_time_limit', 'verifier_timeout'))
            summary = (
                f'Score: {final_score:.6f} over {len(cases)} cases; '
                f'passed={pass_cnt}, no_pass={fail_cnt}, timeout={timeout_cnt}, '
                f'runtime={time.monotonic() - started:.2f}s/{TOTAL_JUDGE_TIMEOUT_SEC}s'
            )
            emit(True, final_score, summary)
except Exception:
    err = traceback.format_exc()
    print(err)
    if not details:
        add_detail('judge_exception', 'ERROR', 0.0, err, reason='judge_exception')
    emit(False, 0.0, 'Judge exception before normal completion; see details')

任务要求

任务要求解题者 "optimize the C++17 CVRPTW solver"（优化该 CVRPTW 求解器），"Modify only src/, include/, and Makefile"（只修改这几个目录和文件），并 "Preserve the cvrptw_solver binary name and CLI"（保留该二进制名称和命令行接口）。CVRPTW 是带时间窗的有容量车辆路径问题：为容量有限的车辆规划路线，使每个客户都在规定的时间窗内被访问。任务 README 描述了把实例分为三组加权，以及每次部署时打乱节点以 "防硬编码答案"。它规定的成本容差为 "≤ 0.05"。类别：组合优化。

我们检查了什么

对于遵守文档所述时限的解题者，没有发现会改变分数的计分问题。有四点需要说明；第三点（触及检查器的求解器改动）的影响没有测量。

1. 小数容差（已检查；不改变分数）。 README 规定了包含端点的 "≤ 0.05" 成本容差。检查器用 binary64（标准双精度浮点数）检验它。

  • 56 个实例中的所有坐标、时间窗和服务时间都是整数。在 282,800 对节点上，任务四舍五入后的 binary64 距离每次都等于精确的整数计算结果（0 处不一致）。因此每个距离和到达时间都恰好是 0.1 的整数倍。
  • 在 20,000 次随机试验中（每次对 120 个十分之一的整数倍求和），binary64 的最大漂移为 1.13e-11。检查器的时间窗检验使用 1e-6 的余量，因此它给出的判定与精确有理数算术的判定完全相同。没有任何可行/不可行的判定依赖于浮点误差。
  • 例子。 在恰好相差 0.05 时，对申报成本的检查表现不一致。真实成本为 12 时，它拒绝申报的 12.05 或 11.95；但真实成本为 4 时，它接受 4.05 和 3.95。
  • 只有当求解器申报的成本恰好偏差 0.05 时，这一点才有影响。一个打印自己求和结果的求解器，与检查器的总和相差约 1e-11 以内。计分使用的距离是检查器自己重新计算的，而不是申报的成本。

2. README 描述了评分器并未实现的计分方式（仅涉及文档）。 README 描述了分三组加权和每次部署时打乱节点，一份内部 README 还描述了用例的打乱副本。评分器在一个固定的、未打乱的测试集上对全部 56 个用例等权平均。分数没有变化。

3. 检查器由提交的头文件和 Makefile 编译而成。 tools/verify.cpp 包含 ../include/types.h。该文件位于解题者可以修改的路径中，它定义了 dist_x10 以及 Node/Instance 结构体。评分器还用提交的 Makefile 运行 make -j4，而随附的 Makefile 用与求解器相同的 CXXFLAGS 构建 tools/verify。因此，一个为了提速、并无作弊意图而修改距离代码、改变 Node 字段类型或改变编译参数（例如加上 -ffast-math）的求解器，也会改变检查器计算可行性和距离的方式。第 1 点中的精确算术结论只对原始头文件和原始编译参数成立。建议的加固措施：在提交代码之外，用评分器自己持有的原始头文件和编译参数构建检查器。

4. 无法在每个实例上都用满 60 秒的时间参数。 求解器以 ./cvrptw_solver <input> <output> <time_budget_sec> 的方式调用。评分器传入 min(60, max(1, int(remaining − 6))) 秒，并在开始 20 分钟后停止一切工作（TOTAL_JUDGE_TIMEOUT_SEC = 20 * 60，PER_INSTANCE_BUDGET_SEC = 60）；来不及开始的实例记 0 分（judge_time_limit）。56 × 60 s = 3,360 s，是 1,200 s 总时限的 2.8 倍。

  • 解题者被告知的内容：任务说明写道 "Hidden judge submissions have a 20-minute total wall-clock budget; keep the solver efficient."（隐藏评测的提交有总的墙钟预算，请保持求解器高效。）README §8 列出 "时间预算（单实例）：60 秒"（即每个实例的时间预算为 60 s）和 "总评测预算上限：20 分钟；每实例最多 60 秒，并受剩余总时限截断"（即总预算 20 分钟；每个实例至多 60 s，并被剩余的总时限截断）。其最后一行用英文重复了这一点。tools/bench.sh 对 100 个客户的实例传入 60 s。因此上限是有文档的，但没有任何文档说明在总时限内每个实例能分到多少秒（1,200 / 56 ≈ 21 s）。
  • 例子。 一个像随时可停（anytime）搜索通常那样、一直运行到所给时间参数用完的求解器，在 56 个实例中只有约 20 个被计分；其余记 0 分。在参考质量（每个实例 100）下，其分数至多为 21 × 100 / 56 = 37.5 分（满分 100；如果构建耗时约一分钟，则为 20 个实例、35.7 分）；即使在每个实例 160 的上限下，也至多为 21 × 160 / 56 = 60 分。一个自行为每个实例预算约 20 s 的求解器，全部 56 个实例都会被计分。
  • 测试框架的时限（eval_timeout 1,200 s）等于评分器自己 20 分钟的截止时间。在这个例子中，评分器在截止时间前约 5 s 完成，因此结果仍会被报告，但这一余量取决于容器启动所需的时间。

随任务发布的说明。 检查器由提交的 include/types.h 和提交的 Makefile 编译而成，因此求解器对距离代码、节点类型或编译参数的改动也会改变检查器；建议的加固措施是用原始头文件和编译参数构建检查器。60 秒的时间参数受 20 分钟总时限的约束：56 个实例各用 60 s 需要 3,360 s，因此用满全部时间参数的求解器只有约 20 个实例被计分；请为每个实例预算约 20 s。分数对全部 56 个实例等权平均，已安装的实例是固定的，其节点没有被打乱（README 中的三组加权和打乱都没有实现）。尽管 README 写的是包含端点的 "≤ 0.05"，与检查器总和恰好相差 0.05 的申报成本仍可能被拒绝；申报计算出的成本即可避免这一点。由于测试集是固定的、公开的 Solomon 集（一个标准基准），实例可以被识别出来，而且存在已发表的参考路线；这是披露和数据污染的问题，不是检查器的缺陷。

影响有多大

  • 容差：对申报自己计算出的成本的求解器没有影响。在申报成本恰好偏差 0.05 的假设情形下，会有一个实例得 0 分，因此影响至多为一个实例的贡献（边界情形见 evidence/scripts/vehicle_routing_time_windows/exact_checks.out）。
  • 关于加权和打乱的文字：分数没有变化。
  • 头文件和编译参数：只影响修改 include/types.h 中距离代码或节点类型、或修改 Makefile 中编译参数的求解器。没有运行这样的情形，因此没有测得分数影响。
  • 时间参数：对于像任务说明和 README §8 所说的那样按 20 分钟总时限做预算的求解器，没有影响。一个在每个实例上都用满 60 秒参数的求解器，会失去 56 个实例中的约 36 个（根据评分器的循环计算得出；没有实际运行）。本任务已记录的五个模型的智能体运行得分为 74.0–90.8 分（满分 100，见 tasks/README.md），高于 21 个实例被计分时 60 分的上限，因此这些运行确实按总时限做了预算。

没有代码改动。上述说明随任务一起发布。

我们如何检查

  • 原始评分器。 我们针对按摘要固定的原始评分器镜像，阅读了原始评测命令（构建、求解、检查、计分）、tools/verify.cpp、include/types.h 和任务 README 的源码。全部 56 条示例路线都通过了原始检查器及调用它的代码，使用的是已安装的 56 行参考表。我们不对不可行性或最优性作任何论断。
  • 独立的精确检查。 一个精确算术程序（exact_checks.py，使用整数和 Fraction 算术）覆盖了全部 56 个已安装实例。它检查了距离是否定义良好、每个实例字段的取值范围、时间窗比较，以及成本容差的边界。
  • 漂移上界。 用 20,000 次随机试验（每次对 120 个十分之一的整数倍求和）给出 binary64 漂移的上界。
  • 这里不适用形式化模型。

局限

  • 没有运行任何 AI 模型或解题者；影响只在我们编写的测试提交和反例上展示。
  • 精确检查使用本地 Python。求解器是在本地用 g++ 9.4（-march=haswell）构建的，而不是在固定的评分器镜像中。
  • 提取的内容中没有已安装的参考（BKS，即已知最优解）CSV；已安装的表记录为 56 行。评分器会给没有参考行的实例记 100 分（bks.get(name, (nv, td))）。早先的审计记录显示，已安装的 56 行表为每个实例都提供了参考值，没有用到回退（Git 标签 earlier-audit-final，evidence/selected/vrptw-all56-native-acceptance.json）；这一点没有重新检查。
  • 时间参数的影响是根据评分器的循环计算得出的；没有运行用满全部时间参数的求解器。
  • 对任务说明的澄清尚未加入任务说明本身，相关文件也不在本仓库中。
  • 关于头文件的说明来自阅读源码；没有构建或评分任何修改了 types.h 的求解器。
