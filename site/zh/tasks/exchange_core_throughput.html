Exchange Core Throughput

已修复 评分逻辑错误（事实性错误） exchange_core_throughput

正确性检查发现不了错误的手续费和丢失的消息，因此有缺陷的引擎也能获得满分。

摘要任务说明如何评分我们的发现文件

摘要

任务
加速一个证券交易所的订单撮合引擎（为买单和卖单配对的软件），使其每秒处理尽可能多的交易，同时不改变其行为。
问题所在
评分器的正确性测试只检查资金总体平衡、订单簿是否一致。两个只改一处的缺陷都能通过：一个向卖方收错手续费，一个不向用户发送成交消息和结果消息。两者都拿到满分，而项目自带的测试能发现这两个缺陷。离线时，原始评分器还会让每份提交都失败，因为缺少一些构建文件。另外，任务没有说明评分器的 CPU 配额：在发布方的 4 个 CPU 下，随附的引擎每秒约处理 100 万笔交易，低于分数刻度的零点（209 万笔），所以得 0 分；在 8 个 CPU 下则得 47 到 76 分。
影响有多大
带这些缺陷的引擎拿到满分，而不是 0 分；各四次运行中，它们得 100 分中的 4.7–24.4 分，正确的引擎得 0–37.5 分，全都在速度噪声范围之内。评分器有 4 个 CPU 时，任何每秒低于约 209 万笔交易的引擎都得 0 分；任务说明自己建议的线程修改，在四次运行中每秒处理 164 万到 209 万笔，得 0–0.02 分。
我们的处理
已修复，发布新版本：测量速度之前，项目自带的 33 个测试必须通过，否则得 0 分；一次计时运行如果在记录速度之后测试失败，现在也得 0 分。修复包补齐了缺失的构建文件，所以可以离线评分。
问题类别
评分逻辑错误（事实性错误）；另涉及：工程与运行环境
验证状态
集成测试门槛已验证：两个只改一处的缺陷从约 2250 降到 0，正常的引擎照常得分，差异在吞吐量噪声范围内；在排行榜设置下（--cpus 4 --memory 8g，3 个作业），v2 以 33 项测试通过门槛；修复包在一台干净的机器上从零重建（materialize-check-g1）。平均值之后 Maven 失败的路径只在一个构造的对照组上测试过。
形式化检验
在 Lean 4 中部分证明。原始的正确性检查只依赖资金总体平衡和最终订单簿，因此无法发现那些不改变最终订单簿的手续费错换或消息丢失（在全部 50 轮中都观察到这一点）。 局限：最终订单簿不变是观察所得，而非证明；修复依赖项目自带的测试，这些测试在此无法证明。

要求智能体做什么

以下是 EdgeBench 的原始任务文本，即 tasks/exchange_core_throughput.json 中的 work.agent_query 字段，来自字节跳动 Seed 团队在 Hugging Face 上发布的 EdgeBench 数据集，采用 CC BY 4.0 许可。文本未作改动，仅从 Markdown 渲染为 HTML；指向任务工作区内文件的链接以纯文本显示。EdgeBench 的评测框架还会附加关于如何提交的标准说明（sforge/harness/evolve_scripts.py），此处未显示。任务说明是 EdgeBench 的原文，在所有语言版本中均以英文显示，未作翻译。

Role

You are a performance engineer optimizing exchange-core, an LMAX Disruptor–based open-source financial matching engine (Java 8, Maven). Your goal is to maximize the throughput (MT/s — millions of transactions per second) of PerfThroughput#testThroughputPeak.

Repository Layout

  • src/main/java/... — engine source (OrderBook, matching service, risk engine, Disruptor wiring, etc.)
  • src/main/resources/ — logging etc.
  • pom.xml — Maven build (Java 1.8 source/target)
  • Tests have been removed from the work container — the judge will re-apply the official throughput test.

Benchmark

The judge runs (with Java 17 runtime, compiled to 1.8 bytecode):

mvn -B test -Dtest=PerfThroughput#testThroughputPeak

The test calls PerformanceConfiguration.throughputPerformanceBuilder().ringBufferSize(32 * 1024).build() — only ringBufferSize is overridden; ME/RE, msgsInGroupLimit and other parameters use the builder defaults (4ME+2RE, msgsInGroupLimit=4096, BUSY_SPIN wait, DirectImpl orderbook, AffinityThreadFactory). You can change these defaults by editing throughputPerformanceBuilder() in PerformanceConfiguration.java. The test uses 100 symbols, 10K accounts, 10K orders, 3M transactions — a multi-symbol peak throughput scenario where thread topology changes (e.g. 4ME+2RE → 2ME+1RE) can have dramatic impact.

The test prints rounds like "<i>. <X.XXX> MT/s" and a final "Average: <Z.ZZZ> MT/s". Higher is better.

Optimization Directions (suggestions)

  • Thread topology: matching engine (ME) / risk engine (RE) thread counts, pinning via CoreWaitStrategy
  • Disruptor wait strategy, ring-buffer size, producer type
  • OrderBook implementation (array-based, naive, direct)
  • Message grouping / batching (message-group parameters)
  • Java GC choice (G1 / ZGC) and heap sizing via MAVEN_OPTS
  • Reduce allocations in hot path

Kimi K2.6 reference: 0.43 → 1.24 MT/s (+185%) by dropping from 4ME+2RE to 2ME+1RE.

Rules

  • Do NOT modify test files (the judge re-applies them)
  • Do NOT change behavior: mvn test must still pass functional assertions
  • You may freely edit src/main/java/**, pom.xml, and add MAVEN_OPTS via a .mvn/jvm.config or .mvn/maven.config file
  • The score is int(round(Average_MT_s * 1000)) (e.g. 1.243 → 1243)
  • CASES_OK = 1 only when mvn test exits 0 AND an MT/s line was parsed

任务要求

智能体要给 exchange-core 提速。exchange-core 是证券交易所的撮合引擎（把买单和卖单配对的软件）。目标是 "maximize the throughput (MT/s — millions of transactions per second) of PerfThroughput#testThroughputPeak"（让这个测试的吞吐量尽量高，单位为每秒百万笔交易）。

规则写道 "Do NOT change behavior: mvn test must still pass functional assertions"（不得改变行为：测试仍必须通过功能断言）。规则还写道 "CASES_OK = 1 only when mvn test exits 0 AND an MT/s line was parsed"（只有测试正常退出、并且解析到吞吐量行，才算通过）。原始结果（换算到 0–100 之前的数值）为 int(round(Average_MT_s * 1000))，按对数刻度（log_max）换算成满分 100 的分数。0 分的参考点是 2090.634594076933，100 分的参考点是 6000。类别：系统与软件工程。

问题出在哪里

有错误的引擎通过了正确性检查，还拿到了分数。吞吐量测试的正确性检查只比较两件事：全局余额必须为零；L2 订单簿（挂单的价格档位）必须一致。测试源码用 // TODO compare events, balances, positions 标出了还没做的比较。我们对随附引擎做了两处看起来很平常的改动，每处只改一个地方，后果如下。

  • feeswap 是一个复制粘贴造成的手续费错误。卖方是 taker（订单立即成交的一方）时，引擎收的是 maker 手续费，不是 taker 手续费。交易所的手续费账簿记下的也是这个错误金额，所以全局余额仍然恰好为零。结果是卖方入账偏多，每笔卖方为 taker 的交易，交易所的手续费收入都少记了。
  • 在 dropevents 中，结果处理阶段不再把命令结果、成交事件、订单缩减事件和拒绝事件转发给用户的结果消费者。API future（调用的返回值）照常完成。

在原始评分器下，两个引擎在全部 50 个检查轮次中都通过了 testThroughputPeak。Maven 以 0 退出，评分器打印 CASE 0000 OK 和 CASES_OK 1。下表是一次运行的结果。

还有一条说明。任务没有写明评分器有多少 CPU，而在 4 个 CPU 下随附引擎得 0 分。任务说明描述了引擎的线程拓扑（"builder defaults (4ME+2RE, msgsInGroupLimit=4096, BUSY_SPIN wait, DirectImpl orderbook, AffinityThreadFactory)"），并说 "thread topology changes (e.g. 4ME+2RE → 2ME+1RE) can have dramatic impact"（线程拓扑的改变可能有巨大影响），但没有写明 CPU 数。在 EdgeBench 的排行榜配置 examples/all-tasks-k8s/experiment.yaml 中（引用见 evidence/impact/edgebench-leaderboard-config.md）（sha256 d9d299794ba946cae8d2b7f68a7879a35bb8565d95e78107edf79802993643be），评分器继承 judge_cpu_limit: 4。这个限制是 CPU 配额。在 --cpus 4 的评分器容器内，nproc 仍报告 8，而 /sys/fs/cgroup/cpu.max 读数为 400000 100000（由 evidence/runs/exchange_core_throughput-cpu4v8-a/run.sh 第 17 行记录；输出文件和镜像摘录一起没有放进仓库）。所以按 nproc 决定线程规模的引擎会以为有 8 个 CPU。

影响有多大

有错误的引擎拿到了全部吞吐量分数，而不是 0 分。每个有错误的引擎在原始评分器上各跑了四次（上面那一次，加上三次并排对照运行）：feeswap 得 7.77–24.40 分，dropevents 得 4.71–15.62 分（满分 100）（原始结果 2,269–2,704 和 2,197–2,465）。未修改的引擎在同批的七次原始评分器运行中（上面的正确测试提交，加上三次并排对照运行的原始评分器一侧）得 0–24.19 分（原始结果 2,008–2,698），所以这些分数都在吞吐量噪声范围内。解题者在优化时只要弄坏了手续费或事件投递、但全局余额仍为零，就会拿到全部分数，而这样的引擎本应得 0 分。

修复

修复版评分器在未修改的计时测试之前，先单独跑一次 Maven，执行项目自带的集成测试 ITFeesExchangeBasic 和 ITExchangeCoreIntegrationRejectionBasic（33 个测试）。只要有一个失败，提交就得 0 分（WA，答案错误）。计时的 Maven 运行没有变。

修复版还改了计时运行的计分方式。Maven 以非零退出时，原始评分器把运行标为 WA，但照样把吞吐量打印成分数（CASE 0000 WA score=<MT/s × 1000> 和 TOTAL_SCORE <MT/s × 1000>），而评测框架不管用例状态，一律按 TOTAL_SCORE 排序（sforge/harness/grading.py 的 extract_score；selection.py 的 _score_first）。修复版在状态不是 OK 时把分数设为 0（repair.patch 中的 if status != "OK": score = 0）。吞吐量从 Average: … MT/s 行解析出来，而测试只在所有轮次都通过检查后才记录这一行（ThroughputTestsModule.java:42-69）；逐轮的行带有日志前缀，匹配不上评分器的行首模式。所以只有 Maven 在记录平均值之后才以非零退出时，才会走到这条路径，例如引擎关闭时出错。规则写道 "mvn test must still pass functional assertions"（测试仍必须通过功能断言）。并排对照中有一组走到了这条路径（shutdownbusy）。它 50 轮全部通过，平均值也记下了，然后引擎在关闭时抛出异常；这只发生在吞吐量配置下，所以集成测试仍然通过。原始评分器打印 CASE 0000 WA score=2939，评测框架把它当作有效提交，得 32.31 分（满分 100）；在修复版下它通过集成测试，评分器打印 WA score=0，得 0 分（原始评分器在第一个作业的两次运行中为 2939 和 2943；修复版在三个作业的全部六次运行中都为 0）。如果在集成测试的配置下关闭也失败（shutdownall），集成测试步骤会先拒绝它。正常的测试提交都没有走到过这条路径。未修改的引擎和 topo21 在全部 18 次修复版计时运行中都是 OK。

修复版还从 Maven Central 预先下载了 30 个缺失的公开文件（surefire、JUnit platform、opentest4j 和 apiguardian 构件），放进镜像的 ~/.m2，所以没有网络也能评分。下表中的原始评分器运行挂载了同样的文件，让原始评分器也能离线运行。"原始镜像，不含新增文件"一行显示的是不挂载这些文件时的原始镜像。

我们如何检查

  • 我们在按摘要固定的原始公开镜像上运行原始评分器。每份提交都在一个新容器中用任务原样的 eval_cmd 运行，参数为 --network none、--cpus 8 和 --memory 6g。
  • 我们用项目自带的集成测试（ITFeesExchangeBasic，5 个测试；ITExchangeCoreIntegrationRejectionBasic，28 个测试）做独立检查，在同一容器中以评分器原样的 Maven 参数运行。
  • 在并排对照运行中，原始评分器和修复版评分器给同样的提交、以及有效和无效的测试提交评分，都用 --network none。我们重复了三次，所有测试提交的判定都没有变化（见 data/paired-repeatability.md）。吞吐量在各次运行之间有波动，但集成测试的判定从来没变过。

局限

  • 我们没有运行任何 AI 模型或解题者。影响只在我们写的测试提交和反例上展示。
  • 在同一种机器上，同一提交的多次运行之间吞吐量最多相差 38%（data/paired-repeatability.md）。在三次并排对照运行中，无论用哪个评分器，未修改的引擎原始结果为 2,008–3,105（满分 100 中的 0–37.52 分；仅看原始评分器为 0–24.19 分）；2,008 和 2,050 低于 0 分参考点（2,090.63），所以正确的引擎也可能得 0 分。上面那一次运行的满分 100 分数，没有排除这种波动的影响。
  • 第二项改动（计时测试的 Maven 运行在打印平均值后失败时记 0 分）只在一个构造的关闭失败上测试过（shutdownbusy，evidence/runs/exchange_core_throughput-v2-paired-shutdownfail），没有在真实解题者的代码上测试过。
  • 这两个集成测试类覆盖手续费、拒绝和事件，但没有覆盖正确引擎必须保持的所有性质，所以有其他类型错误的引擎仍可能通过修复版评分器的测试步骤。
  • 修复版没有把每个用户的余额、持仓或事件流与参考运行比较，用的是随附的集成测试。
  • 我们只测试了两种不正确引擎的改动。
  • 集成测试只在项目非默认的 Maven 配置 it 中运行，不在规则所说的默认 mvn test 中运行；工作镜像里也没有这些测试，所以解题者提交前没法运行它们。修复版用这些测试来落实 "Do NOT change behavior"（不得改变行为）这一规则。
  • 关于 CPU 数的说明只基于一种机器（E2B，8 vCPU Xeon 2.6 GHz）：随附引擎在原始评分器上于 4 个 CPU 下运行 7 次、8 个 CPU 下运行 4 次，2ME+1RE 建议在 4 个 CPU 下运行 4 次、8 个 CPU 下运行 1 次。4 个 CPU 的运行使用 --memory 4g（随附引擎 4 次、建议 1 次）或 --memory 8g（各 3 次）。在 8 个 CPU 下，吞吐量在不同运行和工作节点之间最多相差 36%（3,418–4,638），而且这几次 8 个 CPU 的运行（--memory 4g）比更早的并排对照运行（2,008–3,105，--memory 6g，其他工作节点）更快。
