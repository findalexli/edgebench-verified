Trinity — Jericho Text Adventure

Play the interactive fiction game Trinity by sending commands via an HTTP API and maximize your score.

EdgeBench 如何评分

以下用通俗的话说明评分方式，依据是该任务的定义文件（tasks/trinity_text_adventure.json）和 EdgeBench 评测框架的代码。这里描述的是原始任务；如下文案例所述，修复版可能改动评分器。

游戏服务器
智能体通过 EdgeBench 的游戏服务器玩游戏，服务器的启动命令为：
python /tmp/game_server_app.py --rom /home/roms/trinity.z4
时限
整个评分运行限时 10 分钟（600 秒，eval_timeout）。
提交的内容
原始结果
智能体通过游戏服务器玩的每一局会话，都由游戏本身计分；会话的分数就是原始结果。
原始结果的优劣方向
越高越好（EdgeBench 的默认值；任务未设定方向）。
从原始结果到 0–100 分
直线换算：原始结果为 0 时得 0 分，为 100 时得 100 分，中间的值按线性插值。超出这一范围的结果截断为 0 或 100。 不是有限数的原始结果（例如 inf）不获得 0–100 分。 （rescale.kind = linear）
来源：sforge/harness/score_rescale.py
每次运行保留哪份提交
原始结果最好（最高）的提交。只比较分数，跳过没有分数的提交；分数相同时保留较早的提交（score_first）。
来源：sforge/harness/selection.py
智能体能否联网
否：智能体的环境与网络隔离（internet: false）。
评分机器
EdgeBench 官方排行榜设置中为 4 个 CPU 和 8 GB 内存。该任务没有单独设定，所以采用这一默认值。 设置原文引录。

完整案例，包括测试提交、独立检验和修复。文件路径指向代码仓库中的位置；链接在 GitHub 上打开。案例译自英文原文；如有出入，以英文原文为准。

结论： 保留（附说明）。分数就是游戏自己给出的分数，可以重复，没有发现评分缺陷。说明有两点。计分取最终分数，不取峰值。会话有一些限制，任务文本没有写。

任务要求

任务文本写道 "Play the interactive fiction game Trinity by sending commands via an HTTP API and maximize your score."（通过 HTTP API 发送命令来玩互动小说游戏 Trinity，并使你的分数最大化。）Trinity 是一款文字冒险游戏。任务文本没有规定时间、步数上限或游戏局数。类别：交互式游戏与模拟器。

我们检查了什么

我们没有发现会改变分数的缺陷，检查过的部分如下。

  • 每一步都从 Z-machine（运行该游戏的虚拟机）的内存里读 env.get_score()。会话有四种结束方式，即游戏结束、显式关闭、空闲后关闭（回收），或被更新的会话挤掉（驱逐）。不论哪种，保存的都是该会话的最终分数。一次运行的分数取所有会话最终分数里最高的那个。分数刻度是线性的，从 0（起始分数）到 100，上限就是 Jericho 游戏库给这款游戏设的 max_score（trinity.c:71-73）。任务没有随附初始解法。在主机上回放 610 条命令的通关流程，得 100/100，即 100 分制下的 100 分。
  • 不带种子的 FrotzEnv(rom) 会用库的默认种子 0，所以游戏的随机数与时间无关。我们跑了两个 Trinity 会话，一个是 25 条命令的部分会话，一个是 610 条命令的完整通关（三款 Jericho 游戏共六个会话）。两者在共同的 25 条命令前缀上分数相同（prefix_numeric_equal: true）。命令序列一定，游戏结果就完全确定。

下面两点说明只涉及文档，不改变分数。

  • 保存的是最终分数，不是峰值，而 API 还会返回 peak_score，可能让智能体误会。只有游戏中会丢分时，这一点才有影响。三条随附的轨迹（Anchorhead、Trinity、Tryst）里，最终分数都等于峰值。
  • 测试框架有几条任务文本没提的会话限制。每一步 HTTP 超时 10 s，每次运行最多同时开 3 个会话（新会话会挤掉最旧的），空闲 600 到 660 s 后关闭（空闲检查每 60 s 一次，judge_server.py:156,159）。关闭和驱逐都会保存当前分数，所以分不会丢。但智能体如果在游戏中途停下超过 10 分钟，进行中的游戏就没了，得重新回放。回放花不了多少时间，610 条命令的 Trinity 通关流程，HTTP 回放记录耗时 29.3 s（elapsed_seconds: 29.325236）。

任务随附了这条说明。

  • 分数是最佳的已完成或已关闭会话的最终游戏内分数，以游戏的 max_score（100）为满分。
  • 会话在空闲 600 到 660 s 后关闭，同时至多运行 3 个会话。

影响有多大

两条说明观察到的最大分数影响都是 0。只有依赖 peak_score 的智能体，或在游戏中途停下超过 10 分钟的智能体，才可能受影响。

任务不改，上述说明随任务一起发布。

我们如何检查

  • 我们在固定的测试框架里读了这几部分，即每一步读分数（game_server_app.py）、保存会话和执行限制（judge_server.py）、在 N 个会话里保留最好的那个（selection.py）、有效性检查（grading.py）以及分数刻度（score_rescale.py）。这些副本与按哈希固定的副本逐字节一致。
  • 分数的来源、max_score 和默认种子，都可以在公开的 Jericho 3.3.1 源码包（sdist）里查到。
  • 我们在主机上跑了两个 Trinity 会话（一个 25 条命令的部分会话，一个 610 条命令的完整通关），属于在 Anchorhead、Trinity 和 Tryst 上跑的六个会话。它们跑在一个本地构建的镜像上（built_image_id sha256:a197e54f…），我们没有记下公开评分器镜像的摘要。
  • 这里用不上形式化模型。

局限

  • 没有运行任何 AI 模型或解题者。影响只在通关流程会话上演示过。
  • 我们没有在固定的评分器镜像里跑过游戏。
  • Jericho 的行为依据的是已发布的 3.3.1 源码，我们没有对已安装的文件取哈希核对。
  • 最终分数与峰值分数的差别，没有在会丢分的轨迹上测试过。
  • 可重复性只在 25 条命令的共同前缀上做了比较。
