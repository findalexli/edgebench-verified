SMT Solver

已修复 评分逻辑错误（事实性错误） smt_solver

答案检查器误读了某些有效解，因此有 27 道隐藏题目无法得分。

摘要任务说明如何评分我们的发现文件

摘要

任务
构建一个 SMT 求解器：一个判断一组逻辑约束能否被满足、并在可满足时输出满足它们的取值的程序。
问题所在
检查求解器给出的取值时，评分器按字面文本（例如 "(f x)"）查找函数的值，不管 x 当前代表什么。同一段文本在不同位置表示不同的东西时，没有答案能通过。27 道可满足的隐藏题目因此无法得分；另有 42 道题，评分器会拒绝按任务说明的写法给出的答案。以下只作说明，不属于修复：评分器同时运行 16 个求解器进程。官方排行榜给它 16 个 CPU，每个进程一个；在 CPU 较少（例如 4 个）的评分器上，每个进程分到的更少，一个每道题需要 20 秒计算时间的求解器出现了超时。
影响有多大
一个完美求解器的最高分从 78.61 降到 72.40（6.21 分）。所有求解器都失去这 27 道题；遵循文档格式的求解器还会再失去 42 道。
我们的处理
修复后的检查器在全部 69 个受影响的隐藏文件上接受测试过的有效答案（基础键），并拒绝测试过的错误答案。Lean 的可靠性证明只涵盖检查器一个受限的建模片段，不涵盖每个特性；与按字面文本作键的答案的兼容性，有已记录的例外。
问题类别
评分逻辑错误（事实性错误）；另涉及：任务说明与评分不一致
验证状态
用例集的成对对照已验证；形式化可靠性只涵盖建模的 QF_UF 片段，与实现的对应是论证得出的。
形式化检验
在 Lean 4 中部分证明。在建模的 QF_UF 片段内，对已公布的可满足作用域冲突模式，原始检查器拒绝它的每一个见证。修复后的模型在其覆盖假设下，对基础键见证是可靠且完备的。 局限：一个 sort、一个一元函数、let、=、not 和 and。没有整个评分程序的可靠性证明；与实现的对应是论证并经过差分测试的，不是机器证明的。。

要求智能体做什么

以下是 EdgeBench 的原始任务文本，即 tasks/smt_solver.json 中的 work.agent_query 字段，来自字节跳动 Seed 团队在 Hugging Face 上发布的 EdgeBench 数据集，采用 CC BY 4.0 许可。文本未作改动，仅从 Markdown 渲染为 HTML；指向任务工作区内文件的链接以纯文本显示。EdgeBench 的评测框架还会附加关于如何提交的标准说明（sforge/harness/evolve_scripts.py），此处未显示。任务说明是 EdgeBench 的原文，在所有语言版本中均以英文显示，未作翻译。

Implement an SMT solver from scratch. Read README.md and smtlib_spec.md. Provide build.sh, solve, and src/. The evaluator calls ./solve path/to/input.smt2 and expects unsat or unknown as exactly one line, and sat followed by a JSON model witness that validates the assertions. The benchmark logics include QF_UF, QF_LRA, QF_LIA, and QF_UFLRA. Use the compact benchmarks/ develop set and scripts/evaluate.py for local feedback. Official hidden evaluation uses a 60 second per-case timeout, 16 evaluator workers, perturbation with a private salt, and a 7200 second whole-run wall-clock budget. Do not call external SMT solvers such as z3/cvc5, online services, or hard-code benchmark answers.

结论： 已修复。答案检查器按字面文本查找函数的取值，结果有 27 个可满足的隐藏问题，无论哪个求解器都拿不到分。

任务要求

智能体要写一个 SMT 求解器。这个程序判断一组逻辑约束能否同时满足（"sat"）。能满足的话，还要打印一组满足约束的取值（即一个模型）。求解器必须打印 "sat followed by a JSON model witness that validates the assertions"（sat，后接一个能使各断言成立的 JSON 模型见证）。

随附的 smtlib_spec.md 写道 "Keys are SMT-LIB symbols or canonical ground terms that appear in the assertions"（键是断言中出现的 SMT-LIB 符号或规范的基项）。关于未解释函数（UF，即含义由求解器自己选定的函数），它说取值 "for ground applications needed to evaluate the assertions, such as "(f a)""（针对求值断言所需的基应用给出）。又说 "The evaluator checks every assertion under the witness and enforces congruence"（评测器在见证下检查每条断言，并强制同余）。同余是指输入相同时函数输出也相同。还说 "an invalid or missing model receives 0 for that case"（无效或缺失的模型在该用例上不得分）。预期为 sat 的问题，模型有效才得分。类别：组合优化。

问题出在哪里

隐藏评分器的检查代码只按源文本读 UF 应用的取值，例如 (f x)，不代入 let 绑定（局部名称，例如"让 x 代表 a"）。同一段文本出现在不同的 let 绑定下时，每处出现只能共用一个值。

举个例子，断言为 (distinct a b)、(let ((x a)) (= (f x) a)) 和 (let ((x b)) (= (f x) b))。取 f = 恒等函数时它们可满足。在原始评分器下，结果如下。

  • 按规格的描述使用基项键 (f a) 和 (f b) 时，判定为 invalid_model: missing model value for (f x)。
  • 加上文本键 (f x) 后，判定为 invalid_model: assertion is false。

两处应用读的是同一个键 (f x)，所以什么答案都过不了。

隐藏问题集有 774 个文件（546 个 sat / 228 个 unsat）。

  • 有 27 个 sat 的 QF_UF 文件（15 个 medium、12 个 hard），任何求解器都拿不到分。 这些是拟群（quasigroup）文件，每条断言里都重新绑定 ?v_0 … ?v_n。按检查器的读法，这 27 个文件的公式全是 unsat，真实公式却是 sat。在原始镜像上，QF_UF/79f4ca54c7f5a5f0.smt2 无论用哪种键写法，都拒绝了一个真实的 z3 模型。
  • 另有 42 个隐藏 sat 文件，检查器不接受规格里给出的那种键。 在这些文件上，严格按规格输出基项键的求解器会遭到拒绝，只有文档里没写的文本键约定才行得通。

上面展示的键值缺陷使检查器拒绝正确答案。Lean orig_sound 和 fixed_sound 证明，在建模的单一 sort、一元函数 QF_UF 片段里，检查器接受就意味着公式可满足。它们没有对整个 Python 评分程序、也没有对所有受支持的 SMT-LIB 特性证明这一点。模型与实现的对应关系靠论证和差分测试建立，没有机器证明。另外，原始检查器可能接受一个根本不构成函数的见证。下文的 unused_conflict 让 f 在同一个参数值上取两个值，原始评分器照样接受。

关于评分器 CPU 数另有一条说明，它不属于修复内容。eval_cmd 运行 evaluate.py --timeout 60 --parallel 16，超时按墙钟时间算（proc.communicate(timeout=timeout)，第 690 行），超时得 0 分。四个官方排行榜配置（EdgeBench 提交 6e4e5f4 中的 examples/all-tasks-k8s/experiment*.yaml）都给 smt_solver 设了 judge_cpu_limit: 16，16 个求解器进程各占一个 CPU。如果评分器 CPU 更少，比如配置的默认值 4，每个问题在 60 s 里分到的 CPU 就按比例减少。我们在原始评分器上，用评分器的原样参数和一个替身求解器，在隐藏集的一个 32 题子集（QF_LIA、hard、预期 unsat）上测了这一点。每题需要 20 s CPU 时间的求解器，4 个 CPU 时 32 题全部超时，8 个 CPU 时则能通过（evidence/runs/smt_solver-cpu4v8-a、-b；evidence/runs/smt_solver-v2-paired-cpu、smt_solver-v2-paired-b-cpu、-c-cpu）。任务文本自己也前后矛盾。任务说明写 "16 evaluator workers"，工作镜像里的 smtlib_spec.md:118 却写 "4 evaluator workers"。在官方的 16 个 CPU 下，这两点都不影响评分，所以只作为说明保留。

影响有多大

  • 完美求解器的最高分从 78.61 降到 72.40，少了 6.21 分。15 个拿不到分的 medium 问题占 medium 档的 15/61。
  • 同一段文本有多种含义的那 27 个文件，所有求解器都会丢分。按规格输出基项键的求解器，还会在同一段文本只有一种含义的那 42 个文件上丢分。

修复

修复版只改了 evaluate.py 一个文件。构建检查器时，它对每个属于基应用的答案键求值，把取值登记在"该函数 + 参数*求值后*的值"之下。检查时，检查器先在当前作用域里给 UF 应用的参数求值，再查这张表，查不到才退回原来的文本查找。同余检查覆盖所有表项和每个求值后的应用。解析、扰动、超时和计分都不变。任务 JSON 只改了 judge.image_tag。

分数是否兼容，取决于求解器怎样写键。

  • 答案只用文本键的求解器，修复版分数与原始分数可比，只有一个例外（已在 Lean 中证明）。如果 let 复用了某个已声明常量的名字，修复版检查器可能拒绝它下面的文本键（同一模型改用基项键写就能通过）。774 个隐藏文件里没有一个含这样的 let（evidence/formal/notes/smt_solver.md）。
  • 以下情况分数不可比：
    • 输出基项键的求解器；
    • 在那 27 个多上下文文件上，原始评分器根本无法给分。
  • 如果答案让函数在相同参数值上取两个值，修复版检查器现在会拒绝它。规格里的 "enforces congruence"（强制同余）本来就不允许这种情况。

我们如何检查

  • 我们把构造的问题和真实的隐藏问题都交给原始评分器，用按摘要固定的原始公开镜像和官方参数（--perturb --perturb-salt hidden-sebench）运行。一个打印固定答案的替身求解器代替正确的求解器。评分器也接受了嵌套最深的 sat 文件（括号深度 2621）。
  • 独立检查用的是 z3。z3 是一个广泛使用的 SMT 求解器。我们把检查器的接受条件精确编码，在评分器之外交给 z3 求解。为了验证编码，我们在编码判为 sat 的全部 42 个隐藏文件上把 z3 模型转成答案，原始检查器 42 个全部接受。对全部 774 个隐藏文件的扫描用的是原始的分词规则。z3 确认 69 个 ground 答案全是真实模型，并证明 69 个错误模型答案都不是模型。
  • 我们按任务的分档权重重新算出分数影响。
  • 我们把并排对照运行重复了三次，结论没有变化（data/paired-repeatability.md）。

局限

  • 没有运行任何 AI 模型或求解器。文中的影响只针对我们写的测试提交和反例，也没有估计对排行榜的影响。
  • 答案是替身求解器回放的 z3 模型，不是为该任务写出的完整求解器的输出。
  • "检查器编码拒绝的恰好就是检查器拒绝的"这一说法，依据是一个精确性论证和在原始镜像上的运行，没有经过机器证明。
  • 错误模型测试提交"不是模型"这一点，依赖 z3 4.13.0.0 的判断。每个错误答案只改了一个 UF 取值，所以这些测试提交覆盖不了所有可能的错误模型。
  • 据报告，公开的开发集里有 2 个拿不到分的 sat 问题。这里没有附上对它的扫描输出。
  • 我们没有改写规格文本，其中 "canonical ground terms"（规范的基项）的说法现在与检查器一致了。
  • 我们只深入查了 UF 的取键方式。扰动和预检扫描只做了抽查。超时随评分器 CPU 数变化这一点，是用替身求解器在一个 32 题子集上测的（见上文说明）。
