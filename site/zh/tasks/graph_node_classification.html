摘要任务说明如何评分我们的发现文件

摘要

任务
预测一个图中每个测试节点（网络中的一个点）的类别，按若干准确率指标计分，并对时间和内存使用进行扣分。
问题所在
评分器丢弃不是整数的预测（例如文本或空白），把剩下的预测按顺序与前面的标签配对，并仍将这次运行标记为有效。我们编写的一份测试提交只有一个真实预测、其余都是无效内容，结果每轮只在一个节点上计分，并被算作有效。超出范围的置信度值也经过了检查，是无害的。另外，以整数节点 ID 为键的预测（任务说明允许这样做）匹配不到任何节点：这样的运行得 0 分，却仍被算作有效。
影响有多大
含缺失或非数字预测的提交：增加的随机性可能提高一次运行所保留的最佳分数（一般性证明），但未发现真实求解程序因此获益。以整数节点 ID 为键的提交会失去全部分数；在我们重新评分的真实求解程序提交中，没有一份使用这样的键。
我们的处理
已修复，发布新版本：节点 ID 按文本匹配，因此整数 ID 也能使用；每个测试节点都必须得到一个整数类别，否则这次运行被标记为无效。以字符串节点 ID 为键的诚实提交得分不变，计时噪声（小于 0.03 分）除外；以整数节点 ID 为键的诚实提交原版计 0 分，现在与其以字符串为键的对应提交得分相同。
验证状态
v2.1 经三次并排对照运行验证，在七份提交上比较原始、第一个修复版（v2）和 v2.1 验证器，每次运行分在两台工作机上（graph_node_classification-v2-paired-v21a、-v21b 及其 -rep2、-rep3；台账均为 exit=0；每次运行都用修复包自带的 materialize.sh 生成修复包）。诚实提交的最终分数最多相差 2.9e-4（计时）。Lean 证明针对第一个修复，不涵盖 v2.1 的 str() 键处理和重复键拒绝。
形式化检验
在 Lean 4 中已证明。第一个修复版评分器（v2，`32caddb1…`）接受一个文件当且仅当每个测试节点都有一个整数类别，然后按与原版相同的方式计分。当前的 v2.1（`7b4860ec…`）按 `str()` 匹配键，并拒绝 `str()` 后相同的键，它不在模型范围内：它会为原版计 0 分的整数键文件计分。一个一般性引理表明，保留最佳提交可能把增加的方差转化为期望收益；未发现真实求解程序因此获益。 局限：只对第一个修复（v2，`32caddb1…`）建模；不涵盖 v2.1 的 `str()` 键处理和重复键拒绝。有四个 ASCII 控制字符在 Python 中表现不同；未对大小检查建模。

任务要求

智能体要为图中每个测试节点（网络中的一个点）预测一个类别。接口约定写道："predictions values must be integer class ids … should cover all test nodes of the current split"（预测值必须是整数类别 id……应覆盖当前划分中的所有测试节点），以及 "confidences is optional; if provided, values must be in [0, 1]."（置信度是可选的；如果提供，取值必须在闭区间内。）关于键，它写道："The keys of predictions must be test node IDs, which can be strings or values convertible to strings."（predictions 的键必须是测试节点 ID，可以是字符串或可转换为字符串的值。）测试节点 ID 以整数列表的形式提供给解法。

分数为 overall = 0.4·macro_f1 + 0.3·micro_f1 + 0.2·balanced_accuracy + 0.1·one_minus_ece，减去时间和内存惩罚，再在 10 个划分上取平均。F1 和 balanced accuracy（平衡准确率）是准确率指标。ECE（期望校准误差）衡量置信度与实际准确率的吻合程度。类别：科学问题与机器学习。

问题出在哪里

不完整的预测被当作有效接受。

  • _to_int_labels 会悄悄丢弃 int() 无法转换的预测值，例如 "x"、None 或 NaN。
  • 然后 evaluate() 把答案列表截短到较短列表的长度。
  • judge_eval.py 中的覆盖检查只比较字典的大小，因此仍然通过。

所以一次运行可能只在一个节点上评分，却被报告为 valid: true。严格来说，留下的预测是按顺序与最前面的标签配对的，因此文件前部的一个坏值会让后面的每个预测都错位到错误的节点上。

  • 小例子： 1000 个节点，第一个预测正确，其余都是 "x"。结果：macro_f1 = micro_f1 = 平衡准确率 = 1.0，ECE 为 0。
  • 真实评分器上的例子： 随附的基线，除一个预测外都替换为 "x"。
    • 预期：被拒绝，因为预测不是整数类别 id。
    • 实际：valid: true，每个划分都只在一个节点上评分。在 10 个划分中，对第一个节点的猜测有 2 次正确，overall 为 0.20。这低于这个弱基线诚实作答时的 0.333。

为什么重要：一份违反接口约定的提交，得到的是在错误的节点集合上计算出的有效分数。

以整数节点 ID 为键的完整预测得 0 分，却仍有效。 评分器按答案中的字符串节点 ID（"5"）查找预测，而不转换提交的键，因此以整数 5 为键的预测永远找不到。覆盖检查仍然通过，因为键的数量是对的。在真实评分器上，一个用所给整数 ID 作键的诚实邻居投票解法（neighbor_intkeys）被标为 valid: true，所有质量指标都是 0（overall 0.000000，归一化分数 0），而同样的预测以字符串为键时 overall 为 0.281108。这是对遵循任务说明的善意工作的向下误差。

经检查无害：NaN 或越界的置信度。 _ece() 用 min(1.0, max(0.0, c)) 截断每个置信度。NaN 或负值变为 0，大于 1 的值变为 1。此后分数只取决于截断后的合法值，因此任何越界值都不可能比合法值得分更高。这一点保持不变。

影响有多大

这一问题给分数加入了运气成分。对每个划分，这种单节点赌博的期望值取决于某一个固定节点上的准确率；唯一一次实测的赌博（shrink）overall 为 0.20，低于诚实作答的 0.333（repairs/graph_node_classification-v2/paired/graded.md）。任务保留一次运行中最佳的有效提交（selection: valid_then_score）。一个通用的 Lean 引理表明，在这种取最大值的选取规则下，额外加入一份随机提交永远不会降低所保留分数的期望，而只要它有可能胜过当前最佳，就会提高这一期望（evidence/formal/notes/graph_node_classification.md）。没有展示出任何真实解题者能从中获益。这一部分只影响发送非整数或缺失预测的提交。另外，以整数节点 ID 为键的提交会失去全部分数（变为 0），却仍被算作有效；在我们掌握的 112 次真实解法评分中（见"我们如何检查"），没有任何提交使用这样的键。

修复

修复版只改动 verifier.py 中的 evaluate：

  1. 先用 str() 转换预测和置信度的键，从而按任务说明的允许匹配整数节点 ID。两个转换后字符串相同的键（例如 5 和 "5"）会被拒绝，因为无法确定指的是哪个预测。
  2. 答案中的每个节点 ID 都必须有预测。
  3. 每个预测都严格转换。接受整数、取整数值的有限浮点数（如 3.0）以及十进制整数字符串（如 "3"）。拒绝布尔值、非整数值或非有限的浮点数、非数字字符串、None 以及其他类型。
  4. 答案和预测按节点 ID 配对，不做过滤或截短。

违反上述规则会抛出错误。未改动的运行器和 judge_eval.py 会把它转为它们现有的失败结果（valid: false）。以下内容不变：置信度截断、类别范围之外的整数（仍按错误计）、指标、惩罚、数据、划分和基线。任务 JSON 只改动 judge.image_tag。

我们如何检查

  • 原始评分器。 真实的评分命令（python judge_eval.py）在原始公开镜像中运行，镜像按摘要固定，参数为 --network none。它以随附的基线及其变体运行（NaN、0.0、7.5 和 1.0 的置信度，以及 "shrink" 情形）。
  • 对评分函数的独立检查。 把 verifier.py 当作纯函数，用三种方式测试：逐点探测；20,000 个含 40% 特殊值的随机置信度向量；以及对所有 n ≤ 3 的二分类情形（84 个标签/预测对）的穷举搜索，取值范围是一个 21 点的合法网格加 5 个非法值。随机向量与其截断版本相比有 0 处不一致。穷举搜索找到 0 个非法值胜过最佳合法值的情形。在真实评分器中，全 NaN 与全 0.0 结果相同（overall 0.31144），全 7.5 与全 1.0 结果相同（overall 0.26880）。两者都低于基线自身合法置信度的得分（0.33262）。
  • 原始评分器与修复版评分器的并排对照运行。 通过 TaskSpec 的 eval.sh 完整运行 10 个划分（--network none、4 个 CPU、6 GB），得到上表。重复了三次，判定没有变化（data/paired-repeatability.md）。与修订后修复版（v2.1）的并排对照运行也在全新的工作机上做了三次（evidence/runs/graph_node_classification-v2-paired-v21a、-v21b 及其 -rep2、-rep3）；每次都先由修复包自带的 materialize.sh 从固定镜像重新生成 v2.1 验证器，再构建镜像。
  • 真实解法的运行。 来自第三方 Claude Opus 5.5 运行的 106 份不同提交、共 112 次评分（evidence/runs/opus55-regrade2-graph-a、-b、-c），用原始验证器和最初修复版验证器重新评分。没有任何一次改变有效性，在原版下也没有一次无效；原版的最低分为 0.208，因此没有提交以整数为键。其中两次的 overall 质量略有差别（agent-49：0.876092 对 0.875200；agent-6：0.718849 对 0.715770）；修复版接受了相同的预测，因此这最可能是解法的运行间波动，但没有得到证明。这些评分没有用 v2.1 重做。

局限

  • 影响在我们编写的测试提交和反例上展示。真实解法的提交只用原始验证器和最初修复版验证器重新评分过（见上文），其中没有一份出现这个问题。
  • 只运行了随附的基线、一个弱的诚实邻居投票解法和几个简单的违反约定的变体。没有运行更强的解法。
  • 对 shrink 情形的期望值分析是手工推导的，有一次 10 个划分的运行作为支撑。额外的运气成分如何与"选取一次运行中最佳提交"的规则（selection: valid_then_score）相互作用，只由一个通用引理覆盖（其数值示例假设每个划分的命中率为 1/4）；没有测量。
  • 其他类型的键按其 str() 匹配。像 5.0 这样的浮点数键会变成 "5.0"，与节点 "5" 不匹配，使这次运行无效。这一点没有在真实评分器上运行。
  • 任务说明文本读自评分器镜像中的英文副本和中文源副本，两者在接口约定的句子上一致。没有拉取智能体的工作镜像。
