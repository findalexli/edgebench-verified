摘要任务说明如何评分我们的发现文件

摘要

任务
预测一个图中每个测试节点（网络中的一个点）的类别，按若干准确率指标计分，并对时间和内存使用进行扣分。
问题所在
评分器丢弃不是整数的预测（例如文本或空白），把剩下的预测按顺序与前面的标签配对，并仍将这次运行标记为有效。我们编写的一份测试提交只有一个真实预测、其余都是无效内容，结果每轮只在一个节点上计分，并被算作有效。超出范围的置信度值也经过了检查，是无害的。另外，以整数节点 ID 为键的预测（任务说明允许这样做）匹配不到任何节点：这样的运行得 0 分，却仍被算作有效。
影响有多大
含缺失或非数字预测的提交：增加的随机性可能提高一次运行所保留的最佳分数（一般性证明），但未发现真实求解程序因此获益。以整数节点 ID 为键的提交会失去全部分数；在我们重新评分的真实求解程序提交中，没有一份使用这样的键。
我们的处理
已修复，发布新版本：节点 ID 按文本匹配，因此整数 ID 也能使用；每个测试节点都必须得到一个整数类别，否则这次运行被标记为无效。以字符串节点 ID 为键的正常提交得分不变，计时噪声（小于 0.03 分）除外；以整数节点 ID 为键的正常提交原版计 0 分，现在与其以字符串为键的对应提交得分相同。
问题类别
评分逻辑错误（事实性错误）
验证状态
v2.1 经三次并排对照运行验证，在七份提交上比较原始、第一个修复版（v2）和 v2.1 验证器，每次运行分在两台工作机上（graph_node_classification-v2-paired-v21a、-v21b 及其 -rep2、-rep3；台账均为 exit=0；每次运行都用修复包自带的 materialize.sh 生成修复包）。正常提交的最终分数最多相差 2.9e-4（来自计时）。Lean 证明针对第一个修复，不涵盖 v2.1 的 str() 键处理和重复键拒绝。
形式化检验
在 Lean 4 中已证明。第一个修复版评分器（v2，`32caddb1…`）接受一个文件当且仅当每个测试节点都有一个整数类别，然后按与原版相同的方式计分。当前的 v2.1（`7b4860ec…`）按 `str()` 匹配键，并拒绝 `str()` 后相同的键，它不在模型范围内：它会为原版计 0 分的整数键文件计分。一个一般性引理表明，保留最佳提交可能把增加的方差转化为期望收益；未发现真实求解程序因此获益。 局限：只对第一个修复（v2，`32caddb1…`）建模；不涵盖 v2.1 的 `str()` 键处理和重复键拒绝。有四个 ASCII 控制字符在 Python 中表现不同；未对大小检查建模。

任务要求

智能体要给图中每个测试节点（网络中的一个点）预测一个类别。接口约定写道："predictions values must be integer class ids … should cover all test nodes of the current split"（预测值必须是整数类别 id……应覆盖当前划分中的所有测试节点），以及 "confidences is optional; if provided, values must be in [0, 1]."（置信度可以不提供；如果提供，取值必须在闭区间内。）关于键，它写道："The keys of predictions must be test node IDs, which can be strings or values convertible to strings."（predictions 的键必须是测试节点 ID，可以是字符串或可转换为字符串的值。）测试节点 ID 是以整数列表的形式交给解法的。

分数为 overall = 0.4·macro_f1 + 0.3·micro_f1 + 0.2·balanced_accuracy + 0.1·one_minus_ece，减去时间和内存惩罚，再对 10 个划分取平均。F1 和 balanced accuracy（平衡准确率）是准确率指标。ECE（期望校准误差）衡量置信度与实际准确率吻合得怎样。类别：科学问题与机器学习。

问题出在哪里

不完整的预测被当作有效。

  • _to_int_labels 会悄悄丢掉 int() 转换不了的预测值，例如 "x"、None 或 NaN。
  • 然后 evaluate() 把答案列表截短，与较短的那个列表一样长。
  • judge_eval.py 中的覆盖检查只比较字典的大小，因此仍然通过。

所以一次运行可能只在一个节点上评了分，却报告为 valid: true。更准确地说，留下的预测按顺序与最前面的标签配对，所以文件前部只要有一个坏值，后面的预测就全部错位，对到错误的节点上。

  • 小例子： 1000 个节点，第一个预测正确，其余都是 "x"。结果：macro_f1 = micro_f1 = 平衡准确率 = 1.0，ECE 为 0。
  • 真实评分器上的例子： 随附的基线，除一个预测外都替换为 "x"。
    • 预期：评分器拒绝它，因为预测不是整数类别 id。
    • 实际：valid: true，每个划分都只在一个节点上评分。10 个划分中，对第一个节点的猜测有 2 次猜对，overall 为 0.20。这比这个弱基线完整作答时的 0.333 还低。

结果是，一份违反接口约定的提交，得到了一个在错误节点集合上算出来的有效分数。

用整数节点 ID 作键的完整预测得 0 分，却仍算有效。 评分器用答案中的字符串节点 ID（"5"）去查预测，不转换提交的键，所以以整数 5 为键的预测永远查不到。键的数量是对的，所以覆盖检查照样通过。在真实评分器上，一个普通的邻居投票解法直接用拿到的整数 ID 作键（neighbor_intkeys），被标为 valid: true，所有质量指标都是 0（overall 0.000000，归一化分数 0）；同样的预测换成字符串键，overall 为 0.281108。按任务说明做的提交，在这里被少算了分。

检查后确认无害：NaN 或越界的置信度。 _ece() 用 min(1.0, max(0.0, c)) 截断每个置信度：NaN 或负值变为 0，大于 1 的值变为 1。之后分数只取决于截断后的合法值，所以越界值不可能比合法值得分更高。这一点没有改动。

影响有多大

这个问题给分数掺进了运气。对每个划分，这种单节点赌博的期望值取决于某一个固定节点上的准确率；唯一实测过的一次赌博（shrink）overall 为 0.20，低于完整作答的 0.333（repairs/graph_node_classification-v2/paired/graded.md）。任务保留一次运行中最佳的有效提交（selection: valid_then_score）。一个通用的 Lean 引理表明，在这种取最大值的选取规则下，多加一份随机提交，保留分数的期望永远不会降低；只要它有可能胜过当前最佳，期望就会提高（evidence/formal/notes/graph_node_classification.md）。没有展示出真实解题者能从中得到好处。这一部分只影响给出非整数预测或缺少预测的提交。另外，用整数节点 ID 作键的提交会丢掉全部分数（变为 0），却仍算有效；在我们掌握的 112 次真实解法评分中（见"我们如何检查"），没有提交用这样的键。

修复

修复版只改动 verifier.py 中的 evaluate：

  1. 先用 str() 转换预测和置信度的键，这样就能按任务说明的允许匹配整数节点 ID。如果两个键转换后字符串相同（例如 5 和 "5"），提交会被拒绝，因为无法确定指的是哪个预测。
  2. 答案中的每个节点 ID 都必须有预测。
  3. 每个预测都严格转换。接受整数、取整数值的有限浮点数（如 3.0）和十进制整数字符串（如 "3"）；拒绝布尔值、非整数值或非有限的浮点数、非数字字符串、None 和其他类型。
  4. 答案和预测按节点 ID 配对，不过滤，也不截短。

违反上述规则会抛出错误，未改动的运行器和 judge_eval.py 把它转成现有的失败结果（valid: false）。以下内容不变：置信度截断、类别范围之外的整数（仍算错）、指标、惩罚、数据、划分和基线。任务 JSON 只改了 judge.image_tag。

分数兼容性： 如果提交给每个测试节点都给出一个整数类别 id（int、取整数值的有限浮点数，或十进制整数字符串，不是布尔值），那么除运行间的计时噪声外，它在原版和修复版下得分完全相同。唯一的例外是用 ASCII 分隔符 U+001C 到 U+001F 填充的字符串，例如 "\x1c0"：原始评分器丢掉它，修复版给它评分（形式化说明中的 separator_boundary）。原始评分器用 int() 转换的布尔值和非整数浮点数，在修复版中无效。漏掉测试节点、给某个测试节点非整数值、或者有两个 str() 相同的键，这样的提交在修复版中无效，分数不能与原来的比较。用整数节点 ID 作键的完整提交在两个版本中都有效，但同样不能比较：原版给它 0 分，修复版给它的分数与用字符串作键的同样预测完全相同。

我们如何检查

  • 原始评分器。 真实的评分命令（python judge_eval.py）在按摘要固定的原始公开镜像中运行，参数为 --network none。被评分的是随附的基线及其变体（置信度为 NaN、0.0、7.5 和 1.0，以及 "shrink" 情形）。
  • 对评分函数的独立检查。 我们把 verifier.py 当作纯函数，用三种方式测试：逐点探测；20,000 个含 40% 特殊值的随机置信度向量；对所有 n ≤ 3 的二分类情形（84 个标签/预测对）做穷举搜索，取值是一个 21 点的合法网格加 5 个非法值。随机向量与其截断版本相比，0 处不一致。穷举搜索没有找到非法值胜过最佳合法值的情形（0 个）。在真实评分器中，全 NaN 与全 0.0 结果相同（overall 0.31144），全 7.5 与全 1.0 结果相同（overall 0.26880），两者都低于基线用自己的合法置信度时的得分（0.33262）。
  • 原始评分器与修复版评分器的并排对照运行。 通过 TaskSpec 的 eval.sh 完整运行 10 个划分（--network none、4 个 CPU、6 GB），得到上表。重复了三次，判定都没有变化（data/paired-repeatability.md）。与修订后修复版（v2.1）的并排对照运行也在新的工作机上做了三次（evidence/runs/graph_node_classification-v2-paired-v21a、-v21b 及其 -rep2、-rep3）；每次都先用修复包自带的 materialize.sh 从固定镜像重新生成 v2.1 验证器，再构建镜像。
  • 真实解法的运行。 来自第三方 Claude Opus 5.5 运行的 106 份不同提交、共 112 次评分（evidence/runs/opus55-regrade2-graph-a、-b、-c），我们用原始验证器和最初修复版验证器重新评了分。有效性一次也没有变，在原版下也没有一次无效；原版的最低分为 0.208，可见没有提交用整数作键。其中两次的 overall 质量略有不同（agent-49：0.876092 对 0.875200；agent-6：0.718849 对 0.715770）；修复版接受的是相同的预测，所以最可能是解法自身的运行间波动，但没有得到证明。这些评分没有用 v2.1 重做。

局限

  • 影响在我们写的测试提交和反例上展示。真实解法的提交只用原始验证器和最初修复版验证器重新评过分（见上文），其中没有一份出现这个问题。
  • 只运行了随附的基线、一个较弱的普通邻居投票解法和几个简单的违反约定的变体，没有运行更强的解法。
  • shrink 情形的期望值分析是手工推导的，有一次 10 个划分的运行作为佐证。多出来的运气成分与"每次运行保留最佳提交"的规则（selection: valid_then_score）怎样叠加，只有一个通用引理涉及（其数值示例假设每个划分的命中率为 1/4）；没有测量。
  • 其他类型的键按它的 str() 匹配。像 5.0 这样的浮点数键会变成 "5.0"，对不上节点 "5"，这次运行就无效。这一点没有在真实评分器上运行过。
  • 任务说明文本读自评分器镜像中的英文副本和中文原文副本，两者关于接口约定的句子一致。我们没有拉取智能体的工作镜像。
