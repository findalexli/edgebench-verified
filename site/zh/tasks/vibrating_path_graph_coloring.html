Vibrating Path Graph Coloring

已修复 工程与运行环境 vibrating_path_graph_coloring

在发布方的 4 CPU 评分器上，一个未超出 30 秒时限的解法可能使整份提交没有分数。

摘要任务说明如何评分我们的发现文件

摘要

任务
求解 50 道图着色谜题（为网络中的点着色，使相连的点颜色不同），输出一串点的“hit”序列以及每个点的颜色，使总分尽可能低。
问题所在
评分器同时运行 8 个用例，每个用例的实际时间限制为 30 秒。在发布方的 4 CPU 设置下，每个用例只分到半个 CPU。一个每个用例用 20 秒 CPU 时间的有效解法，因此在 50 个用例中有 48 个超时，而一次超时就会让整份提交没有分数。另外，测试程序只接受两行形式的零 hit 答案，不接受文档所述的三行；零 hit 答案在 37 个用例上已经证明无效，但在其余 13 个用例上，格式问题的影响仍未解决。
影响有多大
在 4 CPU 评分器上，每个用例用约 14 到 30 秒 CPU 时间的解法，可能损失全部分数；按截止时间停止的解法只能用到一半的计算时间。格式不一致在 37 个有证书的用例上影响为零；在其余 13 个用例上的影响仍未解决。
我们的处理
评分器同时运行的用例数不超过 CPU 数，评分有 900 秒。零 hit 答案的格式不一致仍然存在：它的影响在 37 个有证书的用例上已经排除，在其余 13 个用例上仍未解决。一个用例失败仍会让整份提交作废。
问题类别
工程与运行环境；另涉及：任务说明与评分不一致
验证状态
CPU 对照已验证；零命中格式问题的影响只在 50 个用例中的 37 个上排除，在其余 13 个上仍未解决。
形式化检验
在 Lean 4 中部分证明。零 hit 答案在 50 道官方谜题中的 37 道上是错误的，每一道都有一个测试程序无法满足的证书。 局限：其余 13 道大型谜题需要 SAT 规模的反驳；CPU 数修复没有形式化（由运行检验）。

Vibrating Path - Graph K-Coloring (CodeChef VBR)

Write solution.py in the project root that reads from stdin and writes to stdout.

Problem Overview

Read README.md and tools/README.md for full problem details. A baseline solution.py already exists (it produces syntactically valid but low-quality output). Your job is to improve it.

Evaluation

Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Lower is better.

Local Testing

Generate local random tests with ./tools/bin/gen <seed>, using seeds in the range 0..10000 only.

# Generate a random test case (seed-based, deterministic)
./tools/bin/gen 1 > input.txt

# Run your solution
python3 solution.py < input.txt > output.txt

# Score output (Lower is better)
./tools/bin/tester input.txt output.txt
# Outputs to stderr: Score = <N>

Rules

  • Write your solution as solution.py in the project root directory
  • Do NOT modify files in tools/
  • Use tools/bin/gen and tools/bin/tester for local testing
  • Your program should read from stdin and write to stdout
  • Run your solution to completion and verify with the tester before finishing

任务要求

智能体要解一个图着色谜题，即给网络里的点（顶点）着色，相连的点颜色不能相同，过程中还可以"命中"（hit）顶点。任务说明写道 "Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Lower is better."（大意：解法在上述固定测试用例上计分，最终分数为各用例分数之和，越低越好。）它让解题者参阅 "README.md and tools/README.md for full problem details"（这两份文件中的完整题目细节）。README 规定的输出格式有三行。

  • "Line 1: number of hits $Q$"（第一行：命中次数 $Q$）
  • "Line 2: the vertices hit in order (1-indexed)"（第二行：按顺序列出被命中的顶点，从一开始编号）
  • "Line 3: coloring of each vertex ($1 \leq x_i \leq K$)"（第三行：每个顶点的颜色）

README 没有给零命中的情形留任何例外。tools/README.md 里没有输出格式说明，也没有例外。类别：组合优化。

我们检查了什么

按 README，零命中时输出三行，命中那一行为空。测试程序只接受两行格式的零命中。随附的基线 solution.py 打印的是两行格式，tools/src/verifier.py 也按两行读取。

50 个官方用例中有 37 个可以证明，不命中的话输入图无法用 K 种颜色着色。在这些用例上，零命中的答案不管用哪种格式都是错的。其余 13 个固定的图我们没有证书。在假定生成器下得出的概率上界，定不了它们实际能否着色。解题者可以在有证书的用例上用命中、在其他用例上用零命中，所以这 37 个证书说明不了对一份完整提交的影响为零。

  • 37/50 个用例有精确证书（证明该图无法用 K 种颜色着色的简短证明）：
    • K=1 的 13 个用例，证书是任意一条边；
    • K=2 的 12 个用例，证书是一个奇环；
    • N=1000、K=3 的 6 个用例，证书是一个显式的 K4 团（四个两两相连的顶点；用例 0043 中的 K4 还单独检查过）；
    • N=1000、K=4 的 6 个用例，证书是一个显式的 K5 团。
  • 其余 13 个用例的 N=10000、K∈{3,4}、平均度为 20，没有小规模的证书。联合界（把每一种可能的有效着色的概率加起来）在 K=4 时给出 ln P ≤ −14895，在 K=3 时给出 ≤ −29550。这假定用例来自已发布的均匀生成器。

一个用例失败，整份提交就作废。 评测程序把答案错误、超时或运行出错的用例都记为 float('inf')，再加进总分（/tmp/eval_vibrating_path.py，第 20、35、37、39 和 54 行）。所以只要一个用例失败，就是 TOTAL_SCORE inf。EdgeBench 的评测框架把它当作原始结果（无穷大）收下，而 rescale_score 遇到无穷大不给 100 分制的分数（sforge/harness/score_rescale.py:75-76）。于是那份提交没有分数。在 score_first 下，更早的、没有失败用例的提交仍会保留。任务说明只说 "Final score = sum of individual case scores"（最终分数为各用例分数之和），没说失败的用例记多少分。

在 4 个 CPU 的评分器上，每个用例承诺的 30 s 缩水成约 14 s CPU 时间，修复版纠正了这一点。 README 承诺 "Time limit | 30 seconds / test case"（第 54 行）。时限按墙钟时间算（TIME_LIMIT = 30，第 9 行），同时跑 8 个用例（ProcessPoolExecutor(max_workers=min(8, len(case_files)))，第 45 行）。任务没有规定 CPU 数。EdgeBench 的排行榜配置 examples/all-tasks-k8s/experiment.yaml（引文见 evidence/impact/edgebench-leaderboard-config.md）（sha256 d9d299794ba946cae8d2b7f68a7879a35bb8565d95e78107edf79802993643be）里，评分器沿用 judge_cpu_limit: 4。八个用例在 4 个 CPU 上每个约分到半个 CPU，还要和任务的 Python 测试程序抢 CPU。测试程序每个用例要 5.6–19.0 s CPU 时间（50 个用例共 579.6 s，在 1 个 CPU 上对正常对照解法的输出逐个用例测得，见 repairs/vibrating_path_graph_coloring-v2/paired/tester_time.out）。

任务随附了一条说明。零命中时，测试程序接受两行输出，却不接受 README 写的三行格式（命中那一行为空）。在 37 个官方用例上，零命中的答案已证明无效，其余 13 个还没有定论。让解析器两种格式都接受，可以消除格式不一致，但这样的修复不在本修复包里，也没有证明它在官方用例上给出相同的分数。

影响有多大

  • 在发布方的 4 个 CPU 下，有效解法如果每个用例用约 14–30 s CPU，在原始评分器下会丢掉全部分数（用每个用例 20 和 28 s 测得），在修复版下能得分。按截止时间停下的解法，在修复版下每个用例分到约两倍的 CPU（25 s 截止时间的解法，平均 12.84 s → 24.98 s，vibrating_path_graph_coloring-v2-paired-b）。我们没有测量分数会因此变多少。解题者每次提交后都能看到各用例的 TLE 结果，一次运行又会保留最好的有效提交，所以只有一次运行从没交过更快的有效解法时，才会丢分。
  • 一个用例失败即整份作废，这条全有或全无的规则没变，也仍然没有写明。
  • 零命中格式在 37 个有证书的用例上没有分数影响，其余 13 个还没有定论。一个有效的零命中答案如果因为格式遭拒，整份提交的结果就变成非有限值。目前既找不到这样的官方用例实例，也没有一般性的零影响证明。

修复

修复版（repairs/vibrating_path_graph_coloring-v2/）改了 /tmp/eval_vibrating_path.py 同时运行的用例数。新函数 cpu_quota_workers()（与 repairs/grid_turing_robot-v2/ 中的相同）从 cgroup 读取评分器的 CPU 配额（cpu.max，或 cgroup v1 的配额和周期），向下取整成整数个 CPU，没有配额时退回 os.cpu_count()，结果限制在 1 到 8 之间。进程池改为 ProcessPoolExecutor(max_workers=min(cpu_quota_workers(), len(case_files)))。docker run --cpus N 和发布方的 k8s 后端都会设置这个配额。有 8 个或更多 CPU 时，修复版评分器同时跑 8 个用例，和原始版完全一样。

任务 JSON 改了 judge.image_tag，并把 judge.eval_timeout 从 600 s 提高到 900 s。每个用例独占整个 CPU 时，评分时间更长，而本任务的测试程序又慢。有效解法接近 30 s 时限时，4 个 CPU 下最坏情况是 (50 × 30 s + 579.6 s) / 4 + 3/4 × 49 s ≈ 557 s，只比 600 s 低 7%。修复版下测到的最长评分耗时为 558.0 s（25 s 截止时间的解法，vibrating_path_graph_coloring-v2-paired-b），所以 600 s 的余量不够。30 s 的时限、README、测试程序、用例、解析器和分数刻度都不变，一个用例失败整份提交作废的规则也不变。

我们在 --cpus 4 下（另有一组是 --cpus 8）做了并排对照，两个评分器用相同的解法（evidence/runs/vibrating_path_graph_coloring-v2-paired-a、-b、-c，result/out/summary.txt；repairs/vibrating_path_graph_coloring-v2/paired/results.md）。

以下说明仍随修复版一起发布。

  1. 零命中时，测试程序只接受两行格式，不接受 README 的三行格式。在 37 个官方用例上，零命中的答案已证明是错的，其余 13 个上的分数影响还没有定论。
  2. 一个用例崩溃、超时或格式错误，总分就是 inf，整份提交没有分数。

我们如何检查

  • 在 E2B 上的 CPU 运行和并排对照运行中，每个用例做 12 到 28 s CPU 计算的有效解法、一个 25 s 墙钟截止时间的解法和一个 40 s 的错误对照，先在原始评分器上用 --cpus 4 和 --cpus 8 运行（evidence/runs/vibrating_path_graph_coloring-cpu4v8-a、-b），再在原始版和修复版评分器上并排对照（vibrating_path_graph_coloring-v2-paired-a、-b、-c）。每个作业都是 status: exit=0，在按摘要固定的评分器镜像里以 --network none --memory 4g 运行。每个解法先跑我们的正常对照解法（贪心 K 着色，按随附测试程序的规则模拟命中），再做额外计算，然后打印对照解法的答案，并记下自己在每个用例上的开始时间、结束时间和 CPU 时间（result/out/timing/）。每个用例的测试程序耗时另在 --cpus 1 下单独测量（paired/tester_time.out）。
  • 我们在按摘要固定的原始公开镜像里以 --network none 运行原始测试程序和辅助程序。输入包括我们写的图（配两行和三行的零命中输出）、一个已知错误的着色、一个已知正确且带命中的输出，以及六个官方用例。tools/bin/tester 在评分器镜像和智能体工作镜像里完全相同。tools/README.md 是从工作镜像里读的。
  • 精确证书为 50 个官方用例中的 37 个给出"该图无法用 K 种颜色着色"的证明，其余 13 个没有证书。K=1 时是一条边，K=2 时是一个奇环，此外还有逐对检查过的显式 K4 或 K5 团。
  • 对其余又大又稀疏的用例，我们在已发布生成器的模型下给出闭式的联合界。

局限

  • 修复版评分器从 cgroup（cpu.max）读取 CPU 配额。这一点只用 docker run --cpus 测过，没有在 Kubernetes pod（EdgeBench 排行榜设置用的后端）里测。
  • 没有 cgroup 配额时，修复版评分器退回 os.cpu_count()，它数的是主机的全部 CPU，不是评分器实际能用的 CPU（os.sched_getaffinity）。如果只限制了 CPU 集合、没有配额（例如 docker run --cpuset-cpus），或者 pod 看不到自己的 cpu.max，它仍可能和原版一样，同时跑的用例比 CPU 多。改用亲和性计数需要再做一次并排对照运行，所以我们没有改。
  • 没有运行任何 AI 模型或解题者。影响只在我们写的测试提交和反例上演示过。
  • 13/50 个用例靠的是概率上界，并假定用例来自已发布的均匀生成器。没有找到确切的种子，也没有做 SAT 反驳（由可满足性求解器给出的机器证明）。
  • 我们没有审查振动路径图的规则本身。
  • 我们没有检查过去的提交。
  • CPU 的影响是在有 8 个 vCPU 的 E2B 工作节点上，用 4 和 8 个 CPU、单线程的固定计算量和截止时间测试解法测的。多线程的解题者和 3、5、6、7 个 CPU 的情形都没有测试。
  • 4 个 CPU 时，按截止时间停的解题者在修复版下每个用例分到约两倍的 CPU，所以它在两个评分器下的分数不可比，我们没有测量变化多少。
  • 一次原始评分器运行中，25 s 截止时间解法出现 14 次超时，原因是推断的（测试程序只有半个 CPU，撞上了自己 60 s 的超时），没有直接观察到。
  • 测试程序的耗时，以及由此得出、用来定 900 s eval_timeout 的 557 s 上界，针对的都是正常对照解法的输出；检查别的输出可能更慢。评分器 CPU 少于 3 个时，900 s 的 eval_timeout 可能比每个用例 30 s 的时限先起作用（2 个 CPU 时约 1,065 s 的工作量）。配额向下取整，2.5 个 CPU 时同时跑 2 个用例。
