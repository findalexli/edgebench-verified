Treant Forest

已修复 treant_forest

The score scale tops out at 21 of 100 for any submission。

摘要任务说明如何评分我们的发现文件

摘要

任务
Solve 50 fixed cases of a grid puzzle adapted from an AtCoder programming contest; each case scores the number of turns survived, and higher is better.
问题所在
The grader caps each case at 2N² turns, where N is the grid size, so no total can exceed 92,304. The score scale's reference points were set far above this, up to 330,195 for the top rank, so no submission can score above 21.02 out of 100. The README does not mention the cap. At the publisher's 4 grader CPUs each case gets about half a CPU; solutions using up to 58 seconds of computing per case still passed (the slowest took 116 of the grader's 120 seconds), so the README's full 60 seconds would sit at the limit; a solver that stops at a wall-clock deadline gets about half the computing time.
影响有多大
Every submission's score is squeezed into 0 to 21, with ordering kept. A simple honest test submission scored 3.04.
我们的处理
Fixed in a new version: only the score scale changes, running straight from the starter's total (3,418) to the turn cap (92,304). Raw totals are identical; the simple honest test submission now scores 16.36.
形式化检验
在 Lean 4 中部分证明。Each case scores at most 2N². The total bound 92,304 maps to 2543510/121003 under the original scale. The formulas establish conditional per-score conversions, not exact conversion of all published leaderboard averages. 局限：92,304 is an upper bound, not a demonstrated attainable total. Averaging across clipping or piecewise boundaries invalidates conversion from an aggregate alone.。

以下是 EdgeBench 的原始任务文本，即 tasks/treant_forest.json 中的 work.agent_query 字段，来自字节跳动 Seed 团队在 Hugging Face 上发布的 EdgeBench 数据集，采用 CC BY 4.0 许可。文本未作改动，仅从 Markdown 渲染为 HTML；指向任务工作区内文件的链接以纯文本显示。EdgeBench 的评测框架还会附加关于如何提交的标准说明（sforge/harness/evolve_scripts.py），此处未显示。任务说明是 EdgeBench 的原文，在所有语言版本中均以英文显示，未作翻译。

Treant's Forest - Maze Obstruction Strategy (AHC054)

Write solution.py in the project root that reads from stdin and writes to stdout.

Problem Overview

Read README.md and tools/README.md for full problem details. A baseline solution.py already exists (it produces syntactically valid but low-quality output). Your job is to improve it.

Evaluation

Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Higher is better.

Local Testing

Generate local random tests with ./tools/bin/gen <seed>, using seeds in the range 0..10000 only.

# Generate a random test case (seed-based, deterministic)
./tools/bin/gen 0 > input.txt

# Run your solution
python3 solution.py < input.txt > output.txt

# Score output (Higher is better)
./tools/bin/tester input.txt output.txt
# Outputs to stderr: Score = <N>

Rules

  • Write your solution as solution.py in the project root directory
  • Do NOT modify files in tools/
  • Use tools/bin/gen and tools/bin/tester for local testing
  • For local scoring, use only ./tools/bin/tester; do not use tools/src/verifier.py for scores
  • Your program should read from stdin and write to stdout
  • Run your solution to completion and verify with the tester before finishing

我们的发现

完整案例：测试提交、独立检验和修复。文件路径指向代码仓库中的位置；链接在 GitHub 上打开。案例译自英文原文；如有出入，以英文原文为准。

Outcome: Fixed. The original score scale puts its reference points above the most turns the grader allows, so no submission can score above 21.02/100; the fixed version changes only the score scale.

What the task asks

The task is a grid puzzle adapted from the AtCoder contest AHC054: "Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Higher is better." Raw results (before conversion to 0–100) are converted to a 0-100 scale. Category: Combinatorial Optimization.

What goes wrong

Rule. Each case's raw result is its turn count, and the grader's tester program caps turns at max_turns = N*N*2, where N is the grid size (tester:63, loop at :140). The README does not mention this cap. The original score scale is piecewise_max with four reference points: baseline 5,369, rank30 88,189, rank1 330,195 and super 451,198.

Example. The sum of 2N² over the 50 shipped cases is 92,304, an upper bound on the raw result: no submission can exceed it. A submission at that cap should score 100. Under the original score scale it gets 21.02/100 (exactly 2543510/121003), so no submission can score more. Whether any submission reaches the cap on every case is not shown (see Limits).

Why it matters. The rank1 reference point (330,195) is 3.58× the turn cap. So every score above 21.02 out of 100 (nearly all of the 20-80 band and the whole 80-100 band) is out of reach for any submission. The order of submissions is preserved. The origin of the original reference points is unknown; they appear to come from a different scorer or set of cases.

Checked and fine. The worst-case runtime is 7 waves × 120 s = 840 s, under the 870 s limit (tight). The tester is deterministic. Solutions that use a wall-clock time budget depend on the CPU available to the 8 parallel workers.

Note: at the publisher's 4 grader CPUs each case gets about half a CPU. The README promises "Time limit | 60 seconds / test case" (line 71); the grader allows twice that (TIME_LIMIT = 120, /tmp/eval_treants_forest.py line 9) and runs 8 cases at once (max_workers=min(8, len(case_files)), line 45). The task sets no CPU count. EdgeBench's leaderboard settings give this grader 4 CPUs (the default, with no override for this task; quoted in evidence/impact/edgebench-leaderboard-config.md), so 8 cases share 4 CPUs. Measured on the original grader at --cpus 4 (evidence/runs/treant_forest-cpu4v8-a/result/out/summary.txt, -b) with the honest greedy control followed by fixed CPU work: 50 or 58 s of CPU per case passes 50/50 (TOTAL 17,960; the slowest 58 s case took 116.1 s, inside the 120 s limit), the same as at --cpus 8. Solutions using up to 58 s of CPU per case therefore pass. One using the README's full 60 s would take about 120.1 s at the measured ratio (116.10 s for 58 s), at the 120 s limit, so the grader's 2× slack only just absorbs the sharing. A solution needing 70 s of CPU per case, beyond the README's 60 s, timed out on 48 of 50 cases at 4 CPUs (TOTAL 17,960 → 1,018; 3.04 → 0 out of 100 on the original scale) and passed at 8 CPUs; it exceeds the promise, so this is not counted as a defect. A solver that stops at a 55 s wall-clock deadline, as the README invites, got a median of 27.4 s of CPU per case at 4 CPUs against 54.9 s at 8 CPUs, so its output, and so its score, can depend on the grader's CPU count. In these runs the answer was fixed, so no score difference was measured. The fixed version does not change this.

How much it matters

All solvers are affected: every score out of 100 is squeezed into 0–21. The baseline solution that ships with the task (TOTAL_SCORE 3,418, 50/50 cases OK) maps to 0.

The fix

Only judge.rescale (the score scale) in the task JSON changes. The piecewise_max reference points are replaced by "kind": "linear", "lower": 3418.0, "upper": 92304.0. The lower point is the shipped baseline's raw result under the original grader. The upper point is Σ 2N² over the shipped cases, the exact upper bound of the tester's score function (its turn cap). The four old reference-point fields are removed: two lie above the cap, and no exact replacements for the rank-based points exist. The grader image, grader, tester, cases, eval_cmd and timeouts are unchanged, so raw results are byte-identical.

Are scores comparable? Scores out of 100 from the fixed version are not comparable with those from the original for any raw result above the shipped baseline (raw > 3418). Raw TOTAL_SCORE values stay comparable across versions. The rank-based reference points no longer exist, so a score of 20 or 80 in the fixed version has no meaning as a leaderboard percentile.

How we checked it

  • Original grader, from the public image pinned by digest. The original eval_cmd ran in the original grader image and in the fixed image, with --network none. The hashes of the grader, tester and cases inside each image matched the pinned values.
  • Exact arithmetic. The per-case cap 2N² was summed over the 50 shipped case headers twice, by the same one-line formula in two scripts (paired/normalize.py on E2B, check_arith.py locally); the case files are not in the repository. Its value under the original score scale was computed exactly.
  • Source reading. The cap is read directly from the tester source (tools/bin/tester).
  • Repeatability. The side-by-side run of the original and fixed versions was done three times, and no result changed (data/paired-repeatability.md).

Limits

  • No AI model or solver was run. Effects are shown only on the test submissions we wrote.
  • 92,304 is the exact upper bound on the raw result. Reaching it on every case has not been demonstrated. The best honest result on a single case reached 47% of that case's cap (the per-case caps for that run are not saved here).
  • A linear scale from the baseline to the cap squeezes realistic strong scores together. That cost comes from using only exactly computable reference points instead of ones taken from a leaderboard.
  • The 2N² cap is still not disclosed in the README. Disclosing it would be a separate change to what the solver sees.
  • Whether the tester's movement rules match the original AHC054 game was not established, and this fix does not address it.
  • The CPU-share note was measured at 4 and 8 CPUs with single-threaded fixed-work and wall-deadline test solutions. No real anytime solver was run, so the size of the deadline effect on scores is not known. Multi-threaded solvers were not tested.
