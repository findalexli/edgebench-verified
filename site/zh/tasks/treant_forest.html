摘要任务说明如何评分我们的发现文件

摘要

任务
求解一个改编自 AtCoder 编程竞赛的网格谜题的 50 个固定用例；每个用例的得分是存活的回合数，越高越好。
问题所在
评分器把每个用例的回合数上限设为 2N²（N 是网格大小），因此总数不可能超过 92,304。分数刻度的参考点却设得远高于此，最高名次的参考点达 330,195，因此任何提交的得分都不可能超过 100 分中的 21.02 分。README 没有提到这个上限。在发布方的评分器 CPU 数为 4 时，每个用例约分到半个 CPU；每个用例使用最多 58 秒计算时间的解法仍能通过（最慢的用了评分器 120 秒中的 116 秒），因此 README 所说的完整 60 秒会正好处在极限上；一个按截止时间停止的解题者大约只得到一半的计算时间。
影响有多大
每份提交的分数都被压缩到 0 到 21 之间，顺序保持不变。一份简单的诚实测试提交得 3.04 分。
我们的处理
已修复，发布新版本：只改变分数刻度，使其从初始程序的总数（3,418）直线延伸到回合上限（92,304）。原始总数完全相同；这份简单的诚实测试提交现在得 16.36 分。
形式化检验
在 Lean 4 中部分证明。每个用例的得分至多为 2N²，因此总数 92,304 在原始刻度上恰好得 2543510/121003 分；修复后的刻度和换算后的排行榜数值都由已发布的（一位小数的）分数精确推出。 局限：总数 92,304 被当作输入；换算继承了表格的舍入；有两类运行只做了近似换算。

Treant's Forest - Maze Obstruction Strategy (AHC054)

Write solution.py in the project root that reads from stdin and writes to stdout.

Problem Overview

Read README.md and tools/README.md for full problem details. A baseline solution.py already exists (it produces syntactically valid but low-quality output). Your job is to improve it.

Evaluation

Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Higher is better.

Local Testing

Generate local random tests with ./tools/bin/gen <seed>, using seeds in the range 0..10000 only.

# Generate a random test case (seed-based, deterministic)
./tools/bin/gen 0 > input.txt

# Run your solution
python3 solution.py < input.txt > output.txt

# Score output (Higher is better)
./tools/bin/tester input.txt output.txt
# Outputs to stderr: Score = <N>

Rules

  • Write your solution as solution.py in the project root directory
  • Do NOT modify files in tools/
  • Use tools/bin/gen and tools/bin/tester for local testing
  • For local scoring, use only ./tools/bin/tester; do not use tools/src/verifier.py for scores
  • Your program should read from stdin and write to stdout
  • Run your solution to completion and verify with the tester before finishing

任务要求

该任务是一个改编自 AtCoder 比赛 AHC054 的网格谜题："Your solution is scored on 50 fixed test cases. Final score = sum of individual case scores. Higher is better."（大意：解法在一组固定测试用例上计分，最终分数为各用例分数之和，越高越好。）原始结果（换算为 0–100 分之前）会被换算到 0-100 的刻度上。类别：组合优化。

问题出在哪里

规则。 每个用例的原始结果是其回合数，而评分器的测试程序把回合数上限设为 max_turns = N*N*2，其中 N 是网格尺寸（tester:63，循环在 :140）。README 没有提到这个上限。原始分数刻度是 piecewise_max，有四个参考点：baseline 5,369、rank30 88,189、rank1 330,195 和 super 451,198。

例子。 50 个随附用例的 2N² 之和为 92,304，这是原始结果的上界：任何提交都不可能超过它。达到这一上限的提交应当得 100 分。在原始分数刻度下，它只得 21.02/100（精确值为 2543510/121003），因此任何提交的得分都不会更高。是否有提交能在每个用例上都达到上限，本文没有给出证明（见局限）。

为什么重要。 rank1 参考点（330,195）是回合上限的 3.58×。因此，100 分制下高于 21.02 的每个分数（几乎整个 20-80 区间和整个 80-100 区间）都是任何提交无法达到的。提交之间的顺序得以保留。原始参考点的来源不明；它们似乎来自另一个计分程序或另一组用例。

已检查且没有问题的部分。 最坏情况下的运行时间为 7 批 × 120 s = 840 s，低于 870 s 的时限（余量很小）。测试程序是确定性的。使用墙钟时间预算的解法依赖于 8 个并行工作进程可用的 CPU。

说明：在发布方的 4 个评分器 CPU 下，每个用例约分到半个 CPU。 README 承诺 "Time limit | 60 seconds / test case"（第 71 行）；评分器允许的是其两倍（TIME_LIMIT = 120，/tmp/eval_treants_forest.py 第 9 行），并同时运行 8 个用例（max_workers=min(8, len(case_files))，第 45 行）。任务没有设定 CPU 数。EdgeBench 的排行榜设置给这个评分器 4 个 CPU（默认值，本任务没有单独覆盖；引文见 evidence/impact/edgebench-leaderboard-config.md），因此 8 个用例共享 4 个 CPU。我们在原始评分器上以 --cpus 4 测量（evidence/runs/treant_forest-cpu4v8-a/result/out/summary.txt、-b），使用诚实的贪心对照解法，并在其后附加固定量的 CPU 计算：每个用例 50 或 58 s CPU 时，50/50 通过（TOTAL 17,960；最慢的 58 s 用例耗时 116.1 s，在 120 s 时限之内），与 --cpus 8 时相同。因此，每个用例使用至多 58 s CPU 的解法都能通过。按实测比例（58 s 对应 116.10 s），一个用满 README 所说 60 s 的解法约需 120.1 s，恰在 120 s 的时限处，所以评分器 2× 的余量只是勉强吸收了这种共享。一个每个用例需要 70 s CPU（超出 README 所说的 60 s）的解法，在 4 个 CPU 下有 48/50 个用例超时（TOTAL 17,960 → 1,018；原始刻度上 3.04 → 0 分，满分 100），在 8 个 CPU 下通过；它超出了承诺，因此不算作缺陷。一个像 README 所鼓励的那样、在 55 s 墙钟截止时间停止的解题者，在 4 个 CPU 下每个用例的 CPU 时间中位数为 27.4 s，而在 8 个 CPU 下为 54.9 s，因此其输出以及分数可能取决于评分器的 CPU 数。在这些运行中答案是固定的，因此没有测得分数差异。修复版不改变这一点。

影响有多大

所有解题者都受影响：每个 100 分制得分都被压缩到 0–21 之间。随任务附带的基线解法（TOTAL_SCORE 3,418，50/50 个用例 OK）对应 0 分。

修复

只改动任务 JSON 中的 judge.rescale（分数刻度）。piecewise_max 的参考点被替换为 "kind": "linear", "lower": 3418.0, "upper": 92304.0。下参考点是随附基线在原始评分器下的原始结果。上参考点是随附用例上的 Σ 2N²，即测试程序计分函数的精确上界（其回合上限）。四个旧的参考点字段被删除：其中两个位于上限之上，而基于排名的参考点没有可精确计算的替代值。评分器镜像、评分器、测试程序、用例、eval_cmd 和超时都不变，因此原始结果逐字节相同。

分数是否可比？ 对任何高于随附基线的原始结果（原始结果 > 3418），修复版的 100 分制得分与原始版不可比。原始 TOTAL_SCORE 值在各版本之间仍然可比。基于排名的参考点已不复存在，因此修复版中 20 分或 80 分不再具有排行榜百分位的含义。

我们如何检查

  • 原始评分器，来自按摘要固定的公开镜像。 原始 eval_cmd 分别在原始评分器镜像和修复版镜像中以 --network none 运行。每个镜像内评分器、测试程序和用例的哈希都与固定值一致。
  • 精确算术。 每个用例的上限 2N² 在 50 个随附用例的文件头上求和了两次，由两个脚本中同一个单行公式完成（E2B 上的 paired/normalize.py，本地的 check_arith.py）；用例文件不在仓库中。它在原始分数刻度下的取值是精确计算的。
  • 阅读源码。 上限直接从测试程序源码（tools/bin/tester）中读出。
  • 可重复性。 原始版和修复版的并排对照运行做了三次，结果没有变化（data/paired-repeatability.md）。

局限

  • 没有运行任何 AI 模型或解题者。影响只在我们编写的测试提交上展示。
  • 92,304 是原始结果的精确上界。在每个用例上都达到它，尚未得到证明。单个用例上最好的诚实结果达到了该用例上限的 47%（那次运行各用例的上限没有保存在这里）。
  • 从基线到上限的线性刻度会把现实中的高分挤在一起。这一代价源于只使用可精确计算的参考点，而不使用取自排行榜的参考点。
  • README 仍然没有披露 2N² 的上限。披露它将是对解题者所见内容的另一项改动。
  • 没有查明测试程序的移动规则是否与原版 AHC054 游戏一致，本次修复也不涉及这一点。
  • CPU 份额的说明是在 4 个和 8 个 CPU 下测得的，所用的是单线程测试解法（一种做固定量的计算，一种按截止时间停止）。没有运行真实的随时可停（anytime）解题者，因此截止时间对分数的影响有多大并不清楚。多线程解题者没有测试。
