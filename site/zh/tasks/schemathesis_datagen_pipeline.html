摘要

任务
为 Web API 测试工具 schemathesis 构建测试数据生成器，其中一个要以标准 Web 日期格式生成有效日期。
问题所在
隐藏测试只检查每个日期的字母和数字排列是否符合模式。它接受不可能存在的日期（例如四月 31 日）、错误的星期、24:00 这样的时间以及虚构的月份名称。一个约 90% 的时间都生成不可能的日期或错误星期的生成器，仍能通过其所在测试组的全部 15 项测试。
影响有多大
至多约为总分的 1%，只影响生成无效日期或时间的生成器；它们与正确的生成器获得相同的分数。
我们的处理
v2.1 评分器检查日历有效性、星期和时间，并把年份限制为 1900 年或以后。三组并排的原生 eval_cmd 对照在一次干净的运行中（exit 0）通过：有效生成器的得分不变（0.477350），生成 1900 年以前日期和格式错误日期的生成器失去这一项日期测试（0.477350 降到 0.467094）。旧的 Lean 证明尚未修订。
问题类别
评分逻辑错误（事实性错误）
验证状态
v2.1 评分器镜像在工作机中由修复包物化并构建；干净的原生重跑 schemathesis_datagen_pipeline-v2.1-native-20261013b（台账 exit=0）：原始 eval_cmd 的六个对照组，stdlib_1900 0.477350/0.477350，stdlib_any_year 0.477350/0.467094，garbage_shape 0.477350/0.467094。整个任务的认证和新的形式化证明尚未建立。
形式化检验
在 Lean 4 中已证明。历史模型在 1–9999 年范围内检查日历有效性、相符的星期和时间，其星期算法与 Python 一致。这个建模的范围允许所引 HTTP-date 标准禁止的年份；它不是对当前 year≥1900 的 v2.1 修复的证明。 局限：手写的解析器；历史上较宽松的年份范围，不等于符合标准。当前 v2.1 的原生成对 eval_cmd 对照已通过；针对修订后范围的证明和整个任务的认证尚未建立。。

import json
import re
from pathlib import Path

PASSED = "PASSED"
FAILED = "FAILED"
ERROR = "ERROR"


def read_text(path):
    p = Path(path)
    if not p.exists():
        return ""
    return p.read_text(errors="replace")


def parse_weights(script_text, phase_count):
    patterns = [
        r"weights\s*=\s*\[([0-9,\s]+)\]",
        r"PHASE_WEIGHTS\s*=\s*\(([0-9\s]+)\)",
    ]
    for pattern in patterns:
        m = re.search(pattern, script_text)
        if m:
            raw = re.split(r"[,\s]+", m.group(1).strip())
            weights = [float(x) for x in raw if x]
            if len(weights) >= phase_count:
                return weights[:phase_count]

    m = re.search(r"PHASES\s*=\s*\((.*?)\n\)", script_text, re.S)
    if m:
        weights = []
        for line in m.group(1).splitlines():
            line = line.strip()
            if not line or line.startswith("#"):
                continue
            line = line.strip("\"'")
            parts = line.split()
            if parts and re.fullmatch(r"\d+(?:\.\d+)?", parts[-1]):
                weights.append(float(parts[-1]))
        if len(weights) >= phase_count:
            return weights[:phase_count]

    reward_json = Path("/logs/verifier/reward.json")
    if reward_json.exists():
        try:
            data = json.loads(reward_json.read_text(errors="replace"))
            phases = data.get("phases")
            if isinstance(phases, dict):
                weights = []
                for phase in phases.values():
                    if isinstance(phase, dict) and "weight" in phase:
                        weights.append(float(phase["weight"]))
                if len(weights) >= phase_count:
                    return weights[:phase_count]
        except Exception:
            pass

    return [1.0] * phase_count


def parse_statuses(output):
    results = []
    seen = set()
    pattern = re.compile(r"^(tests/roadmap\.py::\S+)\s+(PASSED|FAILED|ERROR)\s*$", re.M)
    for name, status in pattern.findall(output):
        if name in seen:
            continue
        seen.add(name)
        results.append((name, status))
    return results


def parse_phase_number(name, fallback):
    m = re.search(r"(?:test_)?phase_?0*(\d+)\b", name)
    if m:
        return int(m.group(1))
    return fallback


def parse_phase_ratios(output):
    ratios = {}
    counts = {}
    pattern = re.compile(r"^Phase\s+0*(\d+):\s+(\d+)\s*/\s*(\d+)\s+passed\s*$", re.M)
    for n, passed, total in pattern.findall(output):
        n_i = int(n)
        passed_i = int(passed)
        total_i = int(total)
        counts[n_i] = (passed_i, total_i)
        ratios[n_i] = passed_i / total_i if total_i else 0.0

    weighted_pattern = re.compile(
        r"^\s*Phase\s+0*(\d+)\s+\(weight\s*=\s*([0-9.]+)\):\s*([0-9.]+)\s*$",
        re.M,
    )
    inline_weights = {}
    for n, weight, score in weighted_pattern.findall(output):
        n_i = int(n)
        inline_weights[n_i] = float(weight)
        ratios[n_i] = float(score)

    return ratios, counts, inline_weights


def parse_total_score(output):
    m = re.search(r"TOTAL_SCORE\s+([0-9]+(?:\.[0-9]+)?)", output)
    if m:
        return float(m.group(1))
    reward_path = Path("/logs/verifier/reward.txt")
    if reward_path.exists():
        try:
            return float(reward_path.read_text(errors="replace").strip())
        except Exception:
            pass
    return None


def main():
    output = read_text("/tmp/test_full.log")
    script = read_text("/tests/test.sh")

    statuses = parse_statuses(output)
    if not statuses:
        statuses = [("tests/roadmap.py::unknown", ERROR)]

    ratios, counts, inline_weights = parse_phase_ratios(output)
    weights = parse_weights(script, len(statuses))
    for idx, weight in inline_weights.items():
        if 1 <= idx <= len(weights):
            weights[idx - 1] = weight

    details = []
    weighted_total = 0.0
    weight_total = 0.0
    failed_names = []

    for pos, (name, status) in enumerate(statuses, start=1):
        phase_num = parse_phase_number(name, pos)
        weight = weights[pos - 1] if pos - 1 < len(weights) else 1.0
        if phase_num in ratios:
            ratio = ratios[phase_num]
        else:
            ratio = 1.0 if status == PASSED else 0.0
        contribution = weight * ratio
        weighted_total += contribution
        weight_total += weight

        if phase_num in counts:
            phase_passed, phase_total = counts[phase_num]
            message = (
                f"Phase {phase_num}: {phase_passed}/{phase_total} checks passed; "
                f"weighted contribution {contribution:.6f}/{weight:.6f}"
            )
        else:
            message = (
                f"Phase {phase_num}: status {status}; "
                f"weighted contribution {contribution:.6f}/{weight:.6f}"
            )

        if status != PASSED:
            failed_names.append(name)

        details.append(
            {
                "name": name,
                "status": status,
                "message": message,
                "score": contribution,
                "weight": weight,
            }
        )

    passed_count = sum(1 for _, status in statuses if status == PASSED)
    total_count = len(statuses)
    pass_rate = passed_count / total_count if total_count else 0.0
    total_score = parse_total_score(output)
    if total_score is None:
        total_score = weighted_total / weight_total if weight_total else 0.0

    summary = (
        f"{passed_count}/{total_count} phases passed; "
        f"weighted score {total_score:.6f}"
    )
    if failed_names:
        summary += ". Failed: " + ", ".join(failed_names[:10])
        if len(failed_names) > 10:
            summary += f" (+{len(failed_names) - 10} more)"

    result = {
        "valid": True,
        "score": total_score,
        "pass_rate": pass_rate,
        "summary": summary,
        "details": details,
        "metrics": {
            "phase_weighted_total": weighted_total,
            "phase_weight_total": weight_total,
            "source": "roadmap_structured_json",
        },
    }

    print(">>>>> Start Structured Result")
    print(json.dumps(result, ensure_ascii=False, indent=2))
    print(">>>>> End Structured Result")


if __name__ == "__main__":
    main()

我们的发现

完整案例：测试提交、独立检验和修复。文件路径指向代码仓库中的位置；链接在 GitHub 上打开。案例译自英文原文；如有出入，以英文原文为准。

2026-10-13 修订： v2.1 恢复了 RFC 规定的年份下限（年份 ≥ 1900）。一次干净的原生运行（schemathesis_datagen_pipeline-v2.1-native-20261013b，台账记录 exit=0）从修复包构建了 v2.1 镜像，并在六个对照臂上运行原始评测命令：有效的生成器保持 0.477350 的奖励，而生成 1900 年以前日期的生成器和垃圾生成器降到 0.467094。这些有限的对照并不证明整个任务无误。见后续说明。

结论： 原始缺陷已确认；v2.1 修复已在并排的原生对照中验证。针对 HTTP 日期的隐藏测试只检查字符串的形状，因此生成不可能存在的日期和时刻的生成器也能通过；这一漏洞约占分数的 1%。

任务要求

解题者为 schemathesis 4.14.3（一个测试 Web API 的工具）构建数据生成策略。任务要求解题者 "Treat /app/TODO.md as the authoritative task specification."（把该文件视为权威的任务规格。）TODO.md 的 Target 1 要求一个 "HTTP-date strategy: Generate valid HTTP-date values in IMF-fixdate format"（HTTP 日期策略：生成 IMF-fixdate 格式的有效 HTTP 日期值）。它还补充道："In positive generation mode, all generated values should conform to the protocol grammar."（在正向生成模式下，所有生成的值都应符合协议语法。）HTTP 日期的标准 RFC 9110 §5.6.7 把 time-of-day 标注为 00:00:00 - 23:59:60 (leap second)。它把日期各字段的含义交给 RFC 5322 §3.3，后者要求日期时间 "semantically valid"（语义上有效）：月中的日子真实存在、星期与之相符、时刻在范围之内。类别：系统与软件工程。

问题出在哪里

规则。 生成的 HTTP 日期必须是 IMF-fixdate 格式的有效日期。原始测试只用 ^\w{3}, \d{2} \w{3} \d{4} \d{2}:\d{2}:\d{2} GMT$ 检查每个字符串，别无其他。这个模式不检查：

  • 日期是否在日历中存在（31 Apr 和 29 Feb 2023 都不存在）；
  • 星期是否与日期相符；
  • 时刻的范围，例如 24:00；
  • 星期和月份的名称是否是真实的名称。\w{3} 接受任意三个单词字符，因此 "Abc, 99 Xyz 0000 99:99:99 GMT" 也能通过。

例子。 一个现实中可能写出的生成器独立地抽取星期、日、月、年和时刻（independent_fields）。约 90% 的抽样会产生不可能存在的日期和不相符的星期。在随机数固定的 50 次抽样中，原始模式接受了 50/50，修复版检查接受了 5/50。按任务规格的预期：日期测试应当失败。在原始评分器上的实际结果：Phase 1 让这个生成器以 15/15 通过。

为什么重要。 错误的生成器相对正确的生成器并无收益，但两者在 Phase 1 得到相同的分数，因此该测试无法区分它们。

影响有多大

至多约为总分的 1%。日期测试是 Phase 1 的 15 项测试中的 1 项，而 Phase 1 的权重为 2/13，因此影响为总分的 −2/195。只有 http_date_values 会生成无效日期或时刻的解题者受影响。

修复

修复版改动一个文件 /tests/test_01_header_strategies.py。只检查形状的模式被替换为检查 is_imf_fixdate。该检查覆盖 IMF-fixdate 语法、真实的公历日期、星期的一致性和时刻范围，并且只在 23:59 时允许 :60。它要求年份为 1900 或更晚：TODO.md 要求有效的 HTTP 日期值，而 RFC 9110 §5.6.7 的日期语义取自 RFC 5322 §3.3（"any numeric year 1900 or later"，即任何 1900 年或以后的数字年份）。较早的 v2 去掉了这一下限（年份 ≥ 1）；v2.1 将其恢复。这项日期测试的 max_examples 从 50 提高到 200。用 50 个样例时，罕见的时刻缺陷（小时为 24）只在 15/20 个随机种子中被发现；用 200 个样例时，在 20/20 个种子中都被发现。测试数量、test.sh、权重和解析器都不变。在 task.json.in 中，只有 judge.image_tag 改变。

我们如何检查

  • 原始评分器，来自按摘要固定的公开镜像。 评分器镜像中保存了未经修改的 schemathesis 4.14.3 初始文件和 hypothesis 6.155.2（属性测试库），没有参考解法。每个生成器都在全新的 --network none 容器中，分别在完整的原始 judge.eval_cmd 和修复版下运行。这项日期测试还单独用 20 个 Hypothesis 种子运行过。
  • 独立检查。 一个纯 Python 检查在固定字符串上运行原始模式和修复版检查：31 Apr、24:00、错误的星期、29 Feb 2023、29 Feb 2024 和 Sat, 31 Dec 2016 23:59:60。日历有效性用 Python 的公历 calendar 检查。
  • 可重复性。 原始版和修复版评分器的并排对照运行做了三次，结果没有变化（data/paired-repeatability.md）。

局限

  • 没有运行任何 AI 模型或求解器。影响只在我们编写的生成器上展示。
  • 这些生成器是 Target 1 的最小叠加实现。没有可用的上游参考生成器，因此分数只是部分得分。
  • 没有检查闰秒是否真的发生过。:60 只在 23:59 时允许，但没有对照真实的闰秒表检查。
  • 属性测试仍然是随机的。所测的错误生成器在 20/20 个种子中都被发现，但更罕见的缺陷在某个给定种子下仍可能通过。
  • 这类错误在真实提交中出现的频率未知。
