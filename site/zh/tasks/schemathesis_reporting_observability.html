Schemathesis Reporting Observability

已修复 评分逻辑错误，事实性错误 schemathesis_reporting_observability

两项隐藏测试会给错误或损坏的输出计分。

摘要任务说明如何评分我们的发现文件

摘要

任务
为自动测试 Web 服务的工具 Schemathesis 添加报告功能，包括以常见报告格式 JUnit XML 写出测试报告。
问题所在
一项隐藏测试只检查报告中是否出现两个词，因此损坏的文件和缺少错误信息的报告也能通过。另一项测试针对的功能是在某些生成的测试中省略请求体，但它永远不会失败：它查找的条目类型不对，总是什么也找不到。报告测试还会让一个正确的报告写出器失败，只要其测试套件的名称不是 "schemathesis"，而任务说明并没有这样要求。
影响有多大
错误给分约为总分的 2.4%：1/70（约 1.4%）和 1/100（1.0%）；一个使用其他套件名称的正确写出器会损失 1/70。修复版使分数至多下降 4.76 分，或上升 2.76 分（只有当一份提交使 GeneratedValue 类无法导入时，才可能最多上升 4.76 分）。
我们的处理
已修复，发布新版本：报告测试会读取文件，并要求其中记录了错误，套件名称不限；另一项测试现在检查真实的输出。部分得分与原版本不可比较。
问题类别
评分逻辑错误，事实性错误；另涉及：任务说明与评分不一致
验证状态
六次成对运行（均为 exit=0，汇总相同）：完整的参考实现保持 1.0，另一种套件名的写入器从 0.985714 升到 1.0，错误的报告失分；修复包在一台干净的机器上从零重建（materialize-check-g2）。只尝试了一个完整实现；根元素带命名空间的 JUnit 报告不能通过修订后的测试。
形式化检验
在 Lean 4 中部分证明。基于初始文件的已观察行为（12 次运行中 12 次只有一种值类），原始的请求体省略测试永远不会失败；每一个已公布的分数变化都是精确的。 局限：报告格式测试依赖一个 XML 解析器。

import json
import re
from pathlib import Path

PASSED = "PASSED"
FAILED = "FAILED"
ERROR = "ERROR"


def read_text(path):
    p = Path(path)
    if not p.exists():
        return ""
    return p.read_text(errors="replace")


def parse_weights(script_text, phase_count):
    patterns = [
        r"weights\s*=\s*\[([0-9,\s]+)\]",
        r"PHASE_WEIGHTS\s*=\s*\(([0-9\s]+)\)",
    ]
    for pattern in patterns:
        m = re.search(pattern, script_text)
        if m:
            raw = re.split(r"[,\s]+", m.group(1).strip())
            weights = [float(x) for x in raw if x]
            if len(weights) >= phase_count:
                return weights[:phase_count]

    m = re.search(r"PHASES\s*=\s*\((.*?)\n\)", script_text, re.S)
    if m:
        weights = []
        for line in m.group(1).splitlines():
            line = line.strip()
            if not line or line.startswith("#"):
                continue
            line = line.strip("\"'")
            parts = line.split()
            if parts and re.fullmatch(r"\d+(?:\.\d+)?", parts[-1]):
                weights.append(float(parts[-1]))
        if len(weights) >= phase_count:
            return weights[:phase_count]

    reward_json = Path("/logs/verifier/reward.json")
    if reward_json.exists():
        try:
            data = json.loads(reward_json.read_text(errors="replace"))
            phases = data.get("phases")
            if isinstance(phases, dict):
                weights = []
                for phase in phases.values():
                    if isinstance(phase, dict) and "weight" in phase:
                        weights.append(float(phase["weight"]))
                if len(weights) >= phase_count:
                    return weights[:phase_count]
        except Exception:
            pass

    return [1.0] * phase_count


def parse_statuses(output):
    results = []
    seen = set()
    pattern = re.compile(r"^(tests/roadmap\.py::\S+)\s+(PASSED|FAILED|ERROR)\s*$", re.M)
    for name, status in pattern.findall(output):
        if name in seen:
            continue
        seen.add(name)
        results.append((name, status))
    return results


def parse_phase_number(name, fallback):
    m = re.search(r"(?:test_)?phase_?0*(\d+)\b", name)
    if m:
        return int(m.group(1))
    return fallback


def parse_phase_ratios(output):
    ratios = {}
    counts = {}
    pattern = re.compile(r"^Phase\s+0*(\d+):\s+(\d+)\s*/\s*(\d+)\s+passed\s*$", re.M)
    for n, passed, total in pattern.findall(output):
        n_i = int(n)
        passed_i = int(passed)
        total_i = int(total)
        counts[n_i] = (passed_i, total_i)
        ratios[n_i] = passed_i / total_i if total_i else 0.0

    weighted_pattern = re.compile(
        r"^\s*Phase\s+0*(\d+)\s+\(weight\s*=\s*([0-9.]+)\):\s*([0-9.]+)\s*$",
        re.M,
    )
    inline_weights = {}
    for n, weight, score in weighted_pattern.findall(output):
        n_i = int(n)
        inline_weights[n_i] = float(weight)
        ratios[n_i] = float(score)

    return ratios, counts, inline_weights


def parse_total_score(output):
    m = re.search(r"TOTAL_SCORE\s+([0-9]+(?:\.[0-9]+)?)", output)
    if m:
        return float(m.group(1))
    reward_path = Path("/logs/verifier/reward.txt")
    if reward_path.exists():
        try:
            return float(reward_path.read_text(errors="replace").strip())
        except Exception:
            pass
    return None


def main():
    output = read_text("/tmp/test_full.log")
    script = read_text("/tests/test.sh")

    statuses = parse_statuses(output)
    if not statuses:
        statuses = [("tests/roadmap.py::unknown", ERROR)]

    ratios, counts, inline_weights = parse_phase_ratios(output)
    weights = parse_weights(script, len(statuses))
    for idx, weight in inline_weights.items():
        if 1 <= idx <= len(weights):
            weights[idx - 1] = weight

    details = []
    weighted_total = 0.0
    weight_total = 0.0
    failed_names = []

    for pos, (name, status) in enumerate(statuses, start=1):
        phase_num = parse_phase_number(name, pos)
        weight = weights[pos - 1] if pos - 1 < len(weights) else 1.0
        if phase_num in ratios:
            ratio = ratios[phase_num]
        else:
            ratio = 1.0 if status == PASSED else 0.0
        contribution = weight * ratio
        weighted_total += contribution
        weight_total += weight

        if phase_num in counts:
            phase_passed, phase_total = counts[phase_num]
            message = (
                f"Phase {phase_num}: {phase_passed}/{phase_total} checks passed; "
                f"weighted contribution {contribution:.6f}/{weight:.6f}"
            )
        else:
            message = (
                f"Phase {phase_num}: status {status}; "
                f"weighted contribution {contribution:.6f}/{weight:.6f}"
            )

        if status != PASSED:
            failed_names.append(name)

        details.append(
            {
                "name": name,
                "status": status,
                "message": message,
                "score": contribution,
                "weight": weight,
            }
        )

    passed_count = sum(1 for _, status in statuses if status == PASSED)
    total_count = len(statuses)
    pass_rate = passed_count / total_count if total_count else 0.0
    total_score = parse_total_score(output)
    if total_score is None:
        total_score = weighted_total / weight_total if weight_total else 0.0

    summary = (
        f"{passed_count}/{total_count} phases passed; "
        f"weighted score {total_score:.6f}"
    )
    if failed_names:
        summary += ". Failed: " + ", ".join(failed_names[:10])
        if len(failed_names) > 10:
            summary += f" (+{len(failed_names) - 10} more)"

    result = {
        "valid": True,
        "score": total_score,
        "pass_rate": pass_rate,
        "summary": summary,
        "details": details,
        "metrics": {
            "phase_weighted_total": weighted_total,
            "phase_weight_total": weight_total,
            "source": "roadmap_structured_json",
        },
    }

    print(">>>>> Start Structured Result")
    print(json.dumps(result, ensure_ascii=False, indent=2))
    print(">>>>> End Structured Result")


if __name__ == "__main__":
    main()

任务要求

Schemathesis 是一个自动测试 Web API 的工具。解题者扩展 schemathesis 4.13.0 中的报告和可观测性功能，并被要求 "Treat /app/TODO.md as the authoritative task specification."（把该文件视为权威的任务规格。）评分器用隐藏测试为工作评分。这里涉及两个目标：

  • Target 2：一个 "JunitXmlWriter: A context-manager class that writes JUnit XML reports"（写出 JUnit XML 报告的上下文管理器类），带有一个 "records a test error"（记录测试错误）的 record_error 方法。JUnit XML 是 CI（持续集成）系统读取的一种常见测试报告格式。
  • Target 5 的第 2 项修复："The allow-extra-parameters = false configuration suppresses unexpected-properties coverage scenarios for query, header, and cookie parameters, but not for request bodies. Bodies should be included in this suppression."（该配置会为 query、header 和 cookie 参数抑制"意外属性"覆盖场景，但不会为请求体抑制；请求体也应纳入这一抑制。）

类别：系统与软件工程。

问题出在哪里

1. JUnit 测试接受损坏或不完整的报告

规则。 record_error 必须在 JUnit XML 报告中记录一个错误。原始测试只检查字符串 "schemathesis" 和 "test_label" 是否出现在输出中的某处。

例子。 四个测试用写入器：correct（基于初始文件的命令行工具已在使用的 junit_xml 库）、drops_error（格式良好的 XML，但没有 <error>）、unterminated（格式错误的 XML）和 plaintext（根本不是 XML）。预期：只有 correct 通过。在原始测试（"orig"）和修复版测试（"repaired"）下的实际结果：

correct      orig: 1 passed   repaired: 1 passed
drops_error  orig: 1 passed   repaired: 1 failed
unterminated orig: 1 passed   repaired: 1 failed
plaintext    orig: 1 passed   repaired: 1 failed

为什么重要。 一个丢掉 <error> 的写入器会让一次失败的操作在 CI 中看起来像是通过了，而它仍然拿到这项测试的分数。反方向上，一个正确的写入器如果把测试套件命名为 schemathesis 以外的名称，就会在原始测试中失败，因为此时字符串 schemathesis 在其输出中根本不出现（见下文在 E2B 上的修订运行）；而 TODO.md 并没有规定套件的名称。

2. 省略请求体的测试永远不会失败

规则。 在 allow-extra-parameters = false 下，请求体不得产生"意外属性"场景（带有额外的、未声明字段的生成测试输入）。

例子。 未改动的初始文件缺少请求体修复。在它上面，若要求抑制请求体，cover_schema_iter 会产生 12 个值，而且其中出现了不应有的 OBJECT_UNEXPECTED_PROPERTIES 场景。这 12 个值全部属于覆盖模块中的 GeneratedValue 类。测试却按另一个同名的类过滤，因此它得到的场景集合总是空的，其检查永远不会失败。预期：如测试自己的头部注释所说，该测试在初始文件上失败。实际：它在初始文件上通过。它在一个忽略该标志、总是省略请求体的实现上也通过。

为什么重要。 该测试为缺失或错误的行为给分。针对查询参数的对应测试同样永远不会失败，但它守护的只是初始文件已有的行为。

影响有多大

分数为五个阶段上的 Σ wᵢ·passedᵢ/totalᵢ / 10，权重为 2、2、3、2、1（/tests/test.sh）。Phase 2 中一项测试价值总分的 2/(14·10) = 1/70；Phase 5 中一项测试在原始版中价值 1/100，在修复版中价值 1/120。

  • 原始版中的错误得分：JUnit 测试至多给出 1/70（100 分制下约 1.4 分），请求体测试至多给出 1/100（1.0 分）。
  • 原始版中的错误扣分：对于输出不含字符串 schemathesis 的正确写入器，JUnit 测试扣去 1/70（约 1.4 分）。
  • 修复版下的最大降幅：4.76 分。一份在原始版下全部通过、但在修复版 JUnit 测试和全部四项新覆盖测试中失败的提交，在 Phase 2 失去 1/70，在 Phase 5 失去 10·(1 − 8/12)/100 = 1/30，合计 1/70 + 1/30 = 4.76 分。所测的改动版本分别失去 1.43、0.83 和 1.67 分。
  • 修复版下的最大升幅：2.76 分。修订后的 JUnit 测试可能在原始测试失败的地方通过：一个输出中从不含字符串 schemathesis 的正确写入器（例如套件用了别的名称），在原始测试中失败、在修订后的测试中通过，即 1/70 或 1.43 分。在 Phase 5 中，只要覆盖生成器能运行，两项原有的覆盖测试在任何提交上都会通过，因此在没有通过其他 Phase 5 测试的情况下，所占份额从 2/10 变为至多 4/12，即 1.33 分；合计 2.76 分。初始文件和桩实现增加 0.5 分。只有当一份提交从 schemathesis.specs.openapi.negative 中删除了 GeneratedValue 类（原有覆盖测试导入了这个类）时，升幅才可能达到 4.76 分。
  • 所测的错误实现中，没有一个得分高于正确实现；所测的唯一一个正确实现保持 1.0。

修复

修复版改动三个评分器文件：

  • /tests/test_02_reporting.py 会解析 XML。它接受 testsuite 或 testsuites 作为根元素，并要求有一个名为 test_label（即传给 record_error 的标签）的测试用例，其中包含一个以文本或属性形式携带消息的 <error>。这些正是 TODO.md 所述的要点：一份 JUnit XML 报告，以及 record_error "records a test error"（记录测试错误）。测试名称和测试数量都不变。
  • /tests/test_05_email_coverage.py 使用正确的 GeneratedValue 类，并要求得到正确类型的非空值流。它还为请求体和查询参数分别添加了允许额外参数和拒绝额外参数的用例。
  • /tests/test.sh 把 Phase 5 的测试数从 10 提高到 12。权重不变。

在 task.json.in 中，只有 judge.image_tag 改变。

我们如何检查

  • 在按摘要固定的原始镜像中运行原始评分器。 评分器镜像中保存了未经修改的 schemathesis 4.13.0 初始文件。每份测试提交都在全新的 --network none 容器中，分别通过完整的原始 judge.eval_cmd 和修复版评分器运行。
  • 直接检查。 检查了 cover_schema_iter 在初始文件上产生的每个值的类，这说明了原始覆盖过滤为何总是为空。修复版覆盖测试在初始文件、一个正确的修复和一个总是省略请求体的修复上运行。
  • 可重复性。 原始版和修复版评分器的并排对照运行做了三次，结论没有变化（data/paired-repeatability.md）。这些重复使用的是第一版修复。使用修订版修复的运行也做了三次（evidence/runs/schemathesis_reporting_observability-v2-paired-rev2、-rev2-rep2、-rev2-rep3），分数和每项测试的结果都相同。

局限

  • 没有运行任何 AI 模型或求解器。影响只在我们编写的测试提交和改动版本上展示。
  • 作为正确的测试提交，只有一个完整实现可用，而且尝试过的每个正确 JUnit 写入器都基于 junit_xml。修订后的 JUnit 测试仍然假定通常的 JUnit 形式：错误是 <testcase> 中的一个 <error> 元素，且该测试用例的 name 就是标签。一个把错误记录为 <failure>、或只把标签放在 classname 中的写入器会失败，根元素带有 XML 命名空间（<testsuites xmlns=…>）的报告也会失败（本地探测；XML 声明、字节顺序标记、CDATA 或嵌套的 testsuites 都能通过）；TODO.md 对这些细节都没有明确说明。
  • Phase 4 的测试计数有一处反常（预期 9 项，收集到 11 项）未作改动，不在范围之内。
  • 修复包在一台干净的机器上从零重建过（evidence/runs/materialize-check-g2，status: exit=0）：全部 3 个输出与锁定值一致，构建出的镜像中是锁定的测试文件。
  • 更广泛的集成行为（xdist、有状态运行、一处 55/53 的测试计数反常）没有检查。
  • TODO.md 取自工作目录树的云端导出（sha256 097166d3…），而不是从工作镜像中重新提取。
  • 隐藏测试没有保存在本仓库中。重新运行检查时，会从固定的评分器镜像中提取它们。
