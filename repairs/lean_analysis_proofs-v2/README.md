# Lean Analysis Proofs, fixed version (`lean_analysis_proofs`)

**Validation scope:** Component controls validate the corrected statements and target filtering. The paired runs used Mathlib `491a409`, while the actual `eval_cmd` copies the baseline with `3203991`; that execution path and both final image builds remain unverified. These records do not establish a ready end-to-end release.


## What this fixes

Two statements that solvers must prove are false as written, so no honest submission can earn them. The original grader also scores hidden helper declarations that Lean generates, so the score depends on proof style, and three placeholder statements can never be credited. The fixed version corrects the two statements and stops scoring the generated helpers and the placeholders, leaving 2338 scored targets.

## What changes

### The problems in detail

1. **Two false statements** (`reviews/lean_analysis_proofs.md`). `Chapter11.MajorizesOn.anti_symm`
   parses as `∀ x ∈ I, (f x = g x ↔ …)` because of operator precedence. `Chapter11.PiecewiseConstantOn.div`
   puts both hypotheses on `f`, so `g` is unconstrained. The negation of each is checked by Lean's kernel against the
   task's own definitions, so no submission free of `sorry` can earn these 2 targets. A correct proof of
   the intended statement is scored "type changed".
2. **Helper targets generated by the compiler** (`reviews/lean_aux_name_scoring.md`). 560 of the 2901
   targets are names the compiler generates (`X._proof_N`, `X._simp_N`, `X.eq_N`, `X.match_N`,
   `X.congr_simp`, `X._sizeOf_*`, `X._sunfold`, `X._unsafe_rec`). They are credited only if the
   generated name and the printed type match exactly. Honest proofs renumber, merge or reshape them,
   so the score depends on proof style. In the sample run on the grader, a tactic-mode `omega` proof scored 1
   point less than an equally correct term proof. At least 49 points are out of reach.
3. **Three placeholder statements** (`Chapter3.empty_function_{bijective,onto,one_to_one}_iff : … ↔ sorry`).
   The solver has to fill in the statement. Any filled-in statement changes the type text, so these
   targets can never be credited.

### Exact change

- `Analysis/Section_11_3.lean`: `∀ x ∈ (I:Set ℝ), f x = g x ↔ …` becomes `(∀ x ∈ (I:Set ℝ), f x = g x) ↔ …`.
- `Analysis/Section_11_2.lean`: `(hg: PiecewiseConstantOn f I)` becomes `(hg: PiecewiseConstantOn g I)`
  (Tao, *Analysis I*, Lemma 11.2.8).
- `eval_lean.py` (the grader) excludes two kinds of baseline target:
  - names with a component that is generated by the compiler: it starts with `_`, or it is `match_N`,
    `eq_N`, `eq_def`, `congr_simp` or `proof_N`;
  - targets whose baseline type text contains the token `sorry`.

  These names are also not reported as "new bad". `metrics.excluded_baseline_count` is added.
  The scoring logic is otherwise unchanged.
- The two Lean edits go into the grader's baseline repository, which is the only copy in the grader image
  (`/home/workspace/judge/se-bmk-intern/analysis`). They also go into the solver's starter
  (`Dockerfile.work`, `files/work/`).
- The baseline listing is regenerated with the task's own tooling. `lake build ListDeclAxiom` ran
  in the grader image (`paired/run_local.sh`, step 2). It rebuilt Section_11_2 through 11_10,
  `Analysis` and `ListDeclAxiom`. All 90 rewritten files (sources, oleans, ileans, traces, IR) are
  in `files/judge/v2-build-artifacts.tar`, and the `Dockerfile` `ADD`s them at their original paths.
  The grader regenerates the baseline at grading time (`--baseline-repo`), and the new build makes that
  a replay of the fixed version's listing.

**Target set.** The raw listing still has 2901 declarations marked BAD that contain `sorry`. The only difference in the listing
is the two corrected type strings. The fixed version's scored set has **2338 targets**: 2901 − 560 generated −
3 placeholders.
- The 560 are the reviewer's 559 plus `Chapter5.ExtendedReal._sizeOf_inst`, whose parent `Chapter5.ExtendedReal`
  is a target.
- Every excluded helper has a parent that is itself a target. The parent's axiom check follows every dependency, so it
  covers the helper's dependence on `sorry`, and no proof obligation goes unchecked.

**Placeholders are excluded.** The 3 placeholders are not scored by the axiom check alone.
That would accept any filled-in statement, including a trivial one such as `P ↔ P`. Scoring them
properly would need a hidden intended answer, and the task has none. They remain in the starter as
ungraded exercises.

### Why this is the smallest change

- Two one-token edits to the source.
- One filter on the target set, about 20 lines in the grader, with no change to type matching, the list of
  allowed axioms, the HASH logic or the rule for the denominator.
- No new data, no reweighting, and no change to `eval_cmd`, the timeout, the parser or the score scale.

### Are scores comparable? The score scale

**Scores from the fixed version are not comparable with the original.**
- The denominator changes from 2901 to 2338.
- Helper credit is no longer awarded. Partial instance proofs that earned `_proof_N` points in the original
  now earn nothing until the instance is complete.
- Two targets become reachable.
- In the side-by-side sample, the same honest submission scores 26/2901 = 0.00896 in the original and
  15/2338 = 0.00642 in the fixed version.

The reference points of the score scale (`rescale`) are kept unchanged: `linear`, lower 0.0, upper 1.0. They are not
reference points taken from a leaderboard rank. They are the exact bounds of the pass rate, which is a fraction of targets, so they
are exactly computable for the fixed version as well. No new rank-based reference points are invented. Past leaderboard
numbers from the original version must not be placed on the same scale as the fixed version.

## How it was checked

The side-by-side run of the original and fixed graders is in `paired/` (`run_local.sh`, `results.md`). In plain words: the unchanged starter scores 0 under both. A submission that proves the two corrected statements earns them only under the fixed grader. Honest proofs of one module written in term style, tactic style or with `omega` scored 26, 26 and 25 of 2901 on the original grader, and all score the same 15 of 2338 on the fixed grader. A proof with a type error fails to build under both.

## Build and use

Git does not contain any file copied from the EdgeBench images. It holds only our diff (`repair.patch`) and the recipe for rebuilding the full files. Regenerate them, then build:

```bash
./materialize.sh && docker build -t edgebench.judge.lean_analysis_proofs:lean_analysis_proofs-v2-judge .
```

`materialize.sh` takes the following steps:

1. Pull the pinned image(s) by digest, unless already present.
2. Extract the original files with `docker create` and `docker cp`. No container runs in this step.
3. Check each original against `source-lock.json`.
4. Apply `repair.patch` with `patch -p1`.
5. Verify the sha256 of every file under `files/` (and `orig/`) against `source-lock.json` → `materialize.outputs`. Any mismatch fails loudly.

After that, the `Dockerfile` builds without changes. Regenerated files keep the file mode they have in the image.
See `../MATERIALIZE-CHECK.md` for how each package was verified.

`files/judge/v2-build-artifacts.tar` is not stored either. `materialize.sh` rebuilds it inside the original 33 GB grader image. It copies the patched sources in place, runs `lake build ListDeclAxiom` and `lake build` (offline, `--network none --memory 4g --cpus 2`, a few minutes) and packs the 90 artifact paths listed in `source-lock.json`. The oleans are not expected to be byte-identical, so the tar is accepted when two checks pass. The rebuilt file set must equal the locked member list. The regenerated ListDeclAxiom listing must be byte-identical to `paired/out/v2-listing.txt` (sha256 in `materialize.lean_build`). The script holds the machine-wide heavy-job lock `/tmp/ebv-heavy.lock` for the whole run. `MATERIALIZE_SKIP_LEAN_BUILD=1` regenerates only the text files; `docker build` then fails until the tar exists. `files/work/` is copied from the patched grader sources, and `orig/` is regenerated too. Build the solver image with `docker build -f Dockerfile.work -t edgebench.work.lean_analysis_proofs:lean_analysis_proofs-v2-work .`. That build is still unverified, as noted below.

## Limits

- **Not verified, and why: the image builds and the actual `eval_cmd` path.** The grader image unpacks to about 33 GB, and `materialize.sh` with its Lean rebuild, plus `docker build` of both images, needs about 45 GB of free disk, more than the 21 GB E2B workers used for this audit provide: the clean-machine rebuild check of all packages could not pull the grader image there (`evidence/runs/materialize-check-lean`, `no space left on device`; the other 31 packages passed). So neither image was built, and the original `eval_cmd` (Mathlib `3203991`, full rebuild) was not run on the fixed version. This stays a documented limitation until the build is run on a machine with about 45 GB of free disk.
- **The work image was not pulled** (only the 33 GB grader image was).
  - `Dockerfile.work` assumes that the starter lives at `/home/workspace/se-bmk-intern/analysis` and
    equals the grader's sources. It also assumes the files are owned by `agent`.
  - None of these is verified.
- **`docker build` was not run.** An equivalent installation was tested: the same tar was
  extracted over the original image paths, plus `eval_lean.py` (side-by-side run, resume step). Lake then
  rebuilt 0 modules and produced a listing byte-identical to the regenerated one.
- **The side-by-side runs were local, not on E2B.** Each submission build started from the prebuilt
  `.lake/build` in the grader's repository, with Mathlib `491a409`. The original `eval_cmd` instead copies
  `/home/workspace/baseline/.lake`, which has Mathlib `3203991`, and does a full rebuild. This is the
  same deviation as in the earlier reviews.
- Other false targets among the 2338 were not checked.
- The name filter works on the text of names. A declaration named by a user with a final component like `eq_1` would be
  excluded too. None exists in this baseline: all 560 matches were checked.
