# Materialize check (2026-10-12)

**Policy (user decision).** Repair packages in Git contain no files copied from the EdgeBench Docker images. Each `*-v2` package ships the following:

- `repair.patch`: a `diff -u` from each in-image original to the v2 file, with paths `a/files/…` → `b/files/…` and a `# <dst> <- <image>:<path>` line above each file.
- `materialize.sh`, which regenerates the image-derived files.
- `source-lock.json` → `materialize`: the images, the sha256 of each input original, and the sha256 of each output.

Task-JSON hunks were moved verbatim from the old patches to `task-json.diff`. `files/` and `orig/` stay in the working tree; the publish manifest excludes them.

## How the patches and scripts were made

Generator: `tools/make_materialize.py` with template `tools/materialize.sh.in`. It extracts the originals with `docker create` + `docker cp`, so no container runs. It then diffs them against the reviewed reference `files/` tree, byte-exact so CRLF files are preserved.

Before writing anything, the generator ran two checks:

- Every extracted original matched the original sha256 already recorded in that package's earlier lock.
- Every output matched the earlier v2/replacement sha256.

Both checks held for all 21 packages that have files.

## How each package was verified

"Clean copy" means:

1. Copy the package with `files/` and `orig/` removed.
2. Run `./materialize.sh`. It pulls if needed, extracts, checks the originals, patches and verifies the sha256 of every output against `source-lock.json`.
3. Compare byte for byte with the reference tree.
4. Run `docker build` on the unchanged Dockerfile(s).

The E2B jobs started with no images on the worker, so they also exercised `docker pull` by digest. Local runs used images already on the host. The two borden images (about 0.6 GB each) were pulled locally for this check.

### lean_analysis_proofs-v2: what exactly was verified

- `files/judge/v2-build-artifacts.tar` is no longer needed in Git. `materialize.sh` does the following:
  1. Copies the patched `Section_11_2.lean`, `Section_11_3.lean` and `eval_lean.py` into the original judge image.
  2. Runs `lake build ListDeclAxiom` and then `lake build`.
  3. Packs the 90 paths locked in `source-lock.json` → `materialize.lean_build.artifact_members`.
- The script fails unless three checks pass:
  - The regenerated ListDeclAxiom listing has the sha256 of the saved `paired/out/v2-listing.txt`.
  - The set of files the rebuild rewrote equals the 90 locked members.
  - The tar lists exactly those members.
- Clean-copy result:
  - The listing was byte-identical (4743 lines).
  - The member set was identical.
  - **All 90 member files were byte-identical** to those in the saved tar, oleans included. Only the tar container differs (mtimes): sha256 `8fa68b0a…` vs saved `423668a8…`.
  - `docker build` of the judge Dockerfile succeeded. In the built image, the three text files have the locked v2 sha256.
- **Not verified:** `Dockerfile.work`, because the 8 GB work image was never pulled. This is the same limit as before. Materialize derives `files/work/` from the patched judge sources.

## Material limits and side notes

- **File modes follow the in-image originals**, not the earlier hand-made reference copies. The changes:
  - `dabic/eval_dabic_v2.py`: 0555, was 0644.
  - `exchange/eval_exchange_core.py`, `equivalence/checker.cpp` and `tree_block/interactive_lib.cpp`: 0755, were 0644.
  - `borden/orig/*.json`: 0644, was 0755.

  The Dockerfile `COPY` keeps these modes, so the v2 images now match the original modes. Every affected `eval_cmd` runs these files through an interpreter or compiler, so scores are unaffected. The paired results were produced with the earlier modes.
- **Script revision tested on E2B.** E2B ran a `materialize.sh` revision that differed from the final one only in the lean-only lock block, which does not run when `LEAN_BUILD=0`. `repair.patch` and the lock data were identical. Of the E2B packages, all except college and ffmpeg were also re-run locally with the final scripts.
- **Requirements.** `materialize.sh` needs Docker, GNU patch, python3 and sha256sum. Exchange also needs curl and network access to Maven Central. Borden and openrct2 need the EdgeBench `tasks/` directory.
- **Other image-file copies remain outside the repair packages.** A sha256 scan found exact image-file copies in these places:
  - `evidence/scripts/`:
    - `exchange_core_throughput/eval_exchange_core.orig.py`
    - `equivalence_class_divide_and_conquer/checker_original.cpp`
    - `smt_solver/evaluate_original.py`
    - `lean_formalization/eval_lean.py.orig`
    - `lean_family_census/out/*/eval_lean.effective.py`
  - `evidence/runs/*-v2-paired*/pkg/files/`: 17 job directories hold package copies.

  These are outside the `repairs/*-v2` scope of this check. The publish manifest should exclude them, or they need the same treatment.
- Housekeeping: the temporary build tags were removed, and `docker builder prune -f` was run once after the lean build.
- E2B jobs: `e2b/jobs/materialize-check-a` (college, ffmpeg) and `materialize-check-b` (borden, exchange, integer, openrct2, triangulation). Both finished with exit 0 and their workers were killed (`e2b/ledger.jsonl`).
