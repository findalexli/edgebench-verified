# Effect on the published leaderboard

EdgeBench publishes each model's score on every task. This page uses those numbers to work out how the problems we found change each model's average over the 51 public tasks. No AI model was rerun, and the agents' original submissions are not public. Only part of the effect can therefore be calculated. **The total change cannot be determined from public data**: it would require rerunning the models on the fixed tasks, or, for some fixes, regrading the original submissions. What follows is the largest possible change, a range from fixes with a proven limit, and the corrections that can be computed exactly. All ranges assume that no fix turns a failed run into a scored one or the reverse; a fix that does can move a task's average further. Kept tasks are treated as unchanged, including those whose run-to-run variation for scoring agents is unmeasured (ANN, NetHack, Wesnoth). Generated by `tools/estimate_impact.py`; the numbers are in [data/impact.csv](data/impact.csv).

## Summary

Models as EdgeBench names them: Claude Opus 4.8, GPT-5.5, GPT-5.4, GLM-5.1 and DeepSeek-V4-Pro (DS-V4-Pro).

| Model | Published average | After the corrections we can calculate exactly | Range, adding fixes with a proven limit | Largest possible change |
| --- | ---: | ---: | :---: | :---: |
| Opus 4.8 | 44.2 | **46.0** (+1.9) | 45.6 – 47.1 | 36.6 – 63.6 |
| GPT-5.5 | 43.1 | **44.8** (+1.6) | 44.4 – 46.2 | 36.1 – 63.7 |
| GPT-5.4 | 34.2 | **35.6** (+1.4) | 35.2 – 37.6 | 28.6 – 58.1 |
| GLM-5.1 | 30.4 | **31.9** (+1.5) | 31.5 – 33.9 | 25.5 – 54.9 |
| DS-V4-Pro | 25.7 | **26.8** (+1.2) | 26.5 – 28.8 | 21.0 – 49.9 |

- **Calculated exactly.** Where a fix only changes how a raw result becomes 0–100, or removes a task, each published score can be recomputed directly. Together these raise every model's average by 1.2 to 1.9 points: the Treant Forest scale adds 1.0 to 1.4, where the old scale capped every score at 21.02 out of 100; the removal of D-ABIC adds 0.2 to 0.5; and the Borden Inversion scale subtracts 0.01 to 0.08. The order of the models does not change: Opus 4.8 > GPT-5.5 > GPT-5.4 > GLM-5.1 > DS-V4-Pro.
- **Proven limit.** For 11 fixed tasks the largest possible effect is bounded by the task's own scoring (proved or computed from the grader; for PFR partly inferred from its rule; for Portfolio Risk from a decimal sweep, not a proof). Together they can move an average by at most 0.4 points down or 2.0 points up. That is enough to swap Opus 4.8 and GPT-5.5, so the 51 public tasks alone do not show which of them is ahead.
- **Direction known, size unknown.** For 18 fixed tasks we know whether scores go up or down, but not by how much. Finding out would require new runs (for fixes that change only instructions or inputs) or regrading the original submissions (for fixes to the grader). The largest possible change lets every fix, these and the ones with a proven limit, take its largest possible effect: a score that goes down could fall to 0, and one that goes up could rise to 100. These tasks, with the open part of Borden Inversion, account for up to 9.0 points down or 21.1 up. It is an outer limit, not a prediction.

The recomputed average is only the part we can calculate; the other fixes can still push it up or down. Several of the largest effects are in the group whose size is unknown.

## Can two models swap places?

Two neighbouring models can swap if the most one can fall plus the most the other can rise is at least the gap between them.

| Models | Gap after exact corrections | Largest swing with proven limits | Largest swing within the largest possible change |
| --- | ---: | ---: | ---: |
| Opus 4.8 vs GPT-5.5 | 1.2 | 1.8 | 28.4 |
| GPT-5.5 vs GPT-5.4 | 9.1 | 2.3 | 31.1 |
| GPT-5.4 vs GLM-5.1 | 3.8 | 2.4 | 30.1 |
| GLM-5.1 vs DS-V4-Pro | 5.0 | 2.4 | 29.4 |

No order is guaranteed within the largest possible change. Settling it requires rerunning the models on the fixed tasks.

## How EdgeBench computes a published score

From the EdgeBench technical report (arXiv 2607.05155, Appendices B and G) and its evaluation platform; the quoted passages are in [evidence/impact/edgebench-scoring-method.md](evidence/impact/edgebench-scoring-method.md):

- Each model gets **three 12-hour runs** per task. The published task score is the **average over the valid runs**; if a run fails, the average uses the runs that remain.
- Each run is scored by its **best submission so far** at the time limit (2 h, 4 h, … 12 h). Each run's score is converted to 0–100 before averaging.
- A model's headline number is the plain average over tasks. Recomputing it from the published per-task table gives the published values to within rounding.

Three consequences:

1. **Only changes of scale can be undone from published numbers.** Any other fix changes which submissions score what. Only regrading the hidden submissions can show that for fixes to the grader, and only new runs for fixes that change instructions or inputs (ARC, OpenRCT2, OpenTTD, the Borden convention, Triangulation's inputs).
2. **Keeping the best submission magnifies over-crediting.** A run keeps its highest score, so a problem that only sometimes over-credits (noise, a lucky gamble, a lenient check) still raises the run's score. The agents also see their scores and keep trying for 12 hours, so they are more likely than a one-time solver to find a lenient check and keep using it.
3. **Discarding failed runs hides some problems.** A run that a problem kills (a time-out, a crashing program) may be discarded rather than scored 0. The published score then reflects only the runs that survived.

## Large effects whose size is unknown

Of the 32 tasks fixed or removed, 3 can be corrected exactly, 11 have a known maximum effect, and 18 (plus part of Borden Inversion) have a known direction only. The largest of these:

- **Integer Compression Codec.** Every original score is measured against stored reference numbers that the documented starting program cannot reach. On real submissions the original raw result was 2.4 to 3.7 times lower than the documented definition gives (up to about 9 times for a simple honest codec). The fixed version also needs a new 0–100 scale (Section "A check against real agent runs"), so the direction of the change depends on the submission.
- **OpenTTD.** A program that follows the instructions calls a function that does not exist and stops working. Its effect depends on how often agents followed that instruction, which only new runs can show.
- **SMT Solver.** Correct answers are rejected on some hidden problems, so a model's score can only rise or stay the same, by an amount that depends on how it writes its answers.
- **Lean Analysis Proofs.** The set of scored items changes from 2,901 to 2,338, so every score moves, in a direction that depends on which proofs each run completed.
- **Exchange Core, Jagua, FFmpeg, College English.** These accept wrong work. Because a run keeps its best submission, any over-credited submission sets the run's score.

## A check against real agent runs

EdgeBench has not released its runs. A third party has published one run of Claude Opus 5.5 on 16 of the public tasks, four hours each, with every submission and its original score (`adafadaq/edgebench-opus-5-5-xhigh-rollouts` on Hugging Face). Seven of those tasks are ones we fixed. We read the submission histories of all seven, and regraded submissions of two of them (Order Addition and Integer Codec) with both graders (`evidence/runs/opus55-rollouts-meta/`, `evidence/runs/opus55-regrade/`).

| Task | Original grader | Fixed grader | What it shows |
| --- | --- | --- | --- |
| Order Addition | Every submission that produced a result passes 4 of 5 tests (five earlier automatic snapshots without a result pass 2); the run keeps its first agent submission, score 3.79, and ignores a later 41.24 | The three regraded submissions pass 5 of 5, so the run would keep 41.24 | The defect occurs in practice: +37.45 points on this task for this run, because the task keeps the submission that passes the most tests (if you instead keep the highest score, nothing changes) |
| Integer Codec | Best submission: raw 66.31 (75.72 on the run's own machine) | Raw 160.76; 50.08 on the fixed scale | The original 0–100 scale would clip the fixed result to 100, so the fix now uses a scale from 1.0 to 320 |
| Borden Inversion | Best submission: 60.10, reached by iterating against the grader's scores | Not regraded (raw results are identical for the same answer) | An agent that iterates can partly learn the hidden convention; the one-shot 7.0 vs 31.2 gap overstates the effect for such agents |
| Tree Block Partitioning | 100 | Not regraded | No program multiplies a value by itself in place (`v *= v`); no effect in this run |
| Graph Node Classification | Every submission scored as a normal prediction file | Not regraded | No sign of the defect in this run |
| Schemathesis Config | Full marks | Not regraded | Unknown whether the decorator returns the function unchanged |
| Lean Analysis Proofs | 2,810 of 2,901 targets | Not regraded (needs the 33 GB task image) | Unknown |

This is one model, one run per task and four hours instead of twelve. It shows that the problems occur in real runs and that one of our fixes needed a correction; it does not measure the leaderboard effect.

## The exact corrections

These fixes change only how a raw result is converted to 0–100, so each published score converts directly.

| Model | Treant Forest: original → fixed | Borden Inversion: original → fixed | Average over 51 → 50 tasks (50 → 49 for Opus 4.8) |
| --- | ---: | ---: | ---: |
| Opus 4.8 | 18.0 → 86.1 | 48.4 → 44.4 | 44.14 → 45.99 |
| GPT-5.5 | 15.6 → 74.9 | 38.5 → 35.3 | 43.16 → 44.80 |
| GPT-5.4 | 13.3 → 64.2 | 8.0 → 7.3 | 34.26 → 35.65 |
| GLM-5.1 | 16.9 → 80.9 | 15.1 → 13.9 | 30.36 → 31.88 |
| DS-V4-Pro | 13.5 → 65.1 | 38.2 → 35.0 | 25.64 → 26.85 |

- **Treant Forest.** The raw result (the total number of turns) is unchanged. The original scale gives 20 points at 88,189 turns, 80 points at 330,195 and 100 points at 451,198, far above the turn cap of 92,304, so no score can exceed 21.02. The fixed scale runs straight from the starting program's 3,418 turns (0 points) to the cap, 92,304 (100 points). Every published score is below 20, where the original scale is a straight line from 5,369 turns (0 points) to 88,189 turns (20 points), so each converts exactly: turns = 5,369 + score/20 × 82,820. This also holds for an average of runs, because the conversion is a straight line, with two exceptions (Lean shows the formula fails there, `evidence/formal/notes/treant_forest.md`; the sizes below are computed, not proved). A run that scored 0 had a raw result of at most 5,369 turns and scores between 0 and 2.19 on the fixed scale, so the formula can overstate the fixed average by up to 2.19 points divided by the number of runs. A run between 20 and 21.02 falls on the next segment and shifts the result by at most about 0.12 divided by the number of runs.
- **Borden Inversion.** The original task had no 0–100 conversion, so the published value is the raw result, which runs from 0 to 109. The fixed version reports raw × 100/109. This is only the change of scale. The fix also gives agents the grader's physics convention, which raises honest one-shot fits (7.0 → 31.2 raw in our tests; an agent iterating on the grader's feedback can already learn part of it). That part needs new runs and is not included.
- **D-ABIC Gravity Inversion** is removed, so the average is taken over 50 tasks (49 for Opus 4.8, which has no valid result on Rust Multicrate).

## Limits

- **This is not a regraded leaderboard.** The original submissions are not public, so none was regraded.
- **Only the 51 public tasks are covered.** EdgeBench's full leaderboard also includes 83 unreleased tasks.
- **The ranges are not estimates.** The proven-limit range is the largest movement we proved, computed or (for PFR) inferred, and the largest possible change lets every fix take its largest possible effect.
- **Rounding.** Recomputed averages differ from the published ones by at most 0.06, because the per-task table is rounded to one decimal. All corrections are applied to the recomputed averages.
- **Fixed tasks form a new version of the benchmark.** These figures show how much the problems matter. They are not a replacement leaderboard.
