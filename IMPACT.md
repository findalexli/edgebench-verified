# Effect on the published leaderboard

EdgeBench publishes each model's score on every task. This page uses those numbers to work out how the problems we found change each model's average over the 51 public tasks. No AI model was rerun, and the agents' original submissions are not public. Only part of the effect can therefore be calculated; the rest is given as a range. Generated by `tools/estimate_impact.py`; the numbers are in [data/impact.csv](data/impact.csv).

- **Calculated exactly.** Some fixes change only how a raw result is converted to 0–100, so a published score can be converted directly. They raise every model's average by 1.2 to 1.9 points. Most of this comes from Treant Forest, where the old scale capped every score at 21.02 out of 100. The order of the models does not change: Opus 4.8 > GPT-5.5 > GPT-5.4 > GLM-5.1 > DS-V4-Pro.
- **Known maximum.** For 8 fixed tasks we proved or demonstrated the largest possible effect. Together they can move an average by at most 0.3 points down or 1.4 points up. That is enough to swap Opus 4.8 and GPT-5.5, so the 51 public tasks alone do not show which of them is ahead.
- **Direction only.** For 12 fixed tasks we know whether scores go up or down, but not by how much. Finding out would require regrading the original submissions. The widest range lets each of these take its largest possible effect: a score that goes down could fall to 0, and one that goes up could rise to 100. The true values lie inside this range. It is an outer limit, not a prediction.

Read the exact column as the part of the change that is certain, not as the size of the problem. Several of the largest effects are in the direction-only group.

## Can two models swap places?

Two neighbouring models can swap if the most one can fall plus the most the other can rise is at least the gap between them.

## How EdgeBench computes a published score

From the EdgeBench technical report (arXiv 2607.05155, Appendices B and G):

- Each model gets **three 12-hour runs** per task. The published task score is the **average over the valid runs**; if a run fails, the average uses the runs that remain.
- Each run is scored by its **best submission so far** at the time limit (2 h, 4 h, … 12 h). Each run's score is converted to 0–100 before averaging.
- A model's headline number is the plain average over tasks. Recomputing it from the published per-task table gives the published values to within rounding.

Three consequences:

1. **Only changes of scale can be undone from published numbers.** Any other fix changes which submissions score what, and only the hidden submissions can show that.
2. **Keeping the best submission magnifies over-crediting.** A run keeps its highest score, so a problem that only sometimes over-credits (noise, a lucky gamble, a lenient check) still raises the run's score. The agents also see their scores and keep trying for 12 hours, so they are more likely than a one-time solver to find a lenient check and keep using it.
3. **Discarding failed runs hides some problems.** A run that a problem kills (a time-out, a crashing program) may be discarded rather than scored 0. The published score then reflects only the runs that survived.

## Large effects whose size is unknown

Of the 23 tasks fixed or removed, 3 can be corrected exactly, 8 have a known maximum effect, and 12 (plus part of Borden Inversion) have a known direction only. The largest of these:

- **Integer Compression Codec.** Every original score is measured against stored reference numbers that the documented starting program cannot reach. In our tests the fix raises scores about 4 times (starting program) to 8 times (a simple honest codec). The published 75.3 and 74.4 could reach the maximum of 100, but per-dataset caps make the factor for strong codecs uncertain.
- **OpenTTD.** A program that follows the instructions calls a function that does not exist and stops working. GLM-5.1's 0.0 fits this.
- **SMT Solver.** Correct answers are rejected on some hidden problems, so every model's score goes up by an amount that depends on how it writes its answers.
- **Lean Analysis Proofs.** The set of scored items changes from 2,901 to 2,338, so every score moves, in a direction that depends on which proofs each run completed.
- **Exchange Core, Jagua, FFmpeg, College English.** These accept wrong work. Because a run keeps its best submission, any over-credited submission sets the run's score.

## The exact corrections

These fixes change only how a raw result is converted to 0–100, so each published score converts directly.

| Model | Treant Forest: original → fixed | Borden Inversion: original → fixed | Average over 51 → 50 tasks |
| --- | ---: | ---: | ---: |
| Opus 4.8 | 18.0 → 86.1 | 48.4 → 44.4 | 44.14 → 45.99 |
| GPT-5.5 | 15.6 → 74.9 | 38.5 → 35.3 | 43.16 → 44.80 |
| GPT-5.4 | 13.3 → 64.2 | 8.0 → 7.3 | 34.26 → 35.65 |
| GLM-5.1 | 16.9 → 80.9 | 15.1 → 13.9 | 30.36 → 31.88 |
| DS-V4-Pro | 13.5 → 65.1 | 38.2 → 35.0 | 25.64 → 26.85 |

- **Treant Forest.** The raw result (the total number of turns) is unchanged. The original scale gives 20 points at 88,189 turns, 80 points at 330,195 and 100 points at 451,198, far above the maximum possible 92,304, so no score can exceed 21.02. The fixed scale runs straight from the starting program's 3,418 turns (0 points) to the maximum 92,304 (100 points). Every published score is below 20, where the original scale is a straight line from 5,369 turns (0 points) to 88,189 turns (20 points), so each converts exactly: turns = 5,369 + score/20 × 82,820. This also holds for an average of runs, because the conversion is a straight line. The one exception would be a run between 20 and 21.02, which falls on the next segment.
- **Borden Inversion.** The original task had no 0–100 conversion, so the published value is the raw result, which runs from 0 to 109. The fixed version reports raw × 100/109. This is only the change of scale. The fix also gives agents the grader's physics convention, which raises honest fits (7.0 → 31.2 raw in our tests). That part needs new runs and is not included.
- **Dabic Gravity Inversion** is removed, so the average is taken over 50 tasks (49 for Opus 4.8, which has no valid result on Rust Multicrate).

## Limits

- **This is not a regraded leaderboard.** The original submissions are not public, so none was regraded.
- **Only the 51 public tasks are covered.** EdgeBench's full leaderboard also includes 83 unreleased tasks.
- **The ranges are not estimates.** The known-maximum range is the largest movement we proved or demonstrated, and the widest range lets every direction-only fix take its largest possible effect.
- **Rounding.** Recomputed averages differ from the published ones by at most 0.06, because the per-task table is rounded to one decimal. All corrections are applied to the recomputed averages.
- **Fixed tasks form a new version of the benchmark.** These figures show how much the problems matter. They are not a replacement leaderboard.
