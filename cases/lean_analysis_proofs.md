# Lean Analysis Proofs (`lean_analysis_proofs`)

**Outcome:** Repair validated on component controls; full release integration pending. <mark>Two statements the solver must prove are false, and the original grader scores helper declarations that the compiler generates, so correct proofs of the same theorem can score differently depending on proof style.</mark>

![A bar of the original 2901 graded targets shows the 2338 the fixed version keeps, plus 560 hidden compiler-made helpers and 3 placeholder statements it no longer scores, with callouts for two false statements and for a correct proof scoring one point less (25 against 26) when the omega tactic renames a helper.](figures/lean_analysis_proofs.svg)

*Two required statements were false and 560 hidden compiler-made helpers were graded, some in a way that depends on proof style; the fixed version corrects the statements and scores 2338 targets.*

## What the task asks

The task is a formalisation of Tao's *Analysis I* textbook in Lean 4, a language for machine-checked math proofs. The prompt asks the solver to "finish **all** sorries in this folder" (a `sorry` is a placeholder for a missing proof). It says "we value minor progress", and warns: "do not modify the signature of existing lemma/theorem/def as these changes will not pass the judge evaluation." The grader (`eval_lean.py` with the task's `ListDeclAxiom.lean`) treats every declaration that depends on `sorryAx` in the baseline repository as one target worth 1 point. A target is credited only if two things hold in the submission. First, the same name uses only the axioms `propext`, `Classical.choice` and `Quot.sound`. Second, its printed type text equals the baseline text exactly. The original version has 2901 targets. Category: Formal Math & Theorem Proving.

## What goes wrong

**1. Two target statements are false.** As installed, the task's own Lean prints:

```
@Chapter11.MajorizesOn.anti_symm : ∀ {f g : ℝ → ℝ} {I : Chapter11.BoundedInterval},
  ∀ x ∈ ↑I, f x = g x ↔ Chapter11.MajorizesOn f g I ∧ Chapter11.MajorizesOn g f I
@Chapter11.PiecewiseConstantOn.div : ∀ {f g : ℝ → ℝ} {I : Chapter11.BoundedInterval},
  Chapter11.PiecewiseConstantOn f I → Chapter11.PiecewiseConstantOn f I → Chapter11.PiecewiseConstantOn (f / g) I
```

- In `anti_symm`, the binder `∀ x ∈ I,` extends over the whole `↔`. So the statement says that equality at a single point is equivalent to each function majorizing the other (being at least as large) on all of `I`. Counterexample: I = Icc 0 1, f = 0, g = id, x = 0.
- In `div`, both hypotheses are about `f`, so `g` is unconstrained. Counterexample: I = Icc 1 2, f = 1, g = id.
- Expected: a correct proof of the intended statement earns the point. Observed: it prints a different type and is scored "type changed". No submission free of `sorry` can earn these two points. Using the false lemmas elsewhere gains no credit, because the axiom checks follow every dependency.

**2. Helper targets generated by the compiler make scoring depend on proof style.** When Lean compiles a definition or instance, it also creates hidden helper declarations with generated names, such as `X._proof_N`, `X._simp_N`, `X.eq_N` and `X.match_N`. While the parent contains `sorry`, these helpers depend on `sorryAx` too, so the grader lists them as separate targets. 559 of the 2901 targets have such names (`evidence/scripts/lean_aux_names/aux_targets.txt`); the fixed version's filter excludes 560, those 559 plus `Chapter5.ExtendedReal._sizeOf_inst`, whose parent `Chapter5.ExtendedReal` is a target. The task never mentions them. A helper is credited only if a normal build produces a helper with the **same generated name and the same printed type**, and that depends on how the parent was proved:

- **Same facts, different tactic.** `PreInt.instSetoid._proof_1` was credited when the setoid's reflexivity and symmetry were proved in term mode or tactic mode. When the same facts were closed by `omega`, `omega` generated its own helpers first. The original obligation moved to `_proof_3`, and the target was scored "type changed". Both proofs are correct; the `omega` one scored 1 point less.
- **Lost in every style tried.** The parent `Int.equivInt` was credited, but `Int.equivInt._proof_1..4` were lost in every variant: "type changed" in T, S, W and X, and three "type changed" plus one "disappeared" in U. Some were renumbered, some merged into one helper, and one printed its binders as `∀ (h : PreInt) (b : PreInt)` instead of `∀ (a b : PreInt)`.
- **Out of reach whatever the proof.** 35 targets have `sorry` in their baseline type text (32 helpers plus 3 placeholder statements such as `Chapter3.empty_function_bijective_iff : … ↔ sorry`), so any solution free of `sorry` changes the type. At least 12 more helpers leave out a case hypothesis, so their recorded types are false.

## How much it matters

- False statements: 2 of 2901 points are lost for every solver. Taken alone, they would cap the score at 2899/2901 = 99.93%; with the helper targets below, the ceiling is at most 2852/2901 = **98.31%** (`evidence/reviews/lean_aux_name_scoring.md`).
- Overall, **at least 49 of 2901 points (1.69%) are out of reach** for a complete, fully correct solution (the 35 with `sorry` in their type, the 12 that drop a hypothesis and the 2 false statements). About 57 (1.96%) is the likely figure.
- Up to 466 helper points under definition parents could in principle be won or lost by proof style. In the sample, 3 of 15 were lost that way. This was not measured across the whole repository.

## The fix

The fixed version makes two one-token edits to the source and adds one target filter to the grader.

- `Section_11_3.lean` now reads `(∀ x ∈ (I:Set ℝ), f x = g x) ↔ …`.
- `Section_11_2.lean` takes `(hg: PiecewiseConstantOn g I)` (Tao, Lemma 11.2.8).
- Both edits go into the grader's baseline repository and the solver's starter.
- The grader excludes targets whose name has a compiler-generated component (starts with `_`, or is `match_N`, `eq_N`, `eq_def`, `congr_simp` or `proof_N`). It also excludes targets whose baseline type contains `sorry`. Every excluded helper has a parent that is still a target, and the parent's axiom check, which follows every dependency, still covers it.
- The 3 placeholder statements stay in the starter as ungraded exercises. Scoring them would accept any filled-in statement, including a trivial one.
- Type matching, the list of allowed axioms and the rule for the denominator are otherwise unchanged. The scored set is **2338 targets**: 2901 − 560 generated − 3 placeholders.

In the fixed version the term, tactic and `omega` styles credit the same 15 parents, with 0 type_changed, 0 disappeared and 0 new_bad. Every parent credited in the original version is credited in the fixed version. The fixed version credits nothing new apart from the two corrected statements. The proof that goes through a lemma left as `sorry` stays uncredited in both versions, and the proof with a type error fails `lake build` in both.

**Scores from the fixed version are not comparable with the original.** The denominator changes from 2901 to 2338. Helper credit is removed: partial instance proofs that earned `_proof_N` points in the original earn nothing until the instance is complete. And two targets become reachable. The same correct submission scores 26/2901 = 0.00896 in the original version and 15/2338 = 0.00642 in the fixed version. The bounds of the score scale (`rescale`: linear, 0.0 to 1.0) are unchanged, because they are the exact bounds of a pass rate. Numbers from the original version must not be placed on the fixed version's scale.

## How we checked it

- **Original grader, from the public image pinned by digest** (Lean 4.28.0). The unmodified grader ran on the six Section_4_1 variants above. `lake build ListDeclAxiom` in the grader's repository printed `SUMMARY checked=4743 bad=2901`. The helper targets were counted by name pattern, and each helper's parent was queried in the image.
- **Formal check in Lean.** A refutation file that imports the task's own `Chapter11` definitions was run with `lake env lean` in the grader image (`--network none --memory 4g --cpus 2`). Lean's kernel proves the negation of each literal statement, stated against the installed definitions, not against Mathlib (Lean's math library) analogues. A local copy under Lean 4.34.1 gave the same results. Both corrected statements were proved free of `sorry` in the fixed grader's repository. All of these proofs use only the axioms `propext`, `Classical.choice` and `Quot.sound`.
- **Side-by-side runs.** The original and fixed graders ran locally in the grader image on the test submissions above. The comparison was repeated three times, and no result changed ([`data/paired-repeatability.md`](../data/paired-repeatability.md)). For S and W, the first original-grader result is the earlier native run in `evidence/scripts/lean_aux_names/out/report_{S,W}.json.gz` (same image and grader bytes), so for S and W only the two repeat runs (`evidence/runs/lean_analysis_proofs-v2-paired-rep2/` and `-rep3/`) graded them with the original grader inside the side-by-side job.

## Limits

- No AI model or solver was run. Effects are shown only on the test submissions and counterexamples we wrote.
- **The fixed work image was not built,** and the original work image was not pulled. `Dockerfile.work` assumes that the solver's starter is at `/home/workspace/se-bmk-intern/analysis`, equals the grader's sources and is owned by `agent`. None of this is verified.
- **Not verified, and why: the image builds and the actual `eval_cmd` path.** The grader image unpacks to about 33 GB, and `materialize.sh` with its Lean rebuild, plus `docker build` of both images, needs about 45 GB of free disk, more than the 21 GB E2B workers used for this audit provide: the clean-machine rebuild check of all packages could not pull the grader image there (`evidence/runs/materialize-check-lean`, `no space left on device`; the other 31 packages passed). So neither image was built, and the original `eval_cmd` (Mathlib `3203991`, full rebuild) was not run on the fixed version. This stays a documented limitation until the build is run on a machine with about 45 GB of free disk.
- `docker build` of the fixed grader image was not run. An equivalent installation was tested instead: the same artifact tar and `eval_lean.py` were placed over the original image paths. Lake rebuilt 0 modules, and the listing was byte-identical to the regenerated one.
- **The side-by-side runs used the prebuilt Mathlib in the grader's repository (`491a409`).** The original `eval_cmd` copies `/home/workspace/baseline/.lake` (Mathlib `3203991`) and does a full rebuild; that path was not run.
- The proof-style test covers one module (Section_4_1) and six variants. The counts of helpers that drop a hypothesis and of duplicates are lower bounds or estimates based on the text.
- Other false statements among the 2338 targets of the fixed version were not checked; "two" is a lower bound.
- The harness's `total_tests` counts every item the grader reports, including zero-weight "new bad declaration" items for declarations a submission adds, so it can exceed 2901 (2905 to 2931 in a real agent run, `evidence/runs/opus55-rollouts-meta/submission-histories.json`). The score's denominator is the baseline weight only (`eval_lean.py` lines 586–591), so these items do not change the score: for example 933 credited targets scored 933/2901 = 0.3216 while `total_tests` was 2905.
- The name filter in the fixed version works on the text of names. A declaration named by a user that ends in, for example, `eq_1` would also be excluded. All 560 matches in this baseline were checked, and none is named by a user.
