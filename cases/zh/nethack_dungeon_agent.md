# NetHack Dungeon Agent (`nethack_dungeon_agent`)

**结论：** 保留（附说明）。<mark>评分器本应为每局游戏固定随机种子，但这一调用静默失败，因此 20 局计分游戏都是随机的，分数在不同运行之间不可重复。</mark>

## 任务要求

智能体编写 `agent.py`，它 "plays NetHack via the NLE Python environment and maximizes game score"（通过 NLE Python 环境玩 NetHack 并使游戏得分最大化）。NetHack 是一款经典的文字地牢游戏，NLE（NetHack Learning Environment）把它封装成程序可调用的环境。评分器在每一步调用智能体的 `get_action(obs, info, step)`。

评分器默认跑 10 个种子 x 2 次重复，共 20 局。种子是一个数字，本应固定每局游戏的随机布局。每局走满 5,000 步，评分器就结束这一局。任务说明只在本地测试骨架里把 5,000 写成 `--max-steps` 的默认值，没有说这是评分器的上限。评分器另有每局 120 s 的时限，任务说明完全没提。类别：交互式游戏与模拟器。

## 我们检查了什么

**设置种子没有任何效果。** 评分器在 `gym.make` 返回的对象上调用 `env.seed(seed)`。在 gymnasium 1.0 下，该对象是一个 `PassiveEnvChecker` 包装器，没有 `seed` 属性，因此调用会抛出 `AttributeError`。评分器吞掉这个错误，然后不带种子调用 `env.reset()`。（再深一层，`env.unwrapped.seed` 会抛出 NLE 的 `RuntimeError`，即 "NetHackChallenge doesn't allow seed changes"，但评分器根本走不到这一步。）

例如，我们在 3 个进程中分别运行评分器的 "seed 0" 开局，得到 3 局不同的游戏，初始角色（职业）各不相同。按设计，这三次应该是同一局游戏。

| 进程 | 开局指纹 | 初始物品（前几件） |
|---|---|---|
| 1 | `d032b1011fd60c20` | 1234 金币，祝福的 +0 手术刀（Healer） |
| 2 | `3075b9dff32a9560` | +0 战斧、短剑、环甲（Barbarian 类装备） |
| 3 | `28304be1bd905af7` | +1 匕首、+1 弓、52 支箭（Ranger 类装备） |

原始的 `--run-seed 0` 子进程跑了 3 次，结果分别是 WA/0、OK/2 和 WA/0。同一个基线按默认设置完整评了两次，两次结果不一样：

| | 运行 1 | 运行 2 |
|---|---|---|
| 非零用例（用例：得分） | 0007: 3, 0010: 7, 0012: 2, 0018: 8 | 0009: 7, 0015: 4, 0018: 5 |
| 其余所有用例 | 0 (WA) | 0 (WA) |
| `TOTAL_SCORE` | **1.000000** | **0.800000** |
| `CASES_OK` | 4/20 | 3/20 |
| 100 分制得分（线性刻度，原始结果 /1000 x 100） | 0.10 | 0.08 |
| 墙钟时间 | 5 s | 5 s |

同一种子的两次"重复"（用例 2k 和 2k+1）结果也对不上。例如运行 1 中用例 0010 = 7，用例 0011 却是 0。所谓重复，其实只是又开了一局随机游戏。

这意味着同一个智能体每评一次分，分数都可能不同，"10 seeds x 2 repeats" 的设计也就落空了。

随任务发布的说明：

- 20 局计分游戏都没有设置种子，每局角色随机。"10 seeds x 2 repeats" 实际上是 20 局互不相关的随机游戏。
- 分数不可重复：同一基线评两次，`TOTAL_SCORE` 分别是 1.000000 和 0.800000。
- 每局限 5,000 步（任务说明只在本地测试骨架里把它写成 `--max-steps` 的默认值），并限时 120 s（任务说明没有提）。一局超过 120 s 就记 0 分，之前已拿到的分也一并作废：评分器的 `run_seed_subprocess` 遇到 `TimeoutExpired` 时返回 `TLE` 和 0 分，而游戏要到结束时才报告最佳得分。120 s 摊到 5,000 步，每步只有 24 ms，NLE 自身的步进时间也算在内。

## 影响有多大

每个解题者都会遇到运行之间的波动。基线两次相差 0.2 个原始分，折合 100 分制的 0.02 分，在这个分数段可以忽略。较强智能体的波动我们没有测量，大小未知。本任务有记录的智能体运行最高得分是 41.9 分（满分 100，见 `tasks/README.md`），远高于基线。NetHack 的分数呈重尾分布（少数几局的分数远高于其他各局），所以在这个分数段，波动的绝对值很可能大得多，但现有的运行无法估出具体大小。该任务的选取规则（`score_first`）保留最佳提交，因此每次评分的随机波动可能把一次运行记下的最佳成绩抬高。

一局基线游戏（含启动）耗时 0.37-0.44 s，一次 20 局的评分约 5 s，离每局 120 s 的时限很远。如果智能体在完整的 5,000 步游戏里平均每步超过约 24 ms，就会撞上时限，这局记 0 分。较慢、带规划的智能体会不会撞上时限，我们没有测试。

任务本身不改，上述说明随任务一起发布。对评分器做个小修复，也许能让种子真正生效，但我们没能在 NLE 1.2 / `NetHackChallenge` 中验证出一条可用的设种子方法。`env.reset(seed=...)` 不报错，但我们没有测试它是否真的给 NetHack 核心设置了种子。

## 我们如何检查

- **原始评分器。** 在按摘要固定的原始公开镜像里，用默认环境变量运行未改动的 `python3 /tmp/eval_nethack.py`。机器有 8 个 vCPU、7.9 GB 内存，容器参数为 `--network none --memory 6g`，不限 CPU。提交是智能体工作镜像里随附的基线 `agent.py`。一共做了两次完整的默认评分，每次都套在 `timeout 1100` 里。
- **种子诊断。** 一个脚本照评分器的做法调用 `env.seed()`，并检查包装器链。评分器自己的 `seed_process(0)` 和 `reset_env(env, 0)` 在 3 个独立进程中各跑一次。开局状态取指纹（reset 时 `glyphs`、`blstats` 和 `inv_strs` 的哈希）。
- 已安装的软件包：`nle 1.2.0`、`gymnasium 1.0.0`、Python 3.10。

## 局限

- 没有运行任何 AI 模型或解题者。影响只在随附的基线和我们写的诊断脚本上演示过。
- 只运行了随附的随机游走基线。手头没有较强的智能体可作比较，所以能拿分的智能体波动如何、波动有多大，都没有测量。
- 只用了一台不限 CPU 的机器，计时结果只适用于这台机器。
- 开局状态指纹只对 reset 时的 `glyphs`、`blstats` 和 `inv_strs` 取哈希。
