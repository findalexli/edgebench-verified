# NetHack Dungeon Agent (`nethack_dungeon_agent`)

**结论：** 保留（附说明）。<mark>评分器本应为每局游戏固定随机种子，但这一调用静默失败，因此 20 局计分游戏都是随机的，分数在不同运行之间不可重复。</mark>

## 任务要求

智能体编写 `agent.py`，它 "plays NetHack via the NLE Python environment and maximizes game score"（通过 NLE Python 环境玩 NetHack 并使游戏得分最大化）。NetHack 是一款经典的文字地牢游戏，NLE（NetHack Learning Environment）把它封装成程序可调用的环境。评分器在每一步调用智能体的 `get_action(obs, info, step)`。

默认情况下，评分器运行 10 个种子 x 2 次重复（共 20 局）。种子是本应固定一局游戏随机布局的数字。评分器在每局 5,000 步后停止该局；任务说明只在本地测试骨架中把 5,000 作为 `--max-steps` 的默认值给出，并未说明这是评分器的上限。评分器还强制执行每局 120 s 的时限，任务说明没有提到这一点。类别：交互式游戏与模拟器。

## 我们检查了什么

**设置种子没有任何效果。** 评分器在 `gym.make` 返回的对象上调用 `env.seed(seed)`。在 gymnasium 1.0 下，该对象是一个 `PassiveEnvChecker` 包装器，没有 `seed` 属性，因此调用会抛出 `AttributeError`。评分器吞掉这个错误，然后不带种子调用 `env.reset()`。（再深一层，`env.unwrapped.seed` 会抛出 NLE 的 `RuntimeError`，即 "NetHackChallenge doesn't allow seed changes"，但评分器根本走不到这一步。）

例子：评分器的 "seed 0" 开局在 3 个进程中运行，得到 3 局不同的游戏，每局的初始角色（职业）都不同。预期结果是三次相同的游戏。

| 进程 | 开局指纹 | 初始物品（前几件） |
|---|---|---|
| 1 | `d032b1011fd60c20` | 1234 金币，祝福的 +0 手术刀（Healer） |
| 2 | `3075b9dff32a9560` | +0 战斧、短剑、环甲（Barbarian 类装备） |
| 3 | `28304be1bd905af7` | +1 匕首、+1 弓、52 支箭（Ranger 类装备） |

原始的 `--run-seed 0` 子进程运行 3 次，分别返回 WA/0、OK/2 和 WA/0。对同一个基线做两次完整的默认评分，结果不同：

| | 运行 1 | 运行 2 |
|---|---|---|
| 非零用例（用例：得分） | 0007: 3, 0010: 7, 0012: 2, 0018: 8 | 0009: 7, 0015: 4, 0018: 5 |
| 其余所有用例 | 0 (WA) | 0 (WA) |
| `TOTAL_SCORE` | **1.000000** | **0.800000** |
| `CASES_OK` | 4/20 | 3/20 |
| 100 分制得分（线性刻度，原始结果 /1000 x 100） | 0.10 | 0.08 |
| 墙钟时间 | 5 s | 5 s |

同一种子的两次"重复"（用例 2k 和 2k+1）结果也不一致。例如，运行 1 中用例 0010 = 7，而用例 0011 = 0。所谓重复，不过是另一局随机游戏。

为什么重要：同一个智能体每次评分都可能得到不同分数，"10 seeds x 2 repeats" 的设计并不成立。

随任务发布的说明：

- 20 局计分游戏都没有设置种子，每局的角色随机。"10 seeds x 2 repeats" 实际上是 20 局相互独立的随机游戏。
- 分数不可重复：对同一基线的两次评分得到的 `TOTAL_SCORE` 分别为 1.000000 和 0.800000。
- 每局的限制是 5,000 步（任务说明只在本地测试骨架中把它作为 `--max-steps` 的默认值给出）和每局 120 s（任务说明未提及）。运行超过 120 s 的一局得 0 分，包括它此前已获得的分数：评分器的 `run_seed_subprocess` 在 `TimeoutExpired` 时返回 `TLE` 和 0 分，而游戏只在结束时报告其最佳得分。120 s 分摊到 5,000 步，即每步 24 ms，其中包括 NLE 自身的步进时间。

## 影响有多大

运行间波动影响所有解题者。对基线而言，差异为 0.2 个原始分，即 100 分制下的 0.02 分，在这个水平上无关紧要。有能力的智能体的波动没有测量，因此其大小未知。本任务已记录的智能体运行最高得分为 41.9 分（满分 100，见 `tasks/README.md`），远高于基线。NetHack 的分数呈重尾分布（少数几局的分数远高于其他各局），因此在这个水平上，波动的绝对值很可能大得多，但现有运行无法估计其大小。该任务的选取规则（`score_first`）保留最佳提交，因此不同评分之间的随机波动可能抬高一次运行记录下的最佳成绩。

一局基线游戏（含启动）耗时 0.37-0.44 s，每次 20 局的评分约耗时 5 s，远低于每局 120 s 的时限。在完整的 5,000 步游戏中平均每步超过约 24 ms 的智能体会触及时限，该局得 0 分。较慢的、带规划的智能体是否会触及这一时限，我们没有测试。

任务本身不作改动；上述说明随任务一起发布。对评分器做一个小修复或许能让种子真正起作用，但我们没有在 NLE 1.2 / `NetHackChallenge` 中验证出一条可用的设置种子的路径。`env.reset(seed=...)` 没有报错，但没有测试它是否真的为 NetHack 核心设置了种子。

## 我们如何检查

- **原始评分器。** 在按摘要固定的原始公开镜像中，以默认环境变量运行未经修改的 `python3 /tmp/eval_nethack.py`。机器有 8 个 vCPU 和 7.9 GB 内存，容器以 `--network none --memory 6g` 运行，没有 CPU 限制。提交是智能体工作镜像中随附的基线 `agent.py`。共进行了两次完整的默认评分，每次都包在 `timeout 1100` 中。
- **种子诊断。** 一个脚本按评分器的方式调用 `env.seed()`，并检查包装器链。评分器自己的 `seed_process(0)` 和 `reset_env(env, 0)` 在 3 个独立进程中运行。开局状态取指纹（reset 时 `glyphs`、`blstats` 和 `inv_strs` 的哈希）。
- 已安装的软件包：`nle 1.2.0`、`gymnasium 1.0.0`、Python 3.10。

## 局限

- 没有运行任何 AI 模型或解题者。影响只在随附的基线和我们编写的诊断脚本上展示。
- 只运行了随附的随机游走基线。没有可供比较的有能力的智能体，因此能得分的智能体的波动没有测量，波动的大小也没有测量。
- 只使用了一台没有 CPU 限制的机器。计时结果只适用于这台机器。
- 开局状态指纹只对 reset 时的 `glyphs`、`blstats` 和 `inv_strs` 取哈希。
