# Arc Compiler Runtime (`arc_compiler_runtime`)

**结论：** 已修复。<mark>隐藏测试要求 `analyze()` 采用一种返回格式，而解题者能看到的任何文件都没有说明这种格式；TASK.md 还把初始代码的得分写错了。修复版把这两点都写进文档，没有改变任何分数。</mark>

![两根柱子显示同一个诚实的分析器：采用隐藏测试期望的数组返回格式时得 69.26 分，采用初始代码的对象格式时得 35.59 分；解题者能看到的任何文件都没有说明前一种格式。](figures/arc_compiler_runtime.svg)

*隐藏测试需要一种解题者看到的任何内容都没有描述的返回格式，因此相同的逻辑会得 69.26 分或 35.59 分；修复版在文档中说明了这一格式。*

## 任务要求

解题者必须 "Implement the missing Arc compiler and runtime modules under compiler/src/"（在 compiler/src/ 下实现缺失的 Arc 编译器和运行时模块）。Arc 是一种小型编程语言。任务告诉解题者 "Use CHEATSHEET.md, TASK.md, and the public smoke tests as the language contract."（以 CHEATSHEET.md、TASK.md 和公开冒烟测试作为语言规约。）TASK.md 写着 "Starter expectation `SCORE=0.00`"，problem.md 写着 "Expected stripped starter score: 0.00"（即初始代码预期得分为零）。隐藏评分器有 21 个测试套件、448 个用例和 2970 个权重单位。类别：系统与软件工程。

## 问题出在哪里

**`analyze()` 接口没有文档。** 隐藏的类型系统套件调用 `compiler/src/semantic.js` 中的 `analyze()`。它们期望得到一个由 `{level, message}` 对象组成的数组。消息必须包含子串 "Undefined"、"Cannot reassign immutable" 和 "expects 2"。随任务提供的初始代码返回的却是 `{ ok, errors, warnings, program }`。解题者能看到的任何文件都没有给出所需的格式或消息文本。这些套件占 1000/2970 的权重（33.67 分）。

- 例子，在原始评分器上：同一个诚实的分析器，返回隐藏测试使用的数组格式时得 **69.26** 分，保留初始代码的对象格式时得 **35.59** 分。前一种形式通过 128/128 个类型系统用例，后一种通过 0 个。解题者得不到任何关于哪种形式正确的信号。

**所述的初始得分是错的。** TASK.md 和 problem.md 说初始代码得 0.00 分。在原始工作镜像（智能体工作所在的容器）中，初始代码在公开测试上得 `SCORE=100.00`（48/48），在隐藏测试上得 35.59 分。这会误导解题者对自身起点的判断，但不改变任何分数。

**一个挂起的套件会使整份提交作废（未改动，已披露）。** 21 个隐藏套件中的每一个都在一个进程中运行，时限为 90 秒。如果某个套件超时或导致进程崩溃，评分器就会停止并报告 `SCORE_STATUS=INFRA_FAIL`，提交无效，得 0 分。例子，在原始评分器上：初始代码得 35.59 分。同样的初始代码加上一个单字符拼写错误，使字符串插值在 `{items[0]}` 上无限循环，在六次评分中六次都被判为无效（0 分；三次运行中每次各有两个副本 `t_hang` 和 `t_hang_rep2`：`evidence/runs/arc_compiler_runtime-hang-suite`、`-rep2`、`-rep3`）。这种写法只出现在一个套件中（`round2-interpreter`，占 100 分中的 1.35 分），若该套件按 0/8 计分，总分会是 34.75。评估器把这记录为它的基础设施故障策略，但解题者能看到的文件都没有提到。它只影响确实存在不终止缺陷的提交；而在任务的 `score_first` 选取规则下（该规则不读取 `valid`，`sforge/harness/selection.py:83-103`），这份提交按 0 分排序，因此它永远不会取代一份得分高于 0 的提交。

经检查是正确的：恰好运行 448 个用例，每个用例有一个计入的结果。初始代码的运行中没有导入失败。期望值在测试文件中以字面量写出。

## 影响有多大

最多会在没有任何提示的情况下失去 33.67 分（类型系统的全部权重）。这影响所有保留初始代码返回格式、或者没有猜中消息文本的解题者。

## 修复

修复版只改动工作镜像中解题者可见的两个 Markdown 文件，别的都不改：

- `agent-start/TASK.md` 用实测的 `SCORE=100.00`（48/48）替换错误的初始得分行。它新增一节 "Semantic analysis interface"（语义分析接口）。这一节给出返回格式（由 `{level, message}` 组成的数组）、三个必需的子串及产生它们的条件，以及隐藏类型系统套件检查的规则类别（以规则的形式陈述，而不是给出测试程序）。
- `agent-start/problem.md` 用实测值替换错误的 "0.00"，并指向新的一节。

评分器镜像、评分器、测试、初始代码和任务说明都没有改变。`task.json.in` 只改动 `work.image_tag`。我们选择了补充文档，而不是让初始代码返回 `[]`。那样的初始代码会把起始分数从 35.59 提高到 47.21，而且仍然不会说明消息文本。

**分数是否可比？** 单份提交的分数是可比的。同一份 `compiler/src/` 在原版和修复版下得分相同（对 5 个测试提交做了测量）。分数刻度（线性 0–100）及其参考点没有改变。智能体运行的结果**不**可比。修复版的解题者被告知了接口和消息文本，而原版的解题者没有。两个版本上的智能体运行不应合并或一起排名。

## 我们如何检查

- **原始评分器，来自按摘要固定的公开镜像**（修复版中未改动）。它以原始的 `judge.eval_cmd` 在 `--network none` 下运行。每个测试提交评分两次：一次使用原始工作镜像中的 `compiler/src/`，一次使用修复版工作镜像中的。公开的 `score.sh` 也在每个工作镜像中运行过。
- **源码对照。** 隐藏评分器（`score_hidden.sh`）和隐藏的类型系统测试文件与解题者可见的每个文件（TASK.md、problem.md、CHEATSHEET、spec/、docs/、公开冒烟测试）做了对照。
- **用例清点。** 对隐藏套件的静态计数（`case_inventory.py`）得到 21 个套件、448 个用例和 2970 个权重单位。
- **可重复性。** 原版与修复版的并排对照运行重复了三次。没有任何测试提交的结果发生变化（见 `data/paired-repeatability.md`）。

## 局限

- 没有运行任何 AI 模型或解题者。影响只在我们编写的测试提交和反例上展示。
- 测试提交 (d) 的作者读过隐藏测试。它表明文档所述的接口已经足够，但不能表明不了解隐藏测试的解题者表现如何。
- 仍有一部分分数仅凭格式就能拿到。返回 `[]` 可多得 +11.62 分。一个总是返回一条诊断信息的常量分析器得到 57.81 分（在替代运行时下，而非在镜像中）。原因是有些用例只检查结果是否为空。要解决这一点需要修改评分器，而那会改变分数的含义。
- 对抗性类型系统用例（占权重的 32%；未根据清点结果重新推导）来自 9 个模板。修复版没有改变这一点。
- 不声称修复版镜像的重新构建是逐位相同的。修复包在一台干净的机器上从零重建过（`evidence/runs/materialize-check-g3`，`status: exit=0`）：`materialize.sh` 原样运行，全部 4 个输出与锁定值一致，构建出的镜像中是两个锁定的文件。
- `task.json.in` 中修复版工作镜像的标签 `v2-analyze-contract-docs` 是本地构建标签；没有发布修复版镜像，用户需要自行构建并打标签。
- 有一个细节无法解释，但对结论没有影响：在测试提交 (c) 下，`round2-codegen` 为 5/8，而初始代码为 4/8。
- 修复版保留了评分器对挂起或崩溃套件的全有或全无处理方式（实测：初始代码 35.59 分，有效；同样的初始代码在某个套件的写法上无限循环时无效，0 分；`evidence/runs/arc_compiler_runtime-hang-suite`）。触发条件是人为构造的缺陷，而不是某个解题者的代码。接近 90 s 时限的运行是否可重复，没有测量。
