# FFmpeg Swscale Reimplementation (`ffmpeg_swscale_reimplementation`)


**2026-10-13 修订：** v2.2 检查每一次输出，只要有一个工作负载失败，总奖励就恰好为零。它与原始评分器并排运行了一次：完整计分程序共运行六次（每个评分器各三份测试提交），全部正常结束；另有 40 项检查确认它的输出缓冲区与原始辅助函数一致。正确的测试提交在 43 秒内完成；一份跳过重复调用的提交通过了 30/30 个正确性工作负载，但计时输出经检查不对，得零分。下面的“修复”一节介绍 v2.2，历史上的 v2 表格也保留备查。这次后续检验没有重新运行 Rust 提交的构建路径。参见[后续记录](../repairs/ffmpeg_swscale_reimplementation-v2/paired/followup.md)。

**结论：** 原始缺陷已确认；当前修复（v2.2）在三份原生测试提交上与原始评分器并排测试了一次。<mark>计时的速度测试从不检查正确性，所以失败的调用或什么都不做的调用也能拿到速度分；修复版检查每次计时调用的返回码和输出。</mark>

*速度测试从不检查输出，于是未完成的代码最多拿到 18.93 分（满分 100）。智能体要重写 FFmpeg 的图像缩放库，通过 30 项正确性测试后按速度计分。可是评分器从不检查计时调用的结果，所以一次返回错误或什么也没写的调用，会算作快了数千倍。在原始评分器的一次运行中，三个只改了一行的未完成版本分别得 5.39、18.93 和 17.87 分，未改动的初始代码得 0 分，四者都通过了 30 项正确性测试。当前的修复检查每一次计时调用的输出，只要有一次失败，就按任务说明把总分设为恰好 0。在它唯一一次并排对照运行中，一份跳过重复调用的代码通过了全部 30 项正确性测试，得 0 分。*

## 任务要求

解题者要用 Zig 或 Rust 重新实现 FFmpeg 的 libswscale（FFmpeg 的图像缩放和像素格式转换库），做成一个与 C 兼容的共享库。任务文本说这个库 "must handle conversions between any pair of these formats"（必须能在这些格式中的任意两种之间转换）。它还说："If correctness fails on any hidden workload, the score is **zero**."（只要有一个隐藏工作负载的正确性检查失败，分数就是零。）否则 `reward = geometric_mean(baseline_time / candidate_time)`，即相对原始库各项加速比的几何平均。

原始结果（换算到 0–100 之前的数值）用 `log_anchor` 分数刻度换算。这是只有一个参考点的对数刻度：原始结果 14.155（anchor_raw）对应 43 分（anchor_score）。原始结果不超过 1 的记 0 分。类别：系统与软件工程。

## 问题出在哪里

**计时的工作负载不经任何正确性检查就能拿到速度分。** 分数分两步算：

- **正确性检查。** 30 个固定的工作负载与原始库对照，用的是逐平面 PSNR（峰值信噪比，每个颜色平面分别测量）。阈值为：同尺寸转换至少 60 dB，缩放至少 40 dB。
- **计时。** 给 10 个**另外的**工作负载计时。计时循环不看 `swscale_process` 的返回值，也从不读输出缓冲区。

有几种计时配置从来没出现在正确性检查集合中：RGBA→RGB24、RGB24→BGRA、3:1 缩小、1.5× 双三次放大，以及 1080p 和 4K 尺寸。一个返回错误或什么也不做的调用几乎立刻结束，于是得到一个极大的"加速比"。

下面每个变体都模拟正常开发中常见的中间状态：某条路径还没写，或者有一个普通的错误。原始评分器上的结果：

| 变体（所模拟的正常开发情形） | 正确性 | 原始结果 | 100 分制得分（`log_anchor`） | 导致变化的工作负载 |
|---|---|---|---|---|
| 变体 0：随附的初始代码，未改动 | 30/30 | 0.4585 | 0 | 不适用 |
| 变体 1：对 RGBA→RGB24 返回错误 -3（"尚未实现"） | 30/30 | **1.3938** | **5.39** | rgba→rgb24 4K：16,469× |
| 变体 2：对 3:1 缩小返回错误 -3 | 30/30 | **3.2112** | **18.93** | 3:1 bilinear 23,856×，3:1 nearest 7,032× |
| 变体 3：对 3:1 缩小返回成功但什么也不写 | 30/30 | **3.0083** | **17.87** | 23,864× / 4,467× |

例子：变体 1 在 RGBA→RGB24 上调用失败，本应在这一项拿不到速度分。原始评分器却在这个工作负载上记下 16,469× 的加速比，100 分制得分从 0 升到 5.39。计时的运行间波动约为 ±20%，上面原始结果 3 到 7× 的变化远大于此。

**随附的初始代码已经靠错误输出得分。** 在计时工作负载 `rgb24 1080p→360p nearest` 上，未改动的初始代码输出的 **PSNR 为 14.91 dB，而阈值是 40 dB**。初始代码最大的加速比 4.65× 恰恰来自这个工作负载。

崩溃的处理不一样：Python 异常或 NULL 上下文会让这个工作负载记 0，段错误会让 `test.sh` 写入 reward 0。只有返回错误和悄悄什么都不做才会得到奖励。正确性工作负载本身按所述方式检查，只是从来不覆盖计时用的配置。

还有一处不影响分数的问题：任务文本一处说初始代码 "already matches the hidden correctness suite at 30/30"（已全部通过隐藏的正确性测试集），另一处又说它是一个 "which reached 26/30"（只通过了部分正确性测试）的候选实现。在原始评分器上实测为 30/30。

## 影响有多大

对一个正常开发、尚未完成的变体，实测多给的分数最高达 18.93 分（满分 100）。只要库在正确性集合以外的某个计时配置上失败或什么都不做，就会多拿分。

## 修复

修复版（v2.2，当前的补丁）只改动 `compute_reward.py`：

- 一个计时工作负载有 10 次预热调用和 100 次计时调用。每次调用前，它都清空整个输出缓冲区（包括填充部分），这一步不计时。
- 每次调用后，它检查返回码，并把输出与原始库的输出对照，阈值沿用正确性工作负载的逐平面 PSNR 阈值：缩放 40 dB，同尺寸转换 60 dB。这些检查同样不计时。
- 只要有一个计时工作负载失败，总奖励就恰好为 0，与任务文本的说法一致（"If correctness fails on any hidden workload, the score is **zero**"）。即使检查失败，上下文也会正常销毁。

其他什么都不改。

v2.2 的原生并排对照运行（作业 `ffmpeg-native-v2.2-20261013`，台账 `status: exit=0`）：用按摘要固定的原始镜像和 v2.2 镜像，在相同的原生 C 测试提交上运行完整的 `compute_reward.py`（30 个正确性工作负载和 10 个计时工作负载），容器为 2 个 CPU、4 GiB 内存、无网络。六组对照全部以 0 退出。表中数值为原始奖励（[`paired/results.md`](../repairs/ffmpeg_swscale_reimplementation-v2/paired/results.md) 中的 "v2.2 native result" 一节）。

| 测试提交 | 原始评分器 | 修复版 v2.2 | 正确性 原始 / v2.2 |
| --- | --- | --- | --- |
| 把每次调用都转发给 FFmpeg（正确） | 1.056386 | 1.020061 | 30/30 / 30/30 |
| **跳过每个上下文的第二次调用** | **1.038559** | **0.000000** | 30/30 / 30/30 |
| 总是返回错误（坏的对照） | 0.000000 | 0.000000 | 0/30 / 0/30 |

正确的提交仍然得正分；1.056386 与 1.020061 的差距，在原始镜像自己给这份提交评分的运行间波动之内（两次作业中分别为 0.994937 和 1.056386）。跳过一次调用的提交通过了全部 30 个正确性工作负载，但计时输出是错的，所以现在恰好得 0 分。计分之前，40 种原生缓冲区布局都与原始辅助函数逐字节一致。

**历史上的 v2 运行。** 第一个修复版 v2 只比较每个工作负载最后一次计时调用的输出，把失败的工作负载记为加速比 0 并留在几何平均里，所以总分很小，但仍为正。下面保留它的并排对照运行备查；v2.2 已取代它。

| 提交 | 作用 | 原始评分器 | 修复版评分器 | 修复版评分器的说明 |
| --- | --- | --- | --- | --- |
| 转发到原始库的薄封装（每帧处理一次） | 正确 | 0.967353 | 0.980056 | 30/30，无计时错误 |
| 转发到原始库的薄封装（每帧处理两次） | 正确，约慢 2× | 0.509049 | 0.507032 | 30/30，无计时错误 |
| 随附的初始代码 | 起点 | 0.447819 | 0.012416 | 其 1080p→360p nearest 输出低于 40 dB |
| 在 3:1 缩小上返回错误 | **展示问题** | **2.881761** | **0.000464** | 两个计时工作负载返回 -3 |
| 在 3:1 缩小上悄无声息地空操作 | **展示问题** | **2.884506** | **0.000463** | 两个计时输出低于 40 dB |
| 在 RGBA→RGB24 上返回错误 | **展示问题** | **1.305860** | **0.000451** | 计时错误 + PSNR 不达标 |
| 不支持 yuv420p→rgb24 | 无效 | 0.0 (28/30) | 0.0 (28/30) | 两者的正确性检查都失败 |

表中的值是换算到 0–100 刻度之前的原始几何平均加速比。两行封装提交用的是一个很薄的 C 包装层（`ref_shim.c`，源码见 `repairs/ffmpeg_swscale_reimplementation-v2/paired/results.md`），把每个调用都转发给原始 FFmpeg 库，所以输出天然正确。它构建了两次：一次每帧处理一次，一次每帧处理两次，后者结果正确但约慢 2×。这两行是两个不同的正确测试提交，不是同一提交跑两次；它们直接交给 `compute_reward.py`，没有经过 `eval_cmd`，也都不是真正的解法。这张表与第一张表在不同的主机上运行，所以原始评分器的原始值不同，两者都按记录引用。初始代码在修复版评分器上分数下降是对的，因为它在一个计时工作负载上的输出确实错了。

展示问题的三个变体都只在初始代码上改了一行，所以也继承了初始代码在 `rgb24 1080p→360p nearest` 上的错误输出；初始代码本身在历史版 v2 评分器上就只得原始结果 0.012416（满分 100 中的 0 分）。这些变体只在原始评分器和 v2 上运行过，没有在当前的 v2.2 上运行。因此，它们在 v2 上得 0 分，并不能单独说明修复抓住了改动过的工作负载。能说明这一点的是 v2 评分器逐个工作负载报告的错误：对 RGBA→RGB24 变体，它在 `rgba→rgb24 4K` 上报告 `candidate process returned -3`；对 3:1 返回错误的变体，它在两个 3:1 工作负载上都报告该错误；对悄无声息的空操作，它在 `rgb24→yuv420p 1080p→360p bilinear` 上报告 `timed output below PSNR threshold 40.0`，每一处的加速比都为 0（`evidence/runs/ffmpeg_swscale_reimplementation-v2-paired-b/result/out/summary_parsed.txt`）。我们没有在计时输出全部正确的代码基础上构建变体。

**分数兼容性：** 除计时噪声外，正确实现的得分与在原始评分器上相同。在 v2.2 下，只要有一次计时调用输出错误、返回错误或没有输出，实现就恰好得 0 分。修复版评分器的分数与原始评分器的分数不能比较。

## 我们如何检查

- **原始公开镜像中的原始评分器，按摘要固定。** 我们在随附的 Rust 初始代码基础上构建了四份提交，每份只改 `swscale_process` 中的一行，用任务原样的 `eval_cmd` 运行，参数为 `--network none --memory 2g --cpus 2`。这条路径包括 `test.sh`、源码扫描、`cargo build --release` 重新构建、`compute_reward.py` 和 `pytest_shim.sh`。
- **独立的输出检查。** 我们把原始的 `check_correctness` 例程用在 10 个计时工作负载上，PSNR 阈值和随机数序列都相同。评分器自己从不在这些工作负载上做这项检查。
- **v2.2 的原生并排对照运行**：在三个原生 C 测试提交（一个正确的、一个跳过调用的、一个总是失败的；不是上面的三个变体）上运行完整的 `compute_reward.py`（见上文）；在此之前先确认了 v2.2 的缓冲区快照在 40 种布局上与原始辅助函数一致。
- **原始评分器与历史上的 v2 评分器的并排对照测试**，使用相同的提交，参数为 `--network none --memory 4g --cpus 4`。重复了三次，所有测试提交的结果都没有变化；展示问题的测试提交每次在修复版评分器上都接近 0（见 `data/paired-repeatability.md`）。

## 局限

- 我们没有运行任何 AI 模型或解题者。影响只在我们写的测试提交和反例上展示。
- 在 v2.2 上，只要有一个计时工作负载失败，总分就恰好为 0，这与任务文本对正确性失败的规定一致。历史上的 v2 只是把几何平均拉到接近 0。
- v2.2 的检查是在完整的计分程序调用上、用原生 C 测试提交运行的，没有经过任务的 Rust 构建和提交 `eval_cmd`；那条路径只在原始评分器上运行过。
- 计时集合仍与正确性集合不同。修复版检查计时输出，但没有把计时配置加进 30 个正确性工作负载。
- 计时取决于主机：第一张表在本地主机上、在限制为 2 个 CPU 的容器中运行；并排对照表在 8-CPU 的 E2B 主机上、在限制为 4 个 CPU 的容器中运行（`env.txt`、`run.sh`）。
- 分数刻度的参考点（14.155 → 43）应该在修复后重新推导，但没有记录重新推导的参考点。
- 只测试了随附的初始代码、三个单行变体、一个无效测试提交，以及转发到原始库的包装层，没有构建独立的完整实现。
- 评分器隔离不在本次发布的范围内（EdgeBench 的设计选择）。上述发现与它无关。
