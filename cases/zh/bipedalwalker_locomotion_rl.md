# BipedalWalker Locomotion RL (`bipedalwalker_locomotion_rl`)

**结论：** 保留（附说明）。<mark>任务明确把分数上限定为 30，所以分数只在 0 到 30 之间（满分 100）；另外，如果检查点只有一部分与评分器的网络对得上，评分器只加载这一部分，并且不报任何错误。</mark>

## 任务要求

任务说明写道："Train a BipedalWalker policy on CPU in this work container and save the final trained checkpoint as `submission/policy.pth`."（在这个工作容器中用 CPU 训练一个 BipedalWalker 策略，把最终训练好的检查点保存为指定文件。）BipedalWalker 是一个模拟的双足机器人。策略是训练出来、负责选择动作的网络，检查点是保存网络权重的文件。评分器 "only receives the submitted checkpoint and evaluates it on BipedalWalker-v3 and BipedalWalkerHardcore-v3."（只接收提交的检查点，并在 BipedalWalker 的普通版和 Hardcore 版环境上评估它。）30 分的上限写在工作容器的 `task_prompt.md` 中（第 117-118 行）。类别：科学问题与机器学习。

## 问题出在哪里

按任务明确写出的设计，最高只能拿 30 分（满分 100）。评分器分几步算分：

- 普通地面上的奖励 R_normal 换算为 `clip(R_normal/300) × 100`。
- 崎岖地面（"hardcore"）上的奖励 R_hard 换算为 `clip((R_hard+100)/400) × 100`。
- 原始结果（换算到 0–100 之前的数值）为 `raw = 0.4·normal + 0.6·hard`。
- 任务分数为 `min(30, 2.5·(engineering checks passed, max 4) + 0.2·raw)`。

分数刻度是 0 到 100 的线性刻度，所以任务分数就是满分 100 下的同一个数。

| 情形 | 假设的平均奖励（R_normal, R_hard） | 100 分制得分 |
|---|---|---|
| 缺少检查点 | 不评估（−200, −200） | 2.5 |
| 能加载但未训练 | ≤ 0 且 ≤ −100 | **10** |
| 只会在普通地面上行走 | 300, −100 | 18 |
| **完美策略** | ≥ 300, ≥ 300 | **30** |

表中能加载检查点的各行，都假设四项工程检查全部通过。如果一个未训练的策略在崎岖地面上不摔倒，R_hard > −100，得分就会高于 10。例如 R_hard = −60 时，hardcore 得分为 10，raw 为 6，任务分数为 11.2。本仓库没有记录任何未训练策略的平均奖励。

0-100 的范围里只有 0 到 30 能拿到，其中三分之一来自加载检查。100 分的参考点不对应任何策略能达到的水平。任务写明了这个上限，所以我们把它作为说明处理，不算缺陷。

另一个次要问题是，检查点可能只加载一部分，而且不报错。评分器自己加载权重时，每条路径都用 `load_state_dict(strict=False)`（`evaluate_policy.py:119,141,196`）；如果解题者提供了 `load_policy(path)` 钩子，则由解题者自己的代码加载权重。默认路径还会悄悄丢掉所有形状对不上的权重张量（`:188-196`）。

- 举个例子，一个正常解题者的检查点键名变了，比如带有 `module.` 前缀。解题者会以为它要么能加载，要么报错失败。原始评分器这时不会报错，而是把它当作随机初始化的网络来评分，同时照样给加载检查的分。评估器输出的 "Skipping" 消息也会丢失，因为 `sebench_eval.py` 只在子进程出错退出时才保留其输出（`:109-113`），成功时只读取 `mean_reward`（`:114-118`）。所以从反馈里看不出只加载了一部分。

我们还确认了下面这些做法没有问题。评分器在每个环境中用前 10 个固定种子跑十个回合，总共约 3.6 万步，只需几秒钟，而时限是每个环境 300 s、`eval_timeout` 900 s。种子固定，动作是确定性的，所以在同一构建上，结果预计会逐位重复。

随任务发布的说明写了三条。

- 分数范围是 0 到 30，不是 0 到 100。
- 其中 10 分来自加载检查。
- 键名或形状对不上的检查点只会加载一部分，并且不报错。

## 影响有多大

- 上限：这是设计。每个解题者最多拿 30 分（满分 100）。
- 部分加载：只影响检查点键名或形状与评分器网络对不上的解题者。这样的检查点得分与未训练的网络相同（全部检查通过时约 10 分）。

代码没有改动。上述说明随任务一起发布。

## 我们如何检查

- 我们读了从任务源文件中取得的原始评分器源码副本，包括 `sebench_eval.py`（sha256 `9bb2f8bf…838a`）、`eval/evaluate_policy.py`（`43105357…7b68`）和 `task_prompt.md`（`e4023718…adcf`）。上表中的分数用原始评分函数算出。我们没有记录这些副本取自哪个镜像，也没有记录评分器镜像的摘要。任务说明写道 "Hidden evaluator code is not present in this work container"（隐藏的评估器代码不在这个工作容器中）；工作镜像里有没有 `sebench_eval.py`，我们没有检查。
- 我们在原始评分器上用一个始终输出零的策略（覆盖到网络上）跑了 20 个回合，结果与确定性评分一致。

## 局限

- 我们没有运行任何 AI 模型或解题者。影响只在我们写的测试提交和反例上展示。
- 我们没有在评分器上给任何训练好的策略打分。我们只根据源码和算术检查了从奖励到分数的映射，没有在训练好的检查点上检查。
- 键名改变的例子是我们从源码推理出来的，没有实际运行。
- 我们读过的 `sebench_eval.py`、`evaluate_policy.py` 和 `task_prompt.md` 副本没有在本仓库中发布，所以引用的行号（包括 `task_prompt.md` 第 117-118 行的上限）只能凭上面的 sha256 值，对照任务镜像核对。
