# Vehicle Routing Time Windows (`vehicle_routing_time_windows`)

**结论：** 保留（附说明）。<mark>关于小数容差的疑虑，在精确检验下不会改变分数；说明解释了权重和固定的测试集，指出检查器是由提交中的 `include/types.h` 和 `Makefile` 编译而成的，并指出在 20 分钟的总时限内，无法在每个实例上都用满 60 秒的时间参数。</mark>

## 任务要求

任务要求解题者 "optimize the C++17 CVRPTW solver"（优化该 CVRPTW 求解器），"Modify only src/, include/, and Makefile"（只修改这几个目录和文件），并 "Preserve the cvrptw_solver binary name and CLI"（保留该二进制名称和命令行接口）。CVRPTW 是带时间窗的有容量车辆路径问题：为容量有限的车辆规划路线，使每个客户都在规定的时间窗内被访问。任务 README 描述了把实例分为三组加权，以及每次部署时打乱节点以 "防硬编码答案"。它规定的成本容差为 "≤ 0.05"。类别：组合优化。

## 我们检查了什么

对于遵守文档所述时限的解题者，没有发现会改变分数的计分问题。有四点需要说明；第三点（触及检查器的求解器改动）的影响没有测量。

**1. 小数容差（已检查；不改变分数）。** README 规定了包含端点的 "≤ 0.05" 成本容差。检查器用 binary64（标准双精度浮点数）检验它。

- 56 个实例中的所有坐标、时间窗和服务时间都是整数。在 282,800 对节点上，任务四舍五入后的 binary64 距离每次都等于精确的整数计算结果（0 处不一致）。因此每个距离和到达时间都恰好是 0.1 的整数倍。
- 在 20,000 次随机试验中（每次对 120 个十分之一的整数倍求和），binary64 的最大漂移为 1.13e-11。检查器的时间窗检验使用 1e-6 的余量，因此它给出的判定与精确有理数算术的判定完全相同。没有任何可行/不可行的判定依赖于浮点误差。
- **例子。** 在恰好相差 0.05 时，对申报成本的检查表现不一致。真实成本为 12 时，它拒绝申报的 12.05 或 11.95；但真实成本为 4 时，它接受 4.05 和 3.95。
- 只有当求解器申报的成本恰好偏差 0.05 时，这一点才有影响。一个打印自己求和结果的求解器，与检查器的总和相差约 1e-11 以内。计分使用的距离是检查器自己重新计算的，而不是申报的成本。

**2. README 描述了评分器并未实现的计分方式（仅涉及文档）。** README 描述了分三组加权和每次部署时打乱节点，一份内部 README 还描述了用例的打乱副本。评分器在一个固定的、未打乱的测试集上对全部 56 个用例等权平均。分数没有变化。

**3. 检查器由提交的头文件和 Makefile 编译而成。** `tools/verify.cpp` 包含 `../include/types.h`。该文件位于解题者可以修改的路径中，它定义了 `dist_x10` 以及 `Node`/`Instance` 结构体。评分器还用提交的 `Makefile` 运行 `make -j4`，而随附的 `Makefile` 用与求解器相同的 `CXXFLAGS` 构建 `tools/verify`。因此，一个为了提速、并无作弊意图而修改距离代码、改变 `Node` 字段类型或改变编译参数（例如加上 `-ffast-math`）的求解器，也会改变检查器计算可行性和距离的方式。第 1 点中的精确算术结论只对原始头文件和原始编译参数成立。建议的加固措施：在提交代码之外，用评分器自己持有的原始头文件和编译参数构建检查器。

**4. 无法在每个实例上都用满 60 秒的时间参数。** 求解器以 `./cvrptw_solver <input> <output> <time_budget_sec>` 的方式调用。评分器传入 `min(60, max(1, int(remaining − 6)))` 秒，并在开始 20 分钟后停止一切工作（`TOTAL_JUDGE_TIMEOUT_SEC = 20 * 60`，`PER_INSTANCE_BUDGET_SEC = 60`）；来不及开始的实例记 0 分（`judge_time_limit`）。56 × 60 s = 3,360 s，是 1,200 s 总时限的 2.8 倍。

- 解题者被告知的内容：任务说明写道 "Hidden judge submissions have a 20-minute total wall-clock budget; keep the solver efficient."（隐藏评测的提交有总的墙钟预算，请保持求解器高效。）README §8 列出 "时间预算（单实例）：60 秒"（即每个实例的时间预算为 60 s）和 "总评测预算上限：20 分钟；每实例最多 60 秒，并受剩余总时限截断"（即总预算 20 分钟；每个实例至多 60 s，并被剩余的总时限截断）。其最后一行用英文重复了这一点。`tools/bench.sh` 对 100 个客户的实例传入 60 s。因此上限是有文档的，但没有任何文档说明在总时限内每个实例能分到多少秒（1,200 / 56 ≈ 21 s）。
- **例子。** 一个像随时可停（anytime）搜索通常那样、一直运行到所给时间参数用完的求解器，在 56 个实例中只有约 20 个被计分；其余记 0 分。在参考质量（每个实例 100）下，其分数至多为 21 × 100 / 56 = 37.5 分（满分 100；如果构建耗时约一分钟，则为 20 个实例、35.7 分）；即使在每个实例 160 的上限下，也至多为 21 × 160 / 56 = 60 分。一个自行为每个实例预算约 20 s 的求解器，全部 56 个实例都会被计分。
- 测试框架的时限（`eval_timeout` 1,200 s）等于评分器自己 20 分钟的截止时间。在这个例子中，评分器在截止时间前约 5 s 完成，因此结果仍会被报告，但这一余量取决于容器启动所需的时间。

**随任务发布的说明。** 检查器由提交的 `include/types.h` 和提交的 `Makefile` 编译而成，因此求解器对距离代码、节点类型或编译参数的改动也会改变检查器；建议的加固措施是用原始头文件和编译参数构建检查器。60 秒的时间参数受 20 分钟总时限的约束：56 个实例各用 60 s 需要 3,360 s，因此用满全部时间参数的求解器只有约 20 个实例被计分；请为每个实例预算约 20 s。分数对全部 56 个实例等权平均，已安装的实例是固定的，其节点没有被打乱（README 中的三组加权和打乱都没有实现）。尽管 README 写的是包含端点的 "≤ 0.05"，与检查器总和恰好相差 0.05 的申报成本仍可能被拒绝；申报计算出的成本即可避免这一点。由于测试集是固定的、公开的 Solomon 集（一个标准基准），实例可以被识别出来，而且存在已发表的参考路线；这是披露和数据污染的问题，不是检查器的缺陷。

## 影响有多大

- 容差：对申报自己计算出的成本的求解器没有影响。在申报成本恰好偏差 0.05 的假设情形下，会有一个实例得 0 分，因此影响至多为一个实例的贡献（边界情形见 `evidence/scripts/vehicle_routing_time_windows/exact_checks.out`）。
- 关于加权和打乱的文字：分数没有变化。
- 头文件和编译参数：只影响修改 `include/types.h` 中距离代码或节点类型、或修改 `Makefile` 中编译参数的求解器。没有运行这样的情形，因此没有测得分数影响。
- 时间参数：对于像任务说明和 README §8 所说的那样按 20 分钟总时限做预算的求解器，没有影响。一个在每个实例上都用满 60 秒参数的求解器，会失去 56 个实例中的约 36 个（根据评分器的循环计算得出；没有实际运行）。本任务已记录的五个模型的智能体运行得分为 74.0–90.8 分（满分 100，见 `tasks/README.md`），高于 21 个实例被计分时 60 分的上限，因此这些运行确实按总时限做了预算。

没有代码改动。上述说明随任务一起发布。

## 我们如何检查

- **原始评分器。** 我们针对按摘要固定的原始评分器镜像，阅读了原始评测命令（构建、求解、检查、计分）、`tools/verify.cpp`、`include/types.h` 和任务 README 的源码。全部 56 条示例路线都通过了原始检查器及调用它的代码，使用的是已安装的 56 行参考表。我们不对不可行性或最优性作任何论断。
- **独立的精确检查。** 一个精确算术程序（`exact_checks.py`，使用整数和 `Fraction` 算术）覆盖了全部 56 个已安装实例。它检查了距离是否定义良好、每个实例字段的取值范围、时间窗比较，以及成本容差的边界。
- **漂移上界。** 用 20,000 次随机试验（每次对 120 个十分之一的整数倍求和）给出 binary64 漂移的上界。
- 这里不适用形式化模型。

## 局限

- 没有运行任何 AI 模型或解题者；影响只在我们编写的测试提交和反例上展示。
- 精确检查使用本地 Python。求解器是在本地用 g++ 9.4（`-march=haswell`）构建的，而不是在固定的评分器镜像中。
- 提取的内容中没有已安装的参考（BKS，即已知最优解）CSV；已安装的表记录为 56 行。评分器会给没有参考行的实例记 100 分（`bks.get(name, (nv, td))`）。早先的审计记录显示，已安装的 56 行表为每个实例都提供了参考值，没有用到回退（Git 标签 `earlier-audit-final`，`evidence/selected/vrptw-all56-native-acceptance.json`）；这一点没有重新检查。
- 时间参数的影响是根据评分器的循环计算得出的；没有运行用满全部时间参数的求解器。
- 对任务说明的澄清尚未加入任务说明本身，相关文件也不在本仓库中。
- 关于头文件的说明来自阅读源码；没有构建或评分任何修改了 `types.h` 的求解器。
