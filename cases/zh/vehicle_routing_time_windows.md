# Vehicle Routing Time Windows (`vehicle_routing_time_windows`)

**结论：** 保留（附说明）。<mark>小数容差的疑虑经精确检验，不会改变分数。说明交代了三件事：权重和固定的测试集；检查器是用提交里的 `include/types.h` 和 `Makefile` 编译出来的；在 20 分钟的总时限内，不可能每个实例都用满 60 秒的时间参数。</mark>

## 任务要求

任务要求解题者 "optimize the C++17 CVRPTW solver"（优化该 CVRPTW 求解器），"Modify only src/, include/, and Makefile"（只修改这几个目录和文件），并 "Preserve the cvrptw_solver binary name and CLI"（保留该二进制名称和命令行接口）。CVRPTW 是带时间窗的有容量车辆路径问题：给容量有限的车辆排路线，让每个客户都在规定的时间窗内得到服务。任务 README 说实例分三组加权，每次部署时打乱节点以 "防硬编码答案"，成本容差为 "≤ 0.05"。类别：组合优化。

## 我们检查了什么

对于按文档所述时限做预算的解题者，没有发现会改变分数的计分问题。有四点要说明；第三点（求解器改动波及检查器）的影响没有测量。

**1. 小数容差（已检查，不改变分数）。** README 规定成本容差为 "≤ 0.05"，含端点。检查器用 binary64（标准双精度浮点数）来判断。

- 56 个实例的坐标、时间窗和服务时间全是整数。在 282,800 对节点上，任务四舍五入后的 binary64 距离每次都与精确的整数计算结果相同（0 处不一致）。所以每个距离和到达时间都恰好是 0.1 的整数倍。
- 20,000 次随机试验（每次把 120 个十分之一的整数倍相加）中，binary64 的最大漂移是 1.13e-11。检查器的时间窗判断留了 1e-6 的余量，所以它的判定和精确有理数算术完全一致。没有哪个可行/不可行的判定取决于浮点误差。
- **例子。** 申报成本恰好偏差 0.05 时，检查结果前后不一。真实成本为 12 时，申报 12.05 或 11.95 都被拒绝；真实成本为 4 时，4.05 和 3.95 却都被接受。
- 只有求解器申报的成本恰好偏差 0.05 时，这一点才有影响。求解器如果打印自己的求和结果，与检查器的总和相差在约 1e-11 以内。计分用的是检查器自己重算的距离，不是申报的成本。

**2. README 描述的计分方式，评分器并没有实现（仅涉及文档）。** README 说分三组加权、每次部署时打乱节点，一份内部 README 还提到用例的打乱副本。实际上评分器在一个固定、未打乱的测试集上，对全部 56 个用例等权平均。分数不受影响。

**3. 检查器是用提交的头文件和 Makefile 编译的。** `tools/verify.cpp` 包含 `../include/types.h`，这个文件在解题者可以修改的路径里，定义了 `dist_x10` 和 `Node`/`Instance` 结构体。评分器还用提交的 `Makefile` 运行 `make -j4`，而随附的 `Makefile` 构建 `tools/verify` 时用的是与求解器相同的 `CXXFLAGS`。所以求解器即使只是为了提速、并无作弊之意，只要改了距离代码、`Node` 的字段类型或编译参数（例如加上 `-ffast-math`），检查器算可行性和距离的方式也会跟着变。第 1 点的精确算术结论只在原始头文件和原始编译参数下成立。建议的加固办法：不用提交里的代码，改用评分器自己保存的原始头文件和编译参数构建检查器。

**4. 不可能每个实例都用满 60 秒的时间参数。** 求解器的调用方式是 `./cvrptw_solver <input> <output> <time_budget_sec>`。评分器传入 `min(60, max(1, int(remaining − 6)))` 秒，开始 20 分钟后停止一切工作（`TOTAL_JUDGE_TIMEOUT_SEC = 20 * 60`，`PER_INSTANCE_BUDGET_SEC = 60`）；来不及开始的实例记 0 分（`judge_time_limit`）。56 × 60 s = 3,360 s，是 1,200 s 总时限的 2.8 倍。

- 解题者得到的信息：任务说明写道 "Hidden judge submissions have a 20-minute total wall-clock budget; keep the solver efficient."（隐藏评测的提交有总的墙钟预算，请保持求解器高效。）README §8 列出 "时间预算（单实例）：60 秒"（即每个实例的时间预算为 60 s）和 "总评测预算上限：20 分钟；每实例最多 60 秒，并受剩余总时限截断"（即总预算 20 分钟；每个实例至多 60 s，并被剩余的总时限截断）。最后一行又用英文重复了一遍。`tools/bench.sh` 对 100 个客户的实例传入 60 s。所以上限写在了文档里，但没有哪份文档说过，总时限内每个实例实际能分到多少秒（1,200 / 56 ≈ 21 s）。
- **例子。** 随时可停（anytime）搜索通常会一直跑到时间参数用完。这样的求解器在 56 个实例里只有约 20 个能计分，其余记 0 分。按参考质量（每个实例 100）算，它最多得 21 × 100 / 56 = 37.5 分（满分 100；如果构建要用约一分钟，则是 20 个实例、35.7 分）；就算每个实例都到 160 的上限，也最多 21 × 160 / 56 = 60 分。求解器如果自己给每个实例只用约 20 s，56 个实例都能计分。
- 测试框架的时限（`eval_timeout` 1,200 s）和评分器自己的 20 分钟截止时间相同。在这个例子里，评分器在截止前约 5 s 跑完，结果还能报出来，但这点余量取决于容器启动花多少时间。

**随任务发布的说明。** 检查器是用提交的 `include/types.h` 和 `Makefile` 编译的，所以求解器改了距离代码、节点类型或编译参数，检查器也会跟着变；建议用原始头文件和编译参数构建检查器。60 秒的时间参数受 20 分钟总时限约束：56 个实例各用 60 s 需要 3,360 s，用满全部时间参数的求解器只有约 20 个实例能计分；每个实例请按约 20 s 安排。分数对全部 56 个实例等权平均，已安装的实例是固定的，节点没有打乱（README 里的三组加权和打乱都没有实现）。README 虽然写的是含端点的 "≤ 0.05"，但与检查器总和恰好相差 0.05 的申报成本仍可能被拒；申报自己算出的成本就不会有这个问题。测试集是固定、公开的 Solomon 集（一个标准基准），实例认得出来，也有已发表的参考路线；这属于披露和数据污染问题，不是检查器的缺陷。

## 影响有多大

- 容差：申报自己算出的成本的求解器不受影响。假设申报成本恰好偏差 0.05，会有一个实例得 0 分，所以影响最多是一个实例的贡献（边界情形见 `evidence/scripts/vehicle_routing_time_windows/exact_checks.out`）。
- 加权和打乱的描述：分数不受影响。
- 头文件和编译参数：只影响改了 `include/types.h` 里距离代码或节点类型、或改了 `Makefile` 里编译参数的求解器。没有跑过这样的情形，所以没有测到分数影响。
- 时间参数：照任务说明和 README §8 的意思按 20 分钟总时限安排时间的求解器，不受影响。每个实例都用满 60 秒参数的求解器，会丢掉 56 个实例中的约 36 个（按评分器的循环算出，没有实际运行）。本任务有记录的五个模型的智能体运行得分为 74.0–90.8 分（满分 100，见 `tasks/README.md`），高于只有 21 个实例计分时 60 分的上限，可见这些运行确实按总时限安排了时间。

没有改代码，上述说明随任务一起发布。

## 我们如何检查

- **原始评分器。** 对照按摘要固定的原始评分器镜像，我们读了原始评测命令（构建、求解、检查、计分）、`tools/verify.cpp`、`include/types.h` 和任务 README 的源码。用已安装的 56 行参考表，全部 56 条示例路线都通过了原始检查器和调用它的代码。我们对不可行性和最优性不下任何结论。
- **独立的精确检查。** 一个精确算术程序（`exact_checks.py`，用整数和 `Fraction` 算术）覆盖了全部 56 个已安装实例，检查了距离是否有良好定义、每个实例字段的取值范围、时间窗比较，以及成本容差的边界。
- **漂移上界。** 用 20,000 次随机试验（每次把 120 个十分之一的整数倍相加）给出 binary64 漂移的上界。
- 这里用不上形式化模型。

## 局限

- 没有运行任何 AI 模型或解题者；影响只在我们写的测试提交和反例上演示过。
- 精确检查用的是本地 Python。求解器是在本地用 g++ 9.4（`-march=haswell`）构建的，没有在固定的评分器镜像里构建。
- 提取出的内容里没有已安装的参考（BKS，即已知最优解）CSV；已安装的表记录为 56 行。没有参考行的实例，评分器会记 100 分（`bks.get(name, (nv, td))`）。早先的审计记录显示，已安装的 56 行表给每个实例都提供了参考值，没有用到这个回退（Git 标签 `earlier-audit-final`，`evidence/selected/vrptw-all56-native-acceptance.json`）；这一点没有重新检查。
- 时间参数的影响是按评分器的循环算出来的，没有实际运行用满全部时间参数的求解器。
- 对任务说明的澄清还没有写进任务说明，相关文件也不在本仓库里。
- 关于头文件的说明来自阅读源码；没有构建或评分过改了 `types.h` 的求解器。
