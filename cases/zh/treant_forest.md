# Treant's Forest (`treant_forest`)

**结论：** 已修复。<mark>原始分数刻度的参考点比评分器允许的最大回合数还高，所以任何提交都得不到 21.02/100 以上的分；修复版只改了分数刻度。</mark>

![两条数轴。原始 0 到 100 分刻度的参考点为 5,369、88,189、330,195 和 451,198 回合，分别对应 0、20、80 和 100 分；只有到 92,304 回合上限（21.02 分）为止的部分可以达到，其余标为无法达到。修复版刻度从 3,418 回合（0 分）到 92,304 回合（100 分）。一个 17,960 回合的贪心测试解法在原始刻度上为 3.04 分，在修复版刻度上为 16.36 分。](../figures/zh/treant_forest.svg)

*在 Treant Forest 中，任何提交都不可能超过 21.02 分（满分 100），因为分数刻度是按评分器根本不允许的总数设定的。智能体玩一个按回合数计分的网格谜题。评分器在 2N² 回合后结束每局游戏，所以 50 个用例的总回合数最多为 92,304，而原始刻度要 330,195 回合才给 80 分。修复版刻度从初始代码的 3,418 回合（0 分）到 92,304 回合的上限（100 分）。我们的贪心测试解法从 3.04 分变为 16.36 分，提交之间的先后顺序不变；是否有提交能达到上限尚未证明。*

## 任务要求

这是一个网格谜题，改编自 AtCoder 比赛 AHC054："Your solution is scored on **50 fixed test cases**. Final score = sum of individual case scores. **Higher is better.**"（大意：解法在一组**固定测试用例**上计分，最终分数为各用例分数之和，**越高越好**。）原始结果（换算为 0–100 分之前）随后换算到 0-100 的刻度上。类别：组合优化。

## 问题出在哪里

**规则。** 每个用例的原始结果就是它的回合数，而评分器的测试程序把回合数上限设为 `max_turns = N*N*2`，N 是网格尺寸（tester:63，循环在 :140）。README 没提这个上限。原始分数刻度是 `piecewise_max`，有四个参考点：baseline 5,369、rank30 88,189、rank1 330,195 和 super 451,198。

**例子。** 50 个随附用例的 2N² 之和是 **92,304**，这是原始结果的上界，任何提交都超不过它。达到上限的提交理应得 100 分，在原始分数刻度下却只得 **21.02/100**（精确值为 2543510/121003），所以没有哪个提交能得更高的分。至于是否真有提交能在每个用例上都达到上限，本文没有证明（见局限）。

**为什么重要。** rank1 参考点（330,195）是回合上限的 **3.58×**。所以 100 分制下凡是高于 21.02 的分数（几乎整个 20-80 区间，以及整个 80-100 区间），没有哪个提交能拿到。提交之间的先后顺序没有变。原始参考点从何而来不清楚，看起来像是来自另一个计分程序或另一组用例。

**查过、没有问题的部分。** 最坏情况下运行时间为 7 批 × 120 s = 840 s，在 870 s 的时限以内（余量很小）。测试程序是确定性的。按墙钟时间安排计算的解法，要看 8 个并行工作进程能分到多少 CPU。

**说明：在发布方的 4 个评分器 CPU 下，每个用例约分到半个 CPU。** README 承诺 "Time limit | 60 seconds / test case"（第 71 行）；评分器给了两倍时间（`TIME_LIMIT = 120`，`/tmp/eval_treants_forest.py` 第 9 行），同时跑 8 个用例（`max_workers=min(8, len(case_files))`，第 45 行）。任务没有规定 CPU 数。EdgeBench 的排行榜设置给这个评分器 4 个 CPU（默认值，本任务没有另行设置；引文见 [`evidence/impact/edgebench-leaderboard-config.md`](../evidence/impact/edgebench-leaderboard-config.md)），所以 8 个用例共用 4 个 CPU。我们在原始评分器上用 `--cpus 4` 测了这一点（`evidence/runs/treant_forest-cpu4v8-a/result/out/summary.txt`、`-b`）：用正常的贪心对照解法，在后面附加固定量的 CPU 计算。每个用例 50 或 58 s CPU 时，50/50 通过（TOTAL 17,960；最慢的 58 s 用例耗时 116.1 s，在 120 s 时限内），与 `--cpus 8` 时一样。所以每个用例最多用 58 s CPU 的解法都能通过。按实测比例（58 s 对应 116.10 s），用满 README 所说 60 s 的解法约需 120.1 s，正好卡在 120 s 的时限上，评分器 2× 的余量只是勉强抵消了 CPU 共用。每个用例需要 70 s CPU（超出 README 所说的 60 s）的解法，4 个 CPU 时 48/50 个用例超时（TOTAL 17,960 → 1,018；原始刻度上 3.04 → 0 分，满分 100），8 个 CPU 时能通过；它超出了承诺，所以不算缺陷。如果解题者照 README 的建议，在 55 s 墙钟截止时停下，4 个 CPU 时每个用例的 CPU 时间中位数是 27.4 s，8 个 CPU 时是 54.9 s，所以它的输出乃至分数可能随评分器 CPU 数而变。这几次运行里答案是固定的，所以没有测到分数差异。修复版不改变这一点。

## 影响有多大

所有解题者都受影响：100 分制得分全被压缩在 0–21 之间。随任务附带的基线解法（TOTAL_SCORE **3,418**，50/50 个用例 OK）对应 0 分。

## 修复

只改了任务 JSON 里的 `judge.rescale`（分数刻度），把 `piecewise_max` 的参考点换成 `"kind": "linear", "lower": 3418.0, "upper": 92304.0`。下参考点是随附基线在原始评分器下的原始结果。上参考点是随附用例的 Σ 2N²，即测试程序计分函数的精确上界（回合上限）。四个旧的参考点字段删掉了：其中两个在上限之上，而基于排名的参考点找不到可精确计算的替代值。评分器镜像、评分器、测试程序、用例、`eval_cmd` 和超时都不变，所以原始结果逐字节相同。

**分数是否可比？** 原始结果高于随附基线时（原始结果 > 3418），修复版的 100 分制得分与原始版不可比。原始 `TOTAL_SCORE` 值在各版本之间仍可比较。基于排名的参考点没有了，所以在修复版里，20 分或 80 分不再代表排行榜上的某个百分位。

## 我们如何检查

- **原始评分器，来自按摘要固定的公开镜像。** 原始 `eval_cmd` 分别在原始评分器镜像和修复版镜像里以 `--network none` 运行。每个镜像里评分器、测试程序和用例的哈希都与固定值一致。
- **精确算术。** 每个用例的上限 2N² 按 50 个随附用例的文件头求和，算了两遍，两个脚本用的是同一个单行公式（E2B 上的 `paired/normalize.py`，本地的 `check_arith.py`）；用例文件不在仓库里。这个和在原始分数刻度下对应的分数是精确算出的。
- **阅读源码。** 上限直接从测试程序源码（`tools/bin/tester`）里读出。
- **可重复性。** 原始版和修复版的并排对照运行做了三次，结果不变（`data/paired-repeatability.md`）。

## 局限

- 没有运行任何 AI 模型或解题者。影响只在我们写的测试提交上演示过。
- 92,304 是原始结果的精确上界，但能否在每个用例上都达到，还没有证明。单个用例上最好的正常结果达到了该用例上限的 47%（那次运行各用例的上限没有保存在这里）。
- 从基线到上限的线性刻度会把现实中的高分挤在一起。这是只用可精确计算的参考点、不用排行榜参考点的代价。
- README 仍然没有写出 2N² 的上限。要写出来，就是对解题者能看到的内容另做一项改动。
- 没有查明测试程序的移动规则是否与原版 AHC054 游戏一致，本次修复也不涉及这一点。
- CPU 份额的说明是在 4 个和 8 个 CPU 下测的，用的是单线程测试解法（一种做固定量的计算，一种按截止时间停下）。没有运行真正的随时可停（anytime）解题者，所以截止时间对分数影响多大并不清楚。多线程解题者没有测试。
