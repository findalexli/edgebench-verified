# Anchorhead (`anchorhead_text_adventure`)

**结论：** 保留（附说明）。<mark>分数就是游戏自己的分数，同样的命令每次得分相同；说明写的是评分取最终分而非峰值分，以及任务没有写明的会话限制。</mark>

## 任务要求

任务说明写道："Play the interactive fiction game *Anchorhead* by sending commands via an HTTP API and maximize your score."（通过 HTTP API 发送命令，玩互动小说游戏 *Anchorhead*，尽量拿高分。）互动小说就是文字冒险游戏，玩家输入命令，游戏用文字回应。任务说明没有写时间范围、步数上限或要玩几局。类别：交互式游戏与模拟器。

EdgeBench 把任务交给一个 AI 智能体，智能体最多工作 12 小时，再由一个隐藏的评分器程序打分。评分器先得出原始结果（换算到 0–100 之前的数值），再按任务作者选定的参考点换算成满分 100 的分数。

## 我们检查了什么

我们检查了下面几部分，评分都正确。

- 先看分数的定义。每一步，评分器都从 Z-machine（运行这款游戏的虚拟机）的内存中读取 `env.get_score()`。会话有四种结束方式：游戏结束；智能体关闭会话；会话闲置太久，系统把它关闭；系统要给更新的会话腾位置，把它驱逐。会话结束时，评分器保存这个会话的**最终**分数。一次运行的分数，是它所有会话最终分数中的最高者。分数刻度是线性的，0 分的参考点是起始分数，100 分的参考点是 100，等于 Jericho 为这款游戏给出的 `max_score`（`anchor.c:84-86`）。Jericho 是运行这款游戏的库。任务没有提供基线参考点。举例来说，重放通关攻略得到 99/100，即满分 100 中的 99 分。
- 分数可以重复。代码调用 `FrotzEnv(rom)` 时没有给种子，于是使用库的默认种子 0。所以游戏的随机数不依赖时钟。同一串命令，游戏每次的进程完全相同。

下面几点需要说明。

- 评分器取最终分，不取峰值分。API 还会返回一个 `peak_score`，智能体可能误以为峰值分才算数。只有游戏中途可能丢分时，这一点才有影响。随任务提供的三份游戏记录（Anchorhead、Trinity、Tryst）中，最终分都等于峰值分。
- 评测框架执行三项会话限制，任务说明都没有写：
  - 每一步的 HTTP 超时为 10 s；
  - 每次运行同时最多 3 个会话（超出时驱逐最旧的）；
  - 闲置 600 到 660 s 后关闭会话（闲置检查每 60 s 运行一次，`judge_server.py:156,159`）。

  关闭和驱逐时，系统都会在移除会话的游戏容器之后保存当前分数，所以分数不会丢。如果移除失败，会话会保留下来，到下一次闲置检查时再试；移除成功后才保存分数（`judge_server.py:226-239`）。如果智能体在一局游戏中途停下超过 10 分钟，正在进行的游戏就没了，必须重放。重放花不了多少时间。用录制的 HTTP 请求重放 Trinity（610 条命令）和 Tryst（518 条命令）的完整通关攻略，分别用了 29 s 和 32 s。
- 任务没有展示能否拿满分。随任务提供的参考通关攻略在 99 分时结束，game_over=true，victory=false。在固定版本的游戏文件中能否拿到 100/100，我们没有核实。

随任务发布的说明写了三条。

- 分数取已完成或已关闭的会话中最好的一个，按它的游戏内最终分数计，满分为游戏的 max_score（100）。
- 会话闲置 600 到 660 s 后关闭；同时最多运行 3 个会话。
- Anchorhead 的参考通关攻略拿到 99/100；没有展示能拿满分。

## 影响有多大

- 最终分与峰值分：观察到的最大分数影响为 0。
- 会话限制：观察到的最大分数影响为 0。只有在一局游戏中途停下超过 10 分钟的智能体才需要重放。
- 满分：最多 1 分（满分 100），而且只在 100 分拿不到时才成立。

代码没有改动。上述说明随任务一起发布。

## 我们如何检查

- 我们读了原始评分器固定版本中评分各环节的源码：
  - 每一步读取分数（`game_server_app.py`）；
  - 保存会话分数、执行会话限制（`judge_server.py`）；
  - 在所有会话中保留最好的一个（`selection.py`）；
  - 有效性检查（`grading.py`）；
  - 换算到分数刻度（`score_rescale.py`）。

  仓库中的副本与按哈希固定的副本逐字节相同。评分器镜像的摘要没有记录。
- 我们用本仓库中 EdgeBench 评测框架的副本，在主机上跑了六个会话（`JudgeState`，Docker 后端；当时其中的评分和选取文件是早期审计改过的版本，但这里报告的会话分数来自游戏服务器，与这些文件无关）。我们用原始游戏文件构建游戏容器（构建出的镜像 id 为 `sha256:a197e54f…`）；公开评分器镜像的摘要没有记录。Anchorhead、Trinity 和 Tryst 各做了一次完整通关攻略重放和一次 25 条命令的部分重放，每次部分重放的分数都与完整重放的前 25 步一致。Anchorhead 通关攻略（531 条命令）得到 99/100。
- 我们从上游游戏引擎公开的 Jericho 3.3.1 源码包（sdist）中读到分数来源、`max_score` 和默认种子。

## 局限

- 我们没有运行任何 AI 模型或解题者，影响只在通关攻略会话上展示。
- Anchorhead 的可重复性，依据是一次部分重放与一次完整重放在 25 步上的对照，加上 Jericho 固定的默认种子。
- Jericho 的行为来自上游 3.3.1 源码。我们没有计算镜像中所装文件的哈希。
- 我们没有在会丢分的游戏记录上测试最终分与峰值分的问题。
- 我们没有检查 Anchorhead 能否拿到 100/100。如果找到一串命令能在固定版本的游戏文件中拿到 100 分，说明中的这一条就可以去掉，结论不会变。
