# Anchorhead (`anchorhead_text_adventure`)

**结论：** 保留（附说明）。<mark>分数就是游戏自身的分数，同样的命令每次都得到同样的分数；说明涉及按最终分而非峰值分评分，以及任务没有写明的会话限制。</mark>

## 任务要求

任务说明写道："Play the interactive fiction game *Anchorhead* by sending commands via an HTTP API and maximize your score."（通过 HTTP API 发送命令来玩互动小说游戏 *Anchorhead*，并使分数最大化。）互动小说就是文字冒险游戏：玩家输入命令，游戏用文字回应。任务说明没有写明时间范围、步数上限或游戏局数。类别：交互式游戏与模拟器。

EdgeBench 把任务交给一个 AI 智能体，智能体最多工作 12 小时。一个隐藏的评分器程序为结果打分。它的原始结果（换算到 0–100 之前）按任务作者选定的参考点换算为满分 100 的分数。

## 我们检查了什么

不存在评分问题。以下各部分经检查是正确的。

- **分数如何定义。** 每一步，评分器都从 Z-machine（运行该游戏的虚拟机）的内存中读取 `env.get_score()`。会话有四种结束方式：游戏结束、智能体关闭会话、会话闲置后被关闭，或者为给更新的会话腾位置而被驱逐。会话结束时，评分器保存该会话的**最终**分数。一次运行的分数是其所有会话最终分数中的最高者。分数刻度是线性的。0 分的参考点是起始分数，100 分的参考点是 100，等于 Jericho 为该游戏给出的 `max_score`（`anchor.c:84-86`）。Jericho 是运行该游戏的库。任务没有提供基线参考点。例子：重放通关攻略得到 99/100，即满分 100 中的 99 分。
- **可重复性。** 调用 `FrotzEnv(rom)` 时没有给种子，因此它使用库的默认种子，即 0。因此游戏的随机数来源不依赖于时钟。对于给定的命令序列，游戏每次的进展都完全相同。

说明事项：

- **按最终分，而非峰值分。** 评分器保存的是最终分数。API 还会返回一个 `peak_score`，可能让智能体误以为峰值分才算数。只有在游戏过程中可能丢分时这一点才有影响。在随任务提供的全部三份游戏记录（Anchorhead、Trinity、Tryst）中，最终分都等于峰值分。
- **任务说明没有写明的会话限制。** 评测框架执行三项限制：
  - 每一步的 HTTP 超时为 10 s；
  - 每次运行同时最多 3 个会话（最旧的会被驱逐）；
  - 闲置 600 到 660 s 后关闭会话（闲置检查每 60 s 运行一次，`judge_server.py:156,159`）。

  关闭和驱逐都会在会话的游戏容器被移除后保存当前分数，因此不会丢分。如果移除失败，会话会被保留，并在下一次闲置检查时重试；只有移除成功后才会保存其分数（`judge_server.py:226-239`）。在一局游戏中途暂停超过 10 分钟的智能体会失去正在进行的游戏，必须重放。重放的代价很小：完整的 Trinity（610 条命令）和 Tryst（518 条命令）通关攻略的 HTTP 录制重放分别用了 29 s 和 32 s。
- **未证明能达到满分。** 随任务提供的参考通关攻略在 99 分时结束，game_over=true 且 victory=false。在固定版本的游戏文件中能否达到 100/100，没有核实。

说明的内容是：

- 分数是最佳的已完成或已关闭会话的游戏内最终分数，满分为游戏的 max_score（100）。
- 会话闲置 600 到 660 s 后被关闭；同时最多运行 3 个会话。
- Anchorhead 的参考通关攻略达到 99/100；没有展示能达到满分。

## 影响有多大

- 最终分与峰值分：观察到的最大分数影响为 0。
- 会话限制：观察到的最大分数影响为 0。只有在一局游戏中途暂停超过 10 分钟的智能体才需要重放。
- 满分：最多 1 分（满分 100），而且只在 100 分无法达到时才成立。

没有代码修改。上述说明随任务一起发布。

## 我们如何检查

- **原始评分器，固定版本的源码。** 我们阅读了评分各部分的代码：
  - 每一步读取分数（`game_server_app.py`）；
  - 保存会话分数并执行会话限制（`judge_server.py`）；
  - 在所有会话中保留最佳者（`selection.py`）；
  - 有效性检查（`grading.py`）；
  - 换算到分数刻度（`score_rescale.py`）。

  仓库中的副本与按哈希固定的副本逐字节相同。评分器镜像的摘要 没有记录。
- **在主机上运行的会话。** 六个会话通过本仓库中 EdgeBench 评测框架的副本在主机上运行（`JudgeState`，使用 Docker 后端；当时其评分和选取文件是早期审计修改过的版本；这里报告的会话分数来自游戏服务器，不依赖于这些文件），游戏容器由原始游戏文件构建（构建出的镜像 id 为 `sha256:a197e54f…`）；公开评分器镜像的摘要 没有记录。对 Anchorhead、Trinity 和 Tryst 各做了一次完整通关攻略重放和一次 25 条命令的部分重放，每次部分重放的分数都与完整重放的前 25 步一致。Anchorhead 通关攻略（531 条命令）得到 99/100。
- **上游游戏引擎源码。** 分数来源、`max_score` 和默认种子是从公开的 Jericho 3.3.1 源码包（sdist）中读到的。

## 局限

- 没有运行任何 AI 模型或解题者。影响只在通关攻略会话上展示。
- Anchorhead 的可重复性依据的是一次部分重放与一次完整重放在 25 步上的对照，加上 Jericho 固定的默认种子。
- Jericho 的行为来自上游 3.3.1 源码。镜像中安装的文件没有计算哈希。
- 最终分与峰值分的问题没有在会丢分的游戏记录中测试过。
- 没有检查 Anchorhead 能否达到 100/100。如果有一个命令序列能在固定版本的游戏文件中达到 100 分，说明中的那部分就可以去掉。这不会改变结论。
