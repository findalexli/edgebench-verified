方法

我们如何检验这些结论

原始评分器上的证据、范围明确的形式化模型，以及针对具体版本的修复检验

本页介绍的是针对原始版本的第一轮审计。其中哪些发现在当前评分器上站得住，见概览页。

1流程

我们检查的是，按规则完成的工作能否得到任务承诺的分数。发现缺陷、验证补丁、集成发布版本、衡量对排行榜的影响，是几个相互独立的结论。每个任务都记录了当前修复候选版本的证据和尚存的局限。

{{fig:evidence-layers}}
  1. 固定原版，读懂它的约定。把任务说明和公开镜像（按摘要固定）里的评分程序对照着读。记录源文件的指纹和评分路径。
  2. 使用能触发缺陷的对照。条件允许时，让正确的、触发问题的和错误的提交都在原始评分程序上跑一遍。组件检查和基于源代码的论证，与完整的任务运行分开标注。
  3. 独立检验。在能回答具体问题的地方，使用精确算术、另一个实现、穷尽搜索或形式化模型。几个 AI 审查者意见一致，并不等于有人独立复现过。
  4. 追踪到最终分数。区分实测的变化、上限和受限的数值估计。上限不一定能达到；组件层面的差异，也可能被评分流程中更早的否决掩盖。
  5. 验证修改后的版本。成对对照应当表明：触发问题的提交得到纠正；正确的工作分数不变，或者分数变化有解释；评分器仍然拒绝错误的工作。历史结果不能用来验收后来的修订版。完整的发布验收还要求实际的任务命令、依赖、工作镜像和评分器镜像，以及收集结果的评测框架，能在预算内配合运行。

就历史可重复性而言，保存的清单中有 {{n_cmp}} 项评分对照，覆盖 {{n_cmp_tasks}} 个已修复任务，以及已移除任务的部分修复；其中 {{n_cmp3}} 项运行了三次，不含 {{n_cmp_setup}} 次准备性运行。其余 {{n_cmp_once}} 项只运行了一次：Datagen v2.1 和 FFmpeg v2.2 各三项对照、Exchange Core 在 4 个 CPU 下的六行（每行一次运行）、CTA v2.1 的标准答案，以及 Rust 初始代码在修复版下的得分。Lean Analysis 所用的依赖路径与它实际的评分命令不同；PFR 没有展示五个实际目标的得分恢复；Warehouse 需要评测框架的一个等待叠加层，端到端集成尚未完成。详见各修复包的验证状态。

2形式化证据及其局限

Lean 检查证明项，并报告证明依赖哪些公理。TLA+ 在配置好的有限模型里遍历所有可达状态。源代码对应关系和差分检查把这些模型与实现的行为联系起来，但这种联系本身并不是经过机器检验的等价性证明。有两个具名的 Lean 反向对照故意依赖任务中已安装的占位定义，我们不把它们当作普通证明。

保存的清单涵盖 {{formal_tasks}} 个任务、{{lean_files}} 个 Lean 文件（其中 {{lean_thms}} 个定理附有公理报告），以及 {{tla_models}} 个 TLA+ 模型上的 {{tla_runs}} 次运行。其中 {{fix_proved}} 个修复模型归为“已证明”或“已模型检验”（其中 {{fix_earlier}} 个针对修复的早期版本），{{fix_partly}} 个归为部分证明。这些分类针对的是模型，并不认证当前的 {{repair-v2}} 个修复包。保存的 Datagen 证明用的是历史上较宽松的年份范围；FFmpeg 证明对验证过程做了抽象，不涵盖 v2.2；CTA 模型以总敞口为分母，而政策规定的分母是基金净资产；Graph Node 的证明针对第一个修复（v2），不涵盖 v2.1 的 str() 键处理和重复键拒绝；College English 的模型针对 v2.1，不涵盖 v2.2 的 JSON 块选取和十进制字符串读取。SMT 的可靠性只涵盖一个受限的片段。

历史复检记录保存在 RECHECK.md 中。命令 python3 tools/check_formal.py 重新运行已发布的源文件，检查不变式结果是否符合预期，以及是否给出了所要求的公理报告。复检通过，并不能证明模型之外的行为，也不能验证模型没有覆盖的后续候选版本。

3局限

  • 范围限于 51 个公开任务；83 个尚未发布的任务，以及对评分器的蓄意攻击，不在范围内。
  • 我们没有重新运行任何 AI 模型。我们给部分第三方提交重新评了分，但拿不到排行榜的提交。从平均分换算 Treant 的分数，在截断点或分段边界处并不精确。上限超过名次差距，也不能证明名次真的可能反转。
  • Portfolio 的 +0.3921/−0.10 包络来自一次受限的敏感性扫描，不是普遍成立的上限。Equivalence 的 9.67 分上限没有证明可以达到。Vibrating Path 零命中格式问题的影响，在 37 个用例上已经排除，在 13 个用例上仍未解决。
  • CPU 实验证实了结果对资源敏感。只规定墙钟时限，并不等于承诺独占一个核心或同等的 CPU 秒数；限制并行度是一项明确的策略改动。大多数成对作业在 E2B 沙箱中运行；Lean Analysis 用的是一台本地主机。速度测量结果在其他环境中可能不同。
  • 以提交 83181b7f 时的状态计，32 个修复包中有 31 个在干净的机器上从零重建成功；Lean Analysis 例外，它的评分器镜像约需 45 GB 磁盘空间。之后修订过的修复包，只由后来的运行覆盖。
  • CTA 的净资产修正在原始评分命令下通过了成对原生运行，但没有给解题者的输出评分。Triangulation 重新生成的 v2.2 输入恰好覆盖其凸包。有限的对照和形式化模型不能确立整个任务的正确性。

经验

  • 先运行原始评分器，再推理。大多数问题是我们读代码时发现的，但要靠一份能触发问题的提交才能坐实。有几项看似合理的发现没能过这一关。
  • 形式化工具适合小而明确的问题。一个错误的定理、一个算术缺口、一个下界和一个别名缺陷，都得到了确定的结论。大多数评分器问题涉及约定、文件格式或时间，处理这类问题，任何证明都不如一次并排对照运行省事。
  • 证明需要和它描述的代码对应起来。对 {{task:lean_analysis_proofs|Lean Analysis}}，我们在该任务自己的镜像中、用它自己的定义陈述反驳。对 {{task:warehouse_forklift_routing|Warehouse}}，我们在 294 个字符串上把模型和真实的测试程序对照，并把每个 TLA+ 步骤对应到一行源代码。
  • 每项检查都需要反向检验，因为不可能失败的检查什么也说明不了。每个 TLA+ 模型都有一个必定失败的配置，每个 Lean 证明都打印它依赖的公理，每项修复都应该分别拿正确和错误的工作来测试；实际覆盖范围见各案例页。
  • 形式化证明也检查了我们自己的工作。我们把部分修复机制写成 Lean 或 TLA+ 模型，结果发现一项修复的覆盖范围比发布时说的窄，还发现八处表述不够精确。每一处的发现，都是因为某次证明尝试在我们没想到要测的情形上失败了。
  • 要测试修复是否达到目的，不只测它改了什么。{{task:integer_compression_codec|Integer Codec}} 的第一版修复完全按文档改正了基线，也通过了每一项测试，但真实提交表明它让分数刻度饱和了。证明和我们自己写的测试都没发现这一点，拿真实的智能体工作检查修复才发现了它。
  • 审查者认可不等于实测。代码追踪判定许多说法成立。放到当前评分器上用真实提交实测后，其中几条缩小到 1 分或更少，有一条被真实运行推翻，而影响最大的两项发现（SMT 崩溃和 Datagen 接口），审查的任何一轮都没有提到。
