Method

How we verified

Test submissions on the original grader, formal proofs where a claim is precise, and side-by-side tests of every fix

1The procedure

Every claim on this site rests on up to four independent layers of evidence (Figure 1). The first applies to every finding and the third to every fix that changes something that runs; the second applies wherever a claim could be stated precisely enough to prove, and the fourth wherever a public agent run covered the task.

{{fig:evidence-layers}}
  1. Use the original grader. Every check ran on EdgeBench's published grading software, pulled from its public images and identified by a cryptographic fingerprint, with network access switched off except where a task needs it ({{task:new_foundations_consistency|New Foundations}} downloads a dependency to build).
  2. Quote the promise. What a task promises is taken verbatim from the instructions and documents the agent receives, and read next to the grader's code.
  3. Show the problem with test submissions. For each suspected problem we wrote three submissions and ran them through the original grader: a correct one, which must score as promised; one that triggers the problem; and a wrong one, which must be rejected.
  4. Confirm it independently. Claims were checked a second way, with exact arithmetic, a separate implementation, exhaustive search, or a formal proof in Lean 4 or TLA+ (Section 2).
  5. Follow it to the final score. A problem counts only if it changes the 0–100 score of honest work; problems that do not are recorded as notes.
  6. Test every fix side by side. The same test submissions were graded by the original and the fixed grader. A fix is accepted only if the problem disappears, correct work keeps its score and wrong work is still rejected. All but one comparison were run three times. Across {{n_cmp}} graded comparisons ({{n_cmp_tasks}} fixed tasks and the removed task's partial fix; {{n_cmp3}} of them run three times; {{n_cmp_setup}} setup runs that prepare inputs are not counted), one outcome changed, under the original grader: at 4 CPUs, {{task:vibrating_path_graph_coloring|Vibrating Path}}'s valid deadline-based test submission timed out on 14 cases in one of its nine original-grader gradings, the timing problem the fix removes. No fixed-grader outcome changed. Exceptions: {{task:openrct2_theme_park_ai|OpenRCT2}}'s fix changes only its instructions and has nothing to run; {{task:lean_analysis_proofs|Lean Analysis}} repeats ran locally rather than on fresh machines; {{task:integer_compression_codec|Integer Codec}}'s final 0–100 scale was applied to the recorded raw results; the revised {{task:college_english_exam_bank|College English}} grader was itself run three times; and the {{task:rust_multicrate_reconstruction|Rust}} starter's fixed-version score was run once, because each run takes about 40 minutes and nearly fills the machine's disk.

2Formal verification with Lean 4 and TLA+

Testing shows that a problem occurs; it cannot show that something holds for every input. Wherever a claim could be stated precisely, we also checked it with a formal tool. Lean 4 is a proof assistant: a claim counts only once its kernel accepts a complete proof, and every proof lists the basic axioms it relies on, so a hidden gap would show. (Two theorems deliberately apply a refutation to the task's own unfinished definitions and depend on its placeholder; they are excluded from the count.) TLA+ describes a system as a state machine, and its model checker explores every reachable state of a bounded version.

Three rules applied to every formal result. The model is tied to the real grader code: each step maps to a source line, the file's fingerprint is recorded, and wherever possible the model is run against the real code's saved outputs. Each result has a counter-check that must fail, such as the original rule violating the property or a deliberately too-strong claim being false. And each states its limits.

In total, {{formal_tasks}} of the 51 tasks have formal results: {{lean_files}} Lean files with {{lean_thms}} theorems, and {{tla_runs}} model-checking runs over {{tla_models}} TLA+ models (Table 2). TLA+ results are exhaustive only within stated bounds, so Table 2 calls them model-checked rather than proved. For {{fix_proved}} of the {{repair-v2}} fixes, Lean or TLA+ establishes that the fix itself is correct within its model, and {{fix_partly}} more are partly proved. The remaining fixes rest on the side-by-side runs. Some change only instructions or starter files ({{task:arc_compiler_runtime|ARC}}, {{task:openttd_transport_ai|OpenTTD}}, {{task:openrct2_theme_park_ai|OpenRCT2}}, {{task:borden_source_inversion|Borden}}'s convention); some depend on test suites, timing or CPU share ({{task:exchange_core_throughput|Exchange Core}}, {{task:warehouse_forklift_routing|Warehouse}}'s time limit, the CPU limits in {{task:apple_incremental_game|Apple}}, {{task:grid_turing_robot|Grid}}, {{task:molecular_self_assembly|Molecular}}, {{task:vibrating_path_graph_coloring|Vibrating}} and {{task:triangulation_coloring_optimization|Triangulation}}); and some have formal results about the finding or the published numbers rather than the fix itself ({{task:treant_forest|Treant}}, {{task:schemathesis_config_modernization|Schemathesis Config}} and {{task:schemathesis_reporting_observability|Reporting}}). {{task:git_rewrite_in_zig|Git in Zig}}, {{task:pfr_formalization|PFR}} and {{task:juliet_vulnerability_analyzer|Juliet}} were not formalized. "Within its model" means for the simplified version of the code that was written down; a counter-check is a deliberately wrong version that must fail. Every formal result reruns with one command, and the TLA+ checks rerun automatically on every change.

The formal checks also corrected us. One shipped fix was narrower than published: the {{task:college_english_exam_bank|College English}} grader still gave full marks in four rare kinds of contradictory assessment. It has been revised, re-proved, and run side by side three times. Eight other statements said more than the evidence showed and have been corrected, for example the SMT comparability claim, the PSNR thresholds of the FFmpeg fix and a side effect of the Order Addition fix. None changed a score we report. The full list is in CORRECTIONS.md.

3Limitations

  • Only the 51 public tasks are covered; EdgeBench's other 83 tasks are unreleased.
  • No model was rerun. Effects on the leaderboard are computed where possible and bounded otherwise (Leaderboard).
  • Deliberate attacks on the grader by a malicious submission concern how the benchmark isolates its grader, and are out of scope.
  • Most side-by-side tests ran on E2B cloud sandboxes with 8 virtual CPUs and 8 GiB of memory; Lean Analysis ran on a local host with 16 CPUs and 15 GB. The grader's CPU limit ranged from 1 to 8 CPUs, as each case states. Speed-based scores may differ elsewhere.
  • The reviews were carried out by AI agents. Every claim is tied to a saved evidence file and a rerunnable check, which is not the same as independent human reproduction.
