EdgeBench Verified

Which problems in the hidden checkers behind the 51 public EdgeBench tasks hold up

Version 1.12 November 2026 Code, data and fixes on GitHub How to cite

In short

EdgeBench ranks AI agents on 51 public engineering and science tasks. In each task an agent works for hours, and a hidden checker program scores what it submits, from 0 to 100. Our first audit reported problems in 32 of those tasks. We then tried to break our own findings: an independent AI reviewer attacked each one, and we measured what survived on the current community judge, using real agent submissions where they exist. {{rc_confirmed}} tasks hold up as problems that matter: a good-faith solver is scored wrongly or non-repeatably, and we measured how much. The rest are small, already changed upstream, or not confirmed, and we say which.

1What EdgeBench is and how it scores an agent

An EdgeBench task gives the agent written instructions and starter files: make a trading engine faster, write a bot for a strategy game, finish the proofs in a mathematics library, infer the source of groundwater pollution from sensor readings. The agent can submit as often as it likes during its twelve hours, and it sees each score. A hidden checker program (EdgeBench calls it the grader), written by the task's authors, runs every submission on hidden test cases and produces a raw result, such as a cost, a speed or a count of passed tests. EdgeBench converts the raw result to a score from 0 to 100 using reference points the authors chose for that task. Each run keeps its best score. Each model has three runs per task; EdgeBench averages the valid runs and drops a run that failed as a whole, for example by crashing. A model's headline number is its average over tasks.

A score can therefore go wrong at four points (Figure 1): the checker can accept wrong work; it can reject correct work or apply a rule the agent was not told; the conversion to 0–100 can be unreachable or mismeasured; and the run can keep the wrong submission. We found all four, and a fifth source of error outside the checker's code, the machine it runs on. EdgeBench's official settings give a checker 4 CPUs unless the task overrides it, and six checkers run more work at once than that ({{task:vibrating_path_graph_coloring|Vibrating Path}}).

2How we reviewed

The first audit asked of each task whether an agent that solves it correctly and by the rules gets the score the task promises. It tested the original release and published fixes for 31 tasks. The second review, in November 2026, asked which of those findings hold up against the current judge, using EdgeBench's own contribution rule: a good-faith solver is scored wrongly or non-repeatably, and the final score moves.

  1. Attack. An independent model (GPT-6 Astra) reviewed 146 claims in the current code, rechecked 48 from scratch and attacked 46, trying to refute them. It ran pure functions but no containers.
  2. Measure. Where we could, we built the judge from community at 1187e2c and graded a control and a trigger differing only at the defect, repeated at least twice; repeatability claims used at least three gradings of one file. Other evidence includes single agent runs, direct evaluator runs, local scoring tests and calculations, and each result says which.
  3. Check against real runs. A claim counts for less if real solvers score well despite it. One reviewer-approved claim fell this way: on Borden Inversion, a real run reached raw 108.97 of 109.

Limits: most tasks have one model's real runs, or none. The SMT results ran below official resources, because of our cloud account's cap. "Not confirmed" means we could not show harm on the current judge, not that the first audit's measurements on the original release were wrong; those are kept on each task page.

3What holds up

A task is confirmed when the measured change reaches real work: regrading a real submission shows it, or a repeatability failure affects any submission. A defect that is large only on a trigger no real submission we hold uses stays with the others. Graph Node, for example, drops from 90.52-90.57 to 1.95-2.01 if predictions use integer keys, which the task permits.

Each entry gives the defect, the measured effect on a score out of 100 unless stated otherwise, and whether upstream knows.

4The first audit

This review corrects our first audit, which tested the original release, reported problems in 32 of the 51 tasks and estimated ranges for the published leaderboard. Of those 32, 10 are confirmed, 13 are real but small or unseen, 1 has changed upstream and 8 are not confirmed. Those ranges count every first-audit fix, including fixes for claims this review did not confirm, and we have not recomputed them. Each task page keeps the first audit's record.
