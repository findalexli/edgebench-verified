EdgeBench Verified

We tested the hidden checkers that score the 51 public EdgeBench tasks

Version 1.012 October 2026 Code, data and fixes on GitHub How to cite

In short

EdgeBench ranks AI agents on 51 public engineering and science tasks. In each task an agent works for hours, and a hidden checker program scores what it submits, from 0 to 100. We tested each checker the way you would test any program: we gave it correct work, broken work and work that follows the instructions to the letter. In {{n_problem}} of the 51 tasks the checker scored some submissions wrongly. Checkers gave correct solutions zero under time limits stricter than promised, rejected correct answers, gave full credit to broken programs and enforced rules the instructions never stated. On one task's score scale, no submission could score above 21. We published fixes for {{repair-v2}} of these tasks and removed {{exclude}} task. We checked the fixes by grading the same submissions with the original and the fixed checker side by side. Where a public agent run was available, we regraded its submissions too: in one task the run's score moves from 3.8 to 41.2 out of 100. The published averages do not allow the leaderboard to be recomputed, but they are enough to show that its top two places can no longer be confirmed.

1What EdgeBench is and how it scores an agent

An EdgeBench task gives the agent written instructions and starter files: make a trading engine faster, write a bot for a strategy game, finish the proofs in a mathematics library, infer the source of groundwater pollution from sensor readings. The agent can submit as often as it likes during its twelve hours, and it sees each score. A hidden checker program (EdgeBench calls it the grader), written by the task's authors, runs every submission on hidden test cases and produces a raw result, such as a cost, a speed or a count of passed tests. The raw result is converted to a score from 0 to 100 using reference points the authors chose for that task. Each run keeps its best score. Each model has three runs per task, and the valid runs are averaged (a run that failed as a whole, for example by crashing, is dropped). A model's headline number is its average over tasks.

A score can therefore go wrong at four points (Figure 2): the checker can accept wrong work; it can reject correct work or apply a rule the agent was not told; the conversion to 0–100 can be unreachable or mismeasured; and the run can keep the wrong submission. We found all four, plus a fifth outside the checker's code: the machine it runs on. EdgeBench's official settings give a checker 4 CPUs unless the task overrides it, and six checkers run more work at once than that (Section 3.1).

2What we did

For each of the 51 public tasks we asked one question: if an agent solves the task correctly and by the rules, does it get the score the task promises? We traced the evidence to the original checker code and to the final score. Runs of the real checker, tests of its parts and formal models answer different questions; none alone certifies every current fix (Figure 3). Each task then received one of three outcomes:

  • Fixed ({{repair-v2}} tasks). The checker's logic, data or setup can be corrected. We publish each fix as a new version of the task. Case pages state what the side-by-side checks cover and what integration work remains; Applying the fixes lists the open steps.
  • Kept, with a note ({{retain-with-note}} tasks). No correctable problem found. The note records caveats that no change to the checker removes, such as variation between runs or machines.
  • Removed ({{exclude}} task). No sound fix was possible.

3What goes wrong

Every task with a problem ({{n_problem}} tasks: {{repair-v2}} fixed, {{exclude}} removed) has one primary category, chosen by how its main defect arises, and may have secondary ones. The four categories are:

  • {{t:pcat.engineering}} ({{pcat_count_engineering}}): the checker does not run correctly in the real setup.
  • {{t:pcat.grader_logic}} ({{pcat_count_grader_logic}}): the checker marks wrong work as right, or right work as wrong.
  • {{t:pcat.instruction_mismatch}} ({{pcat_count_instruction_mismatch}}): the checker enforces something the instructions do not state, or contradicts them.
  • {{t:pcat.scale_selection}} ({{pcat_count_scale_selection}}): the 0–100 scale cannot be reached, a reference point is wrong, or the wrong submission is kept.

Each category below starts with a short explanation and its list of tasks, then gives two to five examples with a figure each. Every task is listed on the Tasks page, which can be filtered by category, and each has a full case with the test submissions, the independent checks and the fix. Every task name below links to its page.

{{t:pcat.engineering.blurb}}

{{pcat_tasks_engineering}}

{{task:rust_multicrate_reconstruction|Rust Multicrate}}: hidden tests that cannot compile. The agent rebuilds a 14-package Rust project and is told not to edit the tests. The checker adds hidden tests to all 14 packages, and in two of them, search (12 points) and the command-line program (10 points), it places them where they do not compile. Both packages, 22 of the 100 points, score 0 for every solver who leaves the tests and package settings unchanged. A complete, correct solution scores 73.99 out of 100 with the original checker and 94.70 with the fixed one, a gain of 20.71: search +11.29, the command-line program +9.32, and a test the original skipped after an earlier failure +0.10. (A solver could still make search compile by turning on its parallel setting, which edits no test; nothing in the task points to it.) The fix places the hidden tests where they compile and runs every test file.

{{verif:rust_multicrate_reconstruction}}

{{fig:rust_multicrate_reconstruction|rust_multicrate_reconstruction}}

{{task:grid_turing_robot|Grid Robot}}: eight test cases share four processors. The instructions promise 30 seconds per test case. The checker runs eight cases at the same time, and EdgeBench's official settings give it four processors (the settings, quoted), so each case gets about half a processor. A valid solution that computes for 16 seconds per case times out on 48 of its 50 cases, and one timeout throws out the whole submission; with the fix the same solution scores its 19.80 out of 100. The fix runs no more cases at once than the checker has processors. Five more tasks share this problem: {{task:vibrating_path_graph_coloring|Vibrating Path}}, {{task:molecular_self_assembly|Molecular Assembly}}, {{task:apple_incremental_game|Apple Game}}, {{task:triangulation_coloring_optimization|Triangulation}} and {{task:warehouse_forklift_routing|Warehouse Routing}}. In a real agent run on Molecular Assembly, single submissions rose by up to 12.22 points out of 100 under the fix (real runs). Solutions that stop at a fixed clock time are usually not thrown out; they get half the computing time instead.

3.2{{t:pcat.grader_logic}} {{pcat_count_grader_logic}}

{{t:pcat.grader_logic.blurb}}

{{pcat_tasks_grader_logic}}

{{task:exchange_core_throughput|Exchange Core}}: a broken stock exchange passes. The agent makes a stock-exchange engine faster without changing what it does, and is scored on speed. The original checker only confirms that money balances overall and that the order books match. Two realistic small bugs pass and are scored as correct: one charges sellers the wrong fee, the other never delivers trade messages. Across four runs they scored 7.77–24.40 and 4.71–15.62 out of 100, within the run-to-run speed noise of the correct engine (0–24.19 in the original-checker runs alongside them). The project's own tests catch both bugs; the fixed checker requires those tests to pass and gives the broken engines 0.

{{verif:exchange_core_throughput}}

{{fig:exchange_core_throughput|exchange_core_throughput}}

{{task:college_english_exam_bank|College English}}: an empty grading report scores 100. An AI model grades the agent's exam papers against 12 rules worth 100 points. If the model's answer leaves a rule out, the checker's code gives that rule full marks and still calls the result valid. A grading report that assesses nothing scores 100 out of 100; one that skips a single 15-point rule scores 81 instead of 77, or 15 instead of 0. The fixed checker asks the model again and otherwise reports a grading failure. How often real grading reports skipped rules is not known.

{{verif:college_english_exam_bank}}

{{fig:college_english_exam_bank|college_english_exam_bank}}

{{task:smt_solver|SMT Solver}}: correct answers rejected. The agent builds a solver for logic puzzles and must give an example answer whenever a puzzle has one. The checker looks up a value by how it is written, not by what it stands for, so when the same text means two different things in one puzzle, no correct answer can pass. This makes 27 hidden puzzles impossible to win and lowers a perfect solver's maximum from 78.61 to 72.40 out of 100. (A correct "no solution" answer earns at most a fifth of a puzzle's credit, so even a perfect solver tops out at 78.61.) On 42 more puzzles it rejects answers written the way the instructions describe. The fixed checker looks values up by what they stand for and accepts correct answers on all 69.

{{verif:smt_solver}}

{{fig:smt_solver|smt_solver}}

{{task:ffmpeg_swscale_reimplementation|FFmpeg Swscale}}: code that fails instantly earns speed credit. The agent rewrites an image-resizing library and is scored on correctness and speed. The speed tests time conversions without checking their output, so a call that fails or does nothing "finishes" almost instantly. Unfinished code earned up to 18.93 out of 100 this way under the original checker (5.39, 18.93 and 17.87 for three test versions, against 0 for the unchanged starter code, in the same run). The fixed checker checks the output of every timed call, and any failed workload makes the total exactly 0: in its one side-by-side run, code that skips repeated calls passed all 30 correctness tests and scored 0.

{{verif:ffmpeg_swscale_reimplementation}}

{{fig:ffmpeg_swscale_reimplementation|ffmpeg_swscale_reimplementation}}

The one task we removed

{{task:dabic_gravity_inversion|D-ABIC Gravity Inversion}}. About 42 of the 100 points (two parts, worth 12 and 30) come from the submission's own results file and are never verified. A sound fix would need the checker to recompute them from hidden data, so the task was removed. A second problem, a hidden penalty on one of two formulas the instructions allow, was fixed, but that alone does not make the task usable.

{{task:warehouse_forklift_routing|Warehouse Routing}}: promised 150 seconds, cut off at 60. The instructions promise 30 seconds per test case, or 150 seconds for each input of five cases. The checker stops each input after 60 seconds, and a single timeout throws out the whole submission. A test solution that takes 13 seconds per case, less than half the promise, gets no score at all; with the fix all 50 inputs are scored. The fix raises the limit to the promised 150 seconds and runs no more inputs at once than the checker has processors. One part of the fix, which makes sure results that arrive at the very end are counted, has been tested on its own but not yet in a full EdgeBench run. Separately, a bound proved in Lean shows that no valid answer can score above about 30.6 out of 100 on this task's scale; that limit is documented, not changed.

{{verif:warehouse_forklift_routing}}

{{fig:warehouse_forklift_routing|warehouse_forklift_routing}}

{{task:arc_compiler_runtime|Arc Compiler}}: the same code scores 69 or 36. The agent finishes a small compiler. Hidden tests worth a third of the points (33.67 of 100) expect error reports in one particular format, while the starter code uses another and nothing the agent can see says which is right. One error checker, written in good faith, scores 69.26 when it reports errors in the hidden format and 35.59 in the starter's. The fixed task documents the format; the checker and the score of any given code are unchanged.

{{verif:arc_compiler_runtime}}

{{fig:arc_compiler_runtime|arc_compiler_runtime}}

{{task:juliet_vulnerability_analyzer|Juliet Analyzer}}: the public examples teach the wrong format. The agent writes a tool that finds security bugs in C code and reports where each one starts. For command-injection bugs, all 38 public examples mark the start at the line that runs the command, but all 120 hidden answers mark it at the line where the input is read, and the original checker accepts only the hidden form. An analyzer that finds only the command-injection bugs and copies the public examples loses 15 points (45.66 against 60.66 out of 100); one that finds every bug loses 2.49, and the worst case is 26.47 (computed exactly, not run). In a real agent run, 14 of 105 submissions, all early ones, were affected, two by about 25 points (70.00 against 95.22 and 95.26); later submissions and the run's kept score were not. The fixed checker accepts both forms.

{{verif:juliet_vulnerability_analyzer}}

{{fig:juliet_vulnerability_analyzer|juliet_vulnerability_analyzer}}

{{task:borden_source_inversion|Borden Inversion}}: the checker's physics is not the textbook's. The agent locates an underground pollution source from monitoring-well readings. The checker predicts the readings with a physics model whose conventions the instructions never state; for example, it ignores soil porosity. A standard textbook fit scores 7.03 and the same fit using the checker's conventions 31.2 (raw results on this task's 0–109 range; 6.45 and 28.62 out of 100). In a real agent run, whose answers score the same under the unchanged grader, the best score climbed from 7.01 to 60.10 over 36 submissions while the checker reported its error on the hidden wells after each one. The fixed task gives agents the checker's model.

{{task:order_addition_permutation_optimization|Order Addition}}: the run's later, better work never counts. Each run reports its best submission, chosen first by how many of the checker's five tests pass. One test compares a helper file against an outdated fingerprint, so every submission fails it, every scored submission ties at 4 of 5, and the run is stuck with its first scored submission. In a real agent run this kept 3.79 out of 100 instead of the 41.24 a later submission earned. The fix updates the fingerprint; each submission's own score is unchanged. Anyone who keeps the highest score instead is not affected.

{{task:treant_forest|Treant Forest}}: no submission can score above 21. The checker stops each game after a fixed number of turns, so no total can exceed 92,304. The 0–100 scale was set as if totals up to 330,195 were possible, so even a perfect submission would score 21.02 out of 100. The fixed scale runs from the starter's total to the most the checker allows (whether any submission can reach it is not shown). A simple test solution moves from 3.04 to 16.36, and the order of submissions is unchanged.

{{verif:treant_forest}}

{{fig:treant_forest|treant_forest}}

{{task:integer_compression_codec|Integer Codec}}: an impossible reference number. The agent writes a compressor for lists of numbers and is scored against stored reference results for the starter code. One stored figure claims 5.13 bits per number, below the 8-bit minimum for the starter's format; the starter really needs 38.98. As a result the starter scores about 0.23 instead of the documented 1.0 (raw), and the datasets count differently from what is published. The fix measures the starter in the same run and sets a new 0–100 scale from the starter's result to the highest the formula allows. That moves a real agent run from 71.93 to 53.95 out of 100, both regraded on our machines, so a fix can lower a score as well as raise it. (The run itself recorded 75.72 on its own machine.)

4Effect on the published leaderboard

EdgeBench has not released its agents' submissions, so the corrected leaderboard cannot be computed. We could make one check. A third party published one four-hour run of one model on 16 public tasks, nine of them tasks we fixed. We regraded its submissions with the original and the fixed checker. In that run some of the problems did affect the agent and some never came up (figure below).

On the published leaderboard, Opus 4.8 leads GPT-5.5 by {{headline:top_gap}} points ({{headline:top1_pub}} against {{headline:top2_pub}}). 5How we verified

  1. Use the original grader, EdgeBench's published grading software, pulled from its public images and identified by a cryptographic fingerprint.
  2. Quote the promise verbatim from the instructions and documents the agent receives.
  3. Show the problem with test submissions: a correct one, which must score as promised; one that triggers the problem; and a wrong one, which must be rejected.
  4. Confirm it independently, with exact arithmetic, a separate implementation, exhaustive search, or a formal proof in Lean 4 or TLA+.
  5. Follow it to the final score. A problem counts only if it changes the 0–100 score of a good-faith submission.
  6. Compare original and repaired versions on the same test submissions: {{n_cmp}} graded comparisons, {{n_cmp3}} of them run three times.

{{formal_tasks}} of the 51 tasks have formal results, with {{lean_thms}} Lean theorems and {{tla_runs}} TLA+ model-checking runs. The saved formal results prove {{fix_proved}} fixes within explicit models ({{fix_earlier}} of them an earlier version of the fix) and {{fix_partly}} more in part. They do not prove later versions of a fix, the whole checker or the published images. The formal checks also caught a mistake of ours: one shipped fix was narrower than we had published, and we revised it.

6Lessons

  • Run the original grader before reasoning about it. Most problems were found by reading code but settled only by a submission that triggers them. Several plausible findings did not survive that step.
  • Formal tools work best on small, precise questions. They settled a false theorem, an arithmetic gap, a lower bound and an aliasing bug outright. Most grader problems concern conventions, file formats or timing, which no proof addresses as cheaply as a side-by-side run.
  • A proof is only as good as its link to the code. We stated the {{task:lean_analysis_proofs|Lean Analysis}} refutations against the task's own definitions inside its own image. We matched the {{task:warehouse_forklift_routing|Warehouse}} model to the real tester on 294 strings, and mapped each TLA+ step to a line of source. Without those links, a proof would be about something else.
  • Every check needs a counter-check, because a check that cannot fail shows nothing. Each TLA+ model has a configuration that must fail, each Lean proof prints its axioms, and each fix should be tested on wrong work as well as right work; case pages state the actual coverage.
  • Formal proofs also checked our own work. Writing some fix mechanisms down as Lean or TLA+ models exposed one fix that was narrower than published and eight imprecise statements. Each was found because a proof attempt failed on a case we had not thought to test.
  • Test on the publisher's machine settings. Our first round of side-by-side tests ran graders on 8 CPUs. The leaderboard's settings give most of them 4, and at 4 CPUs six graders time out correct work that passes at 8. We also first assumed {{task:smt_solver|SMT Solver}} got 4; its settings give it 16. The code was correct in both settings; only the combination of the machine and the code was wrong.
  • Reviewers new to the work found what we had missed. A second round of reviewers who did not share our context found the CPU problem, two hidden-test problems in {{task:rust_multicrate_reconstruction|Rust Multicrate}}, undisclosed checks in {{task:git_rewrite_in_zig|Git in Zig}} and a hidden placeholder in {{task:pfr_formalization|PFR}}, mostly in tasks we had kept, and several of our own fixes that needed extending or revising. Each was then settled by a run, not by argument.
  • Test what a fix is for, not only what it changes. The first {{task:integer_compression_codec|Integer Codec}} fix corrected the baseline exactly as documented and passed every test, yet real submissions showed it saturated the score scale. Checking fixes against real agent work found what neither proofs nor authored tests did.
