# EdgeBench evidence audit

## Finish work and explain it plainly

The user repeatedly identified two failures: setup displaced task reviews, and reports hid results behind internal terminology. Apply these priorities before preparing another run:

- Conclude evidence already collected before commissioning more setup for the same question. A supported finding can be finished while its repair or whole-task release review remains separate.
- Keep original-task auditing separate from reference implementation development. A full solver needs a named audit question that smaller controls cannot resolve; it is not a prerequisite for confirming a finite defect.
- Dispatch disjoint, decision-changing questions in parallel. Give each assignment one question, an existing evidence pointer and a bounded finish condition; reuse those records instead of creating a new planning framework.
- After one bounded setup correction or roughly 15 minutes without an original task call, record the failed phase and switch to a ready task. Apply this stop across the same question rather than resetting it for each new packet. Name that fallback when assigning setup. Resume the stopped lane only with new evidence addressing the failure and its existing admission gates; never retry or reroute a hold.
- Count completed task decisions, tasks actually checked and new established results separately. Setup, copied receipts and source preparation are operational work, not new audited tasks. Report zero scientific progress explicitly when that is the outcome.

For user-facing updates and repository reports, lead with **what changed since a dated checkpoint, what we concluded, and what it means**. Use ordinary task names and explain a technical term when needed. Put run IDs, hashes, queue details and full diagnostic history behind evidence links. Keep the dated overview in `README.md` and current task decisions in `TASKS.md`; historical evidence snapshots keep their dates. Never make partial checks sound like complete task reviews. A historical tracking bucket is not the union of every task with evidence; compute an explicit ID union before claiming coverage.

Reconcile the handoff and summary when a result becomes terminal, an owner stops, a conclusion is accepted or a reviewed Git batch lands. Check live ownership before describing work as running. Report no new scientific result when that is the outcome. Keep a ready assignment aimed at a remaining inclusion or repair gate; exclusion decisions alone do not deliver a corrected benchmark.

## Recover, then choose the question

Resolve current authority/state from the designated coordinator. Repository copies use `HANDOFF.md` to locate it; local workspace/archive links are provenance, not required Git contents. Missing historical links do not authorize stale state or make another preparation/review necessary.

Read that coordinator's current `AGENTS.md`, `VERIFICATION.md`, compact root handoff (locally `edgebenchverified/audit/evidence/sol-cloud-authorization-v1/current-root-handoff.json`), dated `audit/AUDIT-BRIEF.md` and later steering. Load historical archive keys only for the question at hand. Keep one current task row: exact task/version, claim, accepted evidence/terminal handle, counterevidence, disposition, remaining gates and next decision-changing experiment. Recover the named accepted leaf and exact saved attempt **before** assigning preparation or review. Reuse unchanged sources, controls and reviews; completed science needs no rerun because collection, acceptance or root glue failed.

Dispatch from the latest accepted task row: completed results need conclusion or remaining-gate work; source-ready packets need only their required changed-path review and admission. Before commissioning another review, name the changed bytes, new claim or unresolved independent-reproduction requirement. Reuse unchanged accepted evidence; root integration is not another scientific reproduction.

Honor the user deadline, host/staging guards and automatic-review holds; never retry or reroute held work. Unrelated model/formal/runner failures must not serialize unheld tasks. Current authorization permits up to 50 useful cloud workers and useful reviewed resource increases, without the removed $15 ceiling/$5 reserve. Resolve new reviewer and E2B model settings from the current model policy and latest direct user steering. Frozen attempts retain their regime; a preference change does not authorize retrying a hold. Resets, paid fallback, publication and third-party contact need applicable authorization. Private auditor access is not untouched solver holdout or certification.

## Test the actual promise

Pin task definition, work/judge image and effective version. Read the original loader, command, evaluator and score contract before inventing schema/domain predicates. Inspect provenance/data/label/split/randomness/feedback/adaptation/rights facts needed for the question, retaining domain/expert gaps. Filtered absence is not whole-image absence. Failed authored expectations or fixture/harness failures are counterevidence to those expectations, not upstream defects.

Choose the smallest falsifiable experiment with actual inputs and the **original task path**. A census, mock or launcher success does not pilot an evaluator/compiler workload. Use relevant valid/invalid/empty/partial/malformed/timeout controls, independent small oracles or metamorphic properties; this is not a mandatory checklist for every question. Ordinary reversible bounded diagnostics need no invented source-approval prerequisite; fragile frozen workers keep their actual root/grant and intake gates.

Freeze hypothesis, exact sources/inputs, envelope, observables and necessary changed-path checks together. Reuse maintained execution/collection and accepted unchanged controls. Review the changed question, run a useful pilot, then dispatch disjoint work where supported. After one evidence-based setup correction, reassess at roughly 15 minutes and name the blocker instead of building another controller/review framework. Independent data/native/source/review lanes can proceed within shared ownership and staging bounds.

Preserve first failures and unsuccessful hypotheses. Separate readiness, original test, parser/export and cleanup failures. Collect completed slices and run only the unresolved complement; submitted jobs are not tested cases. Missing diagnostics do not establish historical cause. Private raw IDs/cells/answers/stderr and credentials stay outside public evidence; safely project connector responses and inspect source/archives before sharing.

## Repair and assess evidence

Freeze concrete native-format fixes with exact work/judge targets, patch bytes and required derived-image/manifest identities. Distinguish overlays/prototypes from integrated candidates. Match original/candidate inputs, randomness, resources and scoring, with relevant regressions and a genuinely different pass where required by the task/release protocol. Changed evaluators/types/scores/splits create distinct versions; never merge scores silently.

Label source inspection, authored controls, original-helper components, native tasks, corpus measurements, model runs and independent reproduction separately. Pin artifacts, commands, resources, outcomes and cleanup. Requested model names/messages do not prove served identity. Disclose reuse/reviewer authorship; AI agents are not three independent humans. Finite fictional controls do not establish corpus incidence or benchmark impact.

Use Lean/TLA+ for applicable mathematical/state questions without blocking unrelated tasks. Source-only proofs remain unexecuted until actual tool results; map assumptions/omissions to implementation and distinguish ordinary foundations from admitted proofs.

## Move evidence to conclusions

Decide each distinct versioned claim **confirmed, rejected or unresolved** with its contract, witness, evidence mode, required different review and material limits. Close a supportable finite source conclusion as source evidence; a separate native, rights or certification question does not keep that conclusion pending. Unknown cause/history/score impact/full-corpus coverage/optimality limits broader claims. Further work should change that decision or answer a separately named repair question.

Keep findings, repair validation and task certification separate. Exclusion means withholding an exact original unchanged; distinguish observed contract failures from conservative release-policy choices and disclose affected capabilities. It does not mean every score is wrong or a repair is complete. Exact-version task breadth is a union of IDs; deeper components add depth, not another tested task. Keep unavailable tasks/pending gates in the denominator. Preserve rejected companions and accepted exact-version exclusions; excluded versions skip inclusion gates, corrected versions need separate identity/review.

Use `VERIFICATION.md` and the mechanical checker for retain/repair/exclude/pending dispositions and benchmark release. Record named requirements as satisfied, failed, unavailable or unresolved with exact reasons; invent no sampling/domain thresholds or universal review counts. Finite controls/source GO do not clear whole inclusion gates. Preserve frozen approval bundles, certification gates and holds. Benchmark release needs its gates and applicable authorization; existing explicit instructions supply authority where applicable. Lead updates with closed evidence-backed conclusions, actual results and material limits.
